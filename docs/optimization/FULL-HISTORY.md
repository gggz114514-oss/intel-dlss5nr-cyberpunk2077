# 从 50.82 ms 到 17.45 ms：Vulkan FP16 完整优化历程

这次迭代覆盖整个后端：矩阵供料、片段布局、矩阵之间的交接、算子融合、内存初始化、寄存器生命周期，以及游戏中的跨帧提交。起点已经使用 XMX 协同矩阵；主要进步来自让 XMX 更持续地得到输入，并减少周围的搬运、转换与等待。

测试平台为 Intel Arc B580，NR 输入 1280×720。Full 的历史网络耗时从 **50.821 ms 降到 17.450 ms**，历史端点缩短 **33.371 ms（65.7%），约 2.91 倍速度**。下表是各阶段独立验收记录；同批对照列保留当时的父版本，用于精确阅读每轮收益。

## 1. 最初为何超过 50 ms

原始 `cold-b3-21-v1` 有 152 个逻辑行、491 个 buffer、278 次派发。矩阵指令已经启用，但输入片段需要大量 gather、暂存、重新装载；矩阵输出经过共享内存、转换和同步才到下一个消费者。最初单独的逐派发画像中，C32 gather 族 10 次调用合计 14.439 ms，占该画像约 29.15%。

所以第一步不是更换精度，而是重新组织同一份计算的数据流。保留矩阵累加顺序、half 舍入点和反馈语义，改变布局、运输和调度。

## 2. 从 AMD 方案学到什么，如何适配 XMX

当前 Vulkan 实现大量参考望月 **mochizuki0323 / DLSSNR-AMD** 社区项目的网络组织、布局、生产消费、融合与权重工具。具体贡献见 [AMD 致谢](AMD-ATTRIBUTION.md)。这里的适配以 Intel subgroup、协同矩阵片段映射、DPAS 供料和寄存器分配为落点。

第一轮在 C64/C128/C256 expand 中采用 direct A + tile B：A 直接成为矩阵输入，B 在离线阶段重排为消费布局。对应 SLM 读取减少约 66.3%、72.8%、84.2%。C128 输出投影的 shared 从 36,864 B 降到 0；C256 输出保留有复用价值的 A 缓存，改尾处理后 scratch 从 896 B 降到 0。整轮同批获得 7.831 ms。

第二、三轮进一步复用 C32 的 X/P 生命周期，shared 从 37,376 B 降到 29,184 B；contract 保留成对 M 复用，FFN 和投影使用匹配的权重 tile。ViT 保留有价值的 K/V 缓存，C256 contract 保留 M 复用。整轮获得 6.369 ms。

这些选择形成了后续一直沿用的方法：**删除没有复用价值的中转，保留减少重复读取的缓存；布局必须服务真实消费者。**

## 3. 从 32 ms 到 VK102 的约 25 ms

C32 的九个 body 改为更直接的寄存器交接，并使用合适的工作组组织，整网再省约 1.051 ms。随后网络组织从 278 走到 275、266 次派发，把适合合并的投影、混合与后续计算放进同一阶段。

95→102 阶段还有三个重要来源：

- **删掉完整覆写 buffer 的首清。** 先证明生产者覆盖与消费者读域，再修改 POLICY，保留历史数据和未覆盖区域所需的初始化。
- **地址与运输代码优化。** S22 地址外提；C32 body 的 A transport 使 native 指令 6,283→4,512，再推广到 F1 8,621→6,839、F2 6,540→4,768。
- **expand 中间结果直接写出。** C128/C256 删除 4 KiB private staging，屏障 5→1，保持 half RN-even 舍入。

这一阶段把开销分析扩展到矩阵外的清零、索引、片段运输和提交组织，而非只看 MMA 数量。

## 4. 从 VK102 到 232 派发及 C32 整链

S22 改用 query owner 和寄存器 P，减少 shared P、den 与 rescale 的交接。之后 D034 将 C64/C128/C256 中间层与 contract 合并，删除 33 次独立派发，下一矩阵在融合核内消费生产结果。随后 A1 删除已失去消费者的全局镜像写。

C32 的入口、body、F2、F20 按整条链处理：norm、score、den、归一化、PV、残差和输出投影一起设计 owner，而不是单独减少一个转置。保持原舍入位置与归约顺序，同时控制根广播、shuffle、活跃子组和长寿命累加器。

这阶段也留下了重要经验：减少指令和暂存之后，还要保留独立矩阵工作的并行。四个活跃子组变成八个半活跃子组、提前读取挤占 A 的返回寄存器、累加器数量下降，都可能抵消删除交接的收益。

## 5. F10 的 0.422 ms：实现退化后继续查原因

F10 第一版生产消费布局改造遇到退化。后续沿 native 和生命周期检查，保留新的 A 消费布局，让需要重叠的权重使用独立返回寄存器，并在最后消费后复用。最终整族候选固定输入与反馈过门，无新增 scratch，同批获得 **0.422 ms，95% CI [0.297, 0.547] ms**。

这个案例明确了实验方法：一次实现退化时，对账新增组装、依赖和寄存器压力，再改实现；评价一个方向要看最终可执行的调度，而不是某一种源代码写法。细节见 [方法记录](METHODS.md)。

## 6. 全后端推广到 17.45 ms

最后一轮把方法推广到 F05/F06 宽族、ViT、入口和其他供料链，13 步采纳累计改变 120 个 PASS 行。整包六组同批验证 **18.724→17.450 ms**。逐项记录在 [最后一轮采纳表](ACCEPTED-STEPS.md)。

代表性改造 n39 删除 C256 的恒等 staging：32 KiB Workgroup 内存降到 0，SLM 载入变为直接 UGM 消费，同步发布一起删除；保持矩阵数量和输出，获得 **0.103768 ms**。与早期“删除所有缓存”的做法不同，这里删除的是没有改变数据、也没有必要承担供料角色的一层运输。

## 7. Small 与流式桥接是两条配套成果

**新版 Small：108 派发、约 9.980 ms。** 它复用优化后的后端方法，保留 Small 权重和五个偏移专用核，修正资源范围并重新接线。同批旧 Small 14.324→9.980 ms。默认构建已指向此版本。

**跨帧流式桥接：游戏帧周期 34.81→29.38 ms。** 同一静止场景、同一游戏生命周期的四窗口 1,067 帧，净省 **5.43 ms**，基础帧率 28.74→34.04 FPS。把 CPU 提前阻塞改为延迟退休与受控资源复用，保留 GPU 依赖，减少断供间隙。见 [流式处理](STREAMING.md)。

## English summary

The Full Vulkan backend evolved from **50.821 ms / 278 dispatches to 17.450 ms / 232 dispatches** on B580 at 1280×720 NR input. XMX was already enabled at the starting point. The progress came from direct matrix feeds, offline weight layouts, lifetime reuse, removing redundant initialization and staging, fusion, owner mapping, and register-aware overlapping of independent work. Historical endpoints summarize the development; each stage above also lists its own paired baseline. A direct VK102-to-current batch measured **25.834→17.590 ms**. Optimized Small measured **9.980 ms**; late-latch game integration separately improved frame period by **5.43 ms**.
