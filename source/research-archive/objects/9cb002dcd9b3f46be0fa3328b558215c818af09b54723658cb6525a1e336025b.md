## 0. 先回答卡的第一件事：fb bias 的消息构成与字节（实测）

### 0.1 消息表（`isa-message-census.json`，机器生成）

该核 597 条 `send` 里，**388 条是 `if(debug)` 的 `dbg` 存储**（`pc.p0.z != 0`，
`store.ugm.d32x8t` 384 + `store.ugm.d32x64t` 4），生产 dispatch 不执行。
把它剔掉后的"实际执行路径"是 209 条消息，其中 UGM 读 182 条：

| 形式 | 条数 | 每条字节 | 合计 | 归属 |
|---|---:|---:|---:|---|
| `store.ugm.d32x8t`（uniform, rd:0） | 384 | 32 B | 12288 B | `if(debug)` 的 `dbg` 发布 —— **不执行** |
| `store.ugm.d32x64t`（uniform, rd:0） | 4 | 256 B | 1024 B | `imgout` 输出 |
| **`load.ugm.d32x16t`**（uniform `(1|M0)`, rd:1） | **64** | **64 B** | **4096 B** | **本条卡的 fb bias 逐行 gather** |
| `load.ugm.d32x8t`（uniform, rd:1） | 64 | 32 B | 2048 B | `scale`（stride-0，n01b 已删一半，未采纳） |
| `load.ugm.d64x64t`（uniform, rd:8） | 48 | 512 B | 24576 B | `wb` 权重块读 |
| `load.ugm.d32x64t`（uniform, rd:4） | 4 | 256 B | 1024 B | `imgin` |
| `load.ugm.d32x16t.a64`（flat） | 1 | 64 B | 64 B | push constants（`pc` 64 B） |
| `load.ugm.d32x1t` | 1 | 4 B | 4 B | `headscale = fb[pc.p2.z]` |
| `load.slm.d64x64t`（uniform, rd:8） | 16 | 512 B | 8192 B | `shK`/`shV` 跨 SG 读 |
| `store.slm.d32x64t` / `store.slm.d32x4`（后者 `(16|M0)`） | 4 / 4 | 256 / 256 B | 2048 B | `shK`/`shV` 写（每片段 256 B，8 站点） |
| `fence.slm.none.group` / `signal barrier` / `eot` | 1/1/1 | — | — | 同步 |

> 表内"合计"是**静态**口径（每条静态消息在 4 个 SG 上各执行一次 ⇒ 每 WG 乘 4）。
> 落字节约束自检：`shK`+`shV` 写 = 8 × 256 B × 4 SG = 8192 B = 两个 `shared` 数组总大小 ✓；
> fb bias 64 × 64 B = 4096 B = 每 SG 的 16×64 f32 瓦片 ✓。

**实测口径修正（n01b 的 11% 要改）**：n01b 的"64 条＝send.ugm 11%"是按**未剔 debug 的静态 570 条**
算的。按实际执行路径（182 条 UGM 读）算，fb bias 是 **64/182 = 35.2% 的消息条数**、
4096/31812 = **12.9% 的字节**。字节大头仍是 `wb`（24576 B，77%），条数大头是
`scale`+`bias` 这 128 条 32/64 B 的小消息（70%）。

### 0.2 逐站点形状（`bias-clusters.json`，机器生成）

64 条 = **8 个 `coopMatLoad` 站点 × 8 条消息**，每条**一行**，全部 uniform `(1|M0)`
（每 SG 只发一次，不是逐 lane）：

| 站点 | 源表达式 | 8 条消息的行地址增量（实测立即数） | 消息区 |
|---|---|---|---|
| C0 | `pc.p2.w+(t0+0)*64+0` | 0, 256, 512, 768, 1024, 1280, 1536, 1792 | `0xb748..0xb800` |
| C1 | `pc.p2.w+(t0+8)*64+0` | 同上（256 B 步长） | `0xba58..0xbb00` |
| C2 | `pc.p2.w+(t0+0)*64+16` | 同上 | `0xbef0..0xbf90` |
| C3 | `pc.p2.w+(t0+8)*64+16` | 同上 | `0xc1d0..0xc280` |
| C4 | `pc.p2.w+(t0+0)*64+32` | 同上 | `0xc680..0xc720` |
| C5 | `pc.p2.w+(t0+8)*64+32` | 同上 | `0xc958..0xca00` |
| C6 | `pc.p2.w+(t0+0)*64+48` | 同上 | `0xcd70..0xce80` |
| C7 | `pc.p2.w+(t0+8)*64+48` | 同上 | `0xd0d0..0xd180` |

- 256 B 步长 = `fb` 的**行跨度 64 个 f32**（跨度为 64 列 ＝ 整行长度），每条消息取该行
  里**连续 16 个 f32 = 64 B**。
- 8 条消息的落地寄存器是**同一批 8 个 GRF**（`r4..r11` 或 `r21..r28` 等），
  8 个站点**复用**这批寄存器 ⇒ 每个片段峰值活值 = 8 GRF，逐站点串行消费。
- 一个片段的消费链（实测）：8 条 load → `sync.allwr` → `add (32|M0) rX:f = 累加器 + 消息返回`
  ×4（f32 bias 加，`precise`）→ `mov (16|M0/M16) rY:hf ← rX:f` 窄化 ×8。
  全核 `add :f,:f,:f` 恰好 **32 条 = 8 片段 × 4 component**，即 f32 加法全部就是 bias 加的四处。

### 0.3 位置与并行性

- 唯一 `sync.bar` 在 `0xb520`；64 条 bias 消息全在它**之后**（`0xb748..0xd180`）。
- 这段区间里还夹着 **12 条 `dpas.8x8`**（128 条里 92 条在 bias 之前、24 条在之后）。
  ⇒ bias gather 是**已经和 score/PV 的 DPAS 交织**的（L12 的"被并发隐藏"现场），
  不是一段干净的串行尾巴。
- **bias 表是 dispatch 不变表**：基址 `uint(pc.p2.w) + (t0)*64 + {0,16,32,48}` 只含
  推送常量与 `t0 = sg*16`，**不含 WGID、不含 token 基址**（对照 `imgin` 用的是
  `nr_tok_base(...)` 这种 WG 相关基址）。所以每个 WG 读的是**同一张 16 KiB f32 表**
  （每 SG 4 KiB，4 SG 打满 64 行×64 列），跨 WG 全部命中 L1/L2。
  ⇒ 这 64 条消息**不付 DRAM 钱**，只付**消息发射槽**的钱。这一条是后面所有定价的前提。

## 1. 映射：每个 (lane, component) 代表哪个 (row, col)，消费者要求什么

### 1.1 通道律（从密封头文件推导，`PROOF.json.P1_coordinate_law`）

`register_handoff.glsl`（sha `1c4c7489…`，随父 SPV 身份绑定）里的
`nrh_coord_C(component)` 逐字搬到本卡脚本里跑：

```
x = (lane << 2) | comp
z = ((x & 3) << 5) ^ ((x & 124) >> 2)      ⇒  z = 32*comp + lane
row = z / 16 , col = z % 16
```

闭式：**row = 2*component + (lane>>4)，col = lane & 15**（128 个 (lane,comp) 逐项实测相等）。

### 1.2 站点 → 表坐标 → fb 下标（可枚举，无假设）

设 `b = 站点列块 {0,1,2,3}`、`h = 行半 {0,1}`、`s = 4*h + b`：

```
fb_index(lane, comp, h, b)
    = pc.p2.w + (t0 + 8h + row)*64 + (16b + col)          // t0 = 16*sg
    = pc.p2.w + (16*sg + 8h + 2*comp + (lane>>4))*64 + 16*b + (lane & 15)
row = 2*comp + (lane>>4) ∈ 0..7 , col = lane & 15 ∈ 0..15
```

- **一一覆盖**：8 站点 × 4 component × 32 lane = **1024 个 (lane,comp)**；
  对应表元素（16 行 × 64 列 = 1024）**每个恰好出现一次**，最大重数 = 1
  （`PROOF.json.P2_exact_cover = true`）。
- **无漏读**：每个站点的 `rows_touched = 8h..8h+7`、`cols_touched = 16b..16b+15`，
  4 个 b 与 2 个 h 拼成整块 16×64。
- **无重复写**：整个 bias 路径只有 `coopMatLoad` 写这 8 个片段变量，之后只读；
  片段变量是每站点一个新 `NRH_C bias`（作用域内），无别名。
- **尾块**：基址只用推送常量与 `t0`，**与 token/WG 无关**，本来就不在 `tok_oob` 守卫里
  （父源码 L594/604/626/636/658/668/690/700 全部无条件读；`imgin`/`imgout`
  的 `if(!tok_oob_u)` 8 处逐字未动）⇒ 所谓"尾块"在这条路径上不存在。

### 1.3 消费者要求什么

8 个消费者都是 `NRH_C sc = coopMatMulAdd(qa, shK块, 0)` 的累加器，接着

```
precise float biasedN = scN[N] + bias[N];  scN[N] = biasedN;   // N = 0..3
pNN = nrh_narrow(scN);                                          // f32 → f16，一次舍入
```

即：bias 必须是**同一布局的 NRH_C f32 片段**，按 component 逐元素加到累加器上，
**加完才窄化**。这两点锁死了后面所有候选：bias 不能提前窄化成 half，也不能换布局。

## 2. 删什么真实工作（正常执行路径，不计 debug 声明）

### 2.1 现状里到底有什么是可删的

| 类别 | 量 | 可删？ | 依据 |
|---|---:|---|---|
| bias 消息（uniform 64 B） | **64 条 / 4096 B** | 只有换布局才可能 | §0.1、§0.2 |
| bias 的 f32 加 | 32 条（8 片段×4） | **不可删**（数学） | §1.3 |
| bias 的窄化 `mov hf←f` | 64 条（8 片段×8） | **不可删**（half 舍入点） | §1.3 |
| 所谓"64 条搬移" | 就是上面这 64 条窄化 **本身** | **不是额外开销** | 见 §2.2 |
| 重复读 | **0** | — | `PROOF.json.P3`：64 条消息供给 64×16=1024 个元素，与 1024 个表元素一一对应，**没有一次冗余** |

**对 n01b 持平的修正**：n01b 记的是"64 条消息 + 64 条搬移"。那 64 条搬移是
`nrh_narrow(sc)` 的 half 舍入点（每片段 4 component × 2 个 16-lane 半 = 8），
**不是**消息落地后的展开搬移。也就是说 bias 路径上**唯一可删的就是消息条数**，
并且现有写法里**没有重复读**可删（这跟 n01b 删掉的 stride-0 `scale` 完全不同）。

### 2.2 SLM 方案要删/要加的工作（逐条）

本卡要审的机制是"8×64 转置缓存"。按"消息条数 = 窗口里**极大连续行段**的个数"
这条**实测规则**（见 §4.1：同一核里四类窗口各自验证过）可以把它算死：

**方案 N（线性 SLM 缓存：不转置，最容易写、也是不引入布局假设的唯一写法）**

| | 项 | 条数 |
|---|---|---:|
| 删 | `load.ugm.d32x16t` 64 条 uniform 64 B | −64 |
| 加 | 填充用的宽读：4096 B 连续 → `d64x64t` 512 B/条 | +8（若按 per-lane 标量填则 +32） |
| 加 | 填充写 SLM：4096 B → `store.slm` 512/256 B | +8..+16 |
| 加 | **回读仍要逐行 gather**：`load.slm.d32x16t` 64 B × 8/站点 | **+64（一条都没省）** |
| 加 | `fence.slm` + 新屏障 | +1..+2 |
| **净** | | **+16 .. +24 条消息，且 0 条省下** |

方案 N 的致命点：**转置不在缓存里发生**，`coopMatLoad` 拿到的还是"8 行 × 64 B 不相邻"，
行段数没变，回读照样 8 条/站点。这就是 n17 的"一片片段走 SLM 是 8 条消息"在这里的准确形态。

**方案 T（真转置：填充时按片段布局散写，回读才是 1 条 512 B）**

| | 项 | 条数 |
|---|---|---:|
| 删 | `load.ugm.d32x16t` ×64 | −64 |
| 加 | 宽读 4096 B 连续（`d64x64t`） | +8 |
| 加 | **转置散写**：per-lane 单 dword 散写，128 B/条（4096/128） | **+32** |
| 加 | 转置所需的每 lane 地址位重排 ALU（每 dword 一算） | +32..+96 条 ALU |
| 加 | 回读：8 片段 × 1 条 512 B 连续（`load.slm.d64x64t` 式） | +8 |
| 加 | `fence.slm` + 新屏障 | +1..+2 |
| **净** | | **48 条 vs 64 条 = −16 条消息**（−8.8% 的执行路径 UGM 条数） |

代价：消息管道字节从 4 KiB 变 **12 KiB**（读 4 + 写 4 + 回读 4）、
shared 8192 B → **24576 B**、多 1 道屏障落在 score→softmax 关键路径上、
多 32~96 条 ALU。**换来的只有 16 个消息发射槽。**

**方案 T 的敏感性（必须一起报）**：那 8 条宽读要求编译器把每 lane 的 4 个相邻
标量读合并成一条 512 B 消息。若编译器不合并（每 lane 一条 128 B 的读），
填充读就是 **32 条**，方案 T 变成 **32 + 32 + 8 = 72 条 vs 64 条 = +8**，
即**严格更差**。也就是说方案 T 的"最好情况 −16、现实情况 +8"，
两种都 ≤ 0；这不是边缘判断，而是"最好情况也不赚"。

## 3. 重叠：原来如何重叠，方案 T 会破坏什么

### 3.1 阶段与 owner（7 PASS 每个 dispatch：4 SG/WG，128 lane；
grid 84×48 是从链头 PASS 行字段推断，未经 GPU 复核）

| 阶段 | 生产者 | 片段 | 最后消费者 | 覆盖者 |
|---|---|---|---|---|
| 入口 | `coopMatLoad(imgin)`(WG 相关基址) | `x`(CH) | A 转换 / scale 种子 | `if(debug)` dbg |
| expand G1/G2 | `wb`(p1.x/p1.y) 48 条块读 | `e`,`y` | 激活 → A；`y*scale` | 同块 next |
| QKV | `wb`(p1.z) 12 条块读 | `q/k/v` | norm / 写 shK,shV | — |
| score | `shK`(SLM) 8 条 | `sc0/sc1` | den 树 + PV A | bias 加 |
| **bias（本卡）** | `fb` 64 条 uniform gather | `bias`(C) | `sc + bias` → narrow → exp | 无 |
| PV | `shV`(SLM) 8 条 | `tc` | narrow → ctx | — |
| output | `wb`(p1.w) 4 + `y*scale` | `oc` | narrow → imgout | — |

### 3.2 RAW / WAR / WAW

| 值 | 关系 | 说明 | 方案 T 影响 |
|---|---|---|---|
| `fb[…]` → `bias` 片段 | **RAW** | 只读表，跨 WG 同一 16 KiB | 不变（读同样 4096 B/SG） |
| `bias` 片段 → `scN[N]+bias[N]` | **RAW** | 4 component 逐元素 | 不变 |
| `sc` 累加器（DPAS 写） → bias 加 | **RAW**，**跨 8 个片段串行** | 片段是 DPAS 的出口 | **被打断**：转置缓存必须等 4096 B 全到齐 |
| bias 加载寄存器 `r4..r11` 与后续片段复用 | **WAW/WAR** | 分配器视角 | 活值峰值 8 GRF → 更宽 |
| `shK`/`shV`（同 8192 B SLM） | **WAR** | 屏障 0xb520 前写、后读 | **共享 SLM 池被挤占 3×** |
| 唯一 `barrier()`(0xb520) | — | 输入侧全在前、bias 全在后 | **新增第二道，且落在 score→PV 之间** |

### 3.3 方案 T 把什么串起来了（这是它最贵的地方）

现在的重叠形态（实测）：bias gather 与 **12 条 DPAS 交替发射**，每站点 8 条消息一发出、
`sync.allwr` 后立刻被 4 条 f32 加消费，然后窄化、exp、den 树、PV 继续——
**片段 i 的等待被片段 i+1..7 的 DPAS 覆盖**。

方案 T 插入屏障后：4 KiB 必须**全部**读进 SLM 并可见，任何一个片段才能开始取数 ⇒
把"8 个可独立启动的片段"变成"1 个 4 KiB 的整体前置"。这是 §3.2 表里那行
"跨 8 个片段串行"被打断的直接后果，也是 L12 说的"把独立工作串起来"的反面。

## 4. 新增成本（全部入账，`COST-LEDGER.json`）

### 4.1 布局→消息条数规则（本核实测，四类窗口，用来定价而不是猜）

| 窗口 | 行跨度 | 每条消息 | 条数 | 实测消息形式 |
|---|---|---|---:|---|
| `shK/shV` 16×16 half | 16 half（512 B 连续） | 512 B | **1** | `load.slm.d64x64t` rd:8 |
| `wb` 16×16 half | 16 half（512 B 连续） | 512 B | **1** | `load.ugm.d64x64t` rd:8 |
| `imgin` 8×16 half | 16 half（256 B 连续） | 256 B | **1** | `load.ugm.d32x64t` rd:4 |
| **`fb` bias 8×16 f32** | **64 f32（256 B，只取 64 B）** | **64 B** | **8** | `load.ugm.d32x16t` rd:1 |
| `wb` scale 8×16 half | **0**（同一 32 B 读 8 次） | 32 B | **8** | `load.ugm.d32x8t` rd:1 |

⇒ **规则：条数 = 窗口里极大连续行段的个数。** 这条规则在同一颗核里对 5 类窗口都成立，
所以可以用它给任何"换布局"方案定价，而不需要 GPU 复测。

### 4.2 方案 T 的成本明细

| 项 | 量 | 依据 |
|---|---|---|
| 消息条数 | 64 → 48（**−16**） | §2.2 |
| 消息管道字节 | 4 KiB → 12 KiB | 读+写+回读 |
| SLM 足迹 | **+16384 B**（shared 8192 → **24576 B**） | 每 SG 16×64 f32 = 4096 B，`shared` 是**每 WG** 的 ⇒ 4 SG × 4096 |
| half 缓存（卡里的 1 KiB 前提） | **不可行** | bias 是 f32 且**加完才窄化**（§1.3）；存 half 会在 f32 加之前多一次舍入 ⇒ 违反合同 §3 |
| 新屏障 | +1（`sync.bar` 1 → 2，或 subgroup 版） | 转置写与回读之间必须跨 lane 可见 |
| 新 ALU | +32..+96 | 每 lane 的位重排散写地址 |
| 活值峰值 | 8 GRF/片段 → 宽读需 16~32 GRF 常驻 | 实测 `r4..r11` 八站点复用；`max_r = 127` |
| 有效 lane | 不变（128 lane、4 SG、`if(sg<4u)` 恒真） | 实测 |
| code size | 未测（本卡未建候选） | — |

### 4.3 两个硬约束（本卡实测，不是推断）

1. **寄存器天花板**：该核最高寄存器 **r127** ＝ 128 GRF/thread 上限（与 L9 记录的
   `max_r=127` 同义）。当前 bias 峰值活值 8 GRF（8 站点复用同一批寄存器）。
   宽读 4096 B 要在寄存器里驻留就是 32 GRF；即使按 512 B 流式，转置散写仍要
   per-lane 地址常驻。**方案 T 在 128 GRF 上要抢出 8~24 GRF，是本卡唯一没有前置预算认证的一项。**
2. **SLM 池被共用**：`shared` 8192 B 现在是 `shK[2048]+shV[2048]` half，承担
   **跨 SG 的 K/V 交接**（唯一的 `sync.bar` 就是为它）。方案 T 让同一池涨到 3×，
   而这份 SLM 直接决定跨 SG 供料的延迟。

## 5. 是否真落到 native（预测 + 判据：本卡不建候选，写判据供后续卡）

完整清单见 `NATIVE-PREDICTION.md`。要点：

- 如果谁实现**方案 N（线性 SLM 缓存）**，native 必须看到：
  `load.ugm.d32x16t` 64 → 0、`load.slm.d32x16t` 0 → 64、`store.slm` +8..16、
  `sync.bar` 1 → 2，**总消息数 209 → 225±**，dpas 128 不变、528 条交织 mov 不变。
  **`load.slm` 也是 64 条**这一项本身就是"方案 N 无效"的判据。
- 如果谁实现**方案 T（真转置）**：`load.ugm.d32x16t` 64 → 0、
  `load.slm.d64x64t`(或 512 B 形式) +8、`store.slm` **+32 条 128 B**、
  `sync.bar` 1 → 2、shared 8192 → **24576**、`scratch` 仍 0；
  净 `send` 570 → 554±，`send.slm` 25 → 65±。
- **A 类阈值（写死）**：`load.ugm.d32x16t` 不降 ⇒ 记"实现未落地"，不换写法重跑。
- **实现错误判据**：528 条交织 mov 变化、`dpas.8x8 ≠ 128`、`scratch ≠ 0`、
  最高寄存器 > 127（溢出）。

本卡不建候选，所以这一节全部是**预测**；没有任何"已落地"的声称。

## 6. 整体是否更快（本卡不能测，写清该测什么、如何归因）

- **要测的整体量**：`ordinary`（`warm 1 / reps 30 / feedback`）两臂 6 组交替的组均值差，
  配对 95% CI（df=5）；同时保留 `fixed`（`1755e9c2…`）与 `fb2`（`9c3e511e…`）两套末帧 gold
  （合同 §8.1）。臂：`base` = 链头 `n10-f10-next`（`719f100b…`）；`cand` = 本组 7 PASS 重指。
- **归因边界**：
  - 方案 T 在**每 SG 省 16 条消息**（执行路径 182 → 166，−8.8%），
    但同一条 score→softmax 链上**多一道屏障**；
  - 同一身份、同一 7 PASS 上，n01b 已经实测过**省 32 条消息（−17.6%）→ +0.0127 ms
    CI[−0.0069,+0.0323] INDISTINCT**。方案 T 省得只有它的一半，还多一道屏障 ⇒
    **先验期望落在这条协议分辨率以内**；
  - 再叠加 §0.3 的实测事实：这张 16 KiB 表 **dispatch 内不变**、全部命中 L1/L2，
    64 条消息**不付 DRAM 钱**，而且已经和 12 条 DPAS 交织 —— 正是 L12 说的
    "被并发隐藏的消息不付钱"。
- **结论性归因**：本机制属于 L12 的"并发隐藏"类，不是 L2 的"重复消息删除"类
  （重复读为 0，见 `PROOF.json.P3`）。即使实现完美，可测收益的期望也是 **≈ 0**。
  本卡不因此把方向判死：真正的可删项是把 8 行 gather 变成 1 段连续读，
  而那需要**布局**变化（见 RESUME 的"下一处"）。

## 7. 判定：BLOCKED（合格交付），以及缺哪几条

**判定：BLOCKED。** 定价摘要：

| 方案 | 净消息 | SLM | 新屏障 | 新 ALU | 判定 |
|---|---:|---:|---:|---:|---|
| 卡里的 "8×64 **half** 1 KiB 缓存" | — | — | — | — | **数值非法**（bias 必须在 f32 加之后再窄化） |
| N：线性 SLM 缓存（无布局假设） | **+16 .. +24** | +16 KiB | +1 | 少 | **严格更差** |
| T：真转置（最好情况） | **−16**（48 vs 64） | +16 KiB | +1（关键路径） | +32..+96 | **净收益 ≤ 0**（见 §4.3、§6） |
| T：真转置（填充读不被编译器合并的现实情况） | **+8**（72 vs 64） | +16 KiB | +1 | +32..+96 | **严格更差** |

**缺的三条（任一条成立都能翻案，都必须先补上）：**

1. **省 gather 而不付转置**：需要一条新的"极大连续行段"事实 —— 即让 8 行 × 64 B
   在**不散写**的前提下变成 1 段。目前只有两条路：
   (a) **资产/宿主侧把这张 64×64 f32 bias 表预排成"片段连续"顺序**（一次性 16 KiB，
   内核零成本、无屏障、无 SLM）—— 属模型资产级改动，**不在本线权限内**，
   与 n01b 给 `wb` 的"预排列需用户裁定"同一条；
   (b) **8×64 累加器形状的宽读**（同表连续 2048 B → 4 条 512 B 消息），
   但需要 **8×64 累加器片段的 lane map**；现有密封头文件只给到 8×16
   （`nrh_coord_C`）与 16×16（`nrh_coord_B`），8×64 的映射**没有测过**，
   必须先用一次 `if(debug)` 探针把它测出来（否则是 E 类）。
2. **让新屏障不在关键路径上**：需要一个"同 SG 内 SLM 可见"原语（`subgroupBarrier`/
   `fence.slm` 级），其 ISA 代价已知且**不产生 `sync.bar`**。本卡无法在没有 GPU 的
   条件下证明这一点。
3. **SLM 足迹/常驻模型**：诚实足迹是 **+16 KiB f32**（4 SG × 4 KiB），不是卡里假设的
   1 KiB half；`shared` 8192 → 24576 B 会不会改变驻留 WG 数，需要资源门给出
   SLM 上限与常驻模型（本卡无 GPU，给不出）。

**没有建候选**，因此本卡不交付 `candidate.comp / candidate.spv / plan.txt`
（合同 §5 允许，缺项在本文件与 `RESUME.txt` 说明）；`GPU-REQUEST.json` 是
**空请求**（`arms: []`），不占用 GPU 槽。
