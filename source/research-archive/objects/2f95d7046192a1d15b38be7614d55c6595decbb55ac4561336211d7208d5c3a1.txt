0. 一句话
--------------------------------------------------------------------------------
`shared float16_t qkv[12288]`（24576 B）→ `qkv[8192]`（16384 B），驻留 2 → 4。
做法：V 投影（只依赖 gY + V 权重）从 QKV 段搬到"最后一次 Q/K 读之后"，写进退役的 Q 平面；
V 的 token 归属从 {8t, 8t+32} 改成 {16t, 16t+16)，使 SG t 的 V 写集 = 它自己读过的 Q 集
= [512t, 512t+512) ⇒ 跨 SG WAR = 0。不改 grid、不改 token tile、不改数学。

4. E 类记录（第一次构建，2026-10-28）— 完整记录，建议进 LESSONS
--------------------------------------------------------------------------------
【现象】第一档 C256 fixed 金帧失败：cand 末帧 `c0b498640ff4e373…` vs 金帧 `1755e9c2…`；
  base 臂两门都过、plan 核对干净（16 行替换、shared 全 16384、只动 C256 组）⇒ 不是接线问题。
【根因（单点）】**PV 的 A 操作数用"平面内字面量" `+ 4096u`（VBASE）寻址 V，而它不是 section 步长。**
  源码里两者长得像但语义不同：
      section 基址：`(gl_SubgroupID / 4u) * 6144u`   ← 每 head 一段，改 6144→4096
      V 平面基址  ：`... + 4096u + key*32u + dim`     ← section 内的偏移，必须 4096→0
  第一版只改了前者，于是 PV 读到 `base+4096`：越过 4096 half 的 section；
  第二个 head（base=4096）读 8192..10239，而声明只有 8192 half ⇒ **越界**。
  两处后果叠加 = 全部 C256 块的 gT 被写错 ⇒ 整帧不同。
【修复】三组各 16 处 PV A 读 `4096u → 0u`（`_make_candidates.py` 里的断言式编辑，计数必须 = 16）。
  修复后 c256 的 SPV 从 `3e832d90…` 变为 `236aad96…`；两个 plan 的 sha **不变**
  （plan 只存路径）——所以"plan sha 没变"绝不能当成"候选没变"。
【检出手段（本卡新增的门）】`_addr_audit.py` → `build/addr-audit.json`。
  对每个 `qkv` 访问**剥掉 section 基址**，然后检查
    ① 平面字面量 ∈ 该臂允许集（父 {0,2048,4096}、候选 {0,2048}）；
    ② section 步长（父 6144、候选 4096）；
    ③ 访问族齐全（V store 带 `vt`、Q^T 带 `qg`、PV ≥ 16 处）。
  在**旧**构建上它报 FAIL 并逐行打印那 16 处（`plane 4096 + 2047 >= section 4096`），
  在**新**构建上 PASS。这是唯一一个能在无人能跑 GPU 时抓到它的检查。
【为什么其它门全都没抓到】storage 字节（24576→16384 ✓）、`spv_validate`（✓）、父字节复现（✓）、
  coopmat/NC/FP 多重集一致（✓）、hazard 模型（✓，因为它用的是**意图**偏移而不是源码文本）。
  也就是说：**结构/计数类检查对"地址常量写错"完全免疫**。
【教训（可直接写进 LESSONS）】
  1) 动 SLM 平面的卡，必须把"平面内偏移"与"section 步长"记成**两个不同的量**，
     并在 diff 里逐个列出；
  2) 上线前跑一次"逐访问点的地址基址审计"（本卡模板），而不是只比 SPIR-V 计数；
  3) `plan` 的 sha 不 pin 候选字节（只存路径），派发核对必须用 **SPV sha**。

7. 本卡边界之外、但已量清楚的下一步（写下来防重复）
--------------------------------------------------------------------------------
* 16384 B 是"2 head 并发"结构的下界（每 head 同时要 Q 4096 + K 4096）。
  要 8192 B（⇒ 8 个驻留）必须让**两个 head 在一个工作组里串行**：先做完 head A 的
  QKV→score→V→PV，再做 head B。SLM 需求减半，但 score/PV 段同时只有 4 个 SG 干活
  （当前 8 个），且屏障从 3 道变 6 道。这是 owner/token tile 改动，需要单独一张卡（本卡禁止）。
* 反向探针（24576→49152）已证明"减半驻留 = −1.219 ms / 6 6/6"。**向上的方向本卡测到了**：
  24576→16384（2→4）在 C256 上值 **+0.117 ms**，在 C64+C128 上再值 **+0.126 ms**。
  ⇒ **弹性是不对称的**：向下 1.219 ms 是"1 个驻留 = 没有重叠"，向上只值 0.12 ms 量级
  （2→4 的边际收益远小于 2→1 的边际损失）。后续卡引用时**不要**把 1.219 ms 当成向上收益的上界。
* IGC 已经把 C64/C128 score 段里 8 个 key block 重复的 `Q^T` 读 CSE 成 2 条
  `load.slm.d32x8`（n05e 普查 32+2=34 与模型逐项相等），所以"把 Q^T 提升到 block 外"在 native
  层面大概率已经是免费的——不要再为它开卡。

分诊：**采纳**。这是本战役第一次靠"资源/驻留"而不是"删工作"拿到的收益。

**结论 1（反向弹性，做阈值用）**：F05 把 `qkv` 从 24576 B 填到 49152 B（数学一字不改）
⇒ 每 SM 驻留 2 → 1 ⇒ **−1.218946 ms** CI[−1.237396, −1.200497]，6/6。
注意它**只**是"减半"的代价，**不能**当成"加倍"的收益：本卡向上的第一段只值 0.117 ms（C256）。

**结论 2（驻留阈值表）**：两次反向探针把每 SM 的 SLM 池夹在 **P ∈ [65536, 73728)** 字节，
于是 `驻留(W) = floor(P / W)`，且下表的每一档**在区间两端同值**（与 P 的取法无关）：

| 每 WG shared 字节 | 驻留 WG / SM | 精确 |
|---|---|---|
| 65536 | 1 | ✓ |
| **32768** | **2** | ✓ |
| **21845** | **3** | ✓ |
| **16384** | **4** | ✓ |
| **13107** | **5** | ✓ |
| 10922 | 6 | ✓ |
| 8192 | 8 | ✓ |

（21845 = 65536/3、13107 = 65536/5 的整数下界；24576 与 20480 分别落在 2 档与 3 档内，
这就是"F10 的 20480 B → 3"与"F05 的 24576 B → 2"的由来。）
生成器 = `_adopt.py:threshold_table()`，逐档给出 `at_lo / at_hi / exact` 三个字段，可重跑核对。

**未分离的两个量**：tier2 的 +0.126 ms 是"占用率收益 − 消息代价"的净值。
+9.51 M 消息/帧的代价确实存在（否则净收益会更大），只是**小于**占用率收益；
要分开它们，需要对 C64/C128 各做一次"填充回 49152 B"的探针（§6 第 3 条）。
