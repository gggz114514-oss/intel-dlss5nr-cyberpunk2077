## 1. 方法（232/232 可复核）

1. `evidence/NATIVE-INDEX.json` → 每个 ordinal 的 `baseline_kernel_hash`（= 当前基线 a024c3c5 的 native 指纹）。
2. 在本机磁盘按 `CS_asm<kernel_hash>_simd32_<dispatch>_<pipeline>_<...>_orig.asm` 反查：**232/232 个 ordinal 都找到同 hash 的 ISA 文件**（`_hash2asm.json`），因此"当前身份"的 ISA 证据无缺口。文件 sha256、行号、指令原文全部写进 `NARROW-READ-CENSUS.json`。
3. 两类计数口径（都已写入 JSON，互不替代）：
   - `narrow_messages`：message 名元素宽度是 `d8/d16/d32`（逐 lane 1/2/4 字节标量），不含 `d32xNt` 这类块形。
   - 半宽寄存器搬移（`half_idiom_split`）：按指令原文分类
     `UNPACK_DW` = `mov (32|M0) rD.0<1>:ud rS.N<2;1,0>:uw`（从成对 half 里抽一半装进 dword lane）；
     `UNPACK_WW` = 同上但 word→word（`<2;1,0>` 源跨步 2）；
     `PACK_W` = `mov (32|M0) rD.0<2>:uw rS...`（16+16 交织回填成对 half）；
     `BYTE_G` = `:b/:ub` 且源跨步 ≥4 的字节反交织；
     `QADDR` = `shl ...:q 16` 类 64 位地址拼装（**不是**数据拼装，单独列出以免误判）。
4. 全 232 个核累计：**窄 message 7,741 条；半宽寄存器搬移 33,013 条；ugm send 107,643 条**。

## 2. 全网结论

1. **没有任何一族值得开新的"窄读/拼装"卡**（`worth_card = 0/21`）。窄处只有三种成因，且三种都已在本轮或既有卡里定价：
   - **已经是宽块**（F04/F11/F14 代表核窄 message 恒 0，F04/F13 连半宽搬移都是 0；F13 仅 contract 核每核 20 条，F16 每核 10 条，都只占其宽读的 1% 上下）；
   - **元素宽度等于载荷宽度**（2B 的 half、4B 的 fp32），改宽要么多读字节、要么改变写域；
   - **成对 half 布局的对价**（`UNPACK_*` 与 `PACK_W` 成对出现），这是生产者布局决定的，删除必须跨派发改布局，而该方向已由 f05-kv-consumer-layout / coefficient-reuse 占用，且 n02d 已证片段宽化会被驱动重新窄化（L14）。
2. **全网唯一能给出"4 条窄 message → 1 条 16B message"ISA 级证明的是 F20 与 F21**（4 条 `store.ugm.d32` 共用同一地址寄存器、立即数阶梯 +0/+4/+8/+0xC）：可删 3 条（F20）与 6 条（F21）。两者都是 1 个 PASS 的尾核，且 L12 已实测该内核删 32/64 条 message 为 INDISTINCT，**低于可测下限，不开卡**。
3. **全网不存在"两个 half 用移位/或/掩码拼成一个 dword"的数据拼装**：`and 0xFFFF` / `0xFFFF0000` 掩码 0 处；16 位移位站点全 232 个核只有 16 条（F01 8、F10 8），逐条核过——F01 的 4 条 `shl (16|M0/M16) rX.0<1>:q ... 16:w` 与 F10 的 8 条 `shl (1|M0) r2.8<1>:d ... 16:w` 是 64 位地址/偏移拼装，F01 的 4 条 `shr (32|M0) rX.0<1>:ud ... 16:w` 是 half 宽整数乘法取高半积的算术（`mul :uw` → `shr 16` → `add3`），**没有一条**是把两个 half 合进一个 dword。这条否定结论是本轮最干净的证据（§5 之外的第二个"无"）。

## 4. 逐族判断（每族一处 site，含为什么不开卡）

**F01（ord 0，L224 `0B90`）** `load.ugm.d32` —— 逐 lane 4B gather 73 条/kernel，另有 8 条 `store.ugm.d32`。
地址来自 GRF（`r10`），不是同一基址加立即数；n18b 已证入口块是单发散区（`cmp lane,16 -> goto`），只有 lane 0..15 活，真实流量 301.40 MB、重复 0 B（L11）。把 gather 改宽会读进掩码外的字节 = 新增流量；**可删 0，不开卡**。

**F02（ord 1，L398 `1520`）** 窄 message **0**；读侧全为 `d32x8t/x16t/x64t/d64x64t` 宽块；残下的是 `mov (32|M0) r38.0<2>:uw r46.0<32;16,1>:uw` 这类 16+16 交织（120 条）+ `<2;1,0>:uw` 抽取（152 条）。n01 已实测 528 条 16-lane 交织 mov 是 VNNI 打包、删不掉（L5）；n02d 把 (8,16) 换成 (8,64) 后 ISA 仍是 64 条 `load.ugm.d32x16t` 且 send 597→618（L14）。**不开卡**。

## 5. 唯一两处能证到"可宽化"的站点（以及为什么仍然不开卡）

**F20 / ord 230 / `s37_fold_body_r1a_v1`**（ISA 文件 `work/codex-astra-fp16-int8-audit-20261024/f20-coarse-owner-20261026/captures/native-f20-pixel-owner/ISA/CS_asm76902ef344609c8a_simd32_0000000000000027_38_orig.asm`；sha256 见 JSON）：

```
L4833 [100E8] add  (32|M0) r20.0<1>:f  r24.0<1;1,0>:f  r30.0<1;1,0>:f
L4834 [100F0] send.ugm (32|M0) null r12 r10:2  a0.0       0x24000504  // store.ugm.d32  [A+0x0]
L4836 [10110] send.ugm (32|M0) null r12 r18:2  0x4000:a0.0 0x24000504  // store.ugm.d32  [A+0x4]
L4837 [10120] send.ugm (32|M0) null r12 r20:2  0x8000:a0.0 0x24000504  // store.ugm.d32  [A+0x8]
L4838 [10130] send.ugm (32|M0) null r12 r4:2   0xC000:a0.0 0x24000504  // store.ugm.d32  [A+0xC]
```

- 四条 message **共用同一地址寄存器 `r12`**，只有立即数变（+0/+4/+8/+0xC）；`r12` 由 `[100C8] shl (32|M0) r12.0<1>:d r6.0<1;1,0>:d 4:w` 生成 = 16B 步长 → 每条 lane 的 16B 记录被拆成 4 条 4B message。
- 同一 kernel 内存在 `store.ugm.d32x8t` 96 条；同一网内存在 `store.ugm.d32x4`（每核 F05 24 条 / F10 4 条 / F15 4 条）→ **宽形在 ISA 里确实可用**。
- 可删 = 4−1 = **3 条**/kernel。位型不变（同一批 f32 dword 只是合并成一条 16B/lane message）。
- 代价/闸门：四条 data 寄存器当前是 `r10:2 / r18:2 / r20:2 / r4:2`，**不连续**；要落成 `d32x4` 需要 3 条 mov 重排，等于用 3 条 ALU 换 3 条 message，净收益归零。
- 决定：**不开卡**。L12 已在同一内核实测：删 32 条 / 64 条 fragment message 分别 +0.0257 / -0.0181 ms（INDISTINCT），3 条 message 远低于下限。

**F21 / ord 231 / `ioport_block70_2`**：两组各 4 条 `store.ugm.d32` 共用地址寄存器 `r4`，立即数 +0/+4/+8/+0xC（`[4458]`/`[4480]`/`[44A0]`/`[44C0]` 与第二组），可删 **6 条**。但 `[4450] shl (32|M0) r4.0<1>:d r2.0<1;1,0>:d 2:w` 给出的是 4B 步长，与 "+0xC 同一记录" 不自洽 → **per-lane 记录连续性 = UNKNOWN**，且 data 寄存器 `r96/r94/r92/r36` 不连续。**不开卡**，只记录为 UNKNOWN 前提下的 6 条上限。

## 6. 地址层（base+imm）普查

对 232 个核的全部 `send.ugm` 解析"地址操作数 + 立即数"（`_addr/*.json`）：

| 量 | 数值 |
|---|---|
| ugm send 总数 | 107,643 |
| 带立即数偏移的 send | 817（0.76%） |
| 窄 send 带立即数 | 816 / 7,741（10.5%） |
| 相邻两条 message 复用同一地址寄存器 | 25,970（24.1%） |

- 结论：**当前 native 的 message 地址绝大多数是"逐 lane 在 GRF 里算好"的**；立即数占比可观的只有 F15（512/1,392 = 37%）、F21（6/34 = 18%）、F10（192/2,080 = 9%）、F01（46/656 = 7%），F16 只有 48/8,912（0.5%）。因此"短生命周期基址（lane 项 / tile 项 / K 常量偏移）"这一轴在多数族**没有剩余空间**——与 n04b 的"F05 C128 A 行已是 base+imm"、n09/n04a 的"源码级地址折叠不落地（add/mul 不降）"一致，属于 **L1 已定价方向，不开地址卡**。

## 7. UNKNOWN（不凑数，逐条写明为什么查不到）

1. **payload 字节数 / lane 步长**：反汇编注解 `wr:1+4`、`rd:2` 的确切语义本轮未闭环（同一 kernel 内 `d32x4` 用 4 个 data 寄存器、`d32` 用 2 个，比例不自洽），因此本文所有"可删条数"只用 **message 条数**，不折算字节。
2. **F21 的 per-lane 记录步长**（§5）：`shl r2<<2` 与 +0xC 阶梯矛盾，需源码侧确认记录布局，本轮无法从 ISA 判定。
3. **F20/F21 合并后 GRF 是否真的连续**：取决于编译器寄存器分配，静态 ISA 不能证明"改源码后仍连续"。
4. **F08 的 144 条 4B store 是否有消费者只需要 half**：需要跨派发读者清单，本卡不做（T16 类未证明区）。
5. **F01 gather 的 16-lane 掩码外的地址是否可安全扩展**：n18b 只证了掩码存在与流量，未证地址域边界。
