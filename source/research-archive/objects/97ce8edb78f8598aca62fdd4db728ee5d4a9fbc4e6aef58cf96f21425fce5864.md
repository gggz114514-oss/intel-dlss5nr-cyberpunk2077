## 二、P1：翻转后的共享槽位被误用为物理 y

位置：ROOT/candidates/amd-layout-fusion-resume-20261016/f3-c32-keep-anchor-half-tile-v1/source/fused_body_ds_keep_anchor.comp:1711-1717。

父body的确使用 sx=sg&1、sy=sg>>1。由父 nr_tok_addr 和一个body tile中的2×2均值得到真实池化坐标：

```text
physical_px = 4*wx + 2*sx + dx
physical_py = 4*wy - 2 + 2*sy + dy
```

新核选择翻转共享暂存的两半，这本身可以成立：

```text
ly = 2*(1-sy) + dy
nrf_mean[(4*ly+lx)*32+k] = v
rowbase = sy==0 ? 8 : 0
py0 = 4*wy - 2 + 2*sy
```

但第1713行把共享暂存行ly直接用于全局有效性判断：

```text
int py = 4*int(wy) - 2 + int(ly);
```

ly是共享数组中的排列，不是该body像素的物理行。翻转槽位后，上式相对真实物理y偏移正负两行。两个具体反例：

| 情况 | body真实池化行 | 当前mean判断行 | 最终有效store |
|---|---|---|---|
| wy=0、sy=1、dy=0/1 | 0/1，有效 | -2/-1，被判无效，v保持0 | py0=0，rowbase=0，读取刚被置零的mean并写出第0/1行。 |
| wy=48、sy=0、dy=0/1 | 190/191，有效 | 192/193，被判无效，v保持0 | py0=190，rowbase=8，读取刚被置零的mean并写出第190/191行。 |

对应另一半会读取无效body owner的暂存，但其最终store被half_ok抑制，不能补回丢失的有效mean。保存的SPIR-V main中的命名变量store同样包含：

```text
ly = IAdd(IMul(2, ISub(1, load sy_off)), load dy)  // word offset 6270
py = IAdd(ISub(IMul(4, bitcast(load wy)), 2),
          bitcast(load ly))                     // word offset 6333
```

这不是只有源码注释错，也不是尚需GPU才能定位的疑点。独立符号坐标检查得到：输出y=0、1、190、191，共1344个有效池化像素，其mean被错误置零；其投影影响范围为86016个输出half。这里报告静态合同错误和影响地址范围，没有宣称已经观测到86016个GPU数值差异，固定帧数值门仍未执行。

### 最小修正

保留本轮选用的共享槽位、n0、rowbase、store分工和父锚点，只在新v2中把mean有效性使用的py改为：

```glsl
int py = 4*int(wy) - 2 + 2*int(sy_off) + int(dy);
```

mean的共享索引继续用ly；mean有效性检查改用真实physical_py。不能只改proof中的公式，必须改真实源码、生成器和重新编译的新SPV，并重新核对实际运行表绑定。现有v1和27份argv保持封存，不覆盖后再沿用旧哈希。

本审计只用符号坐标替换上述一行后，所有有效输出到body来源的映射错误数为0；这仍不是FP16算术、驱动编译或GPU数值通过。修后再排首次数值门，数值过门才派性能和计数器臂。

## 三、施工单17的subgroup分工需要澄清

报告17 §3.1 的body owner公式正确。§3.2的DS分工也有独立可行解释：body生产者先按sg的X/Y位把值写入整个WG共享区，barrier之后，DS消费者可以重新分配“8个矩阵行”和“32个输出通道”。消费者SG不必继续只处理同号body生产者的Y半块。

因此，不能仅由body的sy=sg>>1推出DS的row_half也必须=sg>>1。报告17所给 n0=(sg>>1)*32、rowbase=(sg&1)*8、py0=4wy-2+2*(sg&1)，配合未翻转的mean共享排列 ly=2*sy+dy，是一组合法映射，独立符号检查也没有来源错位。旧候选的slot使用2*sy，不能仅凭其不是2*(1-sy)就另判一处错误。

报告17的表格把“DS所消费的body tile行”写作“body行”，同时用了同一个sg符号，确实容易被理解成两阶段SG必须一一对应；本补件明确区分producer_sg和consumer_sg，这处表述应由Codex澄清。WorkBuddy选择另一套分工可以保留，但“位拆分必须这样改，否则原方案自相矛盾”的结论不采信；当前真正错误是翻转暂存后又用暂存行去做物理边界判断。

这也解释静态证明A/B/C/D为何没有拦住：A核ABI，B核store地址集合，C核符号/分支形状，D核局部2×2 tile读取和shared store形状；它们没有贯通验证“父body真实坐标→mean有效性→共享槽→projection矩阵行→最终store坐标”。覆盖集合相同不能代替这条数据来源链。

proof_keep_anchor.py中应增补这条具体关系及首尾反例，保留现有地址/唯一writer检查；无需重扫其他家族或建立通用验证框架。

## 四、C256证明的有效范围

父PASS导出的21×12 tiles、body11×7、shift=(0,-1)，以及DS132×16、IW84/IH48/OW44/OH24、K256/N512、layout1、valid42×24均成立；历史源码注释的42×24 tiles不是该PASS参数。保存的C256已编译SPV与父实际绑定SPV字节相同。

接受有效1008 token、视图padding48 token、分配尾部96 token=98304 B的划分。视图padding遵守父零mean/投影输出合同，尾部没有父视图writer，保留必要首次clear；AMD fswin_body.glsl:3140-3143关于padded tokens写零的注释与此方向一致。

接受父DS的store结论：t=py*44+px，每组8个连续raster token处于同一个16-token物理组，固定16通道片是连续128 half；覆盖全部512通道需32个这样的片，片间距256 half，不是整个M8空间组的4096 half都在一段连续内存中。132个空间组中12个跨视图行，也不破坏每个16通道片的store连续性。因此父DS不需要scatter。

但是，这不能自动推广成未来融合核不需要重排。C256 body WG的四个tile只覆盖4×4池化patch；例如同一池化行x=0..7的父DS M8输入，前四列和后四列分别来自wx=0、wx=1的body WG。旧DS从全局skip22读取它们，本轮还没有实现融合后的数据owner和矩阵行组织。

后续须证明融合核如何在保留原body窗口计算的前提下获得自己的投影输入，再选择合法分块、局部重排/分散写出或有成本说明的其他适配，不能把“父raster store连续”当成“融合输入已经齐备”。这不是不可实现结论。layout0替代方案仍另列L2，并同步全部真实消费者与padding。
