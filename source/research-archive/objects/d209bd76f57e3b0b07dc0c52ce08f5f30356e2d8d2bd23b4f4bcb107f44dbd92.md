# ANALYSIS — idt-identity-recipe（字节身份复原，ALL 族，232 PASS / 39 唯一 SPV）

本卡不改任何 shader、不改 plan、不产候选、不碰 GPU。它回答的是合同里"构建身份三件套"的第 1 条：
**给定 (source, 目标 SPV)，能否亲手重编译出逐字节相同的 SPV。** 结论：**39/39 唯一 SPV、232/232 PASS 可复现**，
其中 35 个纯 glslang 编译即等，4 个需要 NoContraction 装饰迁移。

产物：`RECIPES.json`（机器可读配方）、`reproduce_any.py`（实测入口，退出码 0 = 字节一致）、
`identity_kit.py`（编译 + 装饰引擎）、`IDENTITY-TABLE.md`（39 行表 + PASS 覆盖 + 头文件 pin）、
`BUILD.json`、`evidence/PASS-AUDIT.json`、`evidence/work/IDENTITY-RUN.json`（每条配方的完整记录）。

---

## 1. 映射：每个 (PASS, SPV, 源) 到底对应什么

合同要的"生产者每个 (lane,component) 代表哪个 (token,channel)"在本卡是**身份映射**：一个 PASS 行
= (ordinal, pass 名, 唯一 SPV 路径, SPV sha256, 源路径, 源 sha256)，而配方把 (源, 宏, 头文件字节, 装饰来源)
映射到 SPV 字节。逐层枚举与覆盖证明：

| 层 | 数量 | 覆盖证明 | 证据 |
|---|---|---|---|
| 基线 plan 的 PASS 行 | 232 | `CURRENT-232-ROWS.json` 232 行，逐行 spv 路径都在基线 plan 文本里出现（各 SPV 路径在 plan 内出现 2636 次，含 PASS 行与身份区） | `evidence/PASS-AUDIT.json` |
| 行 → 文件 | 232 | 每行 `spv` 文件存在且 sha256 = 记录值；每行 `source` 文件存在且 sha256 = 记录值；失败 0 行 | `evidence/PASS-AUDIT.json` |
| 文件 → 唯一 SPV | 39 | 按 `spv_sha256` 去重，39 个；每个唯一 SPV 的 ordinal 列表见 `IDENTITY-TABLE.md` 第二表 | `RECIPES.json` 的 `ordinals` |
| 唯一 SPV → 配方 | 39 | 每个 key 都有配方，且 `verified=true`、`verified_sha256 == target_sha256`；失败 0 个 | `RECIPES.json` |
| PASS 覆盖 | 232 | 39 个唯一 SPV 的 `ordinals` 并集 = {0..231}，无重复、无遗漏 | `reproduce_any.py --all` 打印 `232/232` |

**没有漏读/重复写**：ordinal 集合是 0..231 的一个划分（partition）——每个 ordinal 恰好属于一个唯一 SPV
（去重是按 spv sha，行级审计已确认同 sha 的行的 spv 路径指向同一文件）。尾块不是本卡的语义，
但 ordinal 227-229（F02 的 7 个 PASS 里最后 3 个）与 169-191（C256 段）等"靠后"位置全部在覆盖内，
说明覆盖不是靠前段抽样。

## 2. 删什么真实工作

**本卡删除的"工作"不在 GPU 上，而在证据链上**：删掉了"这个 SPV 到底怎么来的"这个不可判定项。
逐条列（删的是**候选方的重复劳动与误判**，不是 kernel 指令）：

| 被删掉的真实工作 | 原来每次的代价 | 依据 |
|---|---|---|
| 每个候选卡重新猜 include 目录 | 22/39 个 shader 曾因找不到 `#include` 直接编译失败（上一轮 `IDENTITY-232.json`：16 raw + 1 decorated + 22 failed） | 本卡把每个 shader 实际读到的头文件字节 pin 住 |
| 每个候选卡重新猜 `-D` | F11 的 `#error`、F12 l3/l4 的 KIND、F17 的 `PROJECT_PAIR` 都会让"重编译父 SPV"这一步失败，从而**整个身份门无法开始** | 3 个需要宏的 shader 已定值 |
| 反复试装饰迁移源 | 4 个 shader 的 NC 集合只能从特定父模块迁移；试错顺序错会得到"能编译但字节不同"的假阳性 | 父模块与迁移方式（含 F19 的 `drop_region`）已定值 |
| 把"不能复现"误记成"工具链不同/源码被改" | 一次误判会让整张卡的"父身份"结论作废 | 分类见 `IDENTITY-TABLE.md`「关键结论」：**缺 -I / 缺 -D / 缺装饰迁移**，无一条需要改源码 |

## 3. 重叠：独立工作原来如何重叠（RAW/WAR/WAW）

本卡没有 kernel 侧的读写，因此按**配方之间是否互相污染**给出等价的依赖表（这才是本卡的 RAW/WAR/WAW）：

| 资源 | 谁读 | 谁写 | 关系 | 处理 |
|---|---|---|---|---|
| `evidence/headers/<spv12>/` | 该 SPV 的 `reproduce_any.py` | 本卡构建时 | **每 SPV 一个独立目录**，无共享写 | 39 个目录互不重叠；同名头文件在不同 SPV 下可以是不同字节（例如 `register_handoff.glsl` 在 F05-c64 与 F10 下内容不同） |
| 工作区同名头文件目录（`header_origins`） | 多条配方可能读到**同一份字节**（例如 `register_handoff.glsl` 的 11 种内容被 5 个 shader 复用） | 只读 | **WAR 风险**：任何一次工作区清理都会让"原始目录"路径失效 | 因此默认走 pin（`pinned_include_dir`），原始目录只作 provenance；`--workspace-headers` 可验证原始目录仍然有效（本轮已验证 39/39） |
| 父 SPV（4 个装饰迁移源） | 装饰迁移 | 只读 | 只读共享，无写 | 记录 `decoration_parent` + `parent_sha256`，父模块若被替换立即能被 sha 检出 |
| 基线 plan / 232 行表 | 行级审计 | 只读 | 不改 | `BUILD.json.baseline_plan.match=true` |

关键点：**"同一个头文件名"不等于"同一份字节"**。把 39 条配方塞进一个共享 include 目录会立刻产生
WAW（后写的 `split16_common.glsl` 覆盖前一个），这正是上一轮 22 个失败的主要成因之一。
本卡用 per-SPV pin 目录把这条依赖拆开。

| 运行期成本 | **0** | 未改 SPV、未改 plan、未改绑定、未改 PUSH、未改 grid |
| 有效 lane / WG / scratch / 活值峰值 | **0 变化** | 复现出的字节就是基线字节（sha 相同），native/资源侧必然一致 |
| 代码体积 | 0 | 同上 |
| 新增长寿命风险 | 无 | 无代码改动 |

**不是"逻辑字节 ≠ DRAM 字节"的问题**：本卡没有任何执行路径变化，唯一新增的是卡目录里的
Python/JSON/头文件副本。

## 5. 是否真落到 native

本卡不声称任何 native 变化；它的判据是**更强的一类**：输出字节与基线 SPV 相同，而 SPV 相同 →
驱动看到的模块相同 → native 必然相同（同一驱动/同一 plan/同一 PUSH）。可核对的判据：

- 判据 A（已达成）：`sha256(rebuilt) == sha256(baseline spv)`，39/39。
- 判据 B（已达成）：`reproduce_any.py --all` 退出码 0，且 `232/232 passes covered`。
- 判据 C（已达成）：行级审计 0 失败——SPV 文件 sha、源文件 sha、plan 绑定三者一致。
- 判据 D（已达成）：只给 pin 目录一个 `-I` 也能字节一致 ⇒ 配方自包含，不依赖"某个目录还存在"。

反过来，"若看不到就等于未实现"的对应物是：**若某条配方重建出的 sha 与基线不同，则该 shader 的
父身份未建立，任何以它为父的候选都不能声称"只改了我想改的地方"**。本卡把这条从 22 个未知降到 0 个。

本卡**没有**做的事（明确记账）：没有验证这些 pin 目录就是当年真实构建目录（只验证了"这些字节能复现"）；
没有验证不同 glslang 版本能否复现（明确 pin 到本二进制 sha）；没有跑 `spv_validate_cpu.exe`
（没有产出新 SPV，且 baseline SPV 早已在别的卡验过）。

## 6. 整体是否更快

本卡不产生性能结论，也不该有。它对后续卡的作用是**让单链归因可做**：

- 任何 232-PASS 候选现在都能在源码级与"字节精确的父"逐条对齐（NoContraction 集合、operand signature、
  指令流），不需要"先怀疑身份"。
- 反过来说：**不允许**把本卡的 `verified` 当作任何性能结论。本卡没有任何毫秒数。
- 要测的整体量与臂：由后续施工卡按合同 §5 的 `GPU-REQUEST.json` 提出；本卡不生成 GPU 请求。

## 已排除项（不能复现时才会用到的清单，本轮全部不适用）

本轮 39/39 复现，因此"原因分类 + 已排除项"只有正面结论；但仍把已经排除掉、不需再试的路径记下来：

1. **已排除：`-Os` / 优化开关**——17 个 shader 用裸 `-V --target-env vulkan1.3` 就能字节一致，说明基线不是用别的优化档编的。
2. **已排除：`--spirv-val`**——`compile.txt` 里出现过 `--spirv-val`，但它不改变输出字节；加不加都一致。
3. **已排除：换 glslang 版本**——不需要：同一二进制 + 正确宏/头/装饰即可全量复现。
4. **已排除："F12 l4 源码缺 `scratch` 声明"**——不是缺源码，是 `#if KIND!=3` 死代码；KIND=3 下不参与编译（详见 `IDENTITY-TABLE.md`）。
5. **已排除："F11 需要 KIND=4"**——KIND=4 编出来的 sha 是 `55336f0f…`，与基线 `cc70e2d6…` 不符；基线是 KIND=1。
6. **未决（不影响本轮结论）**：31 个"raw 复现"的 include 目录，本轮选的是**内容等价**的目录
   （例如 F06-c64 用的是 `codex-sol-int8-long-008-20261019/dce-dead-pack/scratch`），
   而不是当年 `-I` 的那个目录。字节可复现性已证；"当年用的是哪个目录"只影响 provenance 记账。
