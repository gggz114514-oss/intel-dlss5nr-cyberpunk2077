## 0. 结论（先说答案）

**F08 l0 里不存在任何顺序依赖。** n08b 的 fixed 金帧改变不是"双射重排暴露了未声明依赖"，
而是 **n08b 自己的接线错误**：真正被派发的 plan 只有 SPV 路径换了、**grid 字段没换**，
于是"转置后的索引算式"被跑在"未转置的 grid"上——写域不再是双射，权重读到越界地址，
`gf` 里 29.6% 的地址被错误的 WG 覆盖、70.4% 的地址从来没被写。

具名描述（可直接替换 LESSONS L6 的措辞）：

> **PLAN-GRID-DESYNC**：F08 l0 的 token/group 索引算式（`token = WGID.a*K1 + (sg%M)*8`;
> `g = WGID.b*K2 + sg/M`）与 plan 里的 `PASS … gx gy gz`（= 派发网格）是**同一个映射的两半**，
> 必须成对修改；n08b 只把前一半（SPIR-V）换成了转置版本，后一半仍沿用父的 `66 2 1`，
> 于是 132 个 WG 的写域重叠、越界读权重，fixed 帧因此改变。这与执行顺序无关。

三条独立证据（详见 §3）：
1. 被派发的 plan（`queue/n08b-f08-order/plan-rebased.txt`，sha `fa2033aa…`）与基线 plan 只差 **16 行、且每行只差 SPV 路径**，grid 仍是 `66 2 1`；n08b 自己的 plan（`cards/n08b-f08-order/plan.txt`，sha `98a26cfa…`）里那 16 行才是 `4 33 1`，但**从未被派发**。
2. 从 SPIR-V 字节里抽出来的算式：n08b 是 `component[1] × 32` 喂 token、`component[0] × 2` 喂 group（父是 `component[0] × 16`、`component[1] × 4`）——轴确实换了。
3. ISA 侧同样看到 `shl 2 → shl 5`（×4 → ×32，同一操作数 `r69.6`）和 `shl 4 → shl 1`（×16 → ×2，同一操作数 `r69.1`）：**shader 的改动落地了，grid 的没有。**

**F08 可以摘掉"未知"标签**：n08b 的负结果不能当作"顺序敏感"的证据，也不能用来否证
"按权重组聚 WG"这个方向。同时 n08 那 −0.182 ms 的解释不受本卡影响（那是内容变量，不是顺序变量；
且 n08 自己两套金帧都过）。

## 2. A) 机制清单：这个 shader 里一切可能引入顺序依赖的机制

先说方法：全部结论来自**只读静态证据**——SPIR-V 字节（自写 parser，opcode 编号用 glslang
16.5.0 逐操作编译校准，见 `OPCODE-CALIBRATION.json`）、plan 字段、PUSH 常量、以及既有 native
捕获里的 ISA（只读）。没有任何一条依赖"数值噪声"或容差。

| # | 机制 | 存在？ | 硬证据 | 能否产生顺序依赖 |
|---|---|---|---|---|
| A1 | 原子操作 | **否** | 3 个 build 的 opcode 直方图里 227…242 区间为空；校准：本机 glslang 把 `atomicAdd` 编成 **234**（`OPCODE-CALIBRATION.json`） | 不能 |
| A2 | 跨 WG 全局读 / 写 | **写只有 1 个缓冲；读不到写缓冲** | 21 条 cooperative-matrix load（opcode 4457，校准：指针在第 3 个操作数）：20 条根在 binding 0（Weights，`readonly`）+ 1 条根在 binding 2（Input `gx`，`readonly`）；5 条 store（opcode 4458，指针在第 1 个操作数）：**4 条根在 binding 3（Ffwd `gf`）** + 1 条根在 Workgroup 存储（`debugTile`，死路径）。模块内**没有任何**对 binding 3 的读（`OpLoad` 的根只有 Input/Workgroup/Function/PushConstant 四类，13 条未解析的根全是 `OpFunctionParameter`） | 写域两两不交（见 A4）⇒ 不能；写域一旦重叠（本卡 §3 的误派发）⇒ 可以，而且这正是实际发生的事 |
| A3 | SLM 复用 | **有变量，但执行路径上不存在** | `debugTile[1024]`（Workgroup，plan 字段 `shared=2048` 一致）；4 条屏障指令（2×`OpControlBarrier` + 2×`OpMemoryBarrier`）全部位于指令下标 1329/1330/1371/1372，即函数 `debug_half`（起始下标 1308）内部；该函数只在 `if(pc.p5.x != 0)` 分支被调用，而 PASS 23 的 `PUSH p5 = (0, 589824, 2949120, 5308416)` | 不能（跨 SG 零共享：`debugTile` 下标 `sg*128`，每 SG 私有） |
| A4 | `subgroup` / `workgroup` 内置量的隐含假设 | **有，共 2 条** | 模块只装饰/读取 3 个 BuiltIn：`gl_WorkGroupID`(26)、`gl_SubgroupID`(40)、`gl_SubgroupInvocationID`(41)；**没有**读 `SubgroupSize`/`NumSubgroups` | (i) "local_size=256 且 subgroup=32 ⇒ 正好 8 个 SG" 无运行时校验（潜在，但不引起顺序依赖）；(ii) **grid 字段与索引算式是同一映射的两半**——这是真正引爆的那条 |
| A5 | binding 别名 | **否** | 16 个 F08 PASS 的 BIND 逐条核对：slot0=`split16_b23_weights`(3 672 064 B)、slot2=`block22_out`(1 179 648 B)、slot3=`split16_b23_F`(1 179 648 B)、slot9=`split16_debug_dummy`(**4 B**)；输入（slot2）与输出（slot3）不同缓冲，无 in-place 危险 | 不能；但 slot9 只有 4 B，而 `debug_half` 每次调用要写 128 个 float 到 `dbg[p5.y/p5.z/p5.w + …]`（基址 589 824 / 2 949 120 / 5 308 416）——**debug 一旦打开就是越界写**（当前 p5.x=0 所以无害） |
| A6 | 未初始化读 | **基线身份里没有；误派发里全是** | 父：1056 个 SG 的双射覆盖 = 540 672/540 672 half，重数 1，l1 读之前整个 `gf` 都被写过；累加器 `MC(0.0)`、`debugTile` 先写后读 | 本身不产生；但 §3 的误派发让 380 928/540 672（70.4%）的 `gf` 元素从未被写 ⇒ l1..l3 读到 pool 里的陈旧字节 |
| A7 | 跨派发生产者/消费者 | **有（正常链）** | PASS 22 `f3c256_body_ds` 写 `block22_out` → PASS 23 读它（slot2）并写 `split16_b23_F` → PASS 24/25/26（l1/l2/l3）读 `split16_b23_F`（slot3） | 不是派发内顺序依赖，但决定"错值怎么传到帧"：l0 一错，后面三级全被污染 |
| A8 | 编译器重排 / 波次边界 / 发射顺序 | **有，但只影响性能** | 活路径屏障 0 条、原子 0 条、跨 WG 交换 0 条 ⇒ 没有任何同步让"顺序"变成可观测量。**反证**：n08 自己把每 WG 内容与派发形状都改了（`33 4 1`），两套金帧照样逐字节通过 | 不能改字节；只能改毫秒 |

### A4(ii) 展开：为什么"grid + 算式"是一个不可分割的单位

一个 (lane, component) 代表哪个 (token, channel) 完全由这两半共同决定：

| 项 | 父 | n08 | n08b（设计意图） |
|---|---|---|---|
| grid（plan 字段） | `(66,2,1)` | `(33,4,1)` | `(4,33,1)` |
| token | `WGID.x*16 + (sg%2)*8` | `WGID.x*32 + (sg%4)*8` | `WGID.y*32 + (sg%4)*8` |
| group | `WGID.y*4 + sg/2` | `WGID.y*2 + sg/4` | `WGID.x*2 + sg/4` |
| WG 数 / SG 槽 | 132 / 1056 | 132 / 1056 | 132 / 1056 |
| 写集 | 540 672/540 672，重数 1 | 同 | 同（与 n08 **逐元素相同**，本卡已复核） |

前两行里任意一行单独改动都会把双射变成"重复写 + 漏写"。父与 n08 都是成对的，所以都过金帧；
n08b 的两半被拆散了（§3）。

## 4. C) 结论：具名机制 vs 实现 bug

**判为 n08b 自己的实现/接线 bug（不是 shader 里的顺序依赖）**，具体两层：

1. **变更层（根因）**：`COMMON.make_plan()` 只做"把基线 plan 里的 SPV 路径替换成候选路径"
   （`COMMON.py:243-271`，函数体里没有任何 grid 字段处理），而 F08 的重排**同时**要求
   `66 2 1 → 4 33 1`。n08b 的 `RESUME.txt:59` 自己就写着这个陷阱（"不要用 make_plan / rebase_candidate_plan
   单独重写本卡 plan … `66 2 1` 会让转置映射只算 64/1056 token"），但 gate 阶段实际用的正是
   只换路径的那种 rebase（`rebase.replaced_passes=16`、grid 未动）。⇒ **合同 §6 的 A 类
   "实现未落地"，只是发生在 plan 层而不是 SPIR-V 层。**
2. **表象层**：金帧不一致（E 类表象）。它**不是**数值/舍入/K 序/NoContraction 问题——SPIR-V 与父
   逐序号 opcode 相同、仅 6 处整数立即数 + 2 处 WorkGroupID 分量不同；`nan=0 inf=0 normal_close=true`。

对既有条目的更正建议（`evidence/LESSONS.json` 是共享只读文件，本卡不改，只提建议）：

> L6 现文：“A bijective workgroup remap changed the fixed frame in F08, which is unexplained…”
> 建议改为：“**n08b 的 fixed 帧改变已定位为 plan-grid-desync（只换 SPV 未换 grid），
> 不是 WG 顺序依赖；F08 l0 无原子、无跨 WG 交换、写域可分、SLM 只在死路径，跨 WG 重排本身安全。
> 该负结果不得用于推断派发顺序的代价。**”

### 4.1 反过来说：如果 F08 真有顺序依赖，会长什么样

本卡把判据留在这里，供以后任何 F08 顺序实验先做"排除法"：

1. 出现 `OpAtomic*`（本机校准：`atomicAdd` → opcode 234）或对同一地址的跨 WG 读—改写；
2. 活路径出现 `OpControlBarrier`/`OpMemoryBarrier`（当前 4 条全在 `debug_half`，下标 1329…1372）；
3. SLM 下标里出现别的 SG 的偏移（当前 `sg*128`，私有）；
4. 两臂的 **写集**（元素集合，不是顺序）不同——本卡 `model.py` 已给出四套映射的写集枚举，可直接比对；
5. 同一地址出现 ≥2 个写者（WAW）——本卡已经量化：正确配置 0 个，误派发 143 360 个。

只有 4/5 成立时，"双射"这个前提就已经被破坏了，此时任何金帧差异都归因到映射，而不是顺序。

## 5. 对跨派发改造（N16）与后续卡的含义

1. **F08 l0 对"跨派发/持久化"是安全的**：没有原子、没有跨 WG 全局交换、写域互斥（成对配置下）、
   SLM 只在死路径、活路径 0 屏障。持久化/WG 重编号只要能重新算出 `(token, group)`，bytes 不变。
2. **唯一硬约束是 (网格, 算式) 必须成对**：任何把每 WG 工作量、轴语义、grid 改一处的卡，
   plan 里必须同时改 grid，并在 `PROOF.json` 里像 n08b 的 `verify.py` 那样**枚举全部 WG×SG**
   证明双射（只证"每 WG 内容不变"不够，必须证"派发后的写集"）。
3. **工具层现状**（本卡只读核对，不改）：`COMMON.rebase_by_ordinals(..., carry_fields=True)`
   （`COMMON.py:286`）现在会连同 PASS 行字段（含 grid）一起搬，并已有 `test_carry.py` 单测
   （伪造 `169→338` 的 grid、断言只有目标行变化）。n08b 的 gate 早于这个修复，用的是只换路径的
   `COMMON.make_plan()`（`COMMON.py:243-271`，函数体里没有任何 grid 处理）。
   仍建议补一条**独立**断言：候选 SPV 的 `(WorkGroupID 分量, 立即数)` 与父不同、而 plan grid 未变
   直接报错；原型就是本卡 `model.py` 的 `algebra_of()`。
4. **同类风险点**：n08b 的 `census.json` 已列出 5 个 `token_x_group_y` 形状（F08 l0、F09 l1、F11 l3、
   F12 b30_l3/l4）和 4 个 `mn_2d`；它们任何"轴交换"卡都会踩同一个坑，判据同上。
5. **n08 的 −0.182 ms 重新定性**：它的两半是配对的（`33 4 1` × 对应算式），两门都过，
   native 也看到整数立即数变化 ⇒ 那是**内容变量**（每 WG 输入足迹 2×、同 slab 4 条流）的代价，
   与顺序无关；"按权重组聚 WG"的方向**没有被这条负结果证伪**。

## 7. 未决项 / 不能证

1. 没有 GPU，所以"第 16 384 字节确实是第一个不同的字节"仍是**推断**（模型 + 竞争分析），
   不是实测；§3.4 已给出可证伪的预测。
2. 权重越界读的**具体数值**不可知（落在 pool 里别的缓冲/空洞上，取决于分配布局）；这不影响结论，
   只影响"错得多离谱"。`nan=0/inf=0/normal_close=true` 说明没有触发设备错误，与 pool 分配相符。
3. lane→(row,col) 的 DPAS fragment 约定仍无本工作区可引证据（与本卡结论无关：三臂在这一层一致）。
4. `n08b` 的 native 臂同样跑的是 `plan-rebased.txt`（`spec-native.json` 指向它），所以它的
   "shl 5 / shl 1"ISA 观察只证明**shader**改了，不证明 grid 改了——这一点应当在 n08b 的
   `RESULTS`/`RESUME` 里补注（本卡不改别人的目录）。
5. 本卡没有、也不应该产出候选或 plan；F08 组在链头保持不动。
