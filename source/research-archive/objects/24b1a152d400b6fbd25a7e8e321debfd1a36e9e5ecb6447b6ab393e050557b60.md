### 1.4 (lane, component) 层

- 累加器分量映射（**父遗留、本卡未改**）：`component ci of lane lv = (row = 2ci + lv/16, col = lv%16)`，
  4 个分量 × 32 lane = 128 = 8×16，是双射。
- 因为 `(row, col)` 在两设计中**逐元素相同**（§1.3），"哪个 lane 的哪个分量装哪个 (row,col)"
  完全不变；变的只有"(row,col) 对应的 (token,channel)"由哪个子组拥有。
- A/B 片段的 lane 指派由 IGC 的 cooperative-matrix 降级决定、源码不可见；但两侧用的是
  **同形状同 layout 同 stride 的 coopMatLoad**（`BUILD.json:spirv.*.coop_sites`：
  A `8x16` stride 16 RowMajor、B `16x16` stride 512 ColumnMajor），
  而"哪个 (r,cc) 从哪个字节取"由 §1.3 的逐元素地址等式覆盖 ⇒ 不需要 B580 的 fragment CH/C 细节
  也能断定语义等价。

### 1.5 B 的两组消费确实共享同一次载入（合同要求 ④）

三层证据，从源码到 SPIR-V：

1. **源码**：一个 `MB b;` 变量、一次 `coopMatLoad(b, weights, wb+base*512+k, 512, COL)`，
   两个 `coopMatMulAdd(a0,b,acc0)` / `(a1,b,acc1)`。
2. **SPIR-V 数据流**（`BUILD.json:spirv.candidate.dataflow`）：
   候选 `muladd#1 = (a0, b)`、`muladd#2 = (a1, b)` ⇒ `shared_b = true, shared_a = false`；
   父正好是镜像 `shared_a = true, shared_b = false`（`(a,b0)`、`(a,b1)`）。
   即：kept 的操作数从 A 换成 B，共享关系从"1 A 供 2 B"翻成"1 B 供 2 A"。
3. **native**（预测，见 `NATIVE-PREDICTION.md` L1/L2/L8）：权重消息 64→32，
   A 消息 32→64，每 k-step 字节 1280→1024。**这是本卡唯一可被 native 证伪的落地判据**，
   本条不写成"已证明"。

## 3. 重叠：原来谁和谁重叠，删了之后靠什么供料

单 WG 时间轴（父 = 候选，除片段身份外一致）：
`序言 → seed（8 次标量读 + 2×4 分量写）→ K 环（32 × [3 次 load + 2 dpas]，全展开）→ 收窄 + 2 次 store`。

| 边 | 生产者 | 最后消费者 | 覆盖者 | 类型 | 候选里的处置 |
|---|---|---|---|---|---|
| E1 | `weights`（readonly global）→ B 片段 | 本 k-step 的 2 个 MulAdd | 无（只读） | RAW（global→fragment，靠 scoreboard） | **本卡目标边**：1 次载入供 2 个 MulAdd（父是 2 次载入各供 1 个） |
| E2 | `gf` → A 片段 | 本 k-step 的 1 个 MulAdd | 无（KIND0 对本 PASS 的 `gf` 只读不写） | RAW | 变成 2 次载入、每次 1 个 MulAdd（父 1 次载入、2 个 MulAdd） |
| E3 | seed（寄存器直写 acc0/acc1 分量） | 第一个 dpas | 无 | RAW（同 warp 寄存器） | 不变（值/分量/先后都不变） |
| E4 | acc0 / acc1 两条 32 步累加链 | MH 收窄 | 无 | RAW（寄存器） | 不变（仍是 2 条、64 dpas） |
| E5 | `MH(acc)` 收窄 | `coopMatStore` | 无 | RAW（寄存器） | 不变（收窄点唯一且不变） |
| E6 | 本 PASS 写 `gy` | 本 PASS 无读者（下一 PASS 以 `gf` 身份读） | 无 | 跨 PASS RAW | 不变（写集逐地址相同） |
| E7 | 两条 store（side 0/1） | 同 WG 内两两不重叠 | 无 | WAW | **不存在**：写集是本 WG 私有 2048 个元素，逐元素唯一 |

**关键点：重叠结构没有被串行化。** 每 k-step 的独立生产者仍是 3 个（2 A + 1 B），
消费者仍是 2 个 dpas，发射顺序仍是"3 条 load 背靠背 → 2 条 dpas"，
所以父那套"用 3 条消息的延迟互相遮盖"的结构逐条保留；本卡只是把**共享的那一侧**从 A 换成 B。
**没有新增任何同步**（`sync.*` 预期 122 ± 10，`OpControlBarrier` 0→0，无 memory barrier）。
**供料保护**：`PROOF.json:operand_equality` 逐元素证明 A/B 操作数地址与父相等（mismatch 0），
`PROOF.json:order_invariance` 证明 K 序、循环体顺序、累加器条数不变。

**一条必须记下的结构差异**：E2 的读放大从 4× 变 8×（同 WG 8 个子组读同一 512 B 块），
E1 的读放大从 2× 变 1×。二者**在同一 WG 内互补**，见 §4 的 distinct 足迹。

## 5. 是否真落到 native（预测 + 判据，不写"已证明"）

详见 `NATIVE-PREDICTION.md`。四条最关键：

1. **落地判据（两面都入账）**：权重 `load.ugm.d32x8` **64 → 32**（512 B/条），
   A `load.ugm.d32x64t` **32 → 64**（256 B/条）；两者必须同时出现，
   并接受变体 β（A 合成一条 512 B）——那时仍以**每 k-step 字节 1280 → 1024** 为判据。
2. **数学不动的硬不变量**：`dpas.8x8 = 64`（32×2）、两条累加链、末次 `store.ugm` 2 条、
   seed 标量读 13 ± 2、无 `store.slm/load.slm/sync.bar/fence.slm`。
   ⇒ 若 dpas ≠ 64 或出现 SLM 消息，先按 E/A 类处理，不许当性能结论。
3. **地址判据**：每 k-step 的两条 A 消息必须差 **+0x100（256 B = 128 half）**，
   四条 send 只用两套地址寄存器对。
4. **不期待静态指令大降**：父 892 条，预期 884 ± 16。**本卡不是删指令型收益**
   （对照 n09b 的 1684→892）；只看静态指令数会把它误判成 INDISTINCT。

## 7. 本卡的口径与边界（如实登记）

1. **父不是 handoff 基线**：链头 `accepted/n06b-f06-c64` 对这 16 行绑定的是已采纳的
   n09b 候选 `c42eca73`（两代之后的身份）。因此本卡的"父字节复现"目标是 `c42eca73`，
   重编译 n09b 的 `candidate.comp` 逐字节复现它（`BUILD.json:parent.byte_identical=true`）；
   handoff 基线 `59d3aa07` 只作为历史身份记录在 `BUILD.json:group.spv_sha256_handoff_baseline`。
2. **plan 的 `PASS` 值 ≠ ordinal**：被替换的 16 行 PASS 值是
   `{24,28,32,36,40,44,48,52,98,102,106,110,114,118,122,126}`，对应 ordinal
   `{61,65,…,89,135,…,163}`（`BUILD.json:plan.rows[].pass_label` + `name`）。合同 §8.2 口径：
   定位用 ordinal + name + SPV sha + 行号，不用 PASS 值当主键。
3. **plan 里 `shared=16384` 是簿记字段**，不分配 SLM（`clock_runner` 只解析 + `≤49152` 断言）；
   两侧 SPV 的 Workgroup 字节都是 0，本卡不改这个字段（改它属于第二变量）。
