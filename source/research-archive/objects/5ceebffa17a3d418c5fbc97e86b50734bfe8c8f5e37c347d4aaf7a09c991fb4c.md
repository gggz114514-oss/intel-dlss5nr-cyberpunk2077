# n39-f06-c256-slack · ANALYSIS（六问）

卡 id = `n39-f06-c256-slack`，组 = F06 C256（15 PASS）+ F18 C256（1 PASS，ordinal 168）。
父 = 链头 `accepted/n36-f05-arena-c64c128-20261027/plan.txt`（`af6c1287…`）上的
`881dff8c…`（F06，15 行）与 `9057283f…`（F18，1 行），两者都已**字节复现**（`build/repro.json`）。
候选：F06 `8f592cf9…`、F18 `47b20f2f…`、控制臂 `d7c82151…`（`build/candidate*.spv`，全部过 `spv_validate`）。

一句话：父把一个 32 KiB 的 `gT`/`gM` 瓦片整块拷进 SLM（`shT[16384]`）再让 8 个 SG 从 SLM 读 A 操作数；
**这份拷贝与源逐字节相同、源在本 shader 里只读**，所以候选把 A 操作数直接从全局瓦片读，
`Workgroup` 32768 B → **0 B**，值逐位不变。

---

## 1. 映射：生产者每个 (lane, component) 到底代表哪个 (token, channel)？

### 1.1 生产者（staging 拷贝）

```glsl
for (uint e = t_local; e < 16384u; e += 256u)
    shT[e] = gT[w * 16384u + e];      // t_local = gl_LocalInvocationID.x ∈ [0,256)
```

| 项 | 值 |
|---|---|
| 线程 `t` 拥有的 half 集合 | `{ t + 256i : i ∈ [0,64) }` = **第 t 列**（`token = i`，`channel = t`） |
| 每线程写量 | **64 half**（穷举：`producers.halves_per_thread = [64]`） |
| 写地址并集 | `[0, 16384)`，**恰好覆盖整个瓦片**（`write_is_partition_of_tile = true`） |
| 每地址写次数 | **1**（直方图 `{1: 16384}`） |
| 值 | `shT[e] = gT[w*16384 + e]`，**恒等**（无置换/缩放/转换） |

瓦片几何：一个 workgroup 负责 tile `w = wy*11 + wx`，瓦片 = `[64 token][256 channel]`，
`addr = token*256 + channel`（行距 256 half = 512 B）；`w*16384` 是瓦片基址。

### 1.2 消费者（DPAS 的 A 操作数）

```glsl
MAT_A a; coopMatLoad(a, <A_SRC>, <base>, 256u, LROW);   // MAT_A = fp16, Subgroup, 8(M) x 16(K)
```

| 项 | 值 |
|---|---|
| `m0` | `(sg/8u + 1u*j)*8u`；`sg = gl_SubgroupID ∈ [0,7]` ⇒ **`sg/8 == 0` ⇒ `m0 = 8j`**，**与 SG 无关** |
| `k0` | `16*ki`，`ki ∈ [0,16)` |
| 一个片段覆盖的 (token, channel) | `token ∈ [8j, 8j+8)`，`channel ∈ [16ki, 16ki+16)`，共 **128 个** |
| 片段数 | `8 j × 16 ki = 128`/SG，× 8 SG = **1024** |
| `(j,ki,row,col) → (token, channel)` | **双射到 64 × 256 = 16384**（`PROOF.json P1.1`，穷举，无重复、无遗漏） |
| 读地址并集 | `[0, 16384)`，**未读 half = 0**（`unread_halves = 0`） |
| 每地址读次数 | **8**（8 个 SG 各读一次；`read_multiplicity = {"8": 16384}`） |

**一一覆盖**：生产者把 16384 个 half 各写一次；消费者读同一批 16384 个 half 各 8 次。
两边是**同一个地址空间、同一个恒等映射**，所以父的读者与写者的 (token, channel) 完全对齐。

**候选怎么接上**：`<A_SRC>` 从 `shT` 换成 `gT`，基址加瓦片基址：

```
父： coopMatLoad(a, shT, m0*256 + k0, 256u, LROW)
候： coopMatLoad(a, gT,  w*16384u + m0*256u + k0, 256u, LROW)
```

瓦片内偏移（`m0*256 + k0 + row*256 + col`）**一个字都不变**（`PROOF.json P1.2`：逐元素
父地址 == 候选的瓦片内地址）。类型、stride(256)、layout(LROW)、形状(8×16) 全不变
⇒ lane/component 到 (token, channel) 的分配（由 ISA 决定）也必然相同，因为同一条
`OpCooperativeMatrixLoadKHR` 的参数只换了指针来源（`build/build.json`：
A 操作数指针在父解析到 `Workgroup`、在候选解析到 `StorageBuffer`，其余 4 个 load 站点不动）。

### 1.3 尾块

瓦片是**整块**：64 token × 256 channel = 16384 half，`16384 / 256 = 64` half/线程，
`8 j × 8 row = 64` token，`16 ki × 16 col = 256` channel ⇒ **没有尾块、没有边界判断**
（源码里本来也没有 `oob` 判断）。最后一个元素 `(token 63, channel 255)` 由片段
`(j=7, ki=15, row=7, col=15)` 读，父地址 = 候选瓦片内地址 = **16383**（`PROOF.json P6.*`）。

## 3. 重叠：独立工作原来怎么重叠、候选之后怎么变

### 3.1 父的 phase 顺序（debug=0）

```
[拷贝 64 轮：全 256 线程]  →  [barrier]  →  j=0..7{  A读 ×16ki + 权重 ×32 + DPAS ×32 }
     ↑ 串行序幕，任何 DPAS 都不能开始          ↑ 这一段才允许乱序/流水
```

### 3.2 依赖表（逐块、逐 acc、逐残差）

| 生产者 | 产物 | 最后消费者 | 覆盖/交接 | 关系 |
|---|---|---|---|---|
| 拷贝（全 WG） | `shT` 16384 half | j 循环里每个 A 读 | `barrier()` | **RAW**（跨 SG：写者是 1 个 lane，读者是 8 个 SG）→ 由那 1 道屏障关闭 |
| 拷贝的下一轮写 | — | — | — | **WAW / WAR = 无**（只有一轮拷贝） |
| `gY` seed 读（每 j 两块） | `acc0/acc1` 初值 | 该 j 的 2×16 DPAS | 无 | **RAW（同 SG 内）**，与拷贝**无**依赖 ⇒ 本来就可以和拷贝并行，但被屏障与程序序压住 |
| 权重 `b0/b1` 读 | 2 个 B 片段 | 该 ki 的 2 个 DPAS | 无 | 与 A 读**无**依赖，本来就能重叠 |
| `acc0/acc1` 两条累加链 | 2 个 8×16 fp32 | 该 j 末尾的窄化 + 存出 | 无 | 互相独立（A 片段共享、B 不同）⇒ 2 条独立链/片段 |
| 窄化 `MAT_H(acc)` | half 8×16 | `imgout`/`dbg` 存出 | 无 | 舍入点，本卡不动 |

### 3.3 候选之后的变化（这是本卡的第二个（小的）收益）

* 父的拷贝是**串行序幕**：32768 B 的全局读 + 32768 B 的 SLM 写 + 1 道屏障，
  **在这之前任何 DPAS 都不能开始**；A 读只能等屏障之后。
* 候选删掉序幕：每个 A 读只依赖全局瓦片（只读、无屏障），因此在展开的 j/ki 循环里
  **可以和权重读、seed 读、DPAS 自由交错**——也就是 A 读被提升到与权重/seed 同级的
  "可预取"状态，而不是被屏障挡在序幕之后。
* **没有新增任何依赖边**：候选的 A 读与父的 A 读读的是同一批字节（只是从全局而不是 SLM），
  与任何写者都没有 RAW/WAR/WAW（`build/lifetime.json.candidate.hazards.SLM_hazards.count = 0`）。
* **保护供料**：没有把任何消费者串起来；没有新增选择/复制/shuffle；K 序和 DPAS 顺序不变。

## 4. 新增成本：逐项入账

| 项 | 量 | 依据 | 备注 |
|---|---|---|---|
| A 读的**消息条数** | **不变**：1024 条/着色器（`d32x8t`） | `build/lifetime.json dynamic.a_messages`；父 ISA `load.slm.d32x8t` = 1024 | 8 个 SG 读同一片段这件事**父本来就有**，不是本卡引入 |
| A 读的**来源** | SLM → 全局（L1/L2） | `build/build.json cm_load_pointer_roots` | 同一条消息形状，换内存 |

| 新增同步 | **0**（反而 −1 道屏障） | `OpControlBarrier` 2 → 0 | |
| 有效 lane | **不变**（没有加分支、没有缩 lane） | 源码 diff | |
| WG 数 / grid | **不变**（11×6 与 11×7，共 1067 + 66 WG/帧） | 台账 header 字段逐行不变 | |
| 活值峰值 | SLM 活值 **32768 B → 0** | `build/lifetime.json` | 卡片禁止"抬活值"：本卡是**降**到 0 |
| 代码体积 | SPIR-V **860 → 832**（−28 指令） | `build/build.json` | native 指令数预期同步下降（拷贝循环消失） |

| scratch | 要求 **0** | 门 | 未验，见 O8 |

## 6. 整体是否更快：测什么、用哪个臂、怎么归因

* **整体量**：ordinary（`--pool --warm 1 --reps 30 --feedback`）的**帧均时**，6 组配平、
  每组 30 reps、两臂交替；主判据 = 6 组配对差的均值与 95% CI（不出 CI 内不下结论）。
* **臂**（`GPU-REQUEST.json`）：
  1. `base` = 链头 plan `af6c1287…`；
  2. `cand` = `plan.txt`（16 行：15 F06 + 1 F18，Workgroup 0 B）；
  3. `padback` = `plan-padback.txt`（同样 16 行，但 F06 的 15 行指向**只把 32768 B 声明加回去**、
     拷贝仍删掉的对照 SPV）。
  4. （可选，归因用）`f06only` = `plan-f06only.txt`（15 行，不含 F18）。
* **归因**：
  * `cand` 快于 `base`、且 `padback` 慢回去 ⇒ 收益主要来自**驻留台阶**（与 n36/L38 的
    pad-back 结论同构）；
  * `cand` 与 `padback` 同速、都快于 `base` ⇒ 收益来自**删掉拷贝**（那驻留就不是原因）；
  * `cand` 慢于 `base` ⇒ **B 类**（A 读搬去全局的副作用大于驻留收益），下一处改动见
    `RESUME.txt §5`（半 staging：只留 rows 32..63，16384 B、4 驻留、一半 A 读仍在 SLM）；
  * `cand` 与 `f06only` 的差 = F18 那一行的贡献（1 个 dispatch，预期很小）。
* **不要**把本卡的毫秒与 F05 的 `+0.116668` 直接相减或相加：不同批次、不同族。
  本卡只承诺"同批 6×30 的配对差"，并以 `padback` 为同批对照。
* 单批显著不算数：本组 15 个 PASS 合计约 0.56 ms 帧时间，若机制量级是 +0.1~0.3 ms
  应该在 CI 上可见，但仍按 L13 用第二批复现一次再采纳。
