## 0. 本卡改什么：一个 hunk，只改「谁在什么时候执行」

n10 已经把 A slice 做成双窗口：`smem[0,4096)` / `smem[4096,8192)` 交替，且窗口 base 由「每 slice 一次 `base = QKV_OFF - base`」递推。
本卡把这两个窗口从「一次一个」改成**生产者/消费者环**，循环次数 8 → 9：

```
父 (n10)  每个 kc slice i        : stage(w_i) → barrier → consume(w_i) → flip
本卡      迭代 i (i=0..8)        : [i>0] barrier → [i<8] stage(w_i) → [i>0] consume(w_{i-1}) → flip
```

于是同一条源码顺序变成：**下一次的 16 条全局读在本次 24 条 DPAS 之前发出**，而必须等这 16 条读完成的 barrier
落在 DPAS **之后**（父里它落在 DPAS 之前、紧贴 staging 的 SLM 写）。

环的两个索引赋值就是源码里唯一动 `abase`/`kc` 的两句，逐位求值（`PROOF.json` S1）：

| 迭代 i | 进入时 abase | stage 的 slice / 窗口 | consume 的 slice / 窗口 | consume 用的 kc |
|---|---|---|---|---|
| 0 | 4096 | 0 / **[4096,8192)** | — | — |
| 1 | 0 | 1 / [0,4096) | 0 / **[4096,8192)** | 0 |
| 2 | 4096 | 2 / [4096,8192) | 1 / [0,4096) | 64 |
| 3 | 0 | 3 / [0,4096) | 2 / [4096,8192) | 128 |
| 4 | 4096 | 4 / [4096,8192) | 3 / [0,4096) | 192 |
| 5 | 0 | 5 / [0,4096) | 4 / [4096,8192) | 256 |
| 6 | 4096 | 6 / [4096,8192) | 5 / [0,4096) | 320 |
| 7 | 0 | 7 / [0,4096) | 6 / [4096,8192) | 384 |
| 8 | 4096 | —（guard 关） | 7 / **[0,4096)** | 448 |

- 每个 slice 被 stage 的窗口 == 它被 consume 的窗口（逐 slice 断言，S1/M2）。
- consume 的 slice 顺序 = 0,1,…,7（K 累加顺序不变，R3）。
- **末 slice 仍是奇数 slice 7，仍落在 `[0,4096)`**，与 QKV handoff `[4096,10240)` 不重叠，
  所以 `STORE_QKV` 前仍不需要额外 barrier（L3）。这是 n10 选窗口奇偶的唯一理由，本卡原样保留。
- 每个 WG 执行的 barrier 仍是 **8**，模块内 `OpControlBarrier` 仍是 **4**（L4）。

三条 guard 是**WG 一致**的（`i` 是循环计数器，对 WG 内每个 invocation 相同），因此 `barrier()` 仍在 uniform control flow 中。

## 1. 映射：每个 (lane, component) 代表哪个 (token, channel)，消费者要求什么（Q1）

映射本身**不是**本卡改的对象（n10 已证），本卡只改「哪个窗口、哪一次迭代」；因此下面把两部分都列全，并把「环」加进映射。

### 1.1 生产者：每 slice 4096 个 half 由 256 线程写

```
lid ∈ [0,256)     q = lid>>6 ∈ [0,4)      c0 = lid&63 ∈ [0,64)
quadrant g ∈ {0,1,2,3} = (dy,dx) ∈ {(0,0),(1,0),(0,1),(1,1)}
   T_g = (ty+dy)*w4 + (tx+dx)      B_g = 16*T_g      v_g = 该象限合法（逐 WG 一致）
i' ∈ [0,4)        token t = B_g + q + 4*i'          channel c = kc + c0
全局 half         gy[ tiled(t, c, 512) ]            （v_g 假时取 0，且不产生读）
SLM 落点          smem[abase_i + qkv_a_offset(lid + 256*i' + 1024*g)]
                  ⇔ 行 r = 16*g + q + 4*i'，列 k = c0
```

**一一覆盖**：固定 g 时 (q,i') ∈ 4×4 ⇒ `q+4i'` 取遍 0..15；四个 g 的 token 基址相差 16/32/48 ⇒ 四组 16 token 互不相交。
故 `(token, channel)` 对 = 64 token × 64 channel = **4096** = 256 线程 × 16 次 STAGE，无重复写、无漏写。
`qkv_a_offset` 对 4096 个 (r,k) 是双射，地址集合恰为 0..4095（M1，4096 组穷举）。
窗口 base 只是纯平移（`+0` 或 `+4096`），不改变双射。

### 1.2 消费者：每 k-step 每 SG 两条 A 片段

```
SG sg ∈ [0,8)   p = sg/2 ∈ [0,4)   s = sg%2      mA = 16p   mB = mA+8   n0 = 48s
k-step j ∈ [0,4)  k = 16j
a0 = 行 16p..16p+7：smem[acons + ((mA/8)*4+j)*128]  COL8 片段，元素 (m+r', 16j+c') 位于 +c'*8+r'
a1 = 行 16p+8..16p+15：smem[acons + ((mB/8)*4+j)*128]
```

穷举 8 SG × 2 窗口 × 2 个 M8 块 × 4 个 k-block × 8×16 分量 = **16384** 个地址全部还原同一 (r,k)（M2）。
「两个 M 块共同消费」= 同一 SG 的 a0/a1 是**同一片 16 token** 的上下半，同一对 SG（p 与 s=0/1）读**完全相同的 16 token**，只在 N 方向分工（n0=0 / 48）。
所以一个 publish 覆盖该 slice 的全部读者（RAW 见 L1），这也是「一次发布 = 一个 barrier」的前提。
本卡的唯一差别是 `acons` 换成「另一个窗口的 base」（`QKV_OFF-abase`），平移量不变。

### 1.3 尾块

- channel 尾：无（K = 512 = 8×64，slice 恒 64 通道；consume 的 kc 序列 0,64,…,448 与父逐值相同）。
- token 尾：`v_g` 逐 WG 一致，零填充的取值/位置/数量都没变；非法 tile 的读地址上限 7360 half < 输入 589824 half（T2）。
- 迭代两端：i=0 没有 consume（guard 关）、i=8 没有 stage（guard 关）——**不是尾块处理，是环的进出**；
  stage 次数仍是 8、consume 次数仍是 8（B4 计数逐项相等）。

## 2. 删掉什么真实工作（只算正常执行路径）（Q2）

**本卡删除的指令/消息数 = 0。** 这是一个**纯重排**卡，逐项确认（防止把「没删」写成「删了」）：

| 项 | 父 | 候选 | 依据 |
|---|---|---|---|
| 全局 half 读（staging） | 16/线程/slice | 16/线程/slice | B4 计数相等（STAGE 16 次） |
| SLM half 写（staging） | 16/线程/slice | 16 | 同上 |
| A 片段读 | 2/k-step/SG | 2 | B4 |
| 权重读（UMG） | 3/k-step/SG | 3 | B4；每 k-step 每 SG 仍是 b0/b1/b2 三次，地址不同、总量不变 |
| DPAS | 6/k-step（24/slice） | 6 | B4；`OpCooperativeMatrixMulAddKHR` 38→38 |
| workgroup barrier（每 WG，QKV 相） | 8 | 8 | L4（模型 8 = 8；`OpControlBarrier` 4→4） |
| 其它同步消息（fence/signal） | 与 barrier 一一对应 | 同 | 静态 `OpControlBarrier` 4→4 |

**本卡真正改变的是依赖边，不是工作量**：父里「slice i 的 16 条 SLM 写全部完成」是「slice i 的 24 条 DPAS 开始」的**前驱**
（barrier 夹在两者之间）；候选里这条前驱被移到 **slice i 的 DPAS 之后**，于是
**同一 warp 的 DPAS 不再等其它 warp 的 staging 全球读返回**（跨 warp 的 rendezvous 被 DPAS 遮住）。
这是「把屏障从 store→DPAS 的关键路径上挪走」，不是「删了一条屏障」。

**已接受资产（三块 B）的源码身份（`PROOF.json` A1）**：3 条权重读 + 6 条 `acc*=coopMatMulAdd` 语句与父**逐字节相同**、
顺序相同、每个 B 片段仍恰好供 **2** 条 DPAS、每 k-step 每 SG 仍 3 次权重读。物理上是否仍是三个互不重叠的返回区，
是 native 问题（P1），本卡不声称已证。

必须如实说明的**不可删**边界（本卡没碰）：
- 每个 slice 仍必须有一个 publish barrier（RAW，L1）——删掉就错；
- 同一窗口两次使用之间仍必须有中间 slice 的 barrier（WAR/WAW，L2）——删掉就错；
- 末 slice 仍必须落在非 handoff 窗口（L3）——否则 `STORE_QKV` 前要再加 1 个 barrier。

## 7. 未决项与偏差（如实记录）

1. **P2 的字面形式（「kc 环体指令数下降或持平」）在本机制下不可达**：本卡不删任何工作，环体必然多出环的
   离入 guard（+27 own / 585 vs 558）。已改成可测的替代判据（P2 硬门：无新增内存/DPAS 消息 + scratch 0 + 增量全是整数控制），
   并在 `NATIVE-PREDICTION.md` 写明「≥ 40 条增量或任何新内存消息 ⇒ B」。这一条请主代理在裁定口径时确认。
2. 环体的 9 次迭代里 i=0/i=8 各有一条 guard 分支被跳过的 stage/consume 块：**动态总量与父相同**（8 stage + 8 consume），
   但**静态**环体更大；若 IGC 做循环剥离（peeling），静态 `send` 会变多（P4 直接否），这一点只能由 native 回答。
3. `scratch` 无法在 CPU 侧测量；本卡把它当**硬门**（>0 立刻回退），不靠「先测再看」。
4. 未改任何浮点语句（R1 逐条 87 个浮点站点 operand signature 全等、NC 85 个逐位配对），因此**不应出现 E 类**；
   若出现数值差，第一嫌疑是 REM 之外的东西（本卡没有），按合同先定位首差阶段。
