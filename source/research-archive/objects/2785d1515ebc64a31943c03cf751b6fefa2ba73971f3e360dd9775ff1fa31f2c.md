### 1.2 WO matrix multiply vs qX production — the classification, derived not assumed

For every one of the 80 sites the tool follows the B operand through glslang's materialised
cooperative-matrix variables (`OpVariable`/`OpStore`/`OpLoad`/`OpCooperativeMatrixLoadKHR`) and
reports the buffer, the address expression, the stride and the layout. The result is unanimous:

> **All 80 static FP16 sites are WO matrix multiplies: the B operand is an fp16 weight tile
> loaded from the pack buffer (binding 0) at the module's own WO base, with an f32
> accumulator. There is no static matrix multiply anywhere in the qX production path:
> 0 of 80.**

The qX production is real, but it is a *quantise + cooperative int8 store*, so it consumes no
MMA site at all. Per module:

## 2. Deliverable — the three width families' WO weight layouts

Derived from the modules' own `OpCooperativeMatrixLoadKHR` address expressions and strides
(`evidence/SITE-REGISTRY.json::modules.*.cm_loads`), not from documentation.

| | **C64** | **C128** | **C256** |
|---|---|---|---|
| K (context channels) / N (output channels) | 64 / 64 | 128 / 128 | 256 / 256 |
| B fragment (FP16) | 16×16 | 16×16 | 16×16 |
| FP16 tile base | `wo + (n0/16)*1024 + ki*256` | `wo + (n0/16)*2048 + (k0/16)*256` | `wo + n0*256 + k0` |
| FP16 stride / layout | 16 / ColumnMajor | 16 / ColumnMajor | 256 / ColumnMajor |
| FP16 element formula | `(n/16)*1024 + (k/16)*256 + (n%16)*16 + (k%16)` | `(n/16)*2048 + (k/16)*256 + (n%16)*16 + (k%16)` | `n*256 + k` |
| FP16 WO region | 4096 half = **8192 B** | 16384 half = **32768 B** | 65536 half = **131072 B** |
| `wo` (p4.x) in G3 | 0 for all 7 C64 blocks | per block | per block |
| per-channel weight scale source | offline `amax_k abs(W[n][k]) / 127` from the decoded FP16 WO (computed and shipped by this card) | same | same |
| per-channel residual scale source | `pack[p4.z + n]` (f16, stride-0 broadcast) — unchanged, already in the deployed pack | same | same |
| activation scale source | in-kernel per-workgroup amax (this card) | captured or producer contract (open) | producer contract (open) |

Two distinct FP16 layouts hide behind "WO": C64 and C128 use a **16×16 column-major tile grid**,
C256 uses **plain n-major with k contiguous**. The C128 family additionally has a *second*
deployed variant (`c128_d4_epi_only.comp`, plain `n*128+k`), which is **not** the module R07
runs — the 9 C128 PASS bind the `full` variant. Confusing the two would produce a silently
wrong pack, so the card records both and binds the one the plan actually uses.

### Relation to the existing FP16 pack: a re-tile, not a substitution

The INT8 target layout required by the measured I8B K32 adapter is the same in all three
families:

```
int8 index(n,k) = (n/16)*(K/32)*512 + (k/32)*512 + (n%16)*32 + (k%32)
B fragment 32(K) x 16(N), column-major, stride 32  ->  element (k,n) at base + n*32 + k
```

* **C64** (K=64): 4 n-groups × 2 k32-tiles × 512 = 4096 B. The n-group stride 1024 is
  *identical* to the FP16 layout, but the four k16 sub-tiles of 256 merge into two k32 tiles of
  512, i.e. rows interleave: `(n%16)*16 + (k%16)` becomes `(n%16)*32 + (k%32)`.
* **C128** (K=128): 8 n-groups × 4 k32-tiles × 512 = 16384 B; the same merge of eight k16
  sub-tiles into four k32 tiles.
* **C256** (K=256): 16 n-groups × 8 k32-tiles × 512 = 65536 B; here the FP16 layout is
  **n-major**, so the re-tile is total — every element moves.

Therefore: **no whole-pack replacement is possible, and not even a whole-WO-region copy.**
Three independent reasons, each checkable in the frozen data:

1. the FP16 WO lives inside a shared pack together with `WE`/`WM`/`WC`/`WQ`, the residual scales
   and the per-block factors (C64 pack 107024 B, WO region = the first 8192 B), so the pack
   cannot be swapped wholesale without invalidating every other reader in the same PASS;
2. the tiling differs (k16 → k32), so C64/C128 need a row interleave and C256 needs a full
   re-tile;
3. the C128 family's two variants prove the point empirically: the same 128×128 weights appear
   in two different deployed layouts.

The card's choice is therefore a **new 4096 B buffer + a new 256 B f32 scale table per switched
block** (bindings 8 and 9), leaving the FP16 pack byte-untouched — which also keeps A1's D034
finding (no `gM` reader) and every other reader of the same pack valid.

## 3. Deliverable — the residual contract

### 3.1 What the parent does (read off the SPIR-V, not the source comments)

Per output element, the parent is:

```
seed  = H( y_half[o,t] * ars[o] )          // half multiply, stride-0 per-channel broadcast
C     = widen_exact(seed)                  // f32 accumulator initial value
C     = MMA(a_k16, b_k16, C)  x4           // 64 FP32 products, K in four K16 steps
out   = narrow(C)                          // ONE f32->f16 conversion, then store
```

`evidence/SPV-IDENTITY-C64.json::P3_matrix_sites.parent_sites` shows the C operand of every
parent site is `OpFConvert`, and the full chain
`OpFConvert(OpFMul(load gY stride 64, load pack[ars+n0] stride 0))` is recorded per site.

### 3.2 What the INT8 arm must satisfy, and does

```
seed[o,t]      = float( H(y_half[o,t] * ars[o]) )   // unchanged: same multiply, same exact widen
acc[o,t]       = sum_c qWo[o,c] * qC[c,t]           // int32, exact, all K products
out_half[o,t]  = half( float(acc[o,t]) * (sC * sWo[o]) + seed[o,t] )
```

* **one** dequant multiply, **one** FP32 add, **one** narrow — the same shape as R02's
  `nr_i8_deq_add` contract, with the output residual in the seed slot;
* the residual value is **not** rescaled, re-quantised, approximated or dropped: the four `gY`
  loads and the two `pack[ars+n]` loads are **identical** to the parent in buffer, address
  expression, stride, layout and component type
  (`P2_operand_streams.residual_loads_identical: true`, `store_stream_identical: true`);
* the seed value is *not modified*; only its position in the expression changed (it is added
  once after the exact integer sum instead of seeding the FP32 accumulator). An INT32
  accumulator cannot carry an FP32 seed — that is the GUIDE's R02 blocker, and the reference
  above is the answer to it;
* the two roundings are protected: the candidate carries **18 `NoContraction` decorations and
  the parent 0** (12 `OpFMul`, 4 `OpFAdd`, 2 `OpFDiv`), so `acc*fsc` cannot be contracted into
  an FMA with `+seed`; the epilogue is the two-step evaluation written above;
* exactness: the integer sum is exact — the oracle checks int32 == int64 accumulation for every
  element of a real frame (`B_int8_exactness.int32_equals_int64: true`, max |acc| 98609, far
  below 2^24), so the *only* deviation from the FP16 arm is the A/B quantisation;
* accumulation order: the parent adds the seed first and then 64 FP32 products in four K16
  steps; the INT8 arm sums all 64 integer products exactly and adds the seed once. Because the
  integer sum is exact, this is not a reordering error.

### 3.3 Where the qX form differs (and why it is not R07 C64's problem)

Two of the three qX producers quantise **a different value** than any half reader sees:

* `C-producer.spv` (blocks 9,10) quantises the **unrounded FP32 accumulator** and writes no half
  at all — self-consistent, but it means those two PASS have **no half output**, so no half
  reader downstream of blocks 9/10 may be assumed;
* `c256_output_qx_int8_v5.spv` writes both a half `imgout` value and an int8 qX; the v5
  `C256_QX_HALF_MODE=1` fix exists precisely because quantising the unrounded accumulator
  disagreed with the written half by ±1 code on 1693/4032 tokens (the source's own comment).

For the C64 arm there is **no qX at all** (the half image value is final and its reader is
unchanged), so the single-narrow contract above is the whole story. Any future C64 qX must be
quantised **from the half value**, i.e. `code = roundEven(float(half_of(epilogue)) * invX)`,
never from the f32 accumulator.

## 7. Closure item 6 — unresolved blockers, named

1. **C128 arm (11 PASS, 22 static FP16 MMA) — not implemented.** Two module flavours need two
   epilogues: the half-output form (9 PASS) can follow the C64 recipe directly; the int8-qX-only
   form (blocks 9,10) must first settle its qX contract, because today it quantises the
   **unrounded f32 accumulator** and has no half output at all (§3.3). Next step: decide
   "quantise from the half" for that module (a new SPV identity and an arm of its own), then
   build the 16384 B pack. The shared-memory budget is fine (128×64 int8 staging = 8 KiB).
2. **C256 arm (15 PASS, 30 static FP16 MMA) — not implemented, and it has a real arithmetic
   obstacle.** The module already declares `shT[16384]` = 32768 B; an int8 K32 staging tile for
   64 tokens × 256 channels needs 16384 B, which lands on **exactly 49152 B** — the
   per-workgroup shared-memory ceiling the plan lint enforces. Options: reuse part of `shT` (half
   and int8 views of the same slice), stage only the K64 slice a fragment consumes, or move the
   context handover to the producer. Not decided here; recorded as the named blocker rather than
   a silent risk.
3. **block21 and block55 must be wired separately downstream.** Their module is
   `c256_output_qx_last_int8_v5.spv`, compiled with `C256_QX_LAST=1`: it has **no binding 8 and
   no qX store**, and its only output is the half `imgout`. Whatever consumes those two PASS as
   int8 qX does not exist today and cannot be assumed — the GUIDE's R07 note is confirmed against
   the SPIR-V (0 int8 stores in that module, 1 in the `v5` module). In addition blocks 9 and 10
   currently write **only** int8 (`imgout` is `int8_t`), so no half reader can be inserted
   downstream of them without changing that module.
4. **Six of the seven C64 PASS have no captured context tile**, so their INT8 reference is
   defined but unmeasured; only block6 has the A/B/C statistics in §4.6. The kernel needs no
   capture to run (the scale is computed in-kernel), which is why all 7 could be switched — but
   "switched" is not "measured".
5. **No GPU slot**: `GATE`, `ORDINARY`, `QUALITY` and `NATIVE` are all un-run. The 11 job
   definitions (5 gate + 6 ordinary) are in `run/r07-output-proj/jobs.json` as `LISTED_NOT_RUN`,
   with the self-determinism rule for the gate arm (byte equality only between two runs of the
   same candidate plan) and no invented parent-vs-candidate tolerance.
6. **Micro-residuals, reported not hidden:** one `OpBitcast` disappears in the inlined
   image-address code (P5); the `NoContraction` count (18) exceeds the net new `OpFMul` count (9)
   because glslang also marks shared subexpressions of the same `precise` statement. Both are
   numerically inert by the P2 store-stream identity, and neither is explained at compiler level.
