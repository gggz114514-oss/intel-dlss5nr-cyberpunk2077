## 3. 头数、scale 边界与 buffer 容量

### 3.1 C128 的头几何（独立核对，不沿用旧审计的 16×64 描述）

**4 头 × 每头 32 维 = 128 通道，每窗口 64 token。** 五条独立证据（`evidence/SCALE-BOUNDARY.json`）：

1. 12 个 PASS 的 grid z 都是 4（G3 与 ledger 一致），`h = gl_WorkGroupID.z` 只当头索引；
2. QKV 权重偏移是 `(96*h + {0,16,…,80})/16`，即每头 96 个输出通道（6 个 16 片），4 头 = 384；
3. `gT` 地址是 `(w*64+query)*128 + 32*h + dim` 且 `dim < 32`，故 4×32 = 128 通道；
4. `qkv` 共享 slab 是 3 × 64 × 32 half（+0/+2048/+4096），每头 32 维 × 64 token；
5. `auxf[p5.x + h]` 每头一个标量，h < 4。

### 3.2 per-head scale 来源与"不跨头复用"

| scale | 位置 | 资源/offset | 父里是否已存在 | 跨头复用 |
|---|---|---|---|---|
| Q 头标量 | `auxf[pc.p5.x + h]` | `swin_<N>_aux`（binding 1），p5.x = 16384 float = 65536 B，h<4 | 是 | **无**：索引含 h |
| softmax bias | `auxf[pc.p4.w + h*4096 + qg*64 + kb]` | 同 aux，p4.w = 0 | 是 | **无**：h*4096 步长 |
| Q/K norm | `shNorm[t]` / `shNorm[64+t]` | shared，按 token | 是 | 不适用（按 token） |
| **V absmax（新）** | `shVMax`，每 workgroup 一个 | shared，workgroup 局部 | 否 | **不可能**：一个 WG = 一头，且从不写全局 |
| **P per-query（新）** | `pmx`/`pScale`/`pInv`，lane 局部 | 寄存器 | 否 | **不可能**：只由本 lane 自己 query 列的 P 推出并在同 lane 消费 |

没有新增全局 buffer、没有新增描述符、没有跨 workgroup 通信；`shVMax` 只由本 WG 的
`atomicMax` 写、只由本 WG 在自己 barrier 后读。

### 3.3 QKV 权重区域与 PUSH（逐 PASS 核对）

PUSH 32 字解出 `pc.p0..p7`（`evidence/ENTRY-MAP.json` 的 `push_decode`）。本模块只读三个字：
`p3.w`（wq_half）、`p4.w`（bias_float）、`p5.x`（scalar_float）。

- `p4.w = 0`、`p5.x = 16384` 在 12 个 PASS 上**完全一致**。
- **`p3.w` 不一致**：11 个 PASS 是 `131328`，**block14 是 `131200`**（低 128 half = 256 B）。
  逐 PASS 核对权重区 `[wq*2, wq*2+98304)` 与最远 half 索引都在 pack 声明容量 361488 B 之内
  （`qkv_weight_region_fit` 全部 `fits=true`，最坏 360960 B ≤ 361488 B）。
  这正是 GUIDE 要求"独立核对 QKV 权重区域"的原因：**任何这一段（QKV）的 int8 权重包必须按每个
  block 自己的基址生成**，不能用一个 offset 套 12 个 PASS。
- `p0.z/p0.w` 是 shift 标志（0 或 -1，四种组合），`p1.x/p1.y` 是 grid，按设计本就不同。

## 4. 本臂 INT8 参考状态

- 局部 oracle：`evidence/ORACLE-PV.json`，由**本卡**在 CPU 上用与 shader 相同的公式生成
  （一个 owner SG：64 key × 32 维 × 16 query，`numpy default_rng(20261024)`；
  `exp_h` 按父的 bit 构造、概率树按父的 `t_j/part/even/odd` 逐项、量化 `roundEven`+clamp）。
  **非零**：P 的 int8 码 1021/1024 非零，V 的 int8 码 2026/2048 非零。
- int32 累加最大 38602，距 2^31 还有 2147445045；解析最坏界 64·127·127 = 1032256，也不会溢出。
- 与父 FP32 路径（半操作数、FP32 累加）比较：绝对误差 max 0.00489 / mean 0.00067；
  RMS 0.000886 vs 参考 RMS 0.07475 = **1.18%**；全部落在解析界内
  （`within_analytic_bound=true`，界 = (sV/2)·Σ|P| + (sP/2)·Σ|V|）。
- **没有过**任何设备侧门：这是本臂参考，未在 GPU 上验证；`GATE` 未跑。缺的就是 GPU 时段。

概率如何重新量化 / scale 归属 / 是否保持原 P 寄存器交接（`evidence/PV-INT8-SCHEME.json`）：

- **P 的输入与父逐字节相同**：`P := half(P*ivq)`，树、倒数、单次 half 舍入都没动。
  量化输入正是 FP16 消费者会拿到的那个 half 值。
- **P 的 scale 归 per-query（输出列）**：`pmx` = 该 query 在 64 个 key 上的最大 P；一个 lane 拥有
  每个 8-key 块的 4 行、其伙伴 lane（`lane^16`）拥有另 4 行，所以**一次
  `subgroupShuffleXor(pmx,16)`** 就闭合该列。`sP = pmx/127`，量化倒数 `127/pmx`，全在 lane 内，
  不进 shared、不做广播。
- **量化只做一次**：每个 P 元素一次 `roundEven` + clamp[-127,127]（`i8code`，与实测 adapter
  同一 helper），一个 8-key 块的 4 个元素打包成 32-bit 码字的 byte 0..3；`i8_join_B` 只做
  byte 路由，**不重新量化**（`evidence/ABI-MAP.json` 的 `routing_closure`：32 lane × 16 component
  = 512 对全部闭合，`violations = 0`；closed form 与实测 `I8-ABI-MEASURED.json` 逐条相同，
  CH/A/B 三张表各 0 处不符）。
- **退化保护**：`pmx==0` 时量化倒数与 dequant 都取 0，避免 `0*inf`。
- **不会饱和**：`P ≤ 1` 恒成立（`P = exp·inv`，`inv = 1/max(Σexp, 2^-14)`，故
  `max P ≤ Σexp/max(Σexp,2^-14) ≤ 1`），所以 `pmx·(127/pmx) = 127` 永远不越界。
- **两片 K16 → K32 INT8 B**：父的 4 个 K16 站点（j=0..3）变成 2 个 K32 站点；
  slice 0 = key 0..31 =（p00,p01,p10,p11），slice 1 = key 32..63 =（p20,p21,p30,p31）。
  两片共用同一个 sP，所以 INT32 累加仍是同一个数学量。
- **P 寄存器交接保持**：P 从不落地。代价从父的 96 次 group shuffle/owner（4 个 B × 8 组件 ×(1+2)）
  降到 32 次（2 个 B × 16 组件 × 1），因为 int8 侧取的是码字里的 byte，不需要 `nrh_unpack2` 的
  up/down 交换。
- **V 的 scale 归 per-workgroup（= per head per window）**：`shVMax` 在现有 norm pass 里由 64 个
  owner 线程各读 32 通道做 `atomicMax`，被**现有**的 norm 后 barrier 发布；量化本身在**现有**的
  scale pass 里做 stride-1 拷贝（`sv8[k]` 与 `qkv[4096+k]` 是同一个 `ch*64+tok` 索引），被
  **现有**的 scale 后 barrier 发布。**barrier 数 4 → 4，没有新增**（SPV 里 `OpControlBarrier`
  父子都是 4）。

## 7. 未解决阻碍（具名）

- **GAP 0：232 FP16 父 plan 分叉。** 232 plan 的这 12 个 PASS dispatch 的是 u09 重建
  `1b8ef2ed…`（49800 B，shared 12288，源 18982 B，norm 走 `nr_norm_qk_pair`），不是 G3/ledger 的
  `6e48e108…`。本卡候选由审计所指模块派生，因此**能直接换进 G3，不能直接换进 232**。下一步：
  把同样 19 个 hunk（C1–C19）机械移植到 u09 源，重做 u09 的逐字节父复现与 SPV 差分。
- **GAP 1：QKV 的 INT8 权重包没有已验证身份（本段最大缺口，72/276 处）。** 需要
  `N/32 × K/32 × 32×32` int8 tile + per-channel scale 的离线 pack；且 `p3.w` 在 12 个 PASS 上
  不一致（block14 低 256 B），**必须逐 block 按自己的基址生成**。同时要处理 3.4 的入口适配：
  五个具名 Y 生产者（三个 m8col 变体 + 两个 token-major）里，m8col 那三个必须先核对/改成
  消费者要的 token-major 64×128，且要在生产者处直接写目标布局。本卡未做。
- **GAP 2：QK 需要 shared 里的 int8 Q/K + per-head scale（12/276 处）。** A 若是 shared 的 int8，
  直接按 stride 32 LROW 载入即可（int8 A 映射正好是"每 lane 一个 K 列"），B 同理 LCOL stride 32；
  但 score 的 dequant（`sK·sQ`）要插在 bias 与 `c128_exp_h` 之间，且 debug 的 logits 回显地址
  会变成"dequant 后的值"——需要单独定一版 debug 语义。本卡未做。
- **GAP 3：没有 GPU 时段。** gate（fixed/fb2）、per-pass T capture、ordinary 3×30、画质都未跑；
  `run/r05-c128-attn/jobs.json` 只列不跑，per-pass capture 还需要给 12 个 PASS 加 resident OUTPUT。
- **GAP 4：int8 合作矩阵从 shared 载入的 native 合法性未证。** `shared int8_t sv8[2048]` 的基址
  对齐（本卡的 A 基址都是 32 的倍数）与 `coopMatLoad` 的 LDS 访问宽度只有在设备上才能确认；
  本卡只有 `spv_validate_cpu result=0`。若驱动要求更严的对齐，可把 `sv8` 声明成 `uint[512]`
  再以 `int8_t` 视图载入（未实施，先记为备选）。
- **GAP 5：per-query 单 scale 的数值代价。** 局部误差 RMS 1.18%（本卡 oracle，非门）。若 gate
  判定不可接受，可选的**同一 ABI 内**改进是把 V 的 scale 从 per-head 细到 per-dim（需要 32 个
  float 的 shared 发布，多一次 barrier），或对 P 用更细的片内一致尺度（数学上要求两片共用一个
  sP，因此只能 per-query，不能 per-片）。这些都没有实施。
- **GAP 6：ctx debug 回显的语义变了。** `dbg[212992+…]`（T 的 debug 通道）现在写的是
  dequant 后的值（数学上同一个量，数值上是 INT8 路径的值），P 的 debug 通道
  （`dbg[196608+…]`）仍与父**逐字节相同**（P 的 half 值没动）。若诊断要与旧 FP16 值逐字节比，
  必须分清这两条通道。
