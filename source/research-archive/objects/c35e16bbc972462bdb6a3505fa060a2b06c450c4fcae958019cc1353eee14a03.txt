## 3. 身份判定（为什么这个“当前身份”可信）
1. pipeline→PASS 映射不是猜的：runner 的 pipeline 去重 key 是
   `spv + npush + subgroup + bindings[]`，按首次出现顺序编号
   （`phase-diagnosis-20261025/direct-clock/clock_runner.cpp:90` 的 plan 语法、`:354` 的 key）。
   用当前基线 plan 重算该向量，与驱动 `pass_pipeline_indices`
   （`c32-rest-20261026/root-body/run/resources-root-body/pipeline-statistics.json`）**逐元素一致**。
2. 指纹 = 基线捕获里每个 pipeline 的 ISA 文件名内嵌 64-bit kernel hash（ISA 尾部常量也内嵌同一值）。
3. 身份 = kernel hash 命中指纹 ⇒ 同一编译产物。SPV sha 只作旁证：SPV 相同 + subgroup 相同
   ⇒ 同一代码；但**部分捕获**的 pipeline index 不可信，不能拿来归属 PASS。
4. 自检：(a) “结构完整且 plan SPV 与基线同 sha”的捕获里，kernel hash 与指纹不一致的记录 = 0 条；
   (b) 抽查 4248 条 ISA 的文件名 hash 与文件内嵌 hash，不一致 = 0 条；
   (c) 同卡驱动统计若与静态指令行差 >16 视为“来自候选臂”而剔除（保留 3918 / 剔除 101）。

## 4. 已知限制 / 未决项（都不影响上面 0 缺失的结论）
- **部分捕获（1–6 个 ISA 的会话）**：文件名里的 pipeline index 在该会话内从 0 重新编号，
  不能当 plan pipeline。索引里 `mapping.index_mapping_trusted=false`，这类记录只按 hash 判身份。
  同一现象的一个实例：3 个 f20-tail-diagnosis 会话 + 3 个 f05-kv-ready-split 会话里，pass 0 的
  同一 SPV sha 对应三个不同二进制（791 KB / 521 KB / 517 KB，send.ugm 与 send.slm 结构不同）。
  已定位为“会话内 index 0 ≠ plan pipeline 0”这一类，不是“同一 SPV 会编译出不同代码”；但这些
  会话不能作为 pass 0 的证据，索引已按指纹把它们记为 HISTORICAL。
- **plan sha 的来源**：优先用 job manifest 记录的 sha（243 个会话）；manifest 没记 sha 的用扫描时
  重算（43 个）并标 `sha_source`。`plan_stale`（记录 sha ≠ 现文件 sha）本快照 = 0 个。
- **驱动统计口径**：`Instruction Count` 是驱动口径，`isa_scan.instruction_lines` 是文本口径，
  两者差 3 左右；表里混排时已在 `driver_stats.source` / `driver_stats=null` 区分。
- **快照性**：扫描期间 queue/n05a、n08、n09 等卡在写新捕获（会话数从 401 涨到 405），
  任何后续结论请以 `build_index.py` 重跑为准（约 5 分钟，纯磁盘）。
- 未做（也不该在本卡做）：没有运行 gtpin/clock_runner/port_zprof，没有取 GPU 锁，没有重采。
