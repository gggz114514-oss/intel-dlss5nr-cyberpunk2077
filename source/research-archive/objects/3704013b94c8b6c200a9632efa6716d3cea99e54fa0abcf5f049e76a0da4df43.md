# n23-f05-shape / ANALYSIS — the six questions

Card: F05 C128 attention (`block9_swin_body_3` identity, SPV `20f4074f...`), 12 PASS
(19,22,25,28,31,34,195,198,201,204,207,210). Parent = chain head `restore-n10-f10-next`
(`719f100b...`). One workgroup: `local_size_x = 256`, 8 subgroups of 32, grid `21 x 12 x 2`,
shared 24576 B.

Status of the card's B1 in one line: **the shape exists (A = PASS); the weight-pack half is
built and proved; the V accumulator is merged in the shipped candidate (B1-V, 96 -> 80 weight-load
messages, numerically identical); the Q/K merges wait on the 8x32 accumulator lane map, which the
shipped one-dispatch probe measures.** Element access cannot replace that map in this toolchain
(P5: `c[3][5]` is rejected), so the Q/K half is blocked on the measurement, not on coding.

## Q1. Mapping: which (token, channel) does each lane/component really represent?

### 1.1 the parent's two owners inside one workgroup

```
h  = gid.z*2 + sg/4              head (2 heads per WG, 4 heads over gid.z = 0..1)
q  = sg%4                        query-block owner
projection:  per phase p in {0,1}:  tokens  m0 = 8q + 32p .. +7   x   channels 0..95 of head h
score / PV:  queries 16q .. 16q+15  x  keys 0..63  (all of them)
```

so one SG writes `2 phases x 8 tokens x 96 channels = 1536` halves, and the eight SGs of a
workgroup write the whole `12288`-half `qkv[]` exactly once:

| enumeration | value | file |
|---|---|---|
| (head, token, channel) cells per WG | 2 x 64 x 96 = **12288** | `build/writeset.json` |
| owning fragment (sg block, phase, 16-channel block) | **96** = 8 SG x 2 phases x 6 blocks | `build/writeset.json` |
| cells per fragment | exactly **128** = 8 tokens x 16 channels | `build/writeset.json` |
| published halves in `qkv[]` | **12288** = 2 x 6144, bijective, no collision | `build/writeset.json` |

Published address law (parent, all in halves, `base = h*6144`):

| region | law | consumer |
|---|---|---|
| Q `0..2047` | `base + t*32 + dim`, dim 0..31 | score B operand `LCOL, stride 32` -> element (k=dim, n=query) |
| K `2048..4095` | `base + 2048 + (t/8)*256 + dim*8 + (t%8)` | score A operand `LCOL, stride 8` -> element (m=key, k=dim) |
| V `4096..6143` | `base + 4096 + t*32 + dim` | PV A operand `LCOL, stride 32` -> element (m=dim, k=key) |

Every consumer read is the exact inverse of the writer's law (checked cell by cell in
`build/writeset.json` `published_bijective = true`), so **one owner per cell, no duplicate write,
no missed read**.

Tail blocks: there are none. 64 tokens = 4 SGs x 2 phases x 8; 96 channels = 6 x 16; 32 dims =
2 x 16; 64 keys = 8 key blocks x 8. The only "edge" behaviour is the window/image OOB test, which
happens in `c128_img_half_index()` in the *producer* pass and is untouched.

### 1.2 what the merged shape would have to preserve

Merging `Q0+Q1` (and `V0+V1`, `K0+K1`) keeps the *same* 12288 cells and the *same* published
addresses — the merged 8x32 store is byte-identical to the two 8x16 stores it replaces, because
the parent's own layout is 32 channels wide inside one token row (Q/V) or contiguous across the
two 16-dim halves (K):

| merged store | replaces | byte identity |
|---|---|---|
| `coopMatStore(q,  base+m0*32, 32, LROW)` 8x32 | `q0 @ +0`, `q1 @ +16` | element (r,c) -> `+r*32+c`, c=0..31 = the union |
| `coopMatStore(k,  base+2048+(m0/8*2)*128, 8, LCOL)` 8x32 | `k0 @ +0`, `k1 @ +128` | element (r,c) -> `+c*8+r`, c=0..31 = the union |
| `coopMatStore(v,  base+4096+m0*32, 32, LROW)` 8x32 | narrowed `V0`, `V1` | same as Q |
| debug `dbg` 8x32 @ stride 128 | two 8x16 @ +0/+16 | same union, same debug bytes |

That is the whole of proof 1: the write set is *identical*, not merely equivalent.

## Q2. What real work would actually be deleted (and what the ISA says about it)

Counted on the parent's own ISA capture
(`queue/n04b-f05-c128-feed/native/captures/native-native-base/ISA/CS_asmf98d5ab4e239dd54_simd32_*`):

| item | parent | merged | how sure |
|---|---|---|---|
| static DPAS | 128 (`dpas.8x8 (16|M0)`) | 128 (same 96 projection + 16 score + 16 PV; the projection's 48 per phase become 24 wider ones **only if** IGC uses one wider dpas, else unchanged) | measured parent, predicted candidate |
| QKV weight loads `load.ugm.d32x8.bss[a0.2]` | **96** (6 per ki x 8 ki x 2 phases) | **48** with the full N-merge, **80** with the shipped B1-V (V pair only: 2 -> 1 per ki) | arithmetic on the parent's addressing; B1-V is built, the Q/K half is blocked (PROOF.json proof2) |
| shared publish sends `store.slm.d32x8t` | **68** = 32 + 2 (`d32x4`) per phase | **source sites 6 -> 3 per phase**, but message count is *not* expected to drop: the ISA shows these are 1-lane scalar-addressed 8-dword stores (`send.slm (1|M0) ... r3 r32:1 ... store.slm.d32x8t.a32`, addresses `+0,+64,...,+448`), i.e. the cost is the per-lane scatter of the accumulator map, not the matrix width | measured parent; candidate = prediction, see NATIVE-PREDICTION.md |
| A fragment loads | 16 (`load.ugm.d32x8t`) | 16 (shared by all six accumulators in the parent, all three in the merged) | unchanged by construction |
| `f32 -> f16` narrowings (`MC->MH`) | 6 per phase | 3 per phase | arithmetic |
| barriers | 1 | 1 (unchanged; the publication boundary is untouched) | by construction |
| shuffles (norm tree, `nrh_join_rows_to_B`) | unchanged | unchanged | the merge does not touch them |

So the honest deletion is **48 weight-load messages per workgroup** plus 16 f32->f16 conversion
sequences, *not* the "30~45 publish sends per phase" that `n04b` hoped for: the publish sends are
already at the floor set by the accumulator's lane scatter. This is the one number in the n04b
route that the ISA contradicts, and it is why the card's cost ledger separates "source sites
deleted" from "messages deleted".

## Q3. Overlap: who produces, who consumes, what hazard

Blocks in the parent's program order (per workgroup):

| # | block | producer | first consumer | last consumer | overlapping independent work | hazard |
|---|---|---|---|---|---|---|
| A | QKV projection, tokens 8q+0..7 (phase 0) | SG (q,h) | norm pair (same SG) | publish to `qkv` | phase 1 (tokens 8q+32..39) is independent of phase 0 except the shared A rows? no: different tokens, same weights | **WAW** on `qkv` between the two heads' slices: disjoint addresses, so WAR only against the barrier |
| A' | QKV projection, phase 1 | SG (q,h) | idem | idem | independent of phase 0 | same |
| B | `barrier()` | all | all | all | — | **RAW** (publish -> score/PV read) |
| C | score `S^T = K.Q^T`, 8 key blocks x 2 ki | SG (q,h) reads all K, own Q | den tree | PV B join | the eight score blocks are independent; `nrh_join_rows_to_B` shuffles overlap the next block's loads | **RAW** vs barrier (Q,K), **WAR** inside the subgroup when p00/p01 are overwritten by the scaled values (`p00[0] = float16(p00[0]*ivq)`) |
| D | sealed den tree + reciprocal + scale | SG (q,h) | the eight p fragments | PV | independent per query block | **RAW** on all eight p fragments (needs all of them), **WAR** when they are re-written in place |
| E | PV `(feature, query) = V^T . P^T`, 4 accs | SG (q,h) | `gT` store | — | 4 accumulator groups independent | **RAW** vs barrier (V), **WAR** on the scratch A register reused 16 times |
| F | narrow + `gT` store + debug | SG (q,h) | next pass (UGM) | — | debug stores are dead at runtime | **WAW/RAW** across passes only |

The merged design changes nothing in this table: same producers, same consumers, same barrier,
same hazards. It only makes block A produce 3 wider fragments instead of 6 narrow ones. This is
the point the card has to protect: *the merge must not serialise C/D/E* — and it does not, because
the three accumulators are still independent columns of the same instruction.

## Q5. Would it land in native? (prediction + falsifier; no GPU here)

Observables, all counts are static per kernel unless noted:

1. `send.ugm ... load.ugm.d32x8.a32.bss[a0.2]` (the QKV B loads): **96 -> 48**, and the surviving
   messages should carry twice the payload per lane (a `d32x16`-class message or two `d32x8` with
   a stride-2 lane pattern). *If the count stays 96, the merge did not form and the card is
   triage A (implementation not landed).*
2. `dpas` count: **128 -> 128** (counted per instruction, not per element). The projection's
   `dpas.8x8 (16|M0)` groups should become either `dpas.8x8 (32|M0)` (one per ki+accumulator) or
   stay two `(16|M0)` with adjacent destinations. Either is acceptable; the *shape* of the dst
   group is the direct read-out of Lemma 2.
3. accumulator footprint: distinct `dst` GRF of the projection MMAs = **48 (NESTED) or 24
   (LANE-COL)**; `max_r` must stay **127** and `scratch` **1024** (the n05e/n21 boundary).
4. shared publish: `store.slm.d32x8t` **68 -> 68 expected** (34 per phase). A drop to <= 40 would
   be a bonus; a rise above 68 falsifies the "wider store is not more expensive" assumption.
5. `first_dpas` should stay **2560** (the probe/debug prologue is untouched); `sync_allwr`
   **11**; `end of thread` 1.

Falsifier for the whole card: if (1) does not move while (3) does, the merge landed in the
accumulator but not in the weight feed — worth one report, not a resubmission.

## Q6. Would the pass be faster? (what to measure, how to attribute)

* This card cannot measure. The units to measure are the same as `n04b`/`n05e`: `ordinary`
  (`--pool --warm 1 --reps 30 --feedback`, 6 paired process groups, two-sided t on df=P-1) on the
  **12-pass group only**, plus `gates/fixed` + `gates/fb2` frame golds, plus one `native` capture
  of the candidate for the five counts above.
* Attribution ceiling: the group is 12 of 232 passes and the whole-net frame is ~18-19 ms, so a
  -50-instruction change inside ~4800-instruction passes cannot resolve much above noise on its
  own. The *value* of this card is (a) the probe's map answer, which unlocks a shape family, and
  (b) the message arithmetic (96 -> 48) which is the first real reduction in the F05 C128 weight
  feed since `n04b` closed the A side.
* Order of operations that keeps attribution clean: probe (`A.3`) -> if NESTED/LANE-COL, rebuild
  B1 with the norm re-derived for that law -> gates -> native -> ordinary. Do **not** run ordinary
  on a candidate whose map is unknown; a numeric tie would be indistinguishable from a no-op.
