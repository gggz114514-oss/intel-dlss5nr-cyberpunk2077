## 1. 全网第一结论：232 个派发里没有「只做布局搬运」的 PASS

**0 / 232。** 判据是可证伪的：一个纯 layout PASS 应当 `dpas = 0`，且主体只有 load/store；本轮逐 pipeline 统计了 40 个 pipeline（232 行共用 39 个 SPV）的 DPAS 与消息：

| PASS（代表 ordinal） | DPAS | 指令 | 它实际算什么 |
|---|---:|---:|---|
| F21 ord 231 `ioport_block70_2` | **0** | 1 388 | 残差 float4 + base image → clamp/mix/history → 写 history 与 surface；26 load / 8 store，**是尾核数学，不是搬运** |
| F17 ord 133 `t3_b39_project_blend` | **2** | 4 741 | 16×128 投影 + 四角 blend |
| F18 ord 192/166/212 `c3x_pre_*` | **2** | 462 / 1 375 / 297 | 同一 tile 的 projection + four-corner blend，**输出已是消费者 canonical 布局** |
| F03 ord 5 `ioport_block4_0` | 4 | 2 773 | 1×1 GEMM + 4 像素池化 + 寄存器 pack，非 layout |
| 其余 36 个 pipeline | 16–352 | 743–8 710 | GEMM/attention/UPS |

所以 N16 方向在当前基线里**不可能靠删掉某个整派发**成立；布局转换已经全部内联在数学 PASS 的 store/load 索引里。真正存在的是**跨派发的 store→load 布局错配**（第 2 节），以及 PASS 内部的 SLM 往返（第 4 节）。

## 2. 真正的 repack 站点：A 片段的「行跨距」handoff

### 2.1 机制（已在 native 证过形状，不是猜测）

GEMM 的 A 片段是 8 token × 16 channel。生产者按**行主序**（token 行跨距 = K 个 half）存，消费者 `coopMatLoad(..., stride=K, RowMajor)` 读，硬件就发 **8 条 32 B 的 `load.ugm.d32x8t`**（每行一条）。若生产者把每个 8×16 tile 连续写（stride 16），消费者可发 **1 条 256 B 的 `load.ugm.d32x64t`**。

两条独立证据：

1. 同一网络里 `d32x64t`（256 B）的 A 读真实存在：F04 C64/C128 的 `load.ugm.d32x64t` 36/68 条，就是 8×16 A tile 的连续块读，每条后面跟 4 条 `mov:hf` 摊进 DPAS（n03 `ANALYSIS` 51–53；CURRENT ISA pipeline 4/8）。
2. `n06d-f06-c256-atile` 在 SLM 上做了同一件事：`load.slm.d32x8t` **1 025 → 129**、send **1 597 → 741**，且数值全过。**但 15 PASS 整体 −0.0025 ms INDISTINCT**（D 类）。

### 2.3 逐站点的关键证据与证明项

**S1（F13 aHidden）**

- 身份：expand 8 行 `93,98,…,128`（`54029e6b…`），contract 8 行 `94,99,…,129`（`bc629c9b…`），都是 8 个 block 同一 SPV。
- 现行地址：`coopMatStore(result, aHidden, m*4096 + n0 + side*16, 4096, RM)`；`coopMatLoad(af, aHidden, mA*4096 + k0, 4096, RM)`（`vit_nb04_mpair.glsl` 150/73/76）。
- 折叠后：`base((m/8),(n0+side*16)/16) = ((m/8)*256 + (n0+side*16)/16)*128`，store/load 都用 stride 16。
- 预期 native 签名（可证伪）：`load.ugm.d32x8t` **608 → ~76**，同时出现 ~76 条 `load.ugm.d32x64t`；aHidden 的 store **32 → 4** 条 `d32x64t`（总数 64 → 36，因为 gated dbg 的 32 条不变）；DPAS 152 不变、字节不变、scratch 0。
- 证明项：aHidden 只有 contract 一个读者（源码级；plan 里所有 F13–F16 PASS 都 bind 同一组 buffer，**binding 不等于 use**，必须逐 recipe 复核）；写域 288×4096 每元素一次；`m>=live` 的守卫与零填充语义不变；新索引 < 2 359 296 B；dbg 独立且 `p0.w=0` 关闭。
- 风险：16 PASS 低于检出限（L3/L12）；同机制 15 PASS 已 D（n06d）；IGC 可能因对齐证据不足而保留 8 条行消息（L14）；256 B 块仍要 ~4 条 `mov` 摊进 DPAS A 片段（n03），净账是 **−7 message +4 mov / tile**；32 个 N 片重复读不变。

**S2（F13 y）**

- 生产者 contract 的 direct epilogue：`coopMatStore(res, y, p5.w + m*1024 + n0 + side*16, 1024, RM)`（`vit_nb04_mpair.glsl` 37）。
- 消费者一：F14 qkv `coopMatLoad(af, y, ...K=1024, RM)`（n12 §1）；消费者二：F16 projection 的残差 skip 标量读 `y[pc.p5.w + t*1024 + col]`（`vit_nb04_mpair.glsl` 47）。
- 证明项：两个读者都要改地址；skip 是逐元素标量读，仍可用 tile map 重写；写域、范围、barrier 同 S1。
- 风险：读者多一个；24 PASS。

**S3（F15 context）**

- 消费者 F16：`coopMatLoad(af, context, pc.p6.y + r*K + k0, K, RM)`（n11b §1.1）。
- 生产者 F15 的 store 在 ISA 里与 denominator/debug 混在一起（`d16u32` 50、`d32` 64），**本轮不拆分**，写 UNKNOWN。
- F15 内部有 256 `load.slm.d32x8t` + 4 `fence.slm`（qkv 的跨 SG 广播），**不是**边界 repack；不要把它当成本站点的一部分。

**S4（F16 → 下一 block）**

- 生产者 F16：`coopMatStore(res, o, p5.y + m*1024 + n0 + side*16, 1024, RM)`；消费者下一 block expand：`coopMatLoad(af, x, p5.x + mA*K + k0, K, RM)`（K=1024）。
- 8 条 block 边同形；最后一条（block38 的 `o`）消费者可能不是 expand，必须逐 block 从 plan 枚举（UNKNOWN）。

**S5（F18 gM，唯一推荐的代表站点）**

- 生产者 c3x_body_c128（ord 193，`12569d76…`）：`coopMatStore(narrowed, gM, (w*64+m0)*128 + 32*g + 0/16, 128, LROW)`，4 个 acc × 2 r。
- 消费者 block56_swin_body_2（ord 194，`ffde3c3d…`）：`coopMatLoad(a, gM, (w*64+mA)*128 + k0, 128, LROW)`；n20 已实测 **256 条 A 行消息**，且该 PASS `Workgroup Memory 0 / send.slm 0`。
- 为什么它是干净的：gM（`swin_56_M`）只被 pre/body/body_2 bind，源码级只有这一个读者；写域 264×64×128 全覆盖（含图像 OOB token，n20 已证）；无 Y/T 别名；无 feedback。
- 预期 native：A 行 **256 → ~32** 条 `d32x64t`，gM store **64 → ~8**；该边 row 消息 **320 → 40（约 −280/线程）**；DPAS 64 不变、字节不变、scratch 0。
- 为什么仍可能 D：n20 已把「4× A 重读」与「消息数」分开；本折叠只降消息不降字节；n06d 正是 8× 消息下降仍 D。
- 结论：**值得开 1 张 2-PASS 代表卡**，目的不是毫秒，而是把「全局 A handoff 折叠」用一个单读者、地址可逐字节证明的站点钉死；native 看不到 `d32x64t` 就判 A（实现未落地），看到而 ordinary D 就把该方向在全网关掉。

**S6（F04→F05/F06/F07 gY）**

- 生产者 F04：`coopMatStore(v, gY, (w*64 + tA/B)*64 + cg0/1, 64, LROW)`；消费者 F05：`coopMatLoad(a, gY, (w*64+m0q)*64 + k0, 64, LROW)`；F06：`coopMatLoad(seed, gY, (w*64+mA)*64 + n0, 64, LROW)`；F07 也读 gT/gY。
- 三个读者、两种片段形状（A 与 MH 都是 8×16，理论上同一 tile 布局可同时服务），但必须逐宽度、逐读者枚举；69–105 PASS 的包才可能越过检出限。
- 另有 `mLocal` SLM（32 store / 64–256 load）与 K/V `shK/shV`，与本站点无关，不要混入。

**S7（C32 图像域）**

- `io_at(px,py,c,W,H,C,layout_id)` 的 layout id 是 **push 常量**（`pc.p2.x/p2.y`，`ioport_common.glsl` 27–35）；同一 SPV 在不同 PASS 用不同 layout，数据是图像域共享的。任何"折叠"都要改该族 45 个 PASS 中相关 producer/consumer 的 push 契约并重定 fixed-frame gold，**不是静态 repack**。

**S8（F20→F21）**

- 已由 n02b 完成并测：native `store.ugm.d32` 4→0、`d32x4` 0→1，2 PASS 包 +0.004435 ms CI[−0.0179,+0.0268]，D 类。**禁止原样重跑**。

## 3. 为什么「值得开卡」只有 S5，而且只是一张探针卡

三条独立的否决/降级理由：

1. **量级**：S1–S4 单条边是 8–16 PASS，S5 是 2 PASS。L3/L12 已证 8–16 PASS 的静态/消息下降通常低于帧检出限；n06d 在 15 PASS 上做了同类 8× 消息削减，结果 −0.0025 ms INDISTINCT。把 S1–S4 单独开卡，预期就是再交一个 D。
2. **形状**：S6/S7 才是有量级的包（69–105 / 45 PASS），但 S6 有 3 个读者、S7 是 runtime layout，风险与证明面远大于收益证据；在 S5 探针给出「native 落地且非 D」之前，不应启动。
3. **重复**：S8 已测 D；F05 的 K/V 消费布局（n01 111–112）、F18 pre→body 的 canonical 发布（`c3x_pre_c128.comp` 9–12）、F11 的 KIND=1 直写（n09 23）、F14→F15 的 qkv 消费布局（n12 65–69、147）**都已经在消费者布局上**，不是站点。

因此本卡的建议是：**只开 S5 的 2-PASS 代表卡**（F18 C128 `c3x_body_c128` + `block56_swin_body_2`），native 先判 A/落地，再决定是否把同一机制扩成 ViT 32-PASS 包（S1–S4）或 Swin 包（S6）。若 S5 native 落地而 ordinary D，则 N16 的「全局 store→load 布局折叠」在本工程按 D 关闭，不再逐站点试。

## 6. UNKNOWN（不凑数）

1. **动态消息数**：本文件所有条数都是静态的；同一 loop 的 trip count 未乘。
2. **S1/S5/S6 的生产者拆分**：ISA 只给总 store 数（64/160/224），aHidden / gM / gY 与 gated dbg 的拆分是源码推导，未由 ISA 标签证明。
3. **S3 的 context store 拆分**：`d16u32` 50 与 `d32` 64 里哪部分是 context、哪部分是 den/debug，未闭环。
4. **S4 最后一条 block 边的消费者**：8 条边同形，但 block38→F17/F18 的读者未逐 block 枚举。
5. **消息合并是否真发生**：`d32x8t`→`d32x64t` 的 8× 下降只在 SLM 形态（n06d）实测过；UGM 形态是预测，必须由 representative 卡的 native 判定。
6. **对齐**：tile 基址 256 B 对齐由公式保证，但 IGC 是否采用仍取决于编译结果（L14）。
