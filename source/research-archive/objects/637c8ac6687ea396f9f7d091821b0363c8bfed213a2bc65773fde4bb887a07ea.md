## 1. 若有人做删除型候选（本卡已证否）

必须先满足三判据（普查自己写的 `proof_requirement`）：

1. 同文本组内两条**共享同一个 reaching definition**（dword 粒度）；
2. 或两条之间**没有任何对该 dword 的写**，且值来自 push constant / 循环不变量；
3. 每个消费者读到的确实是同一个值（消费者清单一一对应）。

本卡对 F19 实测：**24 个站点 / 24 个 different reaching def / 0 对同值 / 0 条可删**
（`REDUNDANCY.json` 与 n33 方法的 `N33-CROSSCHECK.json` 一致）。
⇒ 任何声称「删 9 条 rsqt / 5 条 inv」的候选在本核上都是**用别的分量的值顶替**，
金帧必然不过（或只在巧合输入上过），应直接判 **E 类（数值失败）**。

## 2. 判据汇总（写进 GPU manifest 时必须带）

* 实现落地：rsqt 16、inv 8、dpas 129、send 604/43/4、scratch 0、max_r ≤127；
* 机制落地：rsqt/inv→首消费者距离 **≥8**（本卡建议的门；普查的 ≥20 在本核连 SPIR-V 都只有 inv 能达到）；
* 数值：fixed `1755…` / fb2 `9c3e…` / ordinary `2b63…` 三套金帧逐字节；
* 资源：XMX/GpuTime 单 PASS 对照；
* 归因：先看 native 是否形成处理，再看 counters，最后才看 ordinary（合同 §8.5）。
