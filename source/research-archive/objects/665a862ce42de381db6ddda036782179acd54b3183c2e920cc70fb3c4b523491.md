## 3. Why these particular numbers (derivation, so the prediction can be audited)

* 304 = 38 shared-fragment load sites × 8 messages; 160 = 20 shared-fragment store sites × 8
  (`build/isa.json → fragment_transfer_cost`, every class divides exactly by its unrolled source
  site count, `all_checks_match = true`).
* the two removed loads are stage-9's seed reloads (RowMajor, stride 32, offsets `m0*32` and
  `m0*32+16`, on the `shY` workgroup object — `build/spv-check-candidate.json`), i.e. 2 × 8 = 16.
* the two stores that become predicated are stage-3's `shY` publication (same object, same stride,
  same offsets), 2 × 8 = 16 further messages that are no longer issued.
* `send` 747 → 731 because only the loads leave the module; the stores stay as instructions
  (n17's Q patch behaved exactly this way: loads 304→288, static stores 160, `send` 747→731).
* instruction band: the 2 loads plus their `AccessChain/IMul/IAdd` address math leave (≈ 16 + 10
  ISA instructions), and ≈ +8 selection/label instructions arrive → net ≈ −18 (band 4 700…4 745
  allows for IGC re-scheduling both ways; n17's comparable Q patch landed at −55).

## 4. If N4 fails (spill): the prepared alternatives

1. **Narrow retention**: keep only `yhalf0` (2 GRF) and reload only the second half from `shY`
   (16 messages removed instead of 32). Halves the win, halves the pressure.
2. **Move the retention boundary**: store `H(Y)` to `shY` as today and *also* keep it in registers
   only from the last barrier before stage 9 (impossible without re-materialising — so this is a
   no-op; recorded so nobody tries it).
3. **Give the budget back**: drop `handoff0/handoff1`'s component copies (4 GRF live to stage 4)
   and rebuild stage 4's A from `yhalf0/yhalf1` instead — the same 4 GRF then serve both stages
   and the peak does not grow. This is a 2-hunk edit of the same parent and should be the *first*
   thing tried if `scratch > 0`.

## 5. What is *not* claimed

* Not claimed: that the dispatch is message-bound (that is the probe's question, at 20 %
  amplitude).
* Not claimed: any millisecond figure. The only statement this card makes about time is the
  *upper bound* 0.068 ms if the dispatch were strictly message-throughput bound, and that is an
  arithmetic identity, not a measurement.
* Not claimed: that a static message drop guarantees a speed-up (L2/L3: message drops have paid in
  F05/F06, static drops alone have not).
