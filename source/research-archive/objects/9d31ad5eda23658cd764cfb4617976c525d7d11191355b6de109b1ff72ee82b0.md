## 1. 期望在 ISA 里看到的可观察变化（逐条，附「凭什么」）

| # | 观察点 | 期望候选值 | 为什么必须是这样 |
|---|---|---|---|
| P1 | `dpas.8x8` | **= 256** | 本卡不动 j/ki 循环、不动两个 acc、不动 seed-before-K；只是把 A tile 的**存放位置**改成连续。若 ≠ 256 ⇒ 实现未落地 |
| P2 | `load.slm.d32x8t.a32` | **= 0**（消失） | 父的这条消息形态是「8 行各一条 32 B 转置消息」的直接产物；tile 连续后没有任何一行需要单独搬 |
| P3 | A 读的 `load.slm.*` 总数 | **128 – 256 / SG**（卡片判据） | 一个 8×16 tile = 128 half = **256 B 连续**；32 lane × 8 B/lane 正好一条消息 ⇒ 128 条；若 IGC 按 4 lane 拆就是 256 条。**仍 1024 ⇒ A 类未落地** |
| P4 | A 读字节 | **32 768 B/SG 不变** | 128 × 256 B = 1024 × 32 B = 32 KiB；8 个 owner 各读全表，512 KiB/WG 不变 |
| P5 | `load.ugm.d32x8.a32.bss`（权重） | **256 不变** | 权重复用形态是本卡禁区（源码一字未动） |
| P6 | `store.slm.d16u32`（发布存） | **16 → 0**，出现 4 条/warp 的 `store.slm.d32x8`（32 B/lane） | 每线程内层 16 次连续 half 存（+2 B/次）是可向量化形态 |
| P7 | `load.ugm.d16u32`（发布读） | **16 → 0**（剩 2 条 scale 读），出现 4 条/warp 的 32 B/lane 读 | 同上，且 gT 侧 16 half 也连续（`16*ki` 列，32 B 对齐） |
| P8 | `sync.bar` dynamic | **1 → 1** | 本卡不加 barrier、不分段：源码只有 1 个主路径 `barrier()`（SPIR-V `OpControlBarrier` 两侧都是 2 个，含 debug 分支那个） |
| P9 | `sync.allwr` / `sync.nop` | 量级不变（8 / ~1229） | 单 barrier 语义不变，仅地址来源变 |
| P10 | workgroup memory / scratch | **32 768 / 0** | shT 未删未改大小；段地址都是标量，没有新增常驻私有数组（`OpLifetimeStart/Stop` 两侧均 0） |
| P11 | max_r | **≤ 127**（不变最好） | 父已是上限 127（128 GRF/线程 → 每核 2 WG）；若 > 127 或 scratch > 0 就是 B 类 |
| P12 | 静态指令 | **7 000 – 7 300**（父 7 087） | SPIR-V 静态 860→947（+87），其中发布体内层多一个 16 次滚动循环、debug 分支多 8 个整数 op；IGC 侧净额应很小 |
| P13 | first_dpas | **不晚于 `$0x1420`** | 首个 DPAS 之前仍是同一次 32 KiB 发布（不早也不晚），本卡不承诺缩短序言 |
| P14 | 一个 warp 的发布写是否 1 024 B 连续 | 期望 **是**（4 次发布各 1 024 B） | 目的地址对 q 恰好是 `q*16` half = `q*32` B 线性，lane 相邻 ⇒ 一个 warp 的 32 lane 写满连续 1 024 B |

## 2. 「若看不到就等于未实现」的判据（**先登记，后测**）

- **A 类（实现未落地）**：A 读的 `load.slm.*` 消息总数仍为 1 024/SG，或 `load.slm.d32x8t`
  仍是 1 024（说明 IGC 没采用新布局），或 `dpas ≠ 256`。→ 记「实现未落地」，**不是**方向无效。
- **B 类（有副作用）**：`scratch > 0`、`max_r > 127`、`workgroup memory ≠ 32 768`、
  静态指令 > 7 400。→ 列增量账，优先怀疑内层循环没展开 / 地址算术溢出到私有临时。
- **B′ 类（A 读降了、发布没变宽）**：P3 达成但 P6/P7 未达成（仍是 `d16u32`，64 条/warp）。
  → 说明 32 B/lane 的连续块没被合并；此时 A 读收益仍在，只是发布端没拿到消息收益。
  **这条是本卡最可能出现的形态**，因为 SPIR-V 里内层 16 次拷贝是滚动循环
  （父的 64 次拷贝也是滚动的，IGC 把它展开成 16 条 static 并跨 lane 合并）。
- **C 类（当前身份无净收益）**：P1–P10 全达成、gates 逐位相同、15 PASS 逐 PASS 不变。
  → 归因到「该 kernel 是字节/带宽受限，不是消息槽受限」，不是方向禁令。
- **E 类（数值失败）**：gates 不同。→ 先查发布 `src` 的 `t>>4 / t&15` 分解与读端
  `m0>>3 / k0>>4` 是否一一对应（PROOF.json publish/read 已穷举 0 mismatch，
  所以真出错更可能是 **tile 序与 j/ki 的对应**被后续改动打乱，或 debug 路径）。

## 3. 与 native 一起必须看的资源侧

- `pipeline-statistics`：Workgroup Memory Size 必须仍 **32 768**，Scratch Memory Size 必须
  **0**，Loop Count 父 6 → 候选 7（SPIR-V 侧内层循环），ISA 侧应看不出多一层（被展开）。
- `resources` 逐 PASS GpuTime：父 15 PASS = 30.0–37.0 µs（单样本 base 臂）。候选逐 PASS 的
  **同向率**比整帧更有分辨力；本卡上限见 COST-LEDGER.ceiling（A 读占数据端口消息 60.5%、
  占字节 18.5%）。
- 归因要点：A 读消息数下降而**字节数不变**，所以若时间不变，说明该 kernel 在字节/带宽上受限；
  若时间下降，下降幅度应显著小于消息降幅（−87%），因为字节没变。
