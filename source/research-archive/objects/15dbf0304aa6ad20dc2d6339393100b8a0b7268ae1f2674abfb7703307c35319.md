## 0. 一句话结论

**父 SPV 并没有把 seed 以 half 形式留到 dequant 前**：四个 `nrh_widen_exact` 调用就贴在 half 乘法后面（同基本块，间隔 15 words），
宽化后的 f32 seed 才是跨 expand+K 存活的那个值；`NRH_C seedN = ycN` 复制也没有被 SSA 消除（还是显式 `OpLoad`+`OpStore`）。
本卡按目标做了最小改写：half seed 存入 `NRH_CH seedH0..3`，宽化移到 `nr_i8_deq_add` 实参处（子模块里每个宽化距其 deq_add 仅 21 words）。
SPIR-V 多重集差分**全部可归因**：`-24` 条指令（`OpName -4 / OpVariable -4 / OpLoad -8 / OpStore -8`），**转换指令 0 增减**（两边都 18 条 `OpFConvert`），
只改 `main`，全局段（LDS 18432 B、15 个非 Function 变量、87 个 NoContraction）逐项相同。
数值上逐位不变（§7）。native 效果未知；**不为同身份安排 GPU 计时**（§9）。

## 3. 关键判断：父是否已经“half 保存、到 dequant 前才宽化”？

### 3.1 方法

本机没有 `spirv-dis`，也无法调用 GPU 侧工具，所以用自写解析器直接读 word：
解析 `OpTypeCooperativeMatrixKHR`（4456）得到 `NRH_CH` = `f16 8x16 use=Accumulator`（type 35）与 `NRH_C` = `f32 8x16 use=Accumulator`（type 33）；
再用模块自带的 `OpName`（glslang 会给全部局部变量命名）定位 `nrh_widen_exact` / `nr_i8_deq_add` / `nrh_narrow` 与 `seed`、`yc0..3`、`seed0..3` 变量，
沿 “值 → 私有变量 → 值” 的 def-use 链把每个读写点枚举出来（`tools/b3_analyze.py`，原始输出 `evidence/seedflow-raw-parent.json`）。

注意：glslang 把每个 GLSL 局部量都降成 `Private`/`Function` 存储的 `OpVariable`，赋值就是 `OpStore`，
所以**任何**复制在 SPIR-V 里都是显式的 load/store；模块里一条 `OpCopyObject` 都没有（父、子均无）。

### 3.2 证据（父，word 偏移 = 模块内字偏移）

| seed | half 乘法（`OpFMul`，type 35） | 宽化调用（`nrh_widen_exact`） | 间距 | 宽化后的 f32 seed 变量 | 该 f32 seed 被读 | 复制（`NRH_C seedN = ycN`） | `nr_i8_deq_add` |
|---|---|---|---|---|---|---|---|
| 0 | w9346 | w9361 | 15 words | `yc0`（type 33） | 2 次 | `OpLoad` w9624 → `OpStore` w9628 | w14445 |
| 1 | w9431 | w9446 | 15 words | `yc1` | 2 次 | w9631 → w9635 | w14476 |
| 2 | w9516 | w9531 | 15 words | `yc2` | 2 次 | w9638 → w9642 | w14507 |
| 3 | w9601 | w9616 | 15 words | `yc3` | 2 次 | w9645 → w9649 | w14538 |

- 宽化与 half 乘法在**同一个基本块**（block 1323）里，紧邻；
- 宽化之后第一个 cooperative-matrix mul-add 在 **w9720**（expand 第一组），K=128 的循环头在 **w14016**（inst 3510），`nr_i8_deq_add` 在 **w14445…w14538**；
- 也就是说父的 f32 seed 从 w9628 一直活到 w14445（≈4800 words；4 个 seed 各 4923–5085 words），half 值只活 15 words；
- `yc0` 的两次读：一次是复制（w9624），一次是 epilogue 后的 `nrh_narrow`；`seed0` 只在 deq_add 的实参装载处被读一次（w14438）。

`nrh_widen_exact` 本体（函数 50，全文 26 条指令；w29702–w29809）：

```
OpVariable 34 377 ; OpStore 377 0.0
  4 × { OpAccessChain 7 380 49 <0|1|2|3> ; OpLoad 6 381 380 ; OpFConvert 28 382 381 ;
        OpAccessChain 52 383 377 <i> ; OpStore 383 382 }
OpLoad 33 396 377 ; OpReturnValue 396
```

即：每个 seed 的宽化 = 4 条标量 `f16→f32` 转换 + 私有变量往返，函数本身没被内联。

### 3.3 结论

**父不是目标形态。** 没有自动 sink、没有 pack，复制也没被消除。
（严格说：glslang 不是优化器，SPIR-V 里指令就是源序；“会不会被后端 sink”是 IGC 的问题，
本卡无 native 证据，不能替它下结论——但这不影响本卡的判断：**前端产物里宽化确实在 K0 之前**。）

## 7. 数值合同（逐位，不改数值）

机器可读版：`evidence/NUMERIC-CONTRACT.json`。

1. **half 乘法不变**：`seed = x * rs` 仍是 f16 cooperative-matrix 乘，一次 half 舍入（RNE），指令与操作数同序（差分里 `OpFMul` / `OpCooperativeMatrix*` 计数全同）。
2. **宽化是精确变换**：`nrh_widen_exact` = 4 条标量 `OpFConvert f16→f32`。binary16 的每个值（有限、次正规、±0、±inf、NaN）在 binary32 里都能精确表示，转换不引入舍入；结果只取决于那 16 个 bit。
3. **中间没有浮点运算**：从旧宽化点 A（w9361…）到新宽化点 B（w14312…）之间，seed 只经过 Private 变量的 store/load，没有任何浮点指令碰它（`evidence/SEED-FLOW.json` 逐点列出；两处之间 seed 的读者只有复制/实参装载与最终 narrow）。
4. **加法与窄化顺序不变**：`nr_i8_deq_add` 里 `precise float p = f[i] * fsc[...]`、`precise float q = p + seed[i]`；seed 只是 f32 加法的第二个操作数，乘法标了 `precise`，装饰 NoContraction 两边都是 87 条，不存在乘加融合的余地。最终 `y0..y3 = nrh_narrow(yc0..yc3)` 顺序不变。

约定层面逐项说清（这些约定本卡**不改变**，只是把宽化挪后）：

- **有限 half**：|v| ≤ 65504，宽化后是同一个 f32 值；half 次正规数在 f32 里是正规数，转换不 flush。
- **signed zero**：`-0.0h → -0.0f`，`+0.0h → +0.0f`；符号由 f16 位决定，位没变。
- **NaN payload**：half NaN → f32 的 quiet NaN，payload 是输入 payload 的确定性函数；输入位相同，转出的位就相同；加之前没有对 seed NaN 做任何算术。
- **顺序**：seed 相加顺序（`yc0..3` 各自一个加法）、最终窄化顺序、store 顺序都没动。

**不声称**：以上是 CPU/静态逐位论证，不是 GPU 数值门；`GATE` 未跑。

## 8. 成本核算（源级，不是实测）

- 静态：−24 条指令（其中 4 条 `OpName` 不执行、4 条 `OpVariable` 是函数入口的变量声明），−88 words。
- 每个执行 seed 路径的 lane：**−16 条 private 内存 load/store**（4 个复制 × (load+store)），宽化工作量不变（4 次调用 × 4 条转换）。
- 路径条件 `if (sg < 4u)`：`local_size_x=128` 时 `sg = tid/32 ∈ {0,1,2,3}` 恒真，编译期仍是均匀分支；动态次数按“每线程一次”计。
- 活跃区间：8×16 的 cooperative matrix 在 32 lane 上每 lane 4 个分量——f32 seed = 4×4 B = 16 B/lane，f16 seed = 4×2 B = 8 B/lane；
  4 个 seed 合计：父 64 B/lane 跨 expand+K 存活，候选 32 B/lane，K 阶段少 8 个 dword/lane 的活值（**寄存器压力假设，不是实测**）。
- 这些是**源级有效指令数**，不是实测 DRAM 字节、不是寄存器分配结果、不是 scratch/spill 统计。

## 9. 未验证项 / GPU 缺口 / 为何不排 GPU 计时

| 资格 | 状态 |
|---|---|

| SPV_IDENTITY | ✅ 多重集差分逐类归因、只有 `main` 变、全局段相同 |

| GATE / ORDINARY / QUALITY | ❌ 未跑：无 GPU |

**不为同身份重复安排 GPU 计时**：本改动转换指令数 0 增减（宽化只是搬家），净删的是每 lane 16 条 private load/store，
在 ordinary 计时噪声下不可分辨；真问题（spill / 寄存器压力）只有 native pipeline-create 的 ISA/occupancy 才能回答，计时臂回答不了。
`run/b3-c32-seed/jobs.json` 明确写 `gpu_jobs: []`，只留一条“若协调入口以后给 GPU 时段，应做 native ISA/occupancy 对照（不是计时臂）”的说明。

**风险也要写明**：父与候选都可能把 seed 溢出到 private/scratch（4×16 B 或 4×8 B per lane）；
若后端选择溢出，本改动减少的是溢出字节，同样只有 native 能证实。没有 native 之前，本卡的收益只能表述为“活值变窄 + 少 16 条 load/store”，不能表述为更快。
