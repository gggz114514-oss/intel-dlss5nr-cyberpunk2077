## 4. The new barrier, and why it is exactly where it is

First E publish call is at `inst 2580`. The added `OpControlBarrier` is at
`inst 2457` / word offset `9670`, exec scope `Subgroup(3)`, memory scope `Subgroup(3)`,
semantics `3400` (`AcquireRelease|WorkgroupMemory|…`, i.e. glslang's `subgroupBarrier()`).
The immediately preceding cooperative-matrix load is `inst 2455` / word `9659`,
**result id 1474**, the one X read.

Checks (`evidence/ADDRESS-PROOF.json → checks`):

* `x_publish_calls_before_x_load` = true (max put_x call `2363` < `2455`),
* `x_load_before_added_barrier` = true (`2455` < `2457`),
* `no_shared_store_between_x_load_and_barrier` = true (0 stores to `sE8` in that window),
* `added_barrier_before_first_e_publish_call` = true (`2457` < `2580`),
* `e_reads_after_e_publish_calls` = true.

A pure memory barrier would not have been enough (no execution rendezvous); the emitted
instruction is a full `OpControlBarrier`. No workgroup-scope barrier was added: the four
subgroup slots are mutually exclusive, so the existing `barrier()` that publishes
`shK`/`shV` is untouched and still required (every SG reads all 2048 elements of `shK`).

## 5. Address proof (exhaustive, `evidence/ADDRESS-PROOF.json`)

Model, straight from the two helpers:

```

e_read (sg,f,n) = 2048*sg + 512*(f//32) + 32*n + (f%32)     # coopMatLoad kg=f//32, k=f%32
x_cand (sg,c,n) = 2048*sg + 32*n + c                        # first 512 B of the slot
x_parent(sg,c,n) =  512*sg + 32*n + c                       # separate sX8 array
```

* **All 8192 triples enumerated** (4 SG × 128 feature × 16 token), `e_write_neq_read = 0`.
* `distinct_e_bytes = 8192` → the map is a bijection onto the four 2048 B slots, and
  `e_bytes_cover_slots_exactly` = true (each slot's 2048 bytes are all used, none shared).
* **Overlap of the X region and the E region, per SG = 512 bytes**, and it is exactly the
  E slab for features 0..31 (slot offsets 0..511); 2048 bytes in total across 4 SGs.
  The other 1536 bytes of each slot are E-only. `x_region ⊆ e_region` = true.
* `x_in_slot_offset_identical_to_parent` = true: B1 is a pure rebase, the in-slot offset

* `lane_map_bijection_8x16` = true: `nrh_coord_CH` covers the 8×16 fragment exactly once

* `all_ok = true`, 25/25 checks.

## 7. Dynamic counts (arithmetic, not measurement)

Geometry: `local_size_x = 128` → 4 subgroups × 32 lanes; each SG owns 16 tokens ×
32 channels; each WG covers 4 token tiles. Let `G` = the runner's dispatch grid
(`grid.x·grid.y`); the plan file carries no grid, so `G` stays symbolic. Declared output
`block1_out` = 16515072 B = 8257536 fp16 ÷ 2048 fp16 per WG ≈ 4032 WGs — *derived from
the plan's buffer size, not from a dispatch record*; it is illustrative only.

| item | per lane | per SG | per WG | per frame (×G) |
|---|---|---|---|---|
| X publish byte-stores | 4 calls × 4 it = **16** | 512 | 2048 | 2048·G |
| X read (`coopMatLoad`, 512 B) | — | **1** | 4 | 4·G (2048·G bytes) |
| E publish byte-stores | 16 calls × 4 it = **64** | 2048 | 8192 | 8192·G |
| E read (4 × 512 B) | — | 4 | 16 | 16·G (8192·G bytes) |
| subgroup barrier pairs (mem+ctrl) | 2 | 2 | 2 | 2·G |
| **new** subgroupBarrier | **+1** | +1 | **+4** | +4·G |
| workgroup `barrier()` | 1 | 1 | 1 | 1·G |

**Deleted nothing, added one synchronisation.** The byte-store and cooperative-load
counts are *identical* to the parent (the same 16 + 64 byte-stores per lane, the same one
X load and four E loads); only the X base address changed and exactly one
`subgroupBarrier()` execution per SG was added (at G ≈ 4032: +16128 barrier executions
per dispatch). So B1 does **not** remove memory traffic; it removes a declared
allocation. Any benefit can only come from the native side (SLM footprint/occupancy),
which is unverified here — and one extra execution rendezvous can equally cost time.
Do not read a direction into this.

## 8. Owner and live region

* Owner of byte `b ∈ sE8` is subgroup `g = b / 2048`, exclusively.
* Within a slot the live region is time-sliced: `[2048g, 2048g+512)` holds **X**
  from the 4 publishes until the single cooperative load completes, then those same 512
  bytes become **E features 0..31** (written by feature group 0, read by the contract's
  `kg = 0` load). Bytes `[2048g+512, 2048g+2048)` hold E features 32..127 only.
* `shK`/`shV` are *not* per-SG private: SG `g` writes 1024 B of each and every SG reads
  all 4096 B, which is why the workgroup `barrier()` at `inst 4789` stays.
* Peak *declared* footprint is the sum of all three arrays (16384 B); the peak *live*
  footprint at any instant is lower, but that distinction is not something this card
  measured.

## 10. CPU conclusion

On the CPU/offline evidence: the change is structurally sound. Every (SG, feature, token)
address the candidate writes is the address it later reads; the four SG slots are
pairwise disjoint; each SG's X copy sits inside its own slot, overlaps exactly the E
slab for features 0..31 of that same SG, and is fully read (one cooperative load) before
any lane of that SG can overwrite it — enforced by an execution barrier in the emitted
SPIR-V, not merely by a memory barrier. The declared Workgroup footprint drops from
18432 B to 16384 B. The SPIR-V delta is 7 classes / 6 word classes, all attributed to
the single intended change.

Because every stored value is produced by the same expressions from the same operands at
the same logical slot, the candidate is *expected* to be bit-identical to the parent —
**but that is an expectation, not a result.** No GPU ran.
