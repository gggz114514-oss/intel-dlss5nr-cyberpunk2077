## 1. ISA 静态计数：**可能不变**，这不是失败

父身份捕获 ISA（kernel hash `76902ef344609c8a`，pipe 38 / ord 230）：4754 条、`sync.bar` **12**、`fence.slm` **11**、
`send.gtwy` 13（12 条 `signal barrier` + 1 条 `end of thread`）、`dpas.8x8` 64、
`store.slm.d32x8t` 160、`load.slm.d32x8t` 304、Workgroup Memory 24576 B、Scratch 0、max_r 127。

**源 16 次 `barrier()` → ISA 12 道 `sync.bar`**：缺的 4 道是四对相邻重复被驱动合并（`STAGE-BLOCK-MATRIX.md` §5 逐道贴了偏移）：

```
{225,227} -> sync.bar @0x11E8     {334,336} -> sync.bar @0x6270   <- 本卡删的是这一对里的正常路径那一道
{394,396} -> sync.bar @0x8C00     {599,601} -> sync.bar @0x101A0
{521,523} 没有被合并（@0xDDE0 与 @0xDE40 是两道指令，中间 6 条收尾指令）
```

后果：被删的那道屏障在父里**已经和 debug 侧合成了一条指令** @0x6270。候选只剩 debug 一侧，那条指令会回到 debug 分支内。

| 期望 | 候选取值 | 若不符合 |
|---|---|---|
| `sync.bar` 静态 | **12**（合并行为不变时）或 **11**（驱动把 debug 侧也省掉） | 13+ ⇒ 有问题，回查 |
| `fence.slm` 静态 | 11 或 10 | — |
| `send.gtwy` 静态 | 13 或 12 | — |

## 2. 执行面：每 WG 的屏障跨越 6 → 5（这是真正的落地判据）

| 观察量 | 父 | 候选期望 | 类别 |
|---|---|---|---|
| 正常路径执行的 `sync.bar` / WG | **6**（源上 5 道无条件 + 驱动从 {225,227} 提到分支外的 1 道） | **5** | 落地 |
| 执行的 `signal barrier` 消息 / WG | 6 | 5 | 落地 |
| 执行的 `fence.slm` / WG | 6 | 5 | 落地 |
| `XVE_STALL_BARRIER`（ord 230，折算 ms） | 0.224124（`evidence/STALL-BUDGET.json`） | **≈0.183**（0.179…0.187，即按执行数 5→4 或 6→5 折算的 −0.037…−0.045；宽判带 0.164…0.194） | 有效 |
| 该 PASS `GpuTime` | 1.346093 ms | 1.301…1.309 ms | 有效 |
| 全帧 ordinary | 17.14 ms 量级 | **+0.020…+0.045 ms** | 待测 |

**判据（缺一不可）**

- **A 类（实现未落地）**：候选 ISA 里那道 `sync.bar` 仍在 stage-4 首个 `dpas` 之前**无条件**执行，
  且 `XVE_STALL_BARRIER` 没动 ⇒ 驱动的合并/提升行为与推断不符，本卡记 A，不是方向无效。
  下一步是把 debug 侧那道也删掉（见 `RESUME.txt`）。
- **B 类（有副作用）**：`store.slm.d32x8t` >160 或 `load.slm.d32x8t` >304 或 `add`/`mov` 明显上升 ⇒
  平面行距的代价超过了屏障收益，按"平面间插、平面内连续"的折中布局修一版（预计仍零额外内存）。
- **C 类（无净收益）**：落地 + 门全过 + BARRIER 确实降了，但帧级 <0.03 ms ⇒ 记 D INDISTINCT（单点作用域小），
  按 L13 走第二批复现或用"整族屏障包"（与 n28 的屏障审计同批）再判。

## 3. 数值面的观察点（不是"应该没问题"，而是"看哪里"）

1. `fixed` 末帧必须仍等于 `1755e9c2fadba97f08cb5b02b7a4294cde3675379bdec75352287505f7e129d6`。
2. `fb2`（`--warm 0 --reps 2 --feedback --save-frames`）末帧必须仍等于 `9c3e511e97a5879247bc2965792c96dd62928dddfd85a48bbf25af1e807d3536`。
3. `ordinary` 末帧必须仍等于 `2b63d4ba1967eebcda61698d538963f59bccaf6d690ef8168f1695a46c5d658d`。
4. 若出现首差：先看是否落在 Q/K/V 的 (token,channel) 交换上（本卡唯一改动的语义面），
   再看 `debug=1` 的 dump 是否仍逐字节相同（`NR_Q/K/V/CTX` 四个宏已跟着改，8192 槽位穷举 0 不符）。
   **不要**先怀疑舍入或 K 序——FP 多重集与 NC 站点两臂完全相同。

## 4. 资源面的观察点

- `L1/SLM` 侧：Workgroup Memory 24576 B 不变 ⇒ **不应**出现 occupancy 下降。
  两臂 `XVE_THREADS_OCCUPANCY_ALL` 若出现 >2% 的差异，说明有别的资源变了（寄存器/调度），要回查而不是当成收益解释。
- 寄存器侧：max_r 127 → 期望 ≤127；若升到 128 或出现 scratch，直接否。
- 本卡**没有**新增长寿命值：`handoff0/1`、`p_cache`、`ctx_half0/1`、`pv_inv` 的生命周期逐段未变。
