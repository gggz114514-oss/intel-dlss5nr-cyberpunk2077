## 3. P 的时机合同（ViT vs Swin），以及为什么 PV 的 INT8 不在本轮

### 3.1 现状语义（父核，逐行读出来的，不是推测）

1. `P` 由 `score → MC→MH 窄化 → vit_exp2` 得到，值域被 exp 的钳位钉死在
   **`[1.439453125, 1.9775390625]`**（`vit_common.glsl:vit_exp` 的 `clamp`）。P **不是概率**，没有归一化。
2. `P` 以**未归一化**的形式进入 PV：`NRH_B pf=nrh_join_rows_to_B(ph0,ph1)` 直接从寄存器取，
   `ctx0..3 += vf_i × pf`，**P 从不落地**（这是 M19 的寄存器交接，替换了 `sp[4096]` 桥）。
3. 分母 `den` 在**全部 chunk 之后**才收尾：`pad=(p0.y-p0.x)*exp(0)`、`den-=pad`、
   `inv=1/max(den, 6.198883056640625e-05)`，然后 `out_i=num_i*inverse` 才写 int8 qT。
   即 **reciprocal 的位置在 5 个 64-key chunk 之后**，PV 期间不知道它。
4. padding：整块死的 16-key 块在父核里是 `sk` 零填充 → 分数 0 → `exp(0)` 进 den；
   P 在 **den 之后**才按行清零，所以 padding 只从 PV 里去掉、不从 den 里去掉，最后一次性减 `pad`。

### 3.2 动态量化应插在哪（如果做 PV）

- **只能插在 den 树之后、PV 之前**（`part[]` 结算完、`ph0/ph1` 归零 padding 之后），
  因为 den 必须继续用 **f16 的 P**：den 是 `pair=ph0[ci]+ph1[ci]` 的 f16 加法树 + `shuffleXor(16)`，
  与量化后的 P 不是同一个数。这一点与 Swin 卡（R04）的结论同向："den 必须与 PV 用同一份量化 P"，
  区别是 **Swin 选择了让 den 用归一化后的 P，ViT 不能**（ViT 的 P 归一化因子在 5 个 chunk 之后才有）。
- **尺度只能 per-(query, chunk)**：per-query 的全局 max（Swin 的 `pmx`）在 PV 时刻**不存在**；
  逐 chunk 的 max 可以就地拿到（每 lane 持有该 chunk 4 行 × 2 列的 P，一次 `shuffleXor(16)` 闭合），
  代价是**每个 chunk 的 int32 结果要单独乘 `sP_c*sV` 再加到 f32 ctx**，
  不再是"一个 int32 累加器跨 chunk 累积"。
- **不增加完整 P 回写**：P 一旦量化就必须以 int8 B 片元出现在 MMA 的 B 操作数上，
  而 int8 coopmat B 只能从内存（shared/global）载入 → 每 chunk 每 score SG 至少要
  32 keys × 16 queries = **512 B 的 int8 P^T 暂存**（不是父核删掉的 `sp[4096]` = 8 KiB 广播桥，
  但也确实是"P 落地"）。**R15 不做**：这条与 GUIDE 77 的"不增加完整 P 回写"相冲突，
  且 v1 的 PV 成本设计（`vit-attn-int8-v1/PV-COST-DESIGN.md`）已判定为负收益。

### 3.3 与 Swin 的逐条差异

| 项 | Swin（R04, c64） | ViT（本卡, blocks31–38） |
|---|---|---|
| P 进 PV 前是否归一化 | 是：`P := half(P*inv)` | **否**：`P = exp(·)`，未归一化 |
| reciprocal 位置 | PV 之前（单窗口 64 key，den 一次算完） | **全部 5 个 64-key chunk 之后** |
| P 值域 | `P ≤ 1`（归一化保证） | `P ∈ [1.439, 1.978]`（exp 钳位），**恒 > 1** |
| per-query 量化尺度 | `pmx = max over 64 keys`，一次 `shuffleXor(16)` 闭合，`sP=pmx/127` | 同一时刻**拿不到**全局 max；只有 per-chunk max |
| 累加器 | 单一 int32 累积（两片 K32 共用同一个 `sP`） | 需要 per-chunk 重标定 → 要么 f32 累加、要么每 chunk 一条 rescale |
| den 与 P 的关系 | den 用归一化 P，量化 P 与 den 同源 | den 用 f16 P（pair 树），量化 P 会与 den 分家 |
| P 是否落地 | 不落地（寄存器 join） | 父核不落地；INT8 化**必须**落地 ≥512 B/SG/chunk |
| padding | 无（窗口内全有效） | 有 32 个 padding key，`exp(0)` 进 den、最后减 `pad` |
| 结论 | PV INT8 已实施（R04） | **PV INT8 推迟到 R15b**，本轮只做 QK |

### 3.4 反过来说 QK 为什么可以现在做（同一份合同下）

QK 的两个操作数都是**静态可量化的外部量**（K、Q 由 qkv producer 在 norm 之后一次算出），
与 P 的时机问题无关：score 的 dequant 因子 `qp[h]=sQ_h*sK_h` 是**每次 dispatch 一个标量**，
不需要任何跨 chunk 的 rescale，也不需要 P 落地。这是选 QK 而不是 PV 的**唯一**理由
（不是"QK 便宜"，是"QK 不碰 P 的时机合同"）。

**没有 NoContraction/RelaxedPrecision 迁移**（`precise` 直接产生装饰，与父同策略）。

### 4.5 本臂 INT8 参考状态（`evidence/ORACLE-QK.json`，CPU，非门）

- 数据：`run/…/batch8-diag-001/dump_vit_block{32..38}_QKV.bin`（288×3072 f16，**真实帧**）
  + `vit-attn-int8-v1/pack/vit_block{32..38}_weights.attnqk.bin` 的 `qi/qp`（真实标定）。
- 21 个 (block, head) 样本，每个 288 key × 288 query × 32 dim：
  **score `rel_l2 ≤ 1.24 %`、`max|Δscore| ≤ 0.0774`、`corr ≥ 0.99990`；
  `P` 的 `rel_l2 ≤ 1.80 %`**（P 是 `vit_exp` 后的值，钳位把分数误差压成 ~0.09 的斜率）。
- 非零性：码值非零，`qi ∈ [2.0, 12.6]`、`qp > 0`；饱和 **36** 个码 / 7×（288×1024×2）≈ 4.1 M（8.7e-6）。
- **K 的 L2 归一化合同实测成立**：`‖K‖ - 1` 的最大偏差 **8.6e-4**（f16 量化误差量级），
  这就是"`|K| ≤ 1` 因此 `qi` 只需 per-head absmax"的证据。
- **跨帧稳定度**：用另一帧（batch8）重算 `qi'`，与包内 `qi` 的最大相对差 **1.33 %**
  ——单帧标定（`SINGLE_FRAME_DIAGNOSTIC_NOT_CALIBRATION`）在这两帧之间是可用的，但只有两帧。
- **包尾自洽**：`qp[h] == 1/(qi[h]*qi[32+h])`，最大相对差 < 1e-6（**语义**精确：
  `sQ=1/qi[h]`、`sK=1/qi[32+h]`）。
- **未过任何设备侧门**：以上是 CPU 参考，`GATE` 未跑。

## 6. 连接成本（只给次数与 owner，不给毫秒）

- 新增量化：qkv producer 端 **589 824 次/block**（每元素 1 次 `roundEven`+clamp），
  7 块/帧 = **4 128 768 次/帧**；attention 端 0 次（不在 attention 里重复量化，
  这正是"K 归 owner 在 producer"的原因：否则每个 key 会被 5 个 x-tile 各量化一次）。
- 新增全局写：**589 824 B/block**（qQ+qK），7 块 = **4 128 768 B/帧**，owner = qkv PASS。
- 新增全局读：attention 端 `qK` 2 048 B/chunk/SG × 4 SG × 5 chunk = **40 960 B/WG**（父核 20 480 B/WG：
  一次全局读进 SLM），每 PASS **+3 276 800 B**，7 PASS **+22 937 600 B/帧**（源级，未测命中率）。
- barrier：**每 chunk 2 次不变**（sv 发布 + WAR），每 WG 5 chunk → 0 变化。
- 声明 shared：attention **8 192 → 4 096 B**；qkv 不变（8 192 B）。
- dispatch / buffer / binding / PUSH / grid：**全部不变**（plan delta 只有 SPV 路径与包路径）。
- `NATIVE` 未知：GRF/scratch、int8 coopmat 从 **global** 直读的 LDS/L1 行为、DPAS 与非 DPAS 指令
  都要设备上才能读；本卡不做声明。

## 7. 具名缺口（不假修）

- **G1 没有 GPU 时段**：门/ordinary/画质全部未跑，`run/r15-vit-attn/jobs.json` 只列不跑。
- **G2 block31 没有 attnqk 包**（**本卡最大缺口**）：`vit-attn-int8-v1` 只铸了 32–38 的包；
  block31 现在的权重包是 X5 修好的真 INT8 包（`9166f9c8…`），它的 `qi/qp` 尾 **全 0**（实测），
  而冻结的 block31 QKV 抓帧（`batch8-diag-001` 等）都发生在 X5 换包**之前**，其 Q/K 统计不可用。
  所以 **block31 的 4 处 QK MMA 仍是 FP16**。下一步：在修好的包下重新抓一帧 block31 QKV，
  用同一 `pack_vit_block_attnqk` 公式铸包，再把这 1 个 PASS 接进来。
- **G3 标定 dump 不在盘上**：`vit-attn-int8-v1/pack/pack-receipt-block*.json` 指定的
  `run/…/capture-all-v7-001/dump_vit_block*_QKV.bin` **已不存在**（该目录现在没有 QKV 文件）。
  我用的是同 buffer 的**另一帧**（`batch8-diag-001`），因此**无法**逐字节复现包尾；
  能证明的是：包尾**语义**自洽（<1e-6）+ 跨帧 `qi` 差 1.33 %。这是一条**降级**的证据，必须记住。
- **G4 门脚本未跑**：`ORACLE-QK.json` 是 CPU 参考（非零、有误差界），不是设备侧门；
  两臂 `jobs.json` 已定义（parent gate / cand gate / ctrl gate / ord-pre / ord-cand），等 GPU 时段。
- **G5 plan 的 `shared` 字段是继承值**：候选 SPIR-V 声明 4 096 B，plan 行仍写 8 192 B
  （与 `vit-attn-int8-v1` 同一处理）。这是**保守方向**（多声明不越界），但 native 分配未知。
- **G6 两帧稳定度不等于标定**：`qi` 的跨帧差 1.33 % 只覆盖两个帧；画质/跨帧风险未验。
