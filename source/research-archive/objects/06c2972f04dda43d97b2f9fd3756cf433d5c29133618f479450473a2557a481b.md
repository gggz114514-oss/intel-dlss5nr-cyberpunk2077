## 1. 映射：每个 (lane,component) 到底代表哪个 (token, channel)

### 1.1 两套布局的精确定义

```
逻辑元素： (w, t, c)    w ∈ [0,264) 窗口, t ∈ [0,64) token, c ∈ [0,128) channel
父（行主序）: old(w,t,c) = (w*64 + t)*128 + c                    // 行距 128 half = 256 B
候选（折叠）: new(w,t,c) = w*8192 + (t/8)*1024 + (c/16)*128
                          + (t%8)*16 + (c%16)                    // 行距 16 half = 32 B
tile 基址   : tile(w, tr, tc) = w*8192 + tr*1024 + tc*128         // tr=t/8, tc=c/16
```
两种布局都是 264 × 64 × 128 = 2,162,688 half = 4,325,376 B，且 `new` 是把每个
8 token × 16 channel 的 tile 变成 256 B 连续块（8 行 × 32 B）。

### 1.2 producer（ord 193）写映射（可枚举，每 WG (w,g)，8 个 subgroup）

源码 `candidate-193.comp` 的 mid epilogue：`m0 = 8*sg`，两个 accumulator 分别对应列组 `32g` 与 `32g+16`。

| sg | acc | tile | token 范围 | channel 范围 | 新基址（half） | 新行距 |
|---:|---:|---|---|---|---|---:|
| 0..7 | 0 | (w, sg, 2g) | `[8sg, 8sg+8)` | `[32g, 32g+16)` | `(w*64+8sg)*128 + 256g` | 16 |
| 0..7 | 1 | (w, sg, 2g+1) | `[8sg, 8sg+8)` | `[32g+16, 32g+32)` | `(w*64+8sg)*128 + 256g + 128` | 16 |

fragment 元素 (i,j)（i<8 行，j<16 列）落在 `基址 + 16i + j`，即
`new(w, 8sg+i, 32g+16·acc+j)`。**注意 `(w*64+m0)*128 == w*8192 + m0*128` 与折叠后的行组基址
`(m0/8)*1024` 数值相同**，所以父的基址项原样保留，只有列 tile 项（`32g → 256g`）和行距（`128 → 16`）变。

### 1.3 consumer（ord 194）读映射（可枚举，每 WG w，8 个 subgroup）

| sg | q=sg/4 | n0=(sg%4)*32 | r | mA | mB | ki | 读到的 tile |
|---:|---:|---:|---:|---:|---:|---|---|
| 0..7 | 0,1 | 0/32/64/96 | 0,1 | `(q+4r)*8` | `mA+16` | 0..7 | `(w, mA/8, ki)`、`(w, mB/8, ki)` |

融合后 load 的基址 = `(w*64+m)*128 + k0*8`（k0 = 16ki），行距 16；fragment 元素 (i,j) 落在
`基址 + 16i + j` = `new(w, m+i, k0+j)`。
`k0*8 == 128*ki` 是 256 B 步进，`(w*64+m)*128` 是 256 B 的整数倍 ⇒ 每条 tile load 是
**256 B 对齐的连续块**（`mapping-proof.json.checks.E_bounds.tile_bases_aligned = true`）。

### 1.4 一一覆盖 / 无漏读 / 无重复写（穷举，`enumerate.py` → `mapping-proof.json`）

| 检查 | 结果 |
|---|---|
| 布局双射：264 个窗口各 8192 个互不同的 half 偏移，全局标记 2,162,688 且重复标记 0 | PASS |
| producer 写域：`(w,g,sg,acc)` 全部展开 = 2,162,688 个地址，**每元素恰好写 1 次**，地址==`new(w,t,c)` | PASS |
| producer 写域在父布局下同样每元素 1 次，且**逻辑 (w,t,c) 映射与候选完全相同** | PASS |
| consumer 读：8 sg × 2 r × 2 (A,B) × 8 ki = **256 次 tile load/线程**，元素读 8,650,752 = 4×2,162,688 | PASS |
| consumer 读到但 producer 未写的地址数 = **0** | PASS |
| 父/候选读到的**逻辑元素集合相等**，且都等于写域集合 | PASS |
| 读放大倍数（每元素被读几次）= **{4}**（与父相同） | PASS |
| 越界：最大地址 2,162,687，末元素字节结束于 4,325,376 = 缓冲区大小 | PASS |

tile 集合本身两边相同：producer 写 `{(w, 8a, 16b)}`，consumer 读 `{(w, mA, 16ki)}`，
而 `mA ∈ {0,8,…,56}`、`16ki ∈ {0,…,112}` ⇒ 同一个 8×16 分块集合，只是每边枚举顺序不同。

### 1.5 尾块 / OOB

- 本 PASS 的 M/N 是编译期满 tile（64×128），**没有 PASS 内尾块**。
- 图像域 OOB（`c128_img_half_index` 的 clamp+oob）发生在 producer 的 expand 读 `imgin` 与
  consumer 的 seed 读 `imgin`，**都不经过 gM**：producer 对 OOB token 照样计算并**照样写 gM**
  （写域覆盖全部 264×64×128，无守卫），consumer 对 OOB 只把 seed 置 0。折叠不改这条语义。
- `POLICY 208 0 192 194 0`：gM 无 `clearFirst`，因此「producer 必须写满 consumer 会读的每个元素」
  是**父就已有**的前提；1.4 的 0 个漏写证明该前提在折叠后仍成立。

### 4.2 ② consumer 每个 (token,channel) 的 A 片段元素与父逐字节相同（穷举）

证明链（`mapping-proof.json`，`verdict=PASS`）：

1. 父：consumer 读 `(w*64+m)*128 + k0 + 128i + j` = 元素 `(w, m+i, k0+j)`。
2. 候选：consumer 读 `(w*64+m)*128 + k0*8 + 16i + j` = `new(w, m+i, k0+j)` —— **同一个三元组**。
3. producer 在候选布局下把值写到 `new(w, t, c)`（穷举：地址 == `new`，每元素一次）。
4. 因此每个 fragment 元素读到的**是同一个逻辑元素、同一个值**；只有地址变。
   父/候选的「读到的逻辑元素集合」逐点相等（`D_logical_identity.read_element_sets_equal = true`），
   且等于写域（无漏写 ⇒ 无读到未初始化）。
5. `k0*8 == 128*ki` 与 `(w*64+m)*128` 都是 128 half 的整数倍 ⇒ 256 B 对齐（`tile_bases_aligned`），
   与同 kernel 里已经合并的 seed load 完全同形。

### 4.3 ③ 同步：两 PASS 之间是 runner 的全量 dispatch barrier，且一处未删

- runner（只读源 `phase-diagnosis-20261025/direct-clock/clock_runner.cpp`，我自己核对）：
  451 行 `for(passIndex…)` → 471 `vkCmdDispatch` → **472–473 紧随其后**
  `barrier(COMPUTE→COMPUTE, SHADER_WRITE→SHADER_READ|SHADER_WRITE)`，

  193→194 正是相邻两个 PASS 行（plan 第 2613/2628 行），没有例外。
- 本卡**没有删除任何同步**：SPIR-V 层面 producer 的 `barrier()`（shA 发布）原样保留，
  consumer 本来就没有 barrier（Workgroup Memory 0 / `OpControlBarrier` 0）；plan 层面 PASS 行数 232 → 232、

- 反向依赖：consumer 只读 gM（writer 集合 = {193}），producer 不读 gM ⇒ 该边只有 RAW 一个方向，
  由同一条 barrier 关闭；跨帧 WAR 由每帧首 barrier（434–436）关闭，未删。

   本折叠只改地址，任何一位差异都是实现错误（E 类），不是「方向无效」。
3. **最后才看整体**：两臂（base = 链头 `restore-n10-f10-next`，cand = 本卡 plan）ordinary
   `--pool --warm 1 --reps 30 --feedback`，交替 6 组 × 30 帧。归因边界：
   - 本卡只动 2 个 PASS（232 中的 2 个），且只动消息数不动字节；
   - 期望的整帧效应极小：该边每帧少 ≈59 万条消息，但 consumer 的 4× A 字节、权重字节、DPAS 全不变；
   - 按 L3/L12，2 PASS 的作用域**低于检出限**，因此本卡的判定价值是 **A/落地的二分**，不是毫秒。
4. **预注册的结论规则**（卡里写死）：native 看到 `d32x64t` 且 ordinary 为 D ⇒ 按 n16 的建议把
   「全局 store→load 布局折叠」这条轴按 **D 关闭**，不再逐站点试；native 看不到 ⇒ **A**（实现未落地），
   与方向无关。

## 8. 风险与反证（写清楚，不掩饰）

1. **IGC 可能不合并 producer 的 256 B 连续 store**（L14：SPIR-V 形状不等于消息形状）。
   若只有 consumer 侧合并，producer 侧 16 条不变 ⇒ **部分落地**；此时仍应记 A（producer 半边未落地），
   但 consumer 半边的 473,088 条/帧减少仍可独立归因。
2. **块载入后的重排 `mov` 可能比 2 条多**（A 片段是 `(16|M0)` 布局，seed 是 accumulator 布局）。
   最坏 +4/tile。若 native 看到 `mov` 暴涨（>6/tile）而消息下降，按 B 类（实现有副作用）记录，
   并只在同一站点内考虑用 `LCOL`/两半块等替代（本卡不做）。
3. **对齐证明失败**：若 IGC 无法证明 tile 基址 256 B 对齐，load 会退化成 4×128 B 或 8×32 B，
   native 签名变成 `d32x16t`/不变 ⇒ A。同一 kernel 的 seed load 已证明该形态可合并，
   所以这是低概率但必须由 native 判定的分支。
4. **收益可能被隐藏**（L12）：consumer 消息下降发生在并发 kernel 内，可能完全被其它 WG 遮住；
   这也是本卡把判定点放在 A/落地而不是毫秒的原因。
