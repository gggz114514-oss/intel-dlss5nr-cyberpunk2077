## 3. K64 → 两个 K32 片：具体方案

**切片**：父的 4 个 K16 步（j=0..3）按 key 升序切成两片 —— slice 0 = key 0..31（父 j=0,1），
slice 1 = key 32..63（父 j=2,3）。没有重排、没有转置：A 仍是 query 行（stride 64），B 仍是
key 行（stride 32），与父的消费布局同构，只是元素宽度 16→8 bit。

**累加**：两片 **累积到同一对 `CACC`（int32 8×16）**，不做片间 rescale、不做 FP32 部分和相加。
因此 int32 累加器就是 `Σ_{k=0..63} Pq[k]·Vq[k]` 的**同一个**数学量：

```
for (ki = 0; ki < 2; ++ki) {                 // 两个 K32 片
    CIAI a;  coopMatLoad(a,  shP8, m0*64 + ki*32, 64, LROW);   // 8x32 int8
    CIBI b0; coopMatLoad(b0, shV8, ki*1024 + 0,   32, LROW);   // 32x16 int8 (dim 0..15)
    CIBI b1; coopMatLoad(b1, shV8, ki*1024 + 16,  32, LROW);   // 32x16 int8 (dim 16..31)
    acc0 = coopMatMulAdd(a, b0, acc0);       // 同一 int32 累加器
    acc1 = coopMatMulAdd(a, b1, acc1);
}
```

**片间 scale 为什么必须相同**：`sP`（每 query 行）与 `sV`（每 head per window）在两片上都是常量，
所以一个累加器就够；若两片用不同 scale，就必须两个累加器 + 一次 FP32 加权和（多一个舍入点），
那是另一种数值身份。本卡刻意让 `sP`/`sV` 与片无关，从而**零片间成本**。

**dequant 只做一次**（父也只有一次 MC→MH 收窄）：`ctx[ci] = half(float32(acc[ci]) * float32(sP[row]*sV))`，
其中 `row = (lane>>4) + 2*ci`（实测 `CH`/`CI` 一致，`evidence/ABI-CHECK.json`），
`shPS[m0+row]` 是行 scale。存回地址与父逐字相同：
`gT[(w*64+m0)*256 + 32h + {0,16}]`，stride 256，LROW。

**scale 归属**：
- `sV`：每 workgroup（= 每 head 每窗口）一个 absmax，`sV=max|V|/127`，`sVinv=127/max|V|`；
  退化 `max=0` 时 `sV=1, sVinv=0`（全零 code，context=0，与父一致）。
- `sP`：**每 query 行**。row-owner 线程本来就遍历该行全部 64 个 key，取 `pmx`，然后
  `pmxq = half(pmx*inv)`。因为 half 舍入单调，`pmxq == max_i half(P_i*inv)`，所以量化后
  最大值恰为 127，`clamp` **永不削顶**（oracle 实测 0 个 clipped code）。
  `sP=float(pmxq)/127`，`qmul=127/float(pmxq)`。

**短寿命调度是否保持**：**是**。Q/K 共享一次 `gY` 加载（`ki` 循环内一个 A 给 4 个 accumulator）、
V 在其后单独一趟 —— QKV/QK 段本卡一字未改。PV 仍是“两个累加器、一次收窄、直写 gT”，
P 仍然从不落地到 global。新增的只有：`shP8`（4 KB）、`shV8`（2 KB）、`shPS/shPM`（各 256 B）、
`shVMax`（4 B），以及**复用现有 barrier 的**两处量化（§4.4）。

### 4.5 本臂 INT8 参考

`evidence/ORACLE-PV.json`（由本卡 `build/r06-c256-attn/oracle_pv.py` 在 CPU 上生成，
`numpy default_rng(20261024)`；一个 owner SG：8 query 行 × 32 dim、K=64）：

- 输入：P 的 raw exp 取在 `c256_exp_h` 的钳位区间 [1.032,1.568]（与真实核同区间）；V ~ N(0,0.5) half。
- 与父 FP16 路径（half 操作数、FP32 累加）比：**max 0.00139 / mean 0.00043 / RMS 0.000519**，
  参考 RMS 0.0727 → **相对 RMS 0.71%**；全部落在解析界内（`within_analytic_bound=true`，
  max 界 0.0088；界 = Σ|P|·sV/2 + Σ|V|·sP/2 + K·sP·sV/4 + 末次 half 收窄）。
- **非零**：P code 4,096/4,096 非零，V code 2,018/2,048 非零；`max|int32 累加| = 92,305`，
  距 2³¹ 有 23,259× 余量。
- **0 个 clipped code**；`max_i half(P_i·inv) == half(max P·inv)` 成立（所以 127 不被削顶）。

## 6. 未解决阻碍（具名）

- **GAP 0（最重要）父分叉**：232 FP16 主父用 u09（`60864afa…`，71,312 B，shared 12,288，
  38 处 FP16 MMA），与 G3/审计模块不同源。本卡的覆盖**只对 G3 臂成立**；要进 232 必须把
  E1–E9 机械移植到 u09 源，并重做父复现、10/38 处站点枚举与 SPV 差分。
- **GAP 1（QKV 6 处/模块 = 96 处）**：需要 ① 离线 `QKV` int8 权重包（N/32 × K/32 × 32×32 tile +
  per-channel scale），当前没有已验证身份（同族 `attn-own/c64/pack/*_wqkv.int8.bin` 是**另一张卡**
  的身份，本卡未核）；② Y 的 int8 输入：每 WG 是 64 token × 256 通道 = 16,384 个 half，
  要 per-token scale 的 int8 slab（或按 K32 片现算），这会把 A 的加载从 `gY` 改成 shared int8；
  ③ `96h+n` 的读取区域与新版 FP16 的 WO 重排不同，不能整包替换（GUIDE 阻碍原话）。
- **GAP 2（QK 2 处/模块 = 32 处）**：需要 int8 Q/K 在 shared + per-head q/k scale；dequant
  `sQ·sK` 要插在 bias 之前（父是 FP32 acc + bias + 一次 half 收窄），debug 的 raw logit 回显
  （`dbgf`）会变成“dequant 后的值”，需要单独定一版 debug 语义。
- **GAP 3 无 GPU**：gate（fixed/fb2）、per-pass T capture、ordinary 3×30、画质全部未跑。
  `run/r06-c256-attn/jobs.json` 只列不跑；capture 还需要一个带 16 个 `swin_NN_T` OUTPUT 的派生
  plan（本卡不越权改 pool plan）。
- **GAP 4 int8 合作矩阵从 shared 载入的 native 合法性未证**：`shared int8_t` 基址对齐
  （本卡 A 基址都是 32 的倍数、B 基址 1,024 的倍数）与 `coopMatLoad` 的 LDS 访问宽度只有设备上
  才能确认；本卡只有 `spv_validate_cpu result=0`。备选：把 `shP8/shV8` 声明成 `uint[]` 再以
  `int8_t` 视图载入（未实施）。
- **GAP 5 shP 仍在（8 KB）+ 多一次 4,096 写**：覆盖阶段刻意保留（GUIDE：性能阶段再谈
  register-P / 转置 score）。P 的量化目前在归一化循环里做（每元素一次 `roundEven`+`clamp`）；
  性能阶段可把量化搬进 row-owner（每行 64 个顺序做）、并把 `shP8` 写在 `shP` 的寿命末尾复用，
  但那会改 owner/调度，必须单独一张卡。
- **GAP 6 声明 shared +6,660 B**：可能跨 occupancy 拐点，方向未知；需要 native 的 SLM/GRF
  对照。删减顺序建议：`shPS/shPM` 折进 `shNorm`（现只用到 192/256 项）、`shV8` 与 half V 二选一。
- **GAP 7 debug 路径未变也未验证**：`p1.w != 0` 的 5 处回显地址逐字保留，但本卡没有设备回执；
  生产门 `p1.w=0`，该分支不影响覆盖结论。
- **GAP 8 V 的 half slab 仍被写**：`qkv[4096..6143]` 现在是“量化源 + debug 回显”的读者，
  不再是矩阵操作数。性能阶段可在 V 产生处直接量化并删掉 half V，但要先证明 debug 消费者退休。
