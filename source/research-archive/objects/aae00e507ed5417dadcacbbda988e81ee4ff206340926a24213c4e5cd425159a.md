# N16 Persistent / tile-chain 可达性评估（只读分析，不删任何同步）

卡 id：`n16-crossdispatch`　日期：2026-10-27
范围：232 派发、当前基线 `a024c3c5…`、现有 runner `clock_runner.exe`（源码 `work/codex-astra-fp16-int8-audit-20261024/phase-diagnosis-20261025/direct-clock/clock_runner.cpp`，只读）。

## 0. 结论（先写死）

**未完成内存模型与反馈 epoch 证明前不得删除任何整派发同步。**

在本工程当前形态下，persistent / tile-chain **不可达**：不是"还没有试"，而是 **runner 的执行模型里没有可承载它的机制**——每帧一个 command buffer、232 个 `vkCmdDispatch`、每个派发之后一条全量 `vkCmdPipelineBarrier`，派发之间不存在设备端 flag/epoch/等待协议；`--feedback` 是主机侧逐帧 buffer copy，不是设备端 epoch。要做 persistent，必须先改 runner（超出本卡与合同授权），并且先补齐第 4 节的五项证明。

## 1. 现状：runner 实际做什么（逐条可核对）

### 1.1 派发之间：一条全量 barrier，没有别的

`clock_runner.cpp` 430–475：

```cpp
for(int rep=-warm; rep<reps; ++rep) {          // 430 每帧
  ...
  for(size_t passIndex=0; passIndex<plan.passes.size(); ++passIndex) {   // 451
    ...
    vkCmdDispatch(command, pass.gx, pass.gy, pass.gz);                   // 471
    barrier(VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT,                        // 472
            VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT,
            VK_ACCESS_SHADER_WRITE_BIT,
            VK_ACCESS_SHADER_READ_BIT|VK_ACCESS_SHADER_WRITE_BIT);       // 473
  }
}
```

即：**每两个相邻 PASS 之间都有一条 src=SHADER_WRITE、dst=READ|WRITE 的 `vkCmdPipelineBarrier`**，外加帧首一条同型 barrier（434–436）。当前 232 派发的正确性（跨 PASS RAW/WAR/WAW）**就是靠这条 barrier 关闭的**；它同时承担了执行依赖（execution dependency）与内存可见性（memory dependency）两件事。

### 1.2 plan 语法里没有 persistent 构造

`clock_runner.cpp` 78–130 的解析器只认：

| 行 | 语义 |
|---|---|
| `BUFFER` | 502 个 buffer（名字/字节/冷数据路径） |
| `PASS` | 一个 PASS = 一个 SPV + subgroup + shared + grid；**没有多 PASS 合并、没有 indirect、没有 workgroup 计数** |
| `BIND` | 每个 PASS 的 binding/资源/偏移/字节 |
| `PUSH` | ≤32 个 dword push constant |
| `OUTPUT` | 回读缓冲 |
| `POLICY` | 池化分配：resident / firstPass / lastPass / clear（**寿命**，不是持久化） |
| `HISTORY` | feedback 的 source/destination/offset/bytes/controls（见 1.3） |

解析器还会拒绝：`pass.shared > 49152`、`subgroup != 32`、`npush > 32`、未覆盖的 152 个 native row。**没有** `PERSISTENT`、`WORKGROUP`、`COUNTER`、`EPOCH`、`INDIRECT` 之类关键字，也没有 `vkCmdDispatchIndirect` / timeline semaphore / device-side queue 的加载或调用。

### 1.3 feedback 是主机侧、每帧一次，不是设备端 epoch

`clock_runner.cpp` 437–449 + 468：

```cpp
if(feedback && frame>0) {
  if(plan.history.size()!=2) throw ...;                  // 438 必须恰好 2 条
  for(auto& h:plan.history) {
    vkCmdCopyBuffer(... h.sourceOffset -> h.destinationOffset, h.bytes);  // 444
    vkCmdUpdateBuffer(... h.controlsOffset+8*4, 4, &enabled);            // 445 写 float 1.0
  }
  barrier(COMPUTE->TRANSFER); barrier(TRANSFER->COMPUTE);                // 439/447
}
...
if(feedback && frame>0 && passIndex==0) { push[22]=frame; push[23]&=~4u; }  // 468
```

当前 plan 的两条 HISTORY（`plan.txt` 尾部）：

```
HISTORY 483 452 14745600 14745680 14745600 14745600
HISTORY 483 478 14745600 14745680 14745600 14745600
```

含义：`frame_out`（resource 483）在**上一帧结束后**由主机拷到两个 feedback buffer（452/478），并在目标 `controlsOffset+32` 写 1.0；**第 0 帧不拷、flag 保持冷数据**。所谓 epoch 只有 `push[22]=frame` 这一个整数和 `push[23]` 的 bit2，**全部由主机在 pass 0 之前写入**；设备端没有任何 epoch 自增、没有跨派发 flag、没有 acquire/release。

### 1.4 runner 没有启用 device-scope 内存模型

`clock_runner.cpp` 539 的 receipt 是**硬编码字符串**（不是查询结果）：

```cpp
"vulkan_memory_model_enabled": true,
"vulkan_memory_model_device_scope_enabled": false,
"vulkan_memory_model_availability_visibility_chains_enabled": false
```

无论硬件是否支持，**runner 没有使用** device-scope / availability-visibility chains。任何设备端 flag/epoch 协议都需要这两类能力或等价的 release/acquire 原语；在当前 runner 下没有落地路径。

### 1.5 内存池只做寿命，不做跨帧持久

`POLICY` 的 `resident/firstPass/lastPass/clear` 只影响池化分配与每帧首次使用前的清零（453–462）。`clearFirst` 的 buffer 在每个 replay 的 firstPass 前被 `vkCmdFillBuffer` 清零——这本身就和"跨帧保留状态"矛盾；persistent 设计若依赖跨帧保留，必须先逐 buffer 关掉 clear 并证明首帧语义。

## 2. persistent / tile-chain 需要哪些全局激活

按依赖顺序：

| # | 激活项 | 现状 | 缺口 |
|---|---|---|---|
| G1 | **device-scope 内存模型** + availability/visibility chains | runner receipt 明确 false | 需要改 runner 的 instance/device 创建与着色器内存语义；本卡无权 |
| G2 | SSBO 上的 **device-scope atomic / release / acquire**（GLSL `atomicAdd`、`memoryBarrierBuffer`/`cooperativeMatrix` 之外的显式语义） | 当前 232 个 SPV 只有 `fence.slm`/`signal barrier`，无 device-scope atomic | 需要新的 SPIR-V 内存语义与驱动支持验证 |
| G3 | **全局 work counter / tile queue**（一个 SSBO，原子领取 tile） | 不存在 | 需要新 buffer + 新 push 契约 + 所有 PASS 改造 |
| G4 | **persistent grid 尺寸** = 可常驻 WG 数，且 WG 之间前向推进有保证 | runner 按 plan 的 grid 逐 PASS 派发，无法指定"常驻 N 个 WG 循环取 tile" | 需要 occupancy 查询与新的派发模型；Vulkan compute 没有 cooperative launch/grid sync |
| G5 | **多 PASS 合并进一个 dispatch**（tile-chain 的最小形态） | plan 模型 1 PASS = 1 SPV；runner 无 multi-entry / device-side launch | 需要 runner 支持（或把多个 SPV 链接成一个 kernel） |
| G6 | **发布 flag/epoch**（producer 写数据 → release 写 flag；consumer acquire 读 flag → 读数据） | 只有主机侧 HISTORY copy + `push[22]` | 需要 G1+G2+G3，并证明 flag 与数据的先后序 |
| G7 | **等待协议**（spin/backoff/超时/死锁避免） | 无 | 需要 G4 的前向推进保证；B580 的 WG 调度顺序不可假设 |
| G8 | **反馈 epoch**（跨帧历史只能来自上一帧，不能是本帧或两帧前） | 主机 copy + `frame>0` 门 | 需要证明设备端 chain 不跨帧、不与 clear/alias 竞争；见第 4 节 P5 |

结论：G1–G5 全部缺失，且都落在 runner/工具链层，不在"改 shader"能解决的范围内。**当前不可达，不是候选问题。**

## 3. 如果要设计发布 flag/epoch 与等待协议（只在证明后）

最小协议应满足（写成可检查项，不是实现）：

1. **单写者 per tile**：tile 的 owner 由 `atomicAdd(counter,1)` 唯一领取；领取本身是 acquire，保证看到上一 epoch 的 retire。
2. **数据先于 flag**：producer 的所有数据 store 必须在 flag store 之前对 device 可见（release semantics 或 `memoryBarrier` + release store）；consumer 必须 acquire 读 flag 后才能读数据。
3. **epoch 单调、可回绕**：epoch 是 32-bit 且每帧 +1；比较必须用模运算且证明"落后一帧以上"不会被误判（ABA）。
4. **retire 协议**：consumer 读完 tile 后写 retire flag；producer 下一帧复用该 tile 前必须等 retire（WAR），等待必须有上限并证明不会饿死。
5. **首帧与 feedback**：frame 0 没有 HISTORY copy，flag/epoch 的初值、清零与"第 0 帧不做历史混合"的语义必须与 `clock_runner` 的 `frame>0` 完全一致；否则 fixed/fb2 gold 会直接变。
6. **失败可回滚**：任何协议错误必须能退回"232 派发 + 全 barrier"的现役形态，且 fixed/fb2/ordinary 三套 gold 可复现。

## 4. 删除任何整派发同步之前必须先证明的五件事

> 这五条是"未完成内存模型与反馈 epoch 证明前不得删除任何整派发同步"的具体化；缺一条就不许删 barrier。

1. **写域与别名（P1）**：每个 buffer 在每个 epoch 的写者集合、每字节写次数（恰好 1 次或证明幂等）、所有读者集合；池化分配的 `firstPass/lastPass/clear` 与 `vkCmdFillBuffer` 不得与持久状态重叠；`POLICY` 502 行逐条核对。
2. **可见性与顺序（P2）**：producer 的数据 store 与 flag store 之间、consumer 的 flag load 与数据 load 之间，必须由 device-scope release/acquire（或等价 barrier）建立 happens-before；当前 runner 的 `device_scope=false` / `availability_visibility_chains=false` 必须先变成 true 并有捕获证据。
3. **epoch / flag 正确性（P3）**：epoch 单调、无 ABA（回绕证明）、单写者、flag 的初值与清零、`push[22]=frame` 与 `push[23]&~4` 的语义在设备端协议里逐条复现；flag 不能在数据之前可见，也不能永久停在"未发布"。
4. **前向推进与活性（P4）**：spin-wait 不会死锁；不能假设 WG 调度顺序、不能假设所有 WG 同时常驻；必须有超时/退避与"tile 被放弃"路径；在 B580 的 EU/线程组占用下给出最坏情况上界。
5. **反馈 epoch 与数值等价（P5）**：跨帧历史只能来自上一帧；`HISTORY` 的两条 copy（source 483、dest 452/478、offset 14745600→14745680、80 B 位移、controls 在 `+32`）与 `frame>0` 门必须在设备端协议下保持同一语义；fixed（`1755e9c2…`）、fb2（`9c3e511e…`）、ordinary（`2b63d4ba…`）三套 gold 逐位不变，且 per-PASS 归因仍可分离。

## 5. 可达性分级（给下一轮的顺序，不是候选）

| 级别 | 形态 | 需要 | 现在能做吗 |
|---|---|---|---|
| L0 | **不跨派发**：保留 232 派发与全部 barrier，只把 producer store 折成 consumer load 布局 | 无（barrier 不动） | 是，见 `REPACK-CENSUS.md`；唯一建议的 S5 代表卡 |
| L1 | 两个相邻 PASS 合成一个 dispatch（共享 SLM / 寄存器直交） | G5（runner 多 entry 或链接 kernel）+ 工作组内同步证明 | 否（runner 不支持） |
| L2 | tile-chain：全局 counter + flag/epoch + spin | G1–G4 + P1–P4 | 否 |
| L3 | 整帧 persistent：一个常驻 kernel 跑完 232 个逻辑 PASS | G1–G7 + P1–P5 + 反馈协议 | 否 |

**当前唯一可做的是 L0**，且 L0 不删除任何整派发同步——它只改 store/load 地址。
