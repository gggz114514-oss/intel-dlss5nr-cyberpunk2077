## 1. 映射：每个 (lane, component) 到底代表哪个 (token, channel)？

GEMM 是转置形式 `C^T[N,T] = W[N,K] · GT^T[K,T]`，`M=8`（channel）× `N=16`（token）。`t0 = 32·WG.x`，`n0 = 64·WG.y + 16·sg`，因此 **16|t0、16|n0**，一个 SG 的 4 个 acc 落在同一个 16×16 supertile 的 4 个象限：

| store | acc | token 范围 | channel 范围 | 元素 | 相对 `ob` 偏移（half） | 偏移（byte） |
|---|---|---|---|---|---|---|
| 0 | c00 | t0+0 … t0+15 | n0+0 … n0+7 | 128 | 0 | 0 |
| 1 | c01 | t0+16 … t0+31 | n0+0 … n0+7 | 128 | 8192 | 16384 |
| 2 | c10 | t0+0 … t0+15 | n0+8 … n0+15 | 128 | 8 | 16 |
| 3 | c11 | t0+16 … t0+31 | n0+8 … n0+15 | 128 | 8200 | 16400 |

元素级映射：`coopMatStore(h,go,base,16u,COL)` 的 stride=16 COL ⇒ 元素 (m=channel, j=token) 落在 `base + j*16 + m`。代入 `base = ob + Δ` 得 `地址 = ob + Δ + j*16 + m`，而 `tiled(t0+j, n0+m, 512)` 在 `16|t0`、`16|n0`、`j<16`、`m<8` 下**恒等于**同一式。也就是说：

> **producer 每个元素写到的地址，就是消费者用 `tiled(token,n,512)` 读该元素时的地址。** 这既是“地址已折叠”的证明，也是本卡改动地址代数而不改语义的前提。

- lane/component：ISA 实测 `(16|M0)`、`wr:1+4` ⇒ **每条 store 16 条活跃 lane，每 lane 4 dword = 8 个连续 half = 一个 token 的 8 个 channel**；lane 索引 = token 索引 j，lane 内 component = channel 索引 m。本卡没有改 store 的 opcode / stride / layout / lane mask，因此 lane→(token,channel) 的物理分配与父**同构**（不是“重新证明”，而是“不可改变”）。
- 消费者：ordinal 64 `split16_b24_l0`，`coopMatLoad(a, gx, tiled(token,0,512)+(k/16)*256, 16u, ROW)`，MA=8×16 ROW stride 16 ⇒ 一次读 8 token × 16 channel（每 token 32 B 连续）= **生产者 store 0+2（或 1+3）恰好拼满一行**。因为 `tiled(t,0,512)+(n/16)*256 = tiled(t,n,512)`，消费者的行基址 + 常量 K 块偏移 = producer 的 `ob`。
- 覆盖证明（穷举，非抽样）：264 WG × 4 SG × 4 象限 × 16 token × 8 channel = **540672 = 1056×512 个元素，全部恰好写一次**：duplicate 0、missing 0、out-of-range 0、象限地址等式 4224 次全过。见 `PROOF-ALGEBRA.json` / `build.py::supertile_algebra`。
- 尾块：token 维 `33×32 = 1056` = 真实 token 数（44×24），**没有半 tile**；padding 区 1056…1151 本 PASS 从不写（改前改后一致）。channel 维 `8×64 = 512` 整除。`half_tail` 边缘路径在 `-DKIND=1` 下不参与任何一臂。

## 2. 删了什么真实工作（正常执行路径，不计 debug、不计编译器已消掉的东西）

先给结论：**F11 的“末次 store”本身已经到底了**——4 条 16 B/lane 的直接 store 消息，100% 象限覆盖、无半块、无 repack 通道、无标量逐元素 global 写。真正还留在正常路径上的、属于“地址重算”的重复工作只有下面这些，本卡全部删掉：

| # | 删的内容 | 父 → 候选 | 依据 |
|---|---|---|---|
| R1 | 函数体内 `tiled()` 调用指令（`OpFunctionCall`） | 18 → 2 | SPIR-V opcode 直方图（源码 10 处 → 2 处，glslang 对 load/store 索引各复制一次） |
| R2 | `OpIAdd`（地址/索引） | 47 → 21（−26） | 同上 |
| R3 | `OpIMul` | 15 → 7（−8） | 同上 |
| R4 | `OpUDiv`（`tiled()` 里的 /16） | 13 → 5（−8） | 同上（`OpUMod` 仍 3，因为 tiled() 还剩 2 次求值） |
| R5 | glslang 传参临时量 `OpVariable`（Function 存储类） | 81 → 41（−40） | `SPV-INTERFACE.json` |
| R6 | 这些临时量的 `OpLoad` / `OpStore` | 106→83 / 91→54 | 同上 |
| R7 | 函数体指令总数 | 449 → 291（−158，−35.2%） | `BUILD.json` |
| R8 | 模块指令数 / 体积 | 745→548 / 12396→9000 B | 同上 |

**没有删、也不打算删的**（逐条核对，避免把“看起来能省”当成收益）：134 条 load 消息、128 条 `dpas.8x8`、4 条 store 消息、4 次 `MC→MH` 转换、4 次残差 seed 的 `half(y*scale)` 乘、32 次 `sync.allwr` 类累加器链同步、任何屏障、任何 lane mask、任何 WG 数。

为什么 `tiled()` 值得删而不是“编译器自己会省”：glslang 不做 CSE，`tiled()` 被保留为真实函数，10 处调用各带 3 个参数，参数经函数作用域变量传递（R5/R6 的来源）。IGC 之后会 inline + mem2reg，所以 R5/R6 不会变成内存流量；**能落到 ISA 的只有 R2–R4 中它没有折叠掉的部分**——这点在 Q5 里给判据，不在 Q2 里假装已发生。

## 3. 重叠：独立工作原来怎么重叠，改动有没有破坏供料

本 kernel 只有一条“K 环”和一条“累加器链”，没有跨阶段并行的独立流；每个 acc 的 32 次 DPAS 是串行 RAW 链，4 个 acc 之间互相独立，靠 4 个 DPAS 交替发射得到重叠。

| 值/流 | 生产者 | 消费者 | 覆盖者 / 重定义 | 关系 | 本卡是否改变 |
|---|---|---|---|---|---|
| `c00..c11` | seed `MC(h*scale)` | 各自 32 次 DPAS | 下一次 DPAS | RAW（同 acc）+ acc 间并行 | 否 |
| `a0`（channel n0..n0+7，16 K） | `coopMatLoad`（每 K 步） | `c00`、`c01` 两次 DPAS | 下一 K 步的同一源码变量 | RAW，尾部 WAR（跨步） | 否（复用对不变） |
| `a1`（channel n0+8..n0+15） | 同上 | `c10`、`c11` | 下一 K 步 | 同 `a0` | 否 |
| `b`（16 K × 16 token） | `coopMatLoad(xo0)`，再 `coopMatLoad(xo1)` | 前 2 个 DPAS / 后 2 个 DPAS | 同一步内第二次 load | 步内 **WAR**（覆盖前必须已被两次 DPAS 读完） | 否（两条 load 与 4 个 DPAS 源码顺序未动） |
| `wo,xo0,xo1`（uniform 字节偏移） | 环前一次初始化 | 环内 4 个 load 站点 | 每步自增 | 新增 RAW 链（标量） | **新增**，见 Q4 |
| `ob,o00..o11`（uniform 超块地址） | 一次 `tiled()` | 4 次 seed load + 4 次 store | 无 | RAW 一次 | 值不变，求值次数 8→1 |
| `scale0/scale1`（channel 增益） | COL stride0 广播 load | seed 乘 | 无 | RAW | 否 |
| store 目标 `go` | 4 条 store | 下一 dispatch（ordinal 64 的 A 片段） | 无（本 kernel 内无 go 回读） | 跨派发 RAW | 否（地址等式已证） |

要保护的是“供料”：本卡一个 load 的**字节地址**都没变（穷举证明），所以 A/B 供料时序、权重读取量、每输出 K 序全部保持；唯一的时序变化是地址标量更早算完（利）与 3 个偏移标量活得更长（弊），两者都记账。

补充两条合同要求但本 kernel 不存在的项（写明“不存在”，不是漏答）：

- **A / 每块 B**：本 kernel 只有一对权重 A 片段（`a0`=channel n0..n0+7，`a1`=n0+8..n0+15）与两块 B（`b` 依次表示 token t0..t0+15 与 t0+16..t0+31），一个 SG 一对 A 供两块 B（这正是“成对权重跨 M 块复用”的**现有**形态，第二方向只是把它扩到更多 M 块）。本卡未改这个配对结构。
- **norm / den**：F11 没有 norm、没有 den、没有 softmax、没有 bias；这些在 F09/F10/F12 各自的 kernel 里。F11 的“残差”是累加器 seed（`half(y*scale)` 直接进 acc），本卡未回退它。

## 5. 是否真落到 native：预测 + 判据（我没有 GPU，不写“已证明”）

完整清单见 `NATIVE-PREDICTION.md`。摘要：

- 期望看到：`add` 254 → 235…254、`mul` 88 → 80…88、静态指令数 995 → 975…995、`shl 11 / shr 2 / or 31` 里地址相关部分小幅下降；4 条 `store.ugm.d32x4` 的偏移操作数变成同一基址 + 常量 {0,16,16384,16400} B。

## 6. 整体是否更快：测什么、怎么归因

老实说的量级边界（先算清再测，避免把 0.003 ms 当作新收益）：

- F11 全组 15 个 PASS 的单 PASS GpuTime 合计 ≈ **0.211 ms**（fixed 0.211349 / fb2 0.211138，单硬件通道 warm0 上下文，**不是** ordinary 帧时间）。
- 本卡能触到的只是其中“地址代数”那一层：SPIR-V 整数运算 −42 / 函数体 −158，在 995 条 ISA 里即使**全部**落地也只有约 4%；而 IGC 大概率已折掉大半 ⇒ 合理预期是 **0–1.5%，即 ≤0.003 ms**，在 ordinary 分辨率（~0.1 ms）以下。
- 因此本卡的正确用法是：**per-dispatch GpuTime 观察 + 静态 ISA 差值**为主要证据，ordinary 只用来确认“不退化、gold 不变”。**不允许**把这一项计入“新增收益”再与 F10 的 0.422 ms 相加。

臂与顺序（主代理执行）：
1. fixed 门 + fb2 门（frame0 与 frame1 都要核）：`fixed=1755e9c2…29d6`、`fb2末帧=9c3e511e…d3536`；
2. native（static ISA diff，主证据）+ resources（scratch/shared 是否仍 0）；
3. ordinary：两臂 6 组交替、warm1/reps30/feedback，样本全留，按组均值差算 CI；
4. 归因只写证据支持的部分：*若* ISA 静态指令下降且 per-dispatch GpuTime 同向，可归因“地址重算删除”；若 ISA 不变，整体计时**不得**解释成该方法无效（判 A）。
5. 建议的成包方式：F11 单点作用域小，若同族（F09/F12/F14/F16 的 tiled 地址重算）实测同向，再按 family 包测整体；禁止挑显著样本。
