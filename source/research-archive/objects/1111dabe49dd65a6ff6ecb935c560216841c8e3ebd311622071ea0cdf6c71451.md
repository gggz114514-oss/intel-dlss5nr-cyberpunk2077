## 3. 本臂 INT8 参考状态

- 局部 oracle：`evidence/ORACLE-PV.json`，由本卡在 CPU 上用与 shader 相同的公式生成（一个
  owner SG：64 key × 32 维 × 16 query，`numpy default_rng(20261024)`）。
  **非零**：V 的 int8 码 2021/2048 非零，P 的 int8 码 1002/1024 非零；int32 累加最大
  29615（远小于 2^31，不会溢出）。
- 与父 FP32 路径（半操作数、FP32 累加）比较：绝对误差 max 0.0108 / mean 0.00175；
  RMS 0.00231 vs 参考 RMS 0.1526 = **1.51%**；全部落在解析界内
  （`within_analytic_bound=true`，界 = (sV/2)·Σ|P| + (sP/2)·Σ|V|）。
- **没有过**任何设备侧门：这是本臂参考，未在 GPU 上验证；`GATE` 未跑。

概率如何重新量化 / scale 归属 / 是否保持原 P 寄存器交接（`evidence/PV-INT8-SCHEME.json`）：

- **P 的输入与父逐字节相同**：`P := half(P*inv)`，树、倒数、单次 half 舍入都没动。量化输入正是
  FP16 消费者会拿到的那个 half 值。
- **P 的 scale 归 per-query（输出列）**：`pmx` = 该 query 在 64 个 key 上的最大 P；一个
  lane 拥有每个 8-key 块的 4 行、其伙伴 lane（`lane^16`）拥有另 4 行，所以**一次
  `subgroupShuffleXor(pmx,16)`** 就闭合该列。`sP = pmx/127`，量化倒数 `127/pmx`，全在 lane 内，
  不进 shared、不做广播。
- **量化只做一次**：每个 P 元素一次 `roundEven` + clamp[-127,127]（`i8code`，与实测 adapter
  同一 helper），一个 8-key 块的 4 个元素打包成 32-bit 码字的 byte 0..3；`i8_join_B` 只做
  byte 路由，**不重新量化**。
- **退化保护**：`pmx==0` 时量化倒数与 dequant 都取 0，避免 `0*inf`。
- **不会饱和**：`P ≤ 1` 恒成立（`P = exp·inv`，`inv = 1/max(Σexp, 2^-14)`，故
  `max P ≤ Σexp/max(Σexp,2^-14) ≤ 1`），所以 `pmx·(127/pmx) = 127` 永远不越界。
- **两片 K16 → K32 INT8 B**：父的 4 个 K16 站点（j=0..3）变成 2 个 K32 站点；
  slice 0 = key 0..31 =（p00,p01,p10,p11），slice 1 = key 32..63 =（p20,p21,p30,p31）。
  两片共用同一个 sP，所以 INT32 累加仍是同一个数学量。
- **P 寄存器交接保持**：P 从不落地。代价从父的 96 次 group shuffle/owner（4 个 B × 8 组件 ×
  (1+2)）降到 32 次（2 个 B × 16 组件 × 1），因为 int8 侧取的是码字里的 byte，不需要
  `nrh_unpack2` 的 up/down 交换。
- **V 的 scale 归 per-workgroup（= per head per window）**：`shVMax` 在现有 norm pass 里由 64 个
  owner 线程各读 32 通道做 `atomicMax`，被**现有**的 norm 后 barrier 发布；量化本身在**现有**的
  scale pass 里做 stride-1 拷贝（`sv8[k]` 与 `qkv[4096+k]` 是同一个 `ch*64+tok` 索引），被
  **现有**的 scale 后 barrier 发布。**barrier 数 4 → 4，没有新增。**

## 6. 未解决阻碍（具名）

- **GAP 0（最重要）：父模块身份分叉。** 当前 FP16 主父 plan（232 PASS，`772e14bf…`）的这 8 个
  PASS dispatch 的是 **u09 构建**
  `candidates/zcode-fp16-compute-backend-20261021/u09-join-wide-c64-attn-v1/spv/b3_20_c64_ownership_fp16.spv`
  （47304 B，`95498306…`，shared 12288，源码 19230 B），**不是**审计 R04 所指的部署模块
  （46692 B，`1755889b…`，shared 12800，源码 17217 B）。两者静态 MMA 分布相同（6/1/16），
  但 norm 组织不同（u09 没有 `shNorm`，用 `nr_norm_qk_pair` 寄存器交接）。本卡的候选由审计所指
  模块派生，因此**不能直接换进 232 父 plan**——那会顺带改 norm。下一步：把同样 12 条改动
  （C1–C12）机械地移植到 u09 源，重做 u09 的逐字节父复现与 SPV 差分，再替换 232 的 8 行。
- **GAP 1：QKV 的 INT8 权重包没有已验证身份。** 需要 `N/32 × K/32 × 32×32` int8 tile +
  per-channel scale 的离线 pack；同族支撑卡
  `candidates/dsh-int8-same-family-20261023/attn-own/c64/pack/swin_{5,6,7,8,62,63,64,65}_wqkv.int8.bin`
  存在且已有源级候选，但那是**另一张卡**的身份，本卡没有验证其 pack 与 plan 的对应，也没有
  它的 gate。
- **GAP 2：QK 需要 shared 里的 int8 Q/K + per-head scale。** A 若是 shared 的 int8，直接按
  stride 32 LROW 载入即可（int8 A 映射正好是"每 lane 一个 K 列"），B 同理 LCOL stride 32；
  但 score 的 dequant（`sK·sQ`）要插在 bias 与 `c64_exp_h` 之间，且 debug 的 logits 回显地址
  会变成"dequant 后的值"——需要单独定一版 debug 语义。本卡未做。
- **GAP 3：没有 GPU 时段。** gate（fixed/fb2）、per-pass T capture、ordinary 3×30、画质都未跑；
  `run/r04-c64-attn/jobs.json` 只列不跑，per-pass capture 还需要给 8 个 PASS 加 resident OUTPUT。
- **GAP 4：int8 合作矩阵从 shared 载入的 native 合法性未证。** `shared int8_t sv8[2048]` 的基址
  对齐（本卡的 A 基址都是 32 的倍数）与 `coopMatLoad` 的 LDS 访问宽度只有在设备上才能确认；
  本卡只有 `spv_validate_cpu result=0`。若驱动要求更严的对齐，可把 `sv8` 声明成 `uint[512]`
  再以 `int8_t` 视图载入（未实施，先记为备选）。
- **GAP 5：per-query 单 scale 的数值代价。** 局部误差 RMS 1.51%（本卡 oracle，非门）。若 gate
  判定不可接受，可选的**同一 ABI 内**改进是把 V 的 scale 从 per-head 细到 per-dim（需要 32 个
  float 的 shared 发布，多一次 barrier），或对 P 用 K32 片内一致的更细尺度（数学上要求两片共
  一个 sP，因此只能 per-query，不能 per-片）。这些都没有实施。
- **GAP 6：`sv8` 的删除时机。** 父的 half V（`qkv[4096..6143]`）在改动后只剩 debug 回显一个
  读者。为了保持 debug 输出逐字节不变，本卡保留了它；优化阶段可在 `pc.p1.w==0` 的编译期/运行期
  分支下去掉 half V 的写，但那会改 QKV 段（本卡明确不碰）。
