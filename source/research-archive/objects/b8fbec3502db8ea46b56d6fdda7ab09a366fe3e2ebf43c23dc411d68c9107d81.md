## 3. 每段的 scale 契约（Q/K/V/P 粒度、K 内是否恒定、INT32 界、K32 对齐、padding、量化、反量化位置）

完整表在 `evidence/SCALE-CONTRACT.json`，这里是摘要。**Swin 契约：P 先归一化再进 PV**（`P := half(P*inv)`，sealed 分母树，然后才量化）。ViT 契约（未归一化 P 进 PV、整块后做一次 reciprocal）**没有使用**，也没有碰任何 ViT 模块。

| 段 | 操作数 A（动态） | A 的 scale 粒度 | 操作数 B | B 的 scale 粒度 | K 内恒定 | INT32 解析界 | K32 对齐 / padding | 量化 | 反量化位置 |
|---|---|---|---|---|---|---|---|---|---|
| QKV | 本 workgroup 的 64×256 Y tile，half→shared int8 | **per-workgroup（= 每窗口每 head）一个标量**：对 16 384 个 Y 取 absmax | 离线 int8 W pack（本 PASS 自己的 BIND 0 窗口） | **per 输出通道** `sW[96h+n]`（768 个/PASS） | 是（A 一个标量、B 每列一个） | `K·127·127` = **4 129 024** | A 基址 `m0·256 + 32k`（32 B 的倍数）、stride 256 B；B 基址 `(96h+n0)·256 + 32k`、stride 256 B；**无 padding**（K=256=8×K32，N=96=6×16，64 token 全部由生产者真实写出，图像 OOB token 也是真值） | `roundEven(float32(v)·(1/s))` clamp ±127；权重 `rint(W/s)` clamp ±127 | `(int32·sW[n])·sY` 一次 FP32 乘链，紧接唯一一次 `MAT_H` 窄化，落在父的 6 个 store 地址 |
| QK | Q 行 8×32（shared int8） | **per-workgroup（每窗口每 head）** 该头 **post-scale** Q 片 absmax | K^T 32×16（shared int8） | **per-workgroup** 该头 **post-scale** K 片 absmax | 是（整个 K32 点积一个标量 `sQ·sK`） | `32·127·127` = **516 128** | 1 个 K32（父要 2 个 K16）；A 基址 `m0·32`、B 基址 `n0·32`、stride 32 B；**无 padding**（head dim 恰 32） | `roundEven(v·(1/sQ or 1/sK))` clamp ±127，**输入是父自己 post-scale 的 half 值** | `int32·(sQ·sK)`，加在 FP32 bias **之前**（`precise float biased = acc[ci] + bias[ci]` 原样保留），在 `MAT_H` 与 `c256_exp_h` 之前 |
| PV | P 行 8×32（shared int8，量化自归一化后的 half P） | **per-query 行**：该行**已舍入** half P 的最大值 | V 32×16（shared int8，key-major） | **per-workgroup** | 是（`sP[row]·sV` 一列一个标量；两片 K32 共用同一 sP/sV） | `64·127·127` = **1 032 256** | 2 片（key 0–31 / 32–63）；A 基址 `m0·64 + 32·slice`、stride 64 B；B 基址 `slice·1024 + {0,16}`、stride 32 B；**无 padding**（64 key = 2×K32） | 同上；P 的码最大值恰为 127（`half` 单调 ⇒ `max_i half(P_i·inv) == half(pmx·inv)`），clamp 永不削顶 | `half(float32(int32)·(shPS[row]·sV))`，每分量一次，落在父的两个直写 `gT` 地址 |

**"不得把静态权重 scale 当动态 Q/K 尺度"**：`sY`、`sQ`、`sK`、`sP`、`sV` 全部来自本次 dispatch 自己的数据（`atomicMax` 或寄存器 `max` 链）；唯一预计算的是 `sW[n]`，而它只乘**权重**操作数（BIND 9 的列向量）。

**"浮点残差 seed 不得丢进 INT32 累加"**：本模块没有任何残差 seed 进入整数点积。QKV 段没有残差；QK 的 bias 在**反量化之后**用 `precise float` 加；PV 段没有残差，P 的归一化 reciprocal 作用在 half P 上、**在量化之前**。

**INT32 不溢出（解析 + 实测）**：解析界即"所有项同号取满"的最坏情形（`±127²` 逐项相加），不依赖数据分布；**解析界本身**距 `2^31-1 = 2 147 483 647` 还有 **520×（QKV）/ 4 161×（QK）/ 2 080×（PV）** 余量。实测（`evidence/REF-attention.json`，block16 真实非零数据 4 窗口 × 8 head）int32 累加绝对值最大 **QKV 108 938 / QK 50 309 / PV 100 838**，占解析界 **2.64% / 9.75% / 9.77%**，距 2^31-1 **19 713× / 42 686× / 21 296×**。

**softmax / 归一化 / P 归一化顺序与父逐项相同**：`c256_norm_sum32`（half 平方 + half S4 树）、`shNorm = half(inversesqrt(max(s, half(0.000062))))`、父的 scale 表达式（`half(half(Q*nq)*sh)` 两次舍入、`half(K*nk)` 一次舍入，**逐字保留**）、`c256_exp_h` 位构造、sealed 分母树（`t_j[c]=P[16j+c]+P[16j+c+8]`、`part[c]=((t0+t1)+t2)+t3`、`even+odd`）、`inv = half(1/max(float(s), 6.103515625e-05))`、`P := half(P*inv)`。本卡**只改操作数 dtype**：这些代码路径一字未动，它们拿到的 logits 变成"反量化后的 int32 点积"，这是换 dtype 的必然结果，不是重新设计。

| **fp16（部署算术，逐行转录）** | **0.1363%** | **57.31 dB** | 0.00781 | 0.9999991 |
| 仅 QKV int8 | 1.8866% | 34.49 dB | 0.04260 | 0.9998223 |
| 仅 QK int8 | 1.0478% | 39.59 dB | 0.01855 | 0.9999451 |
| 仅 PV int8 | 1.5668% | 36.10 dB | 0.02148 | 0.9998772 |
| QKV+QK int8（本卡新增部分） | 2.1027% | 33.54 dB | 0.04346 | 0.9997796 |
| **全 int8（QKV+QK+PV，= 候选）** | **2.6440%** | **31.55 dB** | **0.04480** | **0.9996509** |
| 研究臂：全 int8 + **per-token** Y scale（候选未采用） | 2.4452% | 32.23 dB | 0.03906 | 0.9997010 |

- **转录保真度 0.1363%**：这是 fp16 臂（与父源逐行同构）与捕获 T 的差，比 int8 效应（2.64%）小 **19 倍**，所以上面的比较有意义。它**不可完全解释**：CPU 上无法复现的两处设备近似是 `inversesqrt`（nq/nk 的取整位置）与一次 coopmat K16 点积内部的 FP32 加法顺序；二者都可能让 logits 偏 1 个 half ULP，而 `c256_exp_h` 只取 mantissa 的低 10 位、把 y 的 1 ULP 差放大到 P 的约 1/400 相对差。**本卡不声称已把 0.1363% 归因到哪一项**（具名缺口，见 §7 GAP 2）。
- 饱和/边界：**所有操作数的 clamp 计数都是 0**（Y、W、Q、K、P、V 逐一统计，`clamped=0`；`pre_round` 少量非零只表示 `v·inv` 在取整前略超 127，取整后仍为 127，clamp 不改变任何码）。P 的最大码恰为 127，验证了"per-query scale 取自已舍入 half 的最大值 ⇒ 永不削顶"的论证。
- 码利用率：W 776 416/786 432 非零（98.7%）、Y 225 912/524 288（43.1%）、Q/K ≈ 28 400/65 536（43%）、P 128 602/131 072（98.1%）、V 28 327/65 536（43%）。Y 的非零率偏低是数据本身的性质（layer-norm 后的尖峰分布 + 部分 token 整行为零），也是 per-tile 有代价的直接原因（下一行）。

**per-tile 的代价是可测量的**：把 QKV 的 A 尺度换成 per-token（研究臂，**候选未采用**），同一捕获上 rel_L2 从 2.6440% 降到 2.4452%（0.20 个百分点）。per-token 版要在 epilogue 里按行施加因子，需用到 int32 累加器的 lane/component→(row,col) 映射（r04-r05 卡实测过 CH==CI，但本卡不为一个未在本模块实测的映射假设押注），因此选择 per-workgroup。这是**同一 ABI 内**的第一优化项。

## 7. 未解决阻碍（具名）

- **GAP 1 没有 GPU 时段**：`jobs.json` 只列不跑（`r06cd-diag-001`、`r06cd-gate-fixed-001`、`r06cd-gate-fb2-001`、`r06cd-ordinary-001`）。`GATE`/`ORDINARY`/`QUALITY` 全部未跑；没有 PSNR，也没有阈值。本卡未开设备、未建 pipeline、未探测 `GPU.lock`。
- **GAP 2 本臂没有部署模块自己的逐阶段 oracle**：§4 的捕获属于字节不同的同族模块（block 16），fp16 臂与它的 0.1363% 差**未能**归因到 `inversesqrt` 或 K16 加法顺序中的哪一项。要闭合需要：对**部署模块**自身做一次 `Y`/`T` 双 dump（同一 PASS、同一 PUSH、同一 grid），并额外用 `p1.w=1` 取 `dbgf`（raw logits）与 `dbg`（narrowed logits / exp / P）——那就能把误差分到 L / exp / P / T 四级。
- **GAP 3 QKV 的 activation scale 是 per-workgroup 而不是 per-token**：实测代价 0.20 个百分点（§4 研究臂）。提高粒度需要 epilogue 里的行广播，需先在本模块实测 int32 累加器的 lane/component→(row,col) 映射。**同一 ABI 内**的第一优化项。
- **GAP 4 声明 shared 48 144 B 只比 49 152 B 少 1 008 B**：可能建 pipeline 失败或跨 occupancy 拐点，方向未知，必须 native 对照。删减顺序：Y 量化按 K 折半（-8 192，+2 barrier）→ `sq8/sk8` 别名进 `sy8` 末尾寿命（-4 096）→ `shPS/shPM` 折进 `shNorm`（-512）→ `shV8` 与 half V 二选一（-2 048）。
- **GAP 5 int8 合作矩阵从 shared 载入的 native 合法性未证**：`sy8/sq8/sk8/shP8/shV8` 的基址都是 32 B 的倍数、stride 32/64/256，但只有 `spv_validate_cpu result=0`。备选：把 slab 声明成 `uint[]` 再以 `int8_t` 视图载入（未实施）。
- **GAP 6 父模块身份分叉**：232 PASS 的 FP16 臂这 16 个 PASS dispatch 的是 u09 重建模块 `candidates/zcode-fp16-compute-backend-20261021/u09-join-wide-c256-attn-v1/spv/b3_06_swin_c256_fp16.spv`（71 312 B `60864afa…`，shared 12 288，38 处 FP16 MMA，源码不同源）。本卡候选**只能换进 G3 及其派生累计臂**（G3/`cumulative-v6..v10` 都仍 dispatch `d3_direct.spv`）；换进 232 会顺带改 norm。
- **GAP 7 debug 通道语义变化**：`dbgf` 的 raw logits 现在是**反量化后**的 logits（父是 FP32 累加器原值）；P 的 debug 通道（half 值）与父逐字节相同；Q/K/V 的 half debug 通道仍是父的半值。生产门 `p1.w=0`，不影响覆盖结论。
- **GAP 8 SPIR-V diff 未做逐 opcode control build 归因**（r06-c256-attn 对 PV 段做过四步 control build）。本卡只做了行级 diff + 区间归属 + 静态事实对比；若要复核"未改区段未被编译器重排"，需补 4–6 个增量 control build。
