## 1.（Q1）映射：每个 (lane, component) 代表哪个 (token, channel/K)

### 1.1 内核几何（父＝候选）

| 量 | 值 | 依据 |
|---|---|---|
| WG | 256 线程 = 8 个 SG（32 lane） | `layout(local_size_x = 256)` |
| SG 通道 owner | `n0 = (sg % 8) * 32` → **8 个 32-channel owner**，合 256 channel | 源码第 43 行 |
| 每 WG 覆盖 | 64 token × 256 channel（K=256） | grid 11×6=66 WG（另有 11×7 的 PASS） |
| K | 256 = 16 步 × 16（`ki`, `k0 = 16*ki`） | `ki < 16` |
| 输出窗口 | 8 个，`j`，`m0 = (sg / 8 + j) * 8`（sg<8 ⇒ `m0 = 8j`）→ token 8j…8j+7 | 源码第 50 行 |
| 每 SG 输出 tile | 8 j × 2 acc（n0 / n0+16）= 16 个 8×16 half tile | `acc0/acc1` |
| 每 WG 输出元素 | 64 × 256 = **16 384** half | 8 SG × 16 tile × 128 half |
| shT 元素 | 16 384 half = 32 KiB = 64 token × 256 K，行主序 stride 256 | `shared float16_t shT[16384]` |

### 1.2 shT 的生产者/消费者映射（可枚举）

- **生产者**：`shT[e] ← gT[w*16384 + e]`，`e ∈ [0,16384)`。父：`e = t_local + 256*i`（每线程 64 次、stride 256）；候选：`e = seg*4096 + t_local*16 + u`（4 段 × 每线程 16 个**连续** half）。
  **PROOF.global_read**：两侧各 16 384 次写、覆盖 16 384 个下标、重复 0、缺失 0、**每个下标写同样来源 `gT[w*16384+e]`（mismatch 0）** ⇒ 写域与写值逐元素相同（只是"哪个线程写哪个元素"变了）。
- **消费者**：唯一读取点是
  `coopMatLoad(a, shT, m0 * 256u + k0, 256u, LROW)`（`MAT_A` 8×16；行 `m0+row`，列 `k0+col`）。
  地址表达式、stride、layout、tile 形状 **两侧逐字相同**（`SOURCE-DIFF.patch` 未触碰该行；`PROOF.requests.a_read_index_*` 相同）。
- **读事件计数（穷举）**：8 SG × 8 j × 16 ki × 8 row × 16 col = **131 072** 次 half 读 = 8 × 16 384 ⇒ 每个 shT 元素被 **8 个 owner** 读过，且没有第 9 个读者。`PROOF.windows.read_halves_written_once = 16384`。

### 1.3 覆盖与尾块

- 每个 shT 元素恰好被写 1 次、被 8 个 SG 各读 1 次（每 SG 每次读整 tile 的一行 = 16 half，连续 32 B）。
- **无尾块**：16 384 = 4 段 × 4 096（每段 16 token × 256 K）；4 096 = 256 线程 × 16 half；64 token = 8 × 8；256 K = 16 × 16。`PROOF.tail` 的余数全为 0。
- oob/clamp 路径 `c256_img_half_index` 与其调用点逐字未改 ⇒ oob 域、skip 域、clamp 地址与父相同（布局等价，不是新证明）。
- 段与窗口的关系：窗口 j 的 A 行 = token 8j…8j+7 ⇒ **段 s 恰好包含窗口 j = 2s、2s+1**（`PROOF.windows.reads_outside_owning_segment = 0`，穷举每个读事件的下标落在哪一段）。

## 3.（Q3）重叠：原来如何重叠、现在写了什么 hazard

本 kernel 只有 shT 一处 SLM 通信，没有 WG 内归约、没有原子、没有跨 SG 的输出（每个 8×16 输出 tile 只有一个 SG 写）。

| 值 | 生产者 | 首个消费者 | 最后消费者 | 覆盖者 | 危险 | 父 / 候选 |
|---|---|---|---|---|---|---|
| shT 段 s（4 096 half） | `C256_PUBLISH(s)`（256 线程 × 16 half） | 窗口 `2s` 的第一个 A tile（sg0, ki=0, row=0） | 窗口 `2s+1` 的最后一个 A tile（sg7, ki=15, row=7，程序序） | 无（每元素只写一次） | RAW（发布→读） | 父：整块 → 1 道 barrier；候选：**每段 1 道**（共 4 道） |
| A tile `a`（8×16） | `coopMatLoad(gT→shT)` per (j,ki) | `dpas acc0` | `dpas acc1` | 下一次 ki 的同名 SSA | RAW→WAR（寄存器返回窗） | 不变 |
| 权重 `b0/b1` | `coopMatLoad(pack)` | `dpas acc0` / `acc1` | 同 | 下一次 ki | RAW→WAR | 不变（本卡禁改） |
| `acc0/acc1` | seed 初始化 | 16 次顺序 muladd | `MAT_H(acc)` 窄化 | 每窗口新建 | RAW 链 | 不变 |
| store tile | 窄化结果 | `coopMatStore(imgout)` | — | 无 | 无 | 不变（地址集合相同） |

**RAW/WAR/WAW 表（PROOF.domains，穷举 8 窗口 × 4 段）**：

| 关系 | 判定 | 计数 |
|---|---|---|
| WAW（写–写） | 每元素只写一次 ⇒ 不存在 | **0** |
| RAW（段 s 的写 → 窗口 2s/2s+1 的读） | 由段 s 的发布 barrier 覆盖（barrier 在写之后、读之前，且覆盖全部 8 个读者） | 4 对（owner 对） |
| WAR（窗口 j 的读 → 段 s'≠j/2 的写） | **写域与读域不重叠** ⇒ 无需 barrier | **0 冲突**（32 对里 24 对不相交、8 对是 owner） |
| RAR | 读者之间无序要求 | — |

写域：`W_s = [4096s, 4096s+4095]`（4 段互不相交）；读域：`R_j = [2048j, 2048j+2047]`；`R_j ⊂ W_{j/2}`。

**删掉的同步由哪条依赖覆盖（第 ③ 问）**：
- 一个"双缓冲/轮转 arena"形态必须有的 **compute(s) → publish(s+1) 之间的 WAR barrier 被删除**，覆盖它的是**写域/读域不相交**（publish(s+1) 写的是任何窗口都还没读过、也永远不会再读的区域；`PROOF.domains.read_write_conflicts = 0`）。
- 父的**整块 barrier 被替换成 4 道发布 barrier**：每一道覆盖"段 s 的写 → 段 s 的全部 8 个读者"这一条 RAW；因为所有 owner 都在同一段 barrier 之后才读该段（8 个 SG 执行同一段代码），所以**不需要**第二类"读者间"同步。
- **没有**删除任何数值依赖：K 序、seed-before-K、窄化点、store 域（见 §5）。

## 4.（Q4）新增成本（全账）

| 项 | 量 | 依据 |
|---|---|---|
| WG 内 barrier（动态） | 1 → **4** | 1 道序言 + 循环内 1 道执行 3 次（j=1,3,5）；static 仍 2（父也是 2：1 正路径 + 1 debug） |
| barrier 代价估计 | 每个约 1 个 warp-skew 窗口（数十周期），且 2 个 WG 同核驻留可互相填充 | 8 warp/WG、128 GRF/线程 ⇒ 2 WG/core |
| SPIR-V 指令/字节 | 860 → 1 171（+311）／3 466 → 4 882 words（+40.8%） | `build/spv-stats.json` |
| SPIR-V 整数 ALU | IAdd 56 → **123**（+67）、IMul 34 → 38 | 4 个段基址替代 1 个循环计数器；ILP 教训 L1：源级地址折叠不改变 ISA 工作量，记账为中性 |
| 基本块 | OpLabel 9 → 11、OpBranch 52 → 59、OpBranchConditional 35 → 39 | 循环内多了 2 个 uniform 分支（`(j&1)==0 && j<6` / `(j&1)==1 && j<6`） |
| OpStore / OpLoad（标量） | 66 → 100 ／ 149 → 250 | 16 half 的发布块展开 2 处 |
| shT 存活值/驻留 | **不变**：32 768 B、单数组、同一行主序 | `BUILD.json.workgroup_memory` |
| 累加器 / 活值峰值 | **不变**：每窗口 2 个 MAT_C、16 GRF/lane 峰值，与父相同 | 未新增同时存活值（段地址是标量） |
| 有效 lane / WG 数 / 占用 | **不变**：256 线程、8 SG、全 lane 有效、grid 不变 | — |
| scratch | 期望仍 0（父 0）；无新增 buffer、无新派发、无新绑定 | cpu-check 与 baseline 逐字相同 |
| 逻辑字节 | staging 读写各 32 KiB **不变**；SLM A 读 256 KiB/WG **不变** | 只改消息条数与时序 |

**第 ④ 问（保留的 32 KiB 单读不得变成多 owner 合计更多逻辑请求）**：
- **按定义满足**：A 的读路径（地址表达式、stride 256、LROW、tile 8×16、owner 数 8）逐字未改 ⇒ 每 SG 仍是 1024 条 32 B 的 SLM 读消息、每 WG 8 192 条、256 KiB（`PROOF.requests`：`identical=True`）。
- 另外，staging 仍是**一次** 32 KiB 全局读（不是 8 × 32 KiB 的按 owner 直读）——本卡没有把 staged read 换成 per-owner 直读，故不存在"多 owner 合计更多逻辑请求"的退化。
- 唯一变多是"每线程一次搬 32 B"而不是"每线程 64 次搬 1 half"：消息**变少**（1 024 → 64/WG），字节不变。

**逻辑字节 ≠ DRAM 字节**：gT 每 WG 仍只读一次 32 KiB（66 WG × 32 KiB = 2.1 MiB/PASS，与父相同）；本卡不改变 DRAM 侧任何量，改的是数据端口的**消息条数**与**串行序言长度**。

## 6.（Q6）整体是否更快（本卡不能测，写清怎么测与可分辨性）

- **先门**：`fixed`（frame0 gold `1755e9c2…`）、`fb2`（末帧 gold `9c3e511e…`，`--warm 0 --reps 2 --feedback --save-frames`）。数值预期**逐位相同**：写域/写值逐元素相同（16384/16384，mismatch 0）、A 读地址不变、K 序不变、FP 点集不变（`OpFMul` 2、`OpFConvert` 4、无 FAdd/FSub、无 QuantizeToF16）、NoContraction 两侧 0 ⇒ 不同即 **E 类**。
- **主判据（可分辨的那一层）**：`resources` 作业的**逐 PASS GpuTime**。F06 C256 组 15 PASS 实测 **484.94 µs**（30.0–37.0 µs/PASS，单样本 base 臂），占 17 577 µs 帧的 **2.76%**。逐 PASS 分辨率约 1 µs，能看见组内 5–10% 的变化。
- **整帧**：`ordinary`（warm1/reps30/feedback，两臂 6 组交替）。天花板 485 µs = 2.76%；本卡预期只动其中几个百分点（10–20 µs = **0.01–0.02 ms**），**低于 ordinary 的 CI 分辨率（≈0.03 ms）**，所以整帧预期是 **D/INDISTINCT**，它在这里是回归守门而不是收益证明。
- **归因**：plan 只替换 15 条 PASS 的 SPV 路径，其余 217 条逐字不变 ⇒ 这 15 个 PASS 的逐 PASS 差是单链归因；其余 PASS 是天然对照。**不跨批相减毫秒，不与 F10 0.422 ms 或 C128 +0.0405 ms / C64 +0.0179 ms 相加。**
- **上界**：staging 只占该 kernel 数据端口消息槽的 7.6%、字节的 4.6%，且有第二个驻留 WG 隐藏一部分 ⇒ 组内 3–6% 是乐观上界（≈15–30 µs/帧，0.09–0.17% 帧时）。
- **预登记的负面判据**：A = dpas≠256 或 sync.bar 仍 1；B = scratch>0 或指令暴涨；C = 逐 PASS 同向变慢；E = 数值失败。若 A/B/C 都不成立而 ordinary 不显著 ⇒ **D**，并把"shT 的驻留不是瓶颈"作为本族结论记入台账（而不是方向禁令）。

## 7. 本卡的结论边界（不能说的话）

1. 不能写"C256 shT 分段发布带来 X ms"：本卡无 GPU，只有预测与判据。
2. 不能把 staging 消息 −94% 直接换算成时间：消息条数下降只说明少发了请求，数据端口是否为此瓶颈要由 native/resources 回答。
3. 不能把本卡的 15 PASS 收益与 C128/C64 的已采纳收益相加或跨批相减。
4. 不能写"shT 本身没有成本"：A 的 8 192 条 SLM 读消息/WG（占全部消息槽约 60%）就是 shT 的成本；本卡**故意不动**它（那是布局机制，见 RESUME §5.1）。

## 8. 未决项 / 风险排序

1. **IGC 是否把段循环展开**（最高）：若不展开，`dpas` 数与指令数会同时异常；判据已写死。
2. **发布块是否被下沉到各自 barrier 之前**：那样只保留消息收益、失去重叠收益；用"4 个发布块相对首个 DPAS 的地址位置"判。
3. **3 道额外 barrier 的真实代价**：只能用 resources 逐 PASS 与两臂同向性判断。
4. **32 B/线程 的连续发布块是否真被合并成 1 条 `d32x8`**：`load.ugm.d16u32`/`store.slm.d16u32` 是否消失是唯一硬判据。
5. CARD.txt 与本卡的 15 PASS 归属一致（`FAMILY-GROUPS.json` = 15），无需主代理澄清。
