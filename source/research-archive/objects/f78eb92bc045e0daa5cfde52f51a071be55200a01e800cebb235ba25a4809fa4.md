# n06b-f06-c64 / F06 C64：把 C128 的"tile 只载一次、被 4 条 DPAS 消费"推到 C64

卡片：`n06b-f06-c64`　族：F06　宽度：**C64 7 PASS**（ordinals 8,11,14,216,219,222,225；PASS 行 5,6,7,143,144,145,146）
状态：**BUILT / PREMISE-ALREADY-SATISFIED**（CPU 构建完成、门可跑；本卡未用 GPU、未部署）
父身份：`f06-scale-fragments/family/c64/candidate.comp`（sha256 `48df0ff0…acc9`）→ SPV `39e57376…930a`（17140 B，4285 words）
候选：`candidate.spv` sha256 `ca587aa4…355f`（16640 B，4160 words）；plan sha256 `7ad5b99d…d27f`

> **本卡最重要的结论**：C128 卡（n06）的机制——"一对权重 tile 只载一次、被 4 条 DPAS 消费"——**在 C64 的现行基线里已经存在**。
> C64 父身份每个 SG 已经是 2 M 块 × 2 n-block 的 2×2 块化：权重 tile 每个 (ki, n-block) 只载一次，被两个 M 块的
> 2 条 DPAS 消费；acc 也已经是 **4 个**（`accA0/accA1/accB0/accB1`），不是卡片假设的 2 个。
> 因此"把 512 B 权重载入再减半"在这个几何下**不可能**（§2.3 给出计数证明），本卡把同一句话（"一个 tile 只载一次、
> 被 4 条 DPAS 消费"）落在 C64 里**唯一还停在 2 次复用**的 tile 上：**A tile**。
> 候选把块化从 2×2 改成 **1×4**：A tile 每 (m,k) 只载一次、被 4 条 DPAS（4 个 n-block）消费；
> DPAS 数不变（16/SG），A 载入 8→4，权重载入 8→16（每个权重 tile 的复用从 2 降到 1），
> 每 SG 主路径 send 136→112，L1 sector 数不变（1280/WG）。

## 1.（Q1）映射：每个 (lane, component) 代表哪个 (token, channel)

### 1.1 内核几何（父与候选完全相同）

| 量 | 值 | 依据 |
|---|---|---|
| WG | 256 线程 = **8 个 SG**（subgroup 32 lane） | `layout(local_size_x=256)` |
| 每 WG 覆盖 | **64 token × 64 channel = 4096 输出 = 32 个 8×16 tile** | `w=wy*grid_x+wx`，`w*64` 为 token 基址 |
| 每 SG 覆盖 | 4 个 tile | 32 / 8 |
| K | **64 = 4 步 × 16**（`ki<4`，`k0=ki*16`） | 源码 K 循环 |
| 输出元素 | 4096/WG；与 C128 的 8192/WG 不同（通道数只有 64） | PROOF.mapping |
| 权重 pack 布局 | 每 n-block 1024 half = 4 k 步 × 256（16 n × 16 k），n-block 步长 1024 | `wo + (n0/16)*1024 + ki*256` |
| 无尾块 | 64 = 8×8 token，64 = 4×16 channel | PROOF.tail |

### 1.2 输出 tile 的 owner 表（可枚举，父/候选各 32 个 tile）

父：`(sg) → mA=(sg/2)·8, mB=mA+32, n0=(sg%2)·32`，tile = `(mA,n0),(mA,n0+16),(mB,n0),(mB,n0+16)`。
候选：`(sg) → m=sg·8`，tile = `(m,0),(m,16),(m,32),(m,48)`。

| SG | 父的 4 个 (m,n) tile | 候选的 4 个 (m,n) tile |
|---|---|---|
| 0 | (0,0) (0,16) (32,0) (32,16) | (0,0) (0,16) (0,32) (0,48) |
| 1 | (0,32) (0,48) (32,32) (32,48) | (8,0) (8,16) (8,32) (8,48) |
| 2 | (8,0) (8,16) (40,0) (40,16) | (16,0) (16,16) (16,32) (16,48) |
| 3 | (8,32) (8,48) (40,32) (40,48) | (24,0) (24,16) (24,32) (24,48) |
| 4 | (16,0) (16,16) (48,0) (48,16) | (32,0) (32,16) (32,32) (32,48) |
| 5 | (16,32) (16,48) (48,32) (48,48) | (40,0) (40,16) (40,32) (40,48) |
| 6 | (24,0) (24,16) (56,0) (56,16) | (48,0) (48,16) (48,32) (48,48) |
| 7 | (24,32) (24,48) (56,32) (56,48) | (56,0) (56,16) (56,32) (56,48) |

- 两个臂的 tile **集合完全相同**（32 个），只是**哪个 SG 拥有哪个 tile** 变了（与 n06 在 C128 上做的 owner 置换同性质）。
- 通道方向：父的每个 SG 拿 32 个通道（2 个 n-block），候选拿 64 个通道（4 个 n-block）；token 方向相反（父 2 块、候选 1 块）。
- 每输出仍是 1 个 owner（duplicate 0 / missing 0，PROOF.mapping）。

**覆盖证明（PROOF.json，穷举 4096 元素）**：父/候选各恰好 1 个 owner/元素；tile 集合差集为空；
每元素 store 地址逐元素相等（5 个窗口位形：shift 0/1/-1、grid 42×24/43×25/43×24 等，mismatch 0）；
seed 索引 0 差、scale 索引 0 差、K 序 0 差；每 SG 的 4 条 store 区间两两不重叠（父/候选都 0 冲突）。

### 1.3 尾块与 oob

无尾块（64/8、64/16 整除）。`c64_img_half_index` 的 **oob + clamp 逐字未改**；tile 内 `q=t>>4` 恒定
（tile 起点 m 是 8 的倍数），所以 oob 是 tile 级常量、`if (!oob)` 的跳过域与父相同（oob_mismatches 0）。

## 2.（Q2）删了什么真实工作（正常执行路径，不计 debug 声明）

### 2.1 先回答卡片的前提：C128 的机制在 C64 上**已经落地**

| 指标（每 SG） | C128 父 | **C128 候选（n06，已采纳）** | **C64 父（本卡基线）** | C64 候选（本卡） |
|---|---|---|---|---|
| DPAS | 64 | 64 | **16** | 16 |
| 权重 tile 载入（512 B） | 64 | **32** | **8** | 16 |
| 权重载入 / DPAS | 1 | **2** | **2** | 1 |
| A tile 载入（256 B） | 32 | 32 | **8** | 4 |
| A 载入 / DPAS | 2 | 2 | **2** | **4** |
| acc 数 | 2 | 4 | **4** | 4 |

C64 父的 8 次权重载入 = 2 n-block × 4 k 步；每个权重 tile 被 `accA0/accB0`（或 `accA1/accB1`）两条 DPAS 消费，
**与 C128 候选的 32/64 = 2 完全同形**。所以"一对权重 tile 只载一次、被 4 条 DPAS 消费"在 C64 上不是待做项，而是基线。
（旁证：f06 家族的 `NATIVE-REVIEW.json` 记录 C64 父→候选的 native 变化只有 1026→1003 条指令、227→213 send，
是"direct T/Y seed"那一步，不是权重块化；`owner-output-transfer` 里的上一版 C64 源码已经是 4 acc + M-pair。）

### 2.2 本卡真正删掉的工作：A tile 的**重复读**

父的每个 M-pair 由两个 SG 共同拥有（n0=0 与 n0=32），这两个 SG **各自把同一批 A tile 再读一遍**（每 WG 2× 重复）：

| 工作（每 SG / 每 WG） | 父 | 候选 | 变化 |
|---|---|---|---|
| A tile 载入 / SG | 8 | **4** | **−4** |
| A tile 载入 / WG | 64 | **32** | **−32（重复读归零）** |
| A tile 的 DPAS 消费数 | 2 | **4** | +2（同一 tile 供 4 条） |
| 权重 tile 载入 / SG | 8 | 16 | +8（复用 2→1） |
| 权重 tile 载入 / WG | 64 | 128 | +64 |
| seed 载入 / SG | 4 | 4 | 0 |
| store / SG | 4 | 4 | 0 |
| DPAS / SG | 16 | 16 | **0** |
| 主路径 send / SG | 136 | **112** | **−24** |
| 主路径 send / WG | 1088 | **896** | **−192（−17.6%）** |
| L1 sector / WG | 1280 | 1280 | **0** |
| 逻辑载入字节 / WG | 57 344 | 81 920 | +24 576（+43%） |

- **sector 恰好持平**：A+seed+store 是 32 B 消息（各 1 sector），权重是 512 B（4 sector）。
  父：`(64+32+32)×8 + 64×4 = 1024+256 = 1280`；候选：`(32+32+32)×8 + 128×4 = 768+512 = 1280`。
  即：**消息数 −192，sector 不变，逻辑字节 +24 KiB**。
- **native 层面的"真实工作"**（父的只读采集 `CS_asmd34c8c009fa5ce28_…_7_6_orig.asm`，sha256 `cd7edacb…`）：

| send 形态 | 父 | 候选预测 | 依据 |
|---|---|---|---|
| `load.ugm.d32x8t`（A+seed 转置读） | **96** | **64** | A 8→4 tile，seed 4 不变，8 条/tile |
| `load.ugm.d32x8`（512 B 权重） | **8** | **16** | 2→4 n-block，1 条/tile |
| `store.ugm.d32x8t`（debug 复制/store） | 32 | 32 | 不变 |
| `store.ugm.d32x64t` | 4 | 4 | 图像 store，不变 |
| `load/store.ugm.d16u32`（debug 路径） | 34 / 32 | 34 / 32 | 死路径，不变 |
| 其它（d32x2t/d32x1t/d32x3t） | 5 | 5 | 地址/常量 |
| **`send.ugm` 合计** | **211** | **≈187** | −24 |

- **没有删**：任何 DPAS、任何 store、任何 seed 读、`sync.allwr`（2）、debug 分支、`barrier`（debug 内 1 条）。
  也没有动 exp/倒数/FMA 收缩/clamp/saturate（本 kernel 不含这些；`c64_act_h/c64_exp_h/c64_norm_sum32` 未被调用）。
- **顺带减少的整数地址 ALU**（SPIR-V 模块级静态）：OpIAdd 93→70、OpIMul 52→29、OpUDiv 6→1、OpUMod 2→1。
  来源：一个 `abase` 代替两个 M 基址；store 的 4 个通道块只差常量 256 half，oob/`q` 只算一次。

### 2.3 为什么"权重 512 B 载入接近减半"在本几何下**不可能**（计数证明）

- 每 WG 的**不同**权重 tile 数 = 4 n-block × 4 k 步 = **16**；父的载入次数 = 64（4× 重复，因为 4 个 M-pair 组各读一遍）。
- 一个 SG 若拥有 `n` 个 n-block，必须载 `n×4` 个权重 tile。要 8→4，只能 `n=1`（1 个 n-block）。
- 于是每个 SG 必须覆盖 **4 个 M 块 × 1 个 n-block**（4 个 tile），8 SG × 4 = 32 tile 刚好覆盖 WG。
  这个形状的账（PROOF.ledger.weight_halving_shape）：权重载入 8→**4**（确实减半），但 A 载入 8→**16**，
  每 SG 消息 `(128+32+32)×8 + 32 = 1568/8 = 196`，**比父的 136 更差**；sector 1664 > 1280。
- 若坚持"4 个 M 块 × 2 个 n-block"（这样权重 4 条 DPAS、A 也 2 条），每 SG 是 8 个 tile，8 SG = 64 tile，
  而 WG 只有 32 tile —— 除非把 WG 覆盖扩到 128 token（grid 减半）或 128 channel（C64 没有），两者都违反"grid 不变"。
- 结论：C64 的 2×2 是"消息数 / sector / 字节"三者下的局部最优；**唯一还能减少消息的轴是 A 的重复读**，
  这正是本卡选的 1×4。

## 3.（Q3）重叠：原来如何重叠，现在是否被破坏

本 kernel 无 SLM、无 barrier（debug 分支外）、无 WG 内归约；8 个 SG 只共享 L1/L2 上的 gT/gY/pack 流，
输出 tile 两两不相交。重叠只发生在 **每 SG 内的"供料—DPAS—退休"**。

| 值 | 生产者 | 首个消费者 | 最后消费者 | 覆盖者 | 危险 | 父 → 候选 |
|---|---|---|---|---|---|---|
| A tile `a`（8×16） | `coopMatLoad(gT)` @ (m,k) | DPAS acc0 | DPAS acc3 | 下一次 ki 的同名 SSA | RAW→WAR | 父 2 DPAS → 候选 **4 DPAS**（**唯一被拉长的寿命**） |
| 权重 tile `b0..b3`（16×16） | `coopMatLoad(pack)` @ (nblk,k) | 紧随其后的 1 条 DPAS | 同一条 | 下一次 ki | RAW→WAR | 父 2 DPAS → 候选 **1 DPAS**（寿命变短） |
| `acc0..acc3`（f32） | seed 初始化 | 4 次顺序 muladd | `MAT_H(acc)` 窄化 | 无（每次 SG 新建） | RAW 链 | 4 → 4（不变） |
| `seed`（f16 8×16） | `coopMatLoad(gY)` | `seed*scale`（half） | `MAT_C(seed)` | 无（每块一次） | — | 4 → 4（不变） |
| store tile（8×16 half） | 窄化结果 | `coopMatStore(imgout)` | — | 无 | 无 | 地址集合相同、两两不交 |

- **被保护的重叠**：权重仍然"最后一条 DPAS 发出后才允许被下一次读覆盖"，而且窗口从 2 条 DPAS 缩到 1 条；
  A 的"一次读、多条 DPAS 用"从 2 条扩到 4 条，但 A 只有 2 GRF/lane（8×16 half），不构成寄存器压力。
- **源序**：`a → (b0,b1) → 2 DPAS → (b2,b3) → 2 DPAS`，让 b0/b1 在 b2/b3 被需要前退休，
  峰值 MAT_B 活值仍是 2 个（与父相同，+0 GRF）。
- **没有新增同步点**，没有把 A/B 流合并成单链；8 SG 仍并行，WG 数不变
  （grid 42×24=1008 / 43×24=1032 / 42×25=1050 / 43×25=1075，按 PASS 而定）。

**逻辑字节 ≠ DRAM 字节**：权重区每 block 只有 8 KiB（4 n-block × 1024 half），被 1008 WG 反复读，

8 条 32 B 转置消息，不能按 256 B/tile 折算成 1 条 send。

`OpFMul` 4→4（4 次 half `seed*scale`）、`OpFConvert` 8→8（4 次加宽 + 4 次窄化），
**无** OpFAdd/OpFSub、**无** OpQuantizeToF16、**无** Fma。即舍入点数量、类型、位置逐点不变。

## 5.（Q5）是否真落到 native（预测 + 判据，**未证明**）

父的只读 native 采集（同身份 SPV `39e57376`，kernel `d34c8c009fa5ce28`）：

```
instructions 1004   send.ugm 211 (+2 non-ugm)   dpas.8x8 16   mov 261   add 162
sync.nop 87   sync.allrd 14   sync.allwr 2   scratch 0   workgroup mem 0   max_r 127
```

候选预期（详见 `NATIVE-PREDICTION.md`）：

1. `dpas.8x8` **=16**（每 acc 的 K 序仍是 k0=0,16,32,48）；
2. `load.ugm.d32x8t`（A+seed）**96 → 64**（A 8→4 tile；seed 4 不变）；
3. `load.ugm.d32x8`（512 B 权重）**8 → 16**（2→4 n-block）；
4. `store.ugm.d32x8t` **32 不变**、`store.ugm.d32x64t` **4 不变**、debug 的 `d16u32` **34/32 不变**；
5. `send.ugm` 总数 **211 → ≈187**（−24）；
6. `scratch = 0`、`workgroup memory = 0`、`max_r ≤ 127`（父已 127，是最大风险）；
7. 指令数 **950–1050**（父 1004）。

**判据**：
- 若 `d32x8t` 仍是 96 且 `d32x8` 升到 16 ⇒ **实现未落地（A）**：IGC 把共享 A 重新物化成 2 条，方向未被证伪；
- 若 `scratch > 0` 或指令数 > 1200 ⇒ **副作用（B）**，先查 +2 scale / 4-DPAS A 窗口；
- 若 A 96→64、权重 8→16、DPAS 16 全中但 resources 不变 ⇒ **D**（组内天花板太低，见 Q6）；
- 若 gates 逐位不同 ⇒ **E**（先查 seed/scale 索引与 store 地址，PROOF 已穷举）。

**与 C128 卡（n06）的形态对照**（本卡 native 判据的参照系）：

| | C128 父 → n06 候选（已实测） | C64 父 → 本卡候选（预测） |
|---|---|---|
| 512 B 权重 `d32x8` | **64 → 32** | **8 → 16**（方向相反：C64 已经是最小） |
| A/seed `d32x8t` | 320 → 320（不变） | **96 → 64** |
| `dpas.8x8` | 64 → 64 | 16 → 16 |
| `send.ugm` | 481 → 449（−32） | 211 → ≈187（−24） |
| 指令 | 2257 → 2005 | 1004 → 950–1050 |

⇒ 两张卡是**同一句话在两条不同瓶颈轴上的落地**：C128 的重复读在权重，C64 的重复读在 A。
C64 的权重流已经最小，**不应期待权重载入再降**。

## 6.（Q6）整体是否更快（本卡不能测，写清怎么测）

- **先门**：`fixed`（frame0 gold `1755e9c2…`）、`fb2`（末帧 gold `9c3e511e…`，`--warm 0 --reps 2 --feedback --save-frames`）。
  数值预期**逐位相同**（owner 置换 + 地址/seed/scale/K 序已穷举证明），不同即 E。
- **主判据（可分辨的那一层）**：`resources` 作业的**逐 PASS GpuTime**。C128 组 11 PASS 实测 16.8–18.9 µs/PASS
  （合计 197.7 µs）；C64 组 7 PASS 若同量级 ⇒ **约 105–135 µs**，占 ~19.1 ms 帧的 **0.6–0.7%**。
  逐 PASS 分辨率约 1 µs，足以看到 10–20% 的组内变化。
- **整帧**：`ordinary`（warm1/reps30/feedback，两臂 6 组交替）。**天花板 135 µs = 0.7%**，低于 ordinary 的 CI 分辨率
  （≈±0.1 ms），所以**预期就是 D/INDISTINCT**；它的作用是回归守门，不是收益证明。
- **归因**：plan 只改 7 条 PASS 的 SPV 路径（在 chain head `pkg-vit-16pass` 上替换，replaced==7 断言通过），
  其余 225 条逐字不变 ⇒ 这 7 个 PASS 的逐 PASS 差是单链归因；其余 225 PASS 是天然对照。
  **不跨批相减毫秒，不与 F10 0.422 ms 或 n06 的 0.0405 ms 相加**。
- **建议顺序**：native（确认 A 96→64、权重 8→16、DPAS 16、scratch 0）→ 只有 native 命中才做 resources →
  ordinary 只作回归。**若 native 未命中就直接停**，不要用整帧毫秒倒推机制。

1. **IGC 重新物化 A**（最高）：若它把"一次 A 载入供 4 条 DPAS"拆成 2 条，A 载入仍是 8，权重却升到 16 ⇒ 净亏。
