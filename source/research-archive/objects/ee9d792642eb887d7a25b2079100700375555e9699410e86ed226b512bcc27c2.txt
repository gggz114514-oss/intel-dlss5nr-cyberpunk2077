═══ 四、六问里最关键的两条 ═══
1) 映射/数学：候选只换"喂给 A 载入的行号"，不碰 store 地址、不碰 epilogue 守卫、不碰 k0 序与 muladd 顺序。
   SPIR-V 算术面完全同形：CoopMatMulAdd 3/3、CoopMatLoad 2/2、CoopMatStore 1/1、FConvert 3/3（= 3 个 half 舍入点）、ExtInst Fma 1/1，
   FP 乘/加/除/负全 0/0；新增只有整数 clamp（ISub/UGreaterThan/BitwiseAnd/Constant + 2×UMin）。
2) 代价：删掉的是"循环内 2 个 subgroup-uniform 守卫 × 64 展开步 = 128 个 join"；付出的是 **动态 A 片段读 +11.11%**
   （每列 36→40 个片段 = 每 dispatch +131072 条窄 send = +4.19 MB/PASS），全部落在 clamp 行 280..287 的 16 KiB 热区，
   context 仅 589824 B（L2 常驻）→ DRAM 增量≈0。权重读、静态读条数、有效 lane、WG 数、活值峰值均不变。

═══ 五、与任务书字面的一处偏离（必须知道） ═══
任务书写 `rA/rB = min(m, last)`（last = live-1）。本卡实现为 **块对齐的 last8 = (live-1)&~7 = 280**。
原因：A 片段覆盖 8 行；若 clamp 到 287，死块会读行 287..294，**超出 288 行 / 589824 B 的 context 缓冲 7 行**；clamp 到 280 时死块读 280..287，完全在界内。
父的最大读行 287，候选的最大读行 **也是 287**（读域上界相同）。不放松父的任何前提（父 T2 注释已声明 live 是 8 的倍数）。
clamp 触发次数（per dispatch）：rA 计算 256 次、**真正用于载入 0 次**；rB 计算 512 次、**用于载入 256 次**（mA 活而 mB 死的 4 块/列 × 64 列）、其余 256 次属死块（分支跳过、算了不用）。
→ 活块 rA=mA、rB=mB，读的就是自己的行；clamp 只在死块上生效，结果随 epilogue 守卫丢弃。

═══ 七、下一处具体改动 / 可区分实验 ═══
A) 若 native 显示 mov32 落地但 jmpi 不降 → 判定被编译器重新下沉：把三元换成无 selection 形式
   `uint last8=(max(live,1u)-1u)&~7u;`（少 1 个 SelectionMerge + 2 个 Branch），重编重测。
B) 若 narrow A send >1024 → 片段载入被复制：先确认是不是只是寄存器命名（看 k0 步区域里 send 的偏移/掩码），
   再决定是否把 B 路径改成 `if(mB<live)` 的二级 uniform 分支（那会把 join 加回一半，不优先）。
C) 若成包仍 INDISTINCT（最可能）：按 n11 的结论把该机制记 **D** 并存资产，不再单独重跑 8 PASS；
   下一处改动按 n11 的 next 指向 F13 contract 侧的其它搬运（不是继续改这里）。
D) 若 numeric 失败（E 类）：首查 last8 的块对齐是否被误改成行对齐（会越界）、以及 epilogue 守卫是否被动过。
