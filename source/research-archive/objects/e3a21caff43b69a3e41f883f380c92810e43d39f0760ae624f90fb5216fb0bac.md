读法（L20 口径：每 lane 操作数读上限 512 B；`d32xN` = N dword/lane；exec=1 是 uniform 广播块读）：
- **C256 的 1040 条 `load.slm.d32x8t`@exec1 就是 A 片段读**：MAT_A 8×16 半 = 256 B，
  但 ISA 里被拆成 **8 条 32 B 的 uniform 标量消息**（每行 16 半 = 1 GRF = 32 B），因为 8 行在
  shT 里相隔 512 B（行距 256 半）→ **不连续**。
- C256 的 264 条 `load.ugm.d32x8`@exec16 = 权重 B 片段（16×16 半 = 512 B，1 条/DPAS）。
- C64/C128 的 A 片段读走 **global**（`load.ugm.d32x8t`@exec1），C256 走 **SLM**；条数相同、形状相同，
  只是存储空间不同。**这是三核之间唯一的结构性差别。**

## 3. DPAS

| | C64 | C128 | C256 |
|---|---|---|---|
| DPAS 站点 | 18 | 68 | 264 |
| 全部 exec | 16 | 16 | 16 |
| 每 subgroup 动态 DPAS | 16 主体 + 2 DS | 64 + 4 | 256 + 128 |
| 每 WG 动态 DPAS | 8×18 = 144 | 8×68 = 544 | 8×384 = 3072 |
| 每帧 DPAS | 151 200 | 155 584 | 236 544 |

DPAS 数是**三核里最稳的量**：任何候选都不许动它（动它就是改数学）。C256 的 DPAS 站点 264 与
B 权重读 264 一一对应（1 B 读 / 1 DPAS），说明**权重读已经是理论下界**，没有重复读可删。

## 4. acc / GRF 峰值

- `max_r`：C64 127、C128 127、C256 126（**三者都在 128 GRF 上限**）。
- `accN` 只出现 acc0/acc1（C64/C128）与 acc0/acc1/acc2（C256），且是 `mul` 的扩展精度伪寄存器，
  **不是** DPAS 累加器；DPAS 累加器落在通用 GRF（例：`dpas.8x8 (16|M0) r16:f r16:f r54:hf r63.0:hf`）。
- Scratch：三核驱动口径均 **0**。
- 结论：**没有寄存器余量**。任何 +16 GRF 的形状（8 累加器、合并 DS 两轮、C64 权重去重）都会溢出，
  与 L9/L15/L17 的既有结论一致（L17 实测剥掉 debug 路径只回收 10 GRF，仍不够 6 累加器的 +16）。

三核 Scratch Memory Size = 0（驱动口径，父与子同）。Workgroup Memory 2048 / 4096 / 45056。

## 9. 三核之间是否共享权重/输入（能不能像 F05 M 批那样合并读）

**不能。逐条依据：**

1. **不是同一个张量**：三核的权重块布局同为 `[(n/16)*(K/16)+(k/16)]*256`，但 **K 不同**
   （C64 K=64、C128 K=128、C256 K=256），块步长分别 `(n/16)*1024 / *2048 / *4096`。
   即三个不同层的权重，`pack` 里的偏移 `wo` 不同（push p4.x 三 PASS 各自不同）。
2. **输入不同**：A 行距 64/128/256 半，T/Y 张量各自 `w*64*K` 起始；`gT`/`gY` 的 `w` 索引
   是同一张量的不同层输出，不是同一份输入。
3. **结构上不可能合并**：三个 PASS 是**三个独立 dispatch**（plan 里三行、三个 pipeline 7/11/15），
   中间隔着其他 PASS 的输出依赖；跨 dispatch 的读合并就是 L19 已判 D 类的「跨 PASS 布局折叠」。
4. 唯一「共享」的是 binding 列表（0..4,6..9）和 `pack` 这个 buffer 对象本身，**偏移不同**。

→ **F05 M 批那种「同地址重复读合并」在本族不存在。** 族内真正的重复读只有两处，且都不在
「同 subgroup 内」：C64 的 4× 权重重复（4 个 sg%2 相同的 subgroup 读同一批块）、C128 的 2×。
见 §11。

**只有一项量级够到 L13 的 0.03 ms 探测底噪**：把 C256 的 A 片段读从
「8 条 32 B uniform 消息」变成「1 条 256 B uniform 消息」——即 **D0**：

| D0 | C256 A 片段读的消息宽度 | 1040 → 144 条静态（每 subgroup −896） | **−7168 msg/WG，−46% 本 PASS 消息** | **−11%** | **≈0.038 ms** | 见下 |

D0 不是「把片段变宽」（片段仍是 8×16），而是**把 SLM 里的 A 分块改成片段连续**
（行距 256 半 → 16 半），让 8 行在 SLM 里成为连续 256 B。它不改字节数、不改寄存器、不改 barrier、
不改数学，只改消息条数。**风险**：L20 明确说「宽的 opcode 只在 exec=1 uniform 广播出现，
布局改动换不到更宽的操作数读」，n23 用「reblock 成连续列主序」实测没有换来更宽 opcode。
本卡的差别是：D0 的读**本来就在 exec=1 uniform 区**（父自己已经在这里用 256 B 的
`store.slm.d32x64t` 和 `load.ugm.d32x32t.a64`），不是 n23 的 exec16 逐 lane gather 区。
但这仍是**预测**，不是证明——所以候选的 native 判据写成「看不到就是 A 类」。

## 12. 供候选选择用的结论

1. 三核**不共享**权重/输入（§9），F05 M 批形态在本族**不存在**；族内重复读只有 C64 4× 权重，
   而它被 128 GRF 上限挡死（§11 D5）。
2. C256 是唯一「重」的核：1928 send / 44 barrier / 45056 B SLM / 16% 满宽 lane，
   其中 **46% 的消息是 A 片段读被拆成 8 条 32 B**（§2/§10）。
3. 除 D0 外，所有可删工作的量级都在 0.005 ms 以下，**低于 L13 的 0.03 ms 底噪 6 倍以上**；
   而 D0 的机制（改 SLM 分块使 A 读连续）**从未在本族任何宽度上测过**（C64/C128 的 A 读走 global，
   没有 SLM staging 可改）。
