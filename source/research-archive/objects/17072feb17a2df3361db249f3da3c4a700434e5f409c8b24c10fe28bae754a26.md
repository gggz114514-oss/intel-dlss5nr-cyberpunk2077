## 0. 先回答卡的核心问题：528 条 16-lane 交织 mov 的来源

### 0.1 指令形状与语义（机器枚举，`zip_blocks.py`）

```
mov (32|M0) rD.0<2>:uw   rS.0 <32;16,1>:uw
mov (32|M0) rD.1<2>:uw   rS.16<32;16,1>:uw
--------------------------------------------------------------
dst GRF pair (D, D+1)  <-  src GRF pair (S, S+1)，**字粒度二路交织**
    dst[D].dword[j]   = ( src[S].word[j],     src[S+1].word[j] )      j = 0..7
    dst[D+1].dword[j] = ( src[S].word[8+j],   src[S+1].word[8+j] )
```

- 528 条 = **68 个 zip 块**（56 个 8 条、7 个 4 条、3 个 16 条、2 个尾块），
  dst 基址全为偶数、同块内相邻基址相差 2，src 恒成对出现 `rY.0` / `rY.16`（= `rY`, `rY+1`）。
- 每个块对每对 GRF 做的是**对合置换**（做两次回到原样）——这是识别来源的关键：
  它不是"拷贝"，而是"换布局"。
- 语义：把**线性行主序**矩阵的两个相邻行压进一个 dword ⇒ **DPAS 操作数（VNNI）布局**。
  对 `NRH_B`(16×16, 行 = K) 就是"同一个 N 上相邻两个 K 共用一个 dword"，正是 VNNI 的定义。

### 0.2 逐块定位（`zip_blocks.py` 的进料者分类，机器输出）

| 进料指令 | 块数 | mov 数 | 对应源码站点 |
|---|---:|---:|---|
| `send.ugm … load.ugm.d64x64t`（`wb` 块读，rd:8） | 39 | 312 | **48 个 `coopMatLoad(w,wb,+off,16u,LROW)`**（`NRH_B` 16×16）：expand `p1.x` 16 + `p1.y` 16、QKV `p1.z` 12、output `p1.w` 4 |
| `send.slm … load.slm.d64x64t`（`shK`/`shV` 块读，rd:8） | 17 | 136 | 8 个 `coopMatLoad(b,shK,…16u,LROW)`（score B）+ 8 个 `coopMatLoad(b,shV,…16u,LROW)`（PV B，含 1 个 early） |
| `dpas.8x8` 结果（f32 累加器） | 7 | 56 | `nrh_to_A(nrh_narrow(sc))`：`ea0/ea1`、`ca00..ca11` |
| `mul`（`x*scale` 残差种子） | 4 | 16 | `nrh_to_A(nrh_narrow(nrh_widen_exact(x*scale)))`：`ya00..ya11` |
| 尾块 + 混装 | 3 | 8+16 | shK/shV 尾块、PV 早期 B |

### 0.3 1:1 计数交叉验证（`isa_census.py` 的 send 消息表 —— 独立算术，全部整数闭合）

| 消息 | 条数 | 打开方式 | 源码站点数 | 每站点消息数 |
|---|---:|---|---:|---:|
| `load.ugm.d64x64t` rd:8 | 48 | `wb` `NRH_B`(16×16) 块读 | 48 | 1 |
| `load.slm.d64x64t` rd:8 | 16 | `shK`/`shV` `NRH_B` 块读 | 16 | 1 |
| `load.ugm.d32x64t` rd:4 | 4 | `imgin` `NRH_CH`(8×16)，带 `tok_oob` 零填充分支 | 4 | 1 |
| `load.ugm.d32x8t` rd:1（32 B） | 64 | stride-0 `scale` `NRH_CH`，逐行 | 8 | **8** |
| `load.ugm.d32x16t` rd:1（64 B） | 64 | stride-64 `fb` `bias` `NRH_C`，逐行 | 8 | **8** |
| `store.ugm.d32x8t` rd:0 | 384 | `dbg`/`imgout` 的 `coopMatStore` | 52 | 8 或 4 |
| 其它（`d32x64t` store、`a64`、`d32x1t`、`slm`、`gtwy`） | 20 | — | — | — |

⇒ 528 条 = 64 个 `d64x64t` 块读 × 8 + 16 条尾/混装。

### 0.4 结论（三句话）

1. **来源 = `coopMatLoad` 的"线性块读返回 → DPAS 操作数布局"转换**，8 条/次块读，
   不是 A 交接、不是窄化、不是恒等拷贝。
2. **驱动力是内存布局**：`wb` 只读、行主序、stride 16 half 恰好连续，驱动就用
   **一条均匀单 lane 块消息 + 8 条寄存器交织**把它变成操作数布局。
3. 因此 n01 读法被证实，但也必须修正一句：**K/V 交叉 SG 的 store 侧确实已经是消费者
   B 布局，但 load 侧仍要付 8 条/片段的交织**（17 块 / 136 条，占 25.8%）。
   "store-in-layout" 只省掉了转置，没省掉 VNNI 打包。

## 1. 映射：生产者每个 (lane,component) 代表哪个 (token,channel)，消费者要求什么

### 1.1 片段坐标（只读头文件 `register_handoff.glsl`，未修改）

设 `l = gl_SubgroupInvocationID`(0..31)、`c = component`：

```
nrh_coord_A == nrh_coord_C == nrh_coord_CH:   row = 2c + (l>>4) , col = l & 15    (M-A)
nrh_coord_B :                                 row = 2c + (l&1)  , col = (l>>1)&15 (M-B)
```

双射性（n01 已证，本卡复核）：(M-A) 32×4 = 128 = 8×16，逆 `l = ((row&1)<<4)|col`、`c = row>>1`；
(M-B) 32×8 = 256 = 16×16，逆 `l = (col<<1)|(row&1)`、`c = row>>1`。

### 1.2 本卡改的那四次读：`scale` 片段的 (lane,component) → wb[] 线性下标

`coopMatLoad(m, buf, base, stride, LROW)` 的行主序下标是 `base + row*stride + col`。
本卡改的 4 个站点 **stride = 0u**，于是行项消失：

```
flat(l, c) = base + (2c + (l>>4)) * 0 + (l & 15) = base + (l & 15)          … (S)
```

`PROOF.json.site_map` 对 4 个站点 × 32 lane × 4 component = **512 个 (lane,component) 逐项枚举**，
每一项都给出"删前 A 站点 / 删前 B 站点 / 删后唯一站点"三个地址表达式，三者逐字相同。

| 站点（片段基址） | 删前 | 删后 | 消费者 1 | 消费者 2 |
|---|---|---|---|---|
| `wb[uint(pc.p2.x)+8u]` | 2 次 | 1 次 | `ny00 = nrh_widen_exact(x*scale)` | `ny10 = nrh_widen_exact(x*scale)` |
| `wb[uint(pc.p2.x)+24u]` | 2 次 | 1 次 | `ny01 = …` | `ny11 = …` |
| `wb[uint(pc.p2.y)+0u]` | 2 次 | 1 次 | `oc00 = nrh_widen_exact(y00*scale)` | `oc10 = …` |
| `wb[uint(pc.p2.y)+16u]` | 2 次 | 1 次 | `oc01 = …` | `oc11 = …` |

**(S) 的一个直接推论**：一个 lane 的 4 个 component 读到**同一个 half**（`l&15` 只依赖 lane）。
所以"同一 base 的两次 stride-0 读"在 32×4 上完全逐元素相同，不需要任何 lane 之间的一致性论证。
`PROOF.json` 另记 `row_invariance_holds = true`（`index == ribbon_index`）逐站点验证。

### 1.3 消费者要求什么 & 一一覆盖

- 4 个消费者全部是 `NRH_CH * NRH_CH → NRH_C`（逐元素半精度乘 + 精确加宽），
  仍按 (M-A) 逐 component 取 `x[c]`/`y[c]`，**取数点没变**：`scale` 片段本身还是同一个
  `NRH_CH`，只是不再读第二遍。
- 覆盖：8 个原站点 = 4 个首用点 + 4 个次用点；改后 4 个首用点各读一次、4 个次用点改读同一个
  片段变量。**没有漏读**（每个消费者仍有值）、**没有重复写**（`scale` 片段只被 `coopMatLoad`
  写过一次，之后只读）、**没有新增 store**。
- 尾块：这 4 个站点用推送常量基址（`pc.p2.x` / `pc.p2.y`），与 token/WG 无关，
  **本来就不在 `tok_oob` 的守卫里**（父源码 L116/124/132/140/931/938/945/952 全是无条件读），
  所以去重不改变尾块行为。`imgin`/`imgout` 的 4+4 个 `if(!tok_oob_u)` 守卫逐字未动。

### 1.4 528 条交织 mov 的 (lane,component) 映射（用于 §0 的结论，本卡未改）

对 `NRH_B`(16×16) 的 zip：源 GRF `rS` = 矩阵第 `S` 行（K = S），dst 把 `(K=2k, N=j)` 与
`(K=2k+1, N=j)` 装进同一个 dword。这正是 (M-B) 所要求的 VNNI 打包：B 的 component `c`
对应 `row = 2c + (l&1)`，即同一个 dword 里的两个 half 是**相邻 K**。与 §0.1 的置换逐字吻合。
**本卡没有改这条路径上的任何一次读**：`NRH_B` 载入 64 → 64 不变（`shape_census` 实测）。

## 2. 删了什么真实工作（正常执行路径，不计 debug 声明、不计编译器已消掉的源码）

### 2.1 源码层

改前（4 个"次用点"各一份）：
```
NRH_CH scale; coopMatLoad(scale, wb, base, 0u, LROW);   // 256 B 逻辑片段，32 B 真实数据
ny10 = nrh_widen_exact(x * scale);
```
改后：
```
ny10 = nrh_widen_exact(x * nrh_scale_x0);               // 片段在首用点已读
```

正常路径上消失的是 **4 次 stride-0 片段读**：4 个 `OpVariable`、4 条
`OpCooperativeMatrixLoadKHR`、以及它们的地址算术（`OpAccessChain` + `OpIAdd`）。
**不删**：任何 FP 表达式、任何窄化/舍入点、任何屏障、任何 SLM 往返、任何 `if(debug)` 发布。

### 3.1 阶段与 owner（本 shader，4 SG/WG，128 lane）

### 3.2 RAW / WAR / WAW（本卡涉及的 8 个站点）

| 值 | 关系 | 说明 | 本卡影响 |
|---|---|---|---|
| `wb[…]` → 4 个 `scale` 片段 | **RAW** | 全局只读 | 不变（仍读同一组 16 half） |
| `scale` 片段 → `x*scale` | **RAW** | 片段被乘 | 不变（同一片段的 4 个 component） |
| **`scale` 站点 A 的读 vs 站点 B 的读** | **无依赖**（两读互不写） | 原来各读一遍 | **删除其中一次** |
| `x`（imgin）→ `x*scale` | **RAW** | — | 不变 |
| `ny00`（C 累加器种子）与 `scale` 的寄存器复用 | **WAR** | 分配器视角 | 片段的活值窗口变长，可能改变分配（唯一真实成本） |
| `debug` 分支写 `dbg` | 与 `wb` 无别名 | 不同 descriptor binding | 不变 |
| `barrier()`（L576） | 全 kernel 1 处 | 输入侧 4 站点全在屏障**之前**，输出侧 4 站点全在屏障**之后** | **没有一次重排跨屏障** |

**供料保护**：4 个消费者的**发射点没有前移或后移**——本卡只换"值从哪来"，不换"什么时候可用"。
没有新增预取、没有拉长任何权重/A 的寿命、没有删屏障、没有动 SLM（`coopMatLoad` 80 / `coopMatStore` 60 不变，
shared 8192 B 不变）。

### 3.3 528 条交织 mov 的重叠性质（本卡未动，记录下来供后续卡）

它们与 DPAS 强耦合：一个 zip 块的 8 条 mov 必须在对应 `dpas.8x8` 之前完成，
与相邻块的权重载入/窄化并行。**这就是为什么"改布局"必须同时看发射时序**：
任何把 zip 拆成两次机会的写法都会拉长操作数就绪时间，反而伤供料。

## 5. 是否真落到 native（预测 + 判据，不声称已实现）

完整清单见 `NATIVE-PREDICTION.md`。摘要：

- 硬不变量（任何一项变化 = 实现错误，先查不计时）：
  `dpas.8x8 = 128`、`send.slm = 25`、`sync.bar = 1`、`math.rsqt = 16`、`scratch = 0`、`SLM = 8192`。
- 主判据：`send.ugm` **570 → 538**（目标区间 [−32, −24]）；
  `load.ugm.d32x8t` 条数 **64 → 32**。
- **A 类阈值（写死）**：`send.ugm` 下降 < 24 ⇒ 驱动已把这 8 个站点 CSE 成 4 个，
  本机制在本身份未形成处理 ⇒ 记"实现未落地"，不换写法重跑。
- zip mov：**必须恒为 528**。若变化，说明改动意外动了 `NRH_B` 块读 —— 那是实现错误。
- `mov` 合计：2245 → [2213, 2245]。
- 静态指令：4958 → [4918, 4934]（目标 4926）。
- 预期变化 kernel：body 变体一个（pipeline 2）；pipeline 1/3 不动。

## 6. 整体是否更快（本卡不能测，写清测什么、怎么归因）

- **要测的整体量**：`ordinary`（`warm 1 / reps 30 / feedback`）两臂 6 组交替的组均值差，
  配对 95% CI（df = 5）。同时保留 `fixed` / `fb2` 两套末帧 gold（合同 8.1）。
- **臂**：`base` = 链头 `n09c-f09-b-share`（`25cd7faf…`，**不是** handoff F10 基线）；
  `cand` = 本卡 `715ade76…`。只重指本组 7 个 PASS，其余 225 个 PASS 的已采纳改动全部保留。
- **归因边界（只写证据支持的）**：
  - 本卡覆盖 7/232 个派发；在这 7 个位置上删掉 32/570 条 `send.ugm`（5.6%），
    IR 少 52 条指令（−0.67%）。若 native 的 `send.ugm` 落在 [538, 546]，机制落地，
    此时才允许把计时差归因给本卡。
  - 若 `send.ugm` 没降（A 类），**不许**用整体毫秒倒推"机制无效"或"机制有效"。
  - 单卡上限估算：570 条消息里 32 条是均匀单 lane 块读，量级 0.03–0.10 ms；
    落在本协议的 ±0.09 ms 分辨率附近，**很可能判 D（INDISTINCT）**。
    本卡不因此改判方向 —— 528 条 zip mov 的不可删性（§0.4）是比计时更硬的结论。
- **这一族不要再当收益点的具名结论（更新 n01 的表述）**：
  F02 body 的 load 侧成本有三层，**只有第三层可从 GLSL 改**：

  | 层 | 量 | 可否从源码删 |
  |---|---:|---|
  | `d64x64t` 块读 → 操作数布局的 zip mov | 528（10.6%） | **不可**（渲染布局由只读 `wb` 的行主序决定；SLM 侧预置换会被驱动的固定置换二次置换，见 `RESUME` §5） |
  | `fb` bias 逐行 gather（stride 64 f32） | 64 条消息 + 64 条搬移 | **不可**（需要的 16 列在 `fb` 里不连续；换成连续读会读错数据） |
  | **重复的 stride-0 片段读** | 32 条消息 | **可 —— 本卡做的就是这个** |
