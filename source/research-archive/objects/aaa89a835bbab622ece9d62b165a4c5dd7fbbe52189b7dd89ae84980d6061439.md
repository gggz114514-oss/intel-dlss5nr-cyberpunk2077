# ANALYSIS — n12b-f14-scale（F14：Q scale 系数 hoist 出 group 循环）

卡：`n12b-f14-scale`，族 F14，ordinal **95 / 100 / 105 / 110 / 115 / 120 / 125 / 130**
（PASS 58/63/68/73/78/83/88/93，`vit_block31_qkv … vit_block38_qkv`，grid `3 × 96 × 1`，256 线程）。
八个位置共用同一个 SPIR-V 与同一份源码，所以本卡是一个 shader、一类机制、一次改动。

**本卡是 F14 包成员（与 `n12-vit-qkv` 合成 8 PASS / 2 个改动面）。**
源码父 = n12 的 `candidate.comp`（`b3c6e215…`，norm 倒数每 lane xor 树已实现）；本卡在它上面
只做一处代码移动，n12 的树/倒数/写域逐字保留。

**一句话改动**：`scales[pc.p2.z+(n0%1024u)/32u]` 原来写在 `for(group)` 内的 Q 分支里；驱动把

n12 候选 ISA `0x16F40`、`0x18190`），中间隔着 group 0 的 qkv store，编译期无法跨过 store 做 CSE。

谓词保护，K/V（`n0≥1024`）在父与候选中都**不读**这个系数。

## 1. 映射：生产者 (lane,component) 到底代表哪个 (token, channel)，消费者要什么

### 1.1 F14 生产者（v2 / n12 / 本卡三臂一致，本卡没动）

```
gx = gl_WorkGroupID.x (0..2)   gy = gl_WorkGroupID.y (0..95)   sg = gl_SubgroupID (0..7)
n0 = gy*32        mA = gx*128 + sg*8        mB = mA + 64
qkv[pc.p6.x + t*3072 + n]     3072 = 32 head × 32 channel；Q=0..1023，K=1024..2047，V=2048..3071
```

Intel B580 sealed CH 8×16 half 累加器的 lane 映射（本卡只依赖、未修改）：

| 量 | 表达式 | 含义 |
|---|---|---|
| lane 内 (row, col) | `row = 2*ci + lane/16`，`col = lane%16` | `ci` = 累加器组件 0..3 |
| token | `t = m + row`（`m ∈ {mA,mB}`） | 一个 subgroup 覆盖 16 个 token（两组各 8 行） |
| channel | `n = n0 + side*16 + col`（side 0=h0，1=h1） | 一个 workgroup 的 32 channel 正好一整个 head |
| head | Q `gy`；K `gy-32`；V `gy-64` | `gy = n0/32` |
| 归一化配对 | `f16vec2(h0[ci],h1[ci])` = 同 token 的 d 与 d+16 | 归约轴是行内 16 个 column |

### 1.2 本卡关心的新映射：系数 (gy → head → 输出元素)

| 问题 | 答案 | 证据 |
|---|---|---|
| 系数下标 | `p2.z + (n0%1024)/32`；Q 段 `n0 = gy*32` 且 `gy<32`，所以 `(n0%1024)/32 = gy`，下标 = `p2.z + gy = 0..31` | 地址表达式结构（`OpIAdd(load(pc.p2.z), OpUDiv(OpUMod(n0,1024),32))`）在父/候选**逐节点相同**；plan 的 8 行 PUSH 里 `p2.z = 0`、Scales 128 B = 32 个 float，界内 |
| 谁消费 | Q 段每个 lane 的 8 个 half 输出：`h0[0..3]`、`h1[0..3]`（token 由 `m,ci,lane/16` 定，channel `n0+col` / `n0+16+col`），全部乘同一个 `scale` | 源码；8 个 `vq_scale_q` 调用序列父/候选完全一致（`OpFunctionCall` 26 个，callee 序列相同） |
| 一个系数覆盖多少输出 | 一个 head 内：288 live token × 32 channel = **9,216** 个 Q 元素；32 个 head × 9,216 = 294,912 = 288×1024（= Q 段全部元素） | `evidence/INDEX-PROOF.json.scale`：每个 head 的 factor 集合恰好 1 个下标，`one_to_one=true` |
| 一一覆盖 | 每个 Q 写出元素的 factor 下标 = `n/32`；K 元素不用系数（`vq_scale_k`），V 元素完全不动 | 同上（K 记为 `K:no_scale`） |
| 尾块/padding | `288 = 36×8`，group guard `m>=p0.x` 与父逐行 `t<p0.x` 等价；padding token 288..383 **0 次写** | `INDEX-PROOF.json.tail` |
| 越界 | V 末端 `n0=3040,c=31 → n=3071`（行宽 3072）；head 31 三段各自贴边；行外写 0 | `INDEX-PROOF.json.boundary` |

### 1.3 生产者写集 = 消费者读集（逐元素枚举，不是抽样）

| 检查 | 结果 |
|---|---|
| 生产者写入元素 | **884,736** = 288 live token × 3072 channel（`equals_expected=true`） |

## 2. 删的是什么"真实工作"

计数来自 `evidence/SPV-STATICS.json`（本卡实编译）、`evidence/ISA-STATS.json`（只读引用
`queue/n12-vit-qkv/native/captures` 的两份当前批次 ISA：base = 基线 F14 SPV，n12_cand = 立即父 SPV）
与 `evidence/INDEX-PROOF.json`（逐实例枚举）。debug 路径（`pc.p0.w!=0u` 的 dbg store）不计、也未删。

### 2.1 逐项清单

| # | 删除项 | 静态 | 动态（每个 F14 dispatch） | 依据 |
|---|---|---|---|---|
| 1 | Q 系数标量读 `load.ugm.d32x1t.a32.bss[a0.0]` 的第二份 | **2 → 1** | **1152 → 768（−384，−33.33%）** | ISA 站点：父 `0x17390`/`0x18950`，n12 父 `0x16F40`/`0x18190`；枚举：父每个 live group 一次，候选每个 Q work-item 一次 |
| 2 | `p2.z` 的 push-constant 标量读 `load.ugm.d32x1t.a64.ca.cc.flat[A+0x48]` 的第二份 | **2 → 1** | 与 #1 同批（每个 group 副本一次） | ISA：父 `0x172F0`/`0x188B0`，n12 父 `0x16EA0`/`0x180F0` |
| 3 | 地址 setup `(W) add … r116.x` + `(W) shl … 2:w` 的第二份 | 各 **2 → 1** | 同上 | ISA：`0x17350/0x17370` 与 `0x18910/0x18930`（n12 父 `0x16F00/0x16F20`、`0x18150/0x18170`） |
| 4 | float→2×half 转换 `(W) mov r?.0<2>:hf r?.0<0;1,0>:f` 的第二份 | **2 → 1** | 同上 | ISA：`0x17430` / `0x189F0`（n12 父 `0x16FE0` / `0x18230`），每个后面恰好 8 条 `mul` 消费 |
| 5 | 上述 2/3/4 合起来在第二份 group 里的指令 | — | 预测 native **−7 条**（mov r1.q、mov a0、flat、add、shl、bss、conv） | 见 NATIVE-PREDICTION |

**没有删、也不该删的（如实记账）**

- **没有删系数乘法**：每个 group 仍是 8 个 `vq_scale_q`（`z*5.65625 → *inv → *scale` 三次 half 乘，
  顺序不变），父/候选 callee 序列完全相同。
- **没有删第一次读**：group 0 仍要读系数，只是这一次读被两个 group 共用。
- **没有删 qkv store / 没有改 store 宽度**：4 个 `OpCooperativeMatrixStoreKHR` 与地址表达式不动。
- **没有动 K 循环、A/B 供料、MH 收窄、norm 树、倒数**：立即父的 n12 改动逐字保留。
- **没有动 debug 路径**。

### 2.2 SPIR-V 侧的精确形状（可复核）

父/候选各只有 **1 个** Scales buffer `OpLoad`（SPIR-V 不展开 group 循环），差别只在**块位置**：

| 臂 | scales `OpLoad` 数 | 所在块 | 是否在循环内 | 守卫 |
|---|---|---|---|---|
| 基线 `72e2…` | 1 | 524 | 是（group 循环 header 371） | `n0<2048` + `n0<1024` |
| 立即父 `d008…` | 1 | 474 | 是（header 329） | `n0<2048` + `n0<1024` |
| 候选 `362e…` | 1 | 332 | **否（preheader）** | 仅 `n0<1024` |

系数在 SPIR-V 里本来就是 Function 存储的 f16 名为 `scale`（glslang 把块内局部变量提到函数作用域）：

| 臂 | 定义 store | 8 个消费者 `OpLoad` | 消费者是否在循环内 | Scales 写入 |
|---|---|---|---|---|
| 立即父 | 块 474（循环内，与 buffer 读同块） | 块 474 | 是（header 329） | 0 |
| 候选 | 块 192（0.0 初始化）+ 块 332（preheader，buffer 读同块） | 块 494 | 是（header 350） | 0 |

也就是说：**定义点出了循环，消费者仍在循环里**。驱动展开循环时能复制消费者读，却无法把
"定义 store + buffer 读"复制到循环外——这正是 native 2→1 的机制来源。

**数据流怎么保证消费者读到的是加载值**（不是 0.0 初始化）：候选的定义 store 在块 332（与
buffer 读同块），8 个消费者读在块 494。纯 CFG 支配**不成立**（块 494 还在循环内第二个
`n0<1024` 选择之下，见 `carrier_dominance.cf_dominance=false`），但：

| 检查 | 结果 |
|---|---|
| preheader 守卫 | 块 192，条件 `n0 < 1024` |
| 消费者守卫 | 块 391 `n0 < 2048` + 块 448 `n0 < 1024` |
| 两个 `n0<1024` 条件表达式 | **结构完全相同**（`OpULessThan(load(n0), 1024)`） |
| `n0` 的写 | 只有 prologue 块 5 一次；守卫前不再写（`n0_stable_before_guard=true`） |
| 结论 | 任何一次消费者执行 ⇒ preheader 守卫为真 ⇒ 块 332 的 load+store 已执行；0.0 初始化（块 192）在有值路径上被覆盖 |

`evidence/SPV-SUMMARY.json.carrier_dominance`（逐项可核）。

SPIR-V body 的全部 opcode 变化（其余一条不动）：

```
+1 OpBranch  +1 OpBranchConditional  +2 OpLabel  +1 OpSelectionMerge  +1 OpULessThan
+1 OpStore(0.0 init)  +1 OpLoad(读局部 scale)   (+1 OpLoad 是新增守卫对 n0 的读)
OpFMul 6→6  OpFAdd 5→5  OpExtInst 4→4  OpFConvert 9→9  OpCompositeConstruct 5→5
OpFunctionCall 26→26  OpCooperativeMatrix{Load,Store,MulAdd}KHR 4/4/4 → 4/4/4
OpGroupNonUniformShuffleXor 4→4  OpGroupNonUniformShuffle 0→0  OpBitcast 8→8
```

## 3. 重叠：原来怎么并行、本改动保护了什么

| 值 | 生产者 | 最后消费者 | 覆盖/退休者 | 冲突 |
|---|---|---|---|---|
| `accA0/A1/B0/B1`（FP32 累加器） | 64 次 `coopMatMulAdd` 链 | `MH(acc…)` 收窄 | 收窄后即死 | **RAW** 长链 → **WAR**（本卡不动） |
| `h0/h1`（half 片段） | `MH(acc)` | ①dbg store ②norm ③（缩放后）qkv store | qkv store 后死 | ②③ **RAW**；①只读 |
| `s01/s23` | `vq_pair_sum` | 4 步 xor 树 | 树完成后被倒数消费 | **RAW** 4 级（n12 改动） |
| `inv01/inv23` | `vq_rcp_own`（每 lane） | 8 次 `vq_scale_*` | 下一 group 覆盖 | **RAW**；组间 **WAR** |
| **`scale`（本卡）** | **preheader：`scales[p2.z+gy]` 读一次 → 0.0/值 store** | **group 0 的 8 次 `vq_scale_q`；group 1 的 8 次** | 循环结束退休 | **RAW**（跨 group 0 的整个 qkv store 块）；与树/倒数**独立** |
| qkv 元素 | 本 dispatch store | F15 下一次 dispatch load | — | 跨 dispatch **RAW**；地址互不相同 → 无 WAW |
| dbg 元素 | dbg store | 外部 | — | 不参与（p0.w=0） |
| Scales 元素 | 外部一次性填 | 本 dispatch 只读 | — | 只读（三臂 `OpStore` 到 binding 1 都是 0） |

**原来如何重叠**：`scale` 与 norm 树、倒数本来就无依赖，父里它的读被夹在倒数之后、第一次乘法之前
（native Q 段 `0x172F0` 起）；group 1 的那一份更是排在自己 group 的 Q 块里，前面隔着 group 0 的
16 条 qkv store。也就是说，原来 group 1 必须"先做完 group 0 的发布、再发自己的系数读、再等它回来
才能开始 8 次乘法"。

**本卡保护/改善**：系数读与地址计算移到 group 循环之前，两个 group 的 8+8 次乘法都消费同一个
half 值；group 1 的 Q 缩放不再依赖一次新的内存往返。K 循环、A/B 供料、norm 树、屏障、写域
**一律不动**——删掉的是一次重复读，不是一段流水。

## 4. 新增成本（全部入账）

|---|---|---|
| 重复权重/A 读取 | **0** | K 循环与 coopMatLoad/MulAdd 4/4 不变 |

| 代码体积 | SPIR-V **+29 words / +116 B**（4596/18384 vs 4567/18268）；native 预测 **−5..−7 行**（7498 → 7491..7496） | 逻辑字节 ≠ DRAM 字节；本卡不释放任何内存对象 |

| 数值 | **0 变化** | 见 §5 与 PROOF.json |

`OpStore` 都是 **0**。所以把读提前到 qkv store 之前不可能读到不同的字节。

## 5. 是否真落到 native（预测 + 判据，不声称已实现）

完整清单在 `NATIVE-PREDICTION.md`；三条硬判据（看不到就等于没实现）：

1. **`load.ugm.d32x1t.a32.bss[a0.0]` 站点 2 → 1**（父 `0x17390`/`0x18950`；n12 父 `0x16F40`/`0x18190`），
   且剩下的那一条必须**早于**两个 group 的 Q store 块；`flat[A+0x48]` 同步 2 → 1。
2. **一个 half 寄存器被 16 条 `mul` 消费**（group 0 8 条 + group 1 8 条），而不是父里的 8+8 由两次转换各自供料。
3. **不变项必须真的不变**：`dpas.8x8 256`、`math.rsqt 8`、`sync.allrd 3`、`goto/join 0`（n12 签名）、
   `scratch 0`、`workgroup memory 0`、`max_r ≤ 127`；`send.ugm` **不得增加**（预测 1224 → 1222）。

若站点仍是 2 → **A（实现未落地，驱动把读沉回第二份）**，不得记"方向无效"。

## 6. 整体是否更快（要测什么、用哪条臂、怎么归因）

- **臂**：`base` = 构建时的当前链头 `accepted/n06b-f06-c64-20261027`（`7ad5b99d…`）；
  `cand` = 本卡 `plan.txt`（`82be522e…`，只替换 F14 的 8 行；若 CURRENT.json 之后又前移，
  主代理用 `COMMON.rebase_candidate_plan` 重生成，仍是同样 8 行、同样候选 SPV）。注意 cand 臂包含
  **F14 包的两个改动面**（n12 norm 树 + 本卡系数 hoist），因为 8 个 PASS 共用一个 SPV，
  不存在"只替换其中一面"的合法状态。
- **先看 native（A 类）**：按判据 1–3 定性；n12 的签名（goto/join、`r[a0]`）与本卡的签名
  （scalar bss 站点、flat A+0x48）互不重叠，可以在同一份 ISA 里分别确认两面都落地。
- **数值/资源**：`fixed`（frame0 `1755e9c2…`）、`fb2`（frame0 同、末帧 `9c3e511e…`）、
  `ordinary`（末帧 `2b63d4ba…`）。本卡预期**逐位相同**；任何差异 = E 类实现错误（首选怀疑：
  ①读到旧值/别名 ②num 门用错 gold ③plan 替换错行）。
- **计时**：两臂、6 组交替顺序、每组 30 帧（warm 1、feedback），540 样本全留，按进程组均值差
  算 t(df5) 区间；不剔尖峰、不补跑。
- **归因边界**：n12 单独测过 −0.006942 ms（CI[−0.102441,+0.088558] 跨 0，D 类）；本卡是
  在一个 7,498 条指令、256 条 DPAS 的 kernel 里再省 384 次标量读（−7 条指令），**不得把两个数相加**，
