## 2. Cost account

All counts are **per invocation (lane)** unless stated; the dispatch grid is not in the plan, so
per-WG figures use `local_size_x=128` = 4 SGs × 32 lanes and the grid multiplier is applied by the
runner at execution time. These are *source-effective* counts, not measured DRAM/queue traffic.

### 2.1 Deleted

| item | count | where |
|---|---|---|
| shared E staging | **8192 B per WG** (declared LDS 18432 → 10240) | `sE8[8192]` |
| E int8 shared stores | **64 byte stores per lane** (16 fragments × 4 components) = 8192 per WG = 8192 source bytes | 16 `nr_i8_put_e` calls, parent 293…469 |
| E shared reads | **64 B per lane** (4 × `I8B` coopMatLoad, 16 B/lane each) = 8192 B per WG | parent 482 (`sE8` load in the `kg` loop) |
| barriers | **2 instructions**: `subgroupMemoryBarrierShared()` + `subgroupBarrier()` (parent 472–473) — 2 barrier events per SG, 8 per WG | between expand and contract |
| `nr_i8_put_e` address math | ≈ 5 int ops (udiv, umod, imul, 2× iadd) × 4 components × 16 calls ≈ **320 int ops per lane** | inside the deleted function |

The two barriers that survive are exactly the ones that must: the X publication (now 230–231) and
the cross-subgroup K/V publication (`barrier()`, now 892). **No cross-SG sync was touched**
(`evidence/SPV-DELTA.json`: the device-scope `OpControlBarrier` is present in both modules, only the
subgroup-scope E pair disappears).

### 2.2 Added

| item | count per lane | note |
|---|---|---|
| `c2_i8_pack` | 16 calls = 48 shifts + 48 ors | the 64 `nr_i8_code` quantisations are **unchanged** in count and order |
| `c2_i8_join_B` | 4 calls × 8 `subgroupShuffle` = **32 shuffles** | 8 shuffles per K32 (2 per word), not 16: the two K halves of each word are fetched once |
| byte extract | 4 × 16 = **64 × (shift + and + compare + select)** | exact inverse of the pack's byte insert |
| int8 conversion | 64 `OpSConvert` | same count as the deleted `int8_t()` conversions |
| component-wise fragment build | 4 × 16 = 64 inserts | same shape as the shipped `nrh_join_rows_to_B` (243 instructions vs 240 for `c2_i8_join_B`) |
| live-range extension | 4 `I8C` accumulators (16 int32) now live from K32 step 0 to the epilogue, overlapping the 2 expand accumulators (8 int32) | see 2.4 |

Per hidden channel: one code per (channel, token); per 4 codes (one lane's share of a fragment) one
pack, two shuffles, four byte extracts. I.e. **0.25 pack, 0.5 shuffle, 1 byte extract per code**.

### 2.3 Net, in one line

−8192 B SLM/WG, −64 byte stores and −64 B loads per lane, −2 barriers, −~320 int ALU
against +32 shuffles, +~380 int ALU, +64 int8 conversions (unchanged) and a longer accumulator
live range. Shared-memory traffic falls by 128 accesses/lane; the replacement is shuffle+ALU work,
which is *cheaper per op* on paper but 2.6× more operations. **The trade is not decidable on
paper** — that is precisely why this card asks for one GPU pair rather than an argument.

### 2.4 Register pressure (the named risk)

| | parent | candidate |
|---|---|---|
| expand accumulators (`I8C`) | 2 (8 int32), per group | 2 (8 int32), per group |
| contract accumulators (`I8C`) | 4 (16 int32), live **after** the barrier only | 4 (16 int32), live **from K32 step 0** |
| peak live 32-bit | ≈ 20–24 | ≈ 32–36 |
| private/local storage | 0 B | 0 B (`SPV-DELTA`: `private_bytes 0 → 0`) |

So roughly **+10 int32 registers per lane** at the peak, for most of the expand stage. Whether IGC
spills or lowers occupancy is a native question → **`U1`, unknown**.

## 4. CPU conclusions (and what they are worth)

1. **The register `B32x16` is the same logical matrix** the parent loaded from `sE8`, element for
   element, for all 4 K32 steps (COORD-PROOF C6: 2048/2048). This rests on the *measured* Intel
   B580 int8 map, which this card only reads (sha `fb80ea76…`); it was not re-measured here.
2. **Every code value is bit-identical**: same `nr_i8_code`, same inputs, same scalar, and the
   byte insert/extract pair is an exact inverse on `[-127,127]` (SCALE-ROUND-PROOF S3).
3. **K=128 is fully covered in the original order**, with the original single dequant and single
   seed add (FULLK-PROOF K1…K6).
4. Therefore the candidate is *argued* to be numerically identical to the parent for every input.
   This is a **source-level argument, not a measurement**. The card does not and cannot call it a
   numeric pass; that is `U2`.

### 4.1 One observation about the frozen parent, recorded but not repaired

`SCALE-ROUND-PROOF` **S5**: the frozen scale pack has `sX*invX = 127.00000219` and
`sE*invE = 127.00000923`, i.e. `invS = 127/sS` where the dequant taps (`fsc[4+f] = sX*sWe[f]`,
`sWe = absmax/127`) imply `invS = 1/sS`. Under the stored values every `|E| ≥ sE = 0.03617127`
saturates to ±127, and likewise every `|X| ≥ sX = 0.06625246` — a very strong quantiser. This is a
property of the **parent** (`c32_b1_scales.f32.bin`, sha `f3053c8c…`, cross-checked against
`C32-I8-PACKS.json` and `C32-I8-SCALE-STEPS.json`), not of C2: C2 copies `fsc` verbatim with the
same indices, so C2 ≡ parent whatever the scales mean. It is flagged for the coordinator, not fixed.

## 6. Decision rule for this card (fixed now, before any measurement)

1. Gate mismatch → **STOP**: the measured int8 ABI is dead; do not tune scales, do not add a
   fallback, close as FAIL.
2. Gate equal **and** ordinary faster/flat → hand to integration.
3. Gate equal **and** ordinary slower → **CLOSE the card**. SLM got smaller and the kernel got
   slower, therefore the trade is rejected. **No "fuse a little more" loop, no second variant, no
   re-opening on another position.**
4. Micro-optimisations of the join (e.g. hoisting the byte extracts) may not ride along in the same
   run; they would be a new candidate with its own CPU proof and its own gate.

## 7. Is this worth a GPU gate?

**Yes — one pair, and it is one of the cheaper gate decisions in this package**, for one specific
reason: the gate has a *predicted* outcome. Everything the MMA consumes is provably unchanged on
CPU, so a byte-identical result is the expected result, and a difference is an immediate, decisive
falsification of the measured int8 ABI that other cards in this family also depend on. Either
outcome is worth the slot. The ordinary arm is also informative here (unlike a pure bookkeeping
card): −8192 B SLM/WG and −128 shared accesses/lane against +32 shuffles is a real trade that only
timing can settle.

If the coordinator can afford only the gate and not the ordinary arm: **run the gate** (it is the
ABI check). If only the ordinary arm: run it, but then the card stays `CPU_STRUCT`-qualified and
the numeric claim stays unverified.
