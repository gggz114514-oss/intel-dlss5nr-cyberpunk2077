## 2. X 同源对账（任务第 2 项）

### 2.1 生产者只有一个

`nrf_lift(sg, g)`（`c32_f1_i8.comp:1714-1722`）= `coopMatLoad(nrf_feat, q*256, 16, LCOL)` ×
`coopMatLoad(lift, wb, p7.x + g*128, 16, LROW)` → `NRH_C`（fp32）→ `nrh_narrow` 一次舍入 →
`NRH_CH`（8 行 = 通道 × 16 列 = token）。`g=0..3` → 32 通道。**X 只被计算一次**，
debug 存储与 int8 量化拿的是**同一个 `x0..x3` 寄存器值**（源码 203-210 存，218-221 量化），
不存在第二次 lift 求值。

### 2.2 两份拷贝的地址对账

| 项 | debug 拷贝 | 消费拷贝（int8） |
|---|---|---|
| 载体 | binding 4 / 资源 455 / `float16_t dbg[]` | `shared int8_t sX8[2048]` |
| 区域 | half 22528..24576（4096 B） | sX8 0..2048（2048 B） |
| 元素地址 | `22528 + sg*512 + tok*32 + ch` | `sg*512 + tok*32 + ch` |
| 布局 | `coopMatStore` LCOL，8 行(通道)×16 列(token)，stride 32，四片基址 +0/+8/+16/+24 | `coopMatLoad(xb8, sX8, sg*512, 32, LCOL)` → I8B 32(K=通道)×16(N=token)，同一 stride |
| 写入覆盖 | lane `lv`、分量 `i` → (row = 2i⊕(lv>>4), col = lv&15)，32 lane×4 分量 = 8×16 **双射**，每 sg 512 个元素各写一次 | 同一映射，逐字节写 |
| 有效域 | 4 sg × 16 token × 32 ch = **2048** | 同 |

**地址层面：同一块、同一公式、同一有效域**。debug 的 stride 32 与 +0/8/16/24 的四片基址，
恰好把"4 个 8×16 片"拼成与 `sX8` 完全相同的线性序，没有偏移/转置/stride 差异。

### 2.3 消费点（pass 读取点）

1. **INT8 expand**：`coopMatLoad(xb8, sX8, sg*512u, 32u, LCOL)`（`c32_f1_i8.comp:260`），16 处静态 MMA；
2. **FP16 seed**：`seed = x_g * scale`，`scale` 由 `coopMatLoad(wb, p2.x+8, stride 0, LCOL)` 得到
   ——**stride 0 ⇒ 单一广播 half `wb[17288]`**，再 `nrh_widen_exact` 进 contract 的 FP32 累加器。
   参考臂模型是逐通道 `rs[c] = pack[17280+8+c]`。第 3.4 节的闭合证明：用逐通道模型重算 2048 个 Y
   **全部逐位相等**，所以在这份捕获上广播式与逐通道式数值等价，**seed 不是失败的自由参数**。

### 2.4 判定

**同源成立（块/坐标/域），逐位不成立（值）**：2048 个 (token, channel) 中有 **5 个**，
kernel 真正量化的 int8 code 与"用 dump 出来的 half 重新量化"的 code 差 ±1。
差异量级 ≤ 1 个 half ULP，且全部发生在取整边界（见 §3.2 的统计）。

## 3. 首差定位与归因（任务第 3 项）

### 3.1 比较序上的首差

| 数组 | 坐标 | dump 下标 | GPU 臂 | 参考臂 | 差 |
|---|---|---|---|---|---|
| E | token 23, feature 0 | 2944 | 0.054656982421875 (`0x2aff`) | 0.055328369140625 (`0x2b15`) | 6.7e-4 |
| Y | token 23, channel 0 | 8928 | −0.34716796875 (`0xb58e`) | −0.34423828125 (`0xb582`) | 2.9e-3 |

差异只出现在 **5 个 token**：`23, 24, 30, 46, 52`（E 与 Y 的受影响 token 集合完全相同），
其余 59 个 token 的 E、Y **全部逐位相等**。这是"少数位置事件"，不是系统性数学错误。

### 3.2 根位置：5 个量化边界事件

对每个异常 token，用**精确重算**（不靠反解，直接穷举 `code[k] += d` 后重算整行 E 和 Y）验证：
存在且仅存在一个 `(channel, d)` 使该 token 的 **128 个 E 与 32 个 Y 全部逐位命中**。

| token | sg | patch (x,y) | channel | dump X (half / bits) | X·invX (f32) | 边界距离 | half ULP | code（dump→消费） |
|---|---|---|---|---|---|---|---|---|
| 23 | 1 | (7,1) | 19 | 0.48974609375 `0x37d6` | 34.5018959 | 0.00190 | 2.44e-4 | 35 → **34** |
| 24 | 1 | (4,2) | 14 | 0.035491943359375 `0x288b` | 2.5003555 | 0.00036 | 3.05e-5 | 3 → **2** |
| 30 | 1 | (6,3) | 1 | −0.50390625 `0xb808` | −35.4994583 | 0.00054 | 4.88e-4 | −35 → **−36** |
| 46 | 2 | (2,7) | 8 | −0.30517578125 `0xb4e2` | −21.4991875 | 0.00081 | 2.44e-4 | −21 → **−22** |
| 52 | 3 | (4,5) | 6 | −0.27685546875 `0xb46e` | −19.5040627 | 0.00406 | 2.44e-4 | −20 → **−19** |

- `invX = fsc[1] = 70.44853973388672`（`1/sX`，`sX = 0.014194758608937263`）。
- 5 个位置的取整边界**都落在 dump 值的半个 half-ULP 区间内**；翻转方向**混合**（4 个向小、1 个向大），
  所以**不是**某种舍入模式（截断/RZ、或 invX 整体偏移）造成的偏置，而正是"量化器吃到的值与 dump 出来的值
  相差 ≤1 half ULP"的特征。
- 偶然概率：边界落入半个 ULP 区间的概率 = `ULP·invX`，五个位置（半 ULP 分别为 2.44e-4、3.05e-5、
  4.88e-4、2.44e-4、2.44e-4，`invX = 70.44853973388672`）分别是 **1.72e-2、2.15e-3、3.44e-2、1.72e-2、1.72e-2**，
  **联合 ≈ 3.8e-10**。

### 3.3 优先级判定

| 候选 | 判定 | 依据 |
|---|---|---|
| **窄化点**（lift 累加器 fp32→f16 的窄化 vs int8 code 点） | **CAUSE** | 5/5 根位置边界落在半个 ULP 区间；方向混合；其余 59 token 逐位一致 |
| lift 段 | **排除为本次失败原因** | 同一寄存器值同时喂 debug 与量化；无第二次 lift 求值；修正 5 个 code 后 dump 的 X 能逐位重建 E/Y。注意：该门**按构造看不见 lift 错误**（它把 dump 的 X 当输入），所以本卡既不指控也不为 lift 背书 |
| scale 应用点 | **排除** | `invX / mult_e[128] / mult_c[32]` 对 59 token 已经逐位成立，修正后 64 token 全部成立 |
| dump 选错块 | **排除** | 区域、偏移、stride、元素公式、有效域 1:1 对账通过；饱和计数（x=1, e=1）也逐值重放一致 |

### 3.4 闭合证明（本卡的核心证据）

只把这 5 个位置的 code 改成 kernel 真正消费的值（其余一切不动、不调任何阈值），用同一份 dump 重算：

- **E：0 / 8192 不等**
- **Y：0 / 2048 不等**

即 630 + 151 的**全部**差距都由这 5 个量化边界事件解释；INT8 expand/contract 的整数累加、
FP32 反量化乘子、激活、FP32 seed、单次窄化**全部逐位正确**。
这是 CPU 重放闭合，**不是** GPU 门通过：GPU 门的输入（X）本身仍与消费值差 1 ULP，
所以门在"零容差"口径下仍然**打不开**——除非把量化器输入 dump 出来（§6）。

### 3.5 对历史假设的更正

`work/int8-coverage-v2-20261020/C32-BATCH-REPORT.md:91-93` 写的是
"最可能是 fused lift/feature 路径的边界 token 与 debug X 不完全同一输入"。

- **"lift 路径"**：不成立为原因（§3.3）。

### 4.3 INT8 的实际入口

- **expand**：`w8[0..16384)`，16 个 1024 B 块，`w_e(f,k) = w8[(f//8)*1024 + k*32 + (f%8)]`；
  输入 `sX8` 的 code；`nr_i8_deq(a, mbase, 4)` → `f32(acc) * fsc[4+mbase+row]`；epilogue 一次 f16 窄化 + 4 次 `nr_act_h`。
- **contract**：`w8[16384..32768)`，`w_c(o,e) = w8[16384 + ((o//8)*4 + e//32)*1024 + (e%32)*32 + (o%8)]`；
  输入 `sE8` 的 code；`nr_i8_deq_add(a, mbase, 132, seed)` → `f32(acc)*fsc[132+mbase+row] + seed`；
  K=128 走完才窄化一次。
