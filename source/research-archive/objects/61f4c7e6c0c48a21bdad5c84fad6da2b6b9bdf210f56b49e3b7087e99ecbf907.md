## 4. Pack 证据：证明它就是那块 FP16 矩阵，不是"另生成一份"

### 4.1 内核真正读的两种布局

```
INT8（本卡）：coopMatLoad(b, gWo8, (n0/16)*4096 + ki*512, 32, LCOL)   32x16, 列主, 列步长 32 B
  ⇒ byte = (n/16)*4096 + (k/32)*512 + (n%16)*32 + (k%32)     [ng][ki][c][r]
FP16（父，部署形态）：coopMatLoad(b, pack, wo + n*256 + k, 256, LCOL) 16x16, 列步长 256 half
  ⇒ W[n][k] = pack[wo_half + n*256 + k]
反量化：coopMatLoad(wsc, gWosc, n0, 0, LROW) ⇒ 一列一个 float，即**逐输出通道**步长 sc[n]
```

判据不是"像不像"，而是用**错误布局做负对照**（同一 65,536 字节换个解法必须明显变差）：

| 布局 | rel_L2 范围（15 块） | 结论 |
|---|---|---|
| 内核布局 `[ng][ki][c][r]` | **7.168e-03 … 7.525e-03** | 正确 |
| 行主 `[n][k]` | 1.401 … 1.433 | 错 |
| 列主 `[n][k]ᵀ` | 1.428 … 1.441 | 错 |
| 分组内 c 连续（貌似合理的错解） | 1.419 … 1.433 | 错 |
| 内核布局但 W 转置 | 2.277 | 错 |

### 4.3 两种 FP16 pack 的关系（这条否则会误判）

G3 部署的 pack（`round4-integrated/.../swin_16_weights.fp16.bin`）与 GPU fixture 用的 pack（`s1-output-complete/c256/packs-WO-only/…`）**前 131,072 字节不同**，因为两者是同一矩阵的两种布局：

```
retile(round4-integrated[0:65536] as [n][k]) == packs-WO-only[0:65536] as [N16][K16][N16][K16]   ✔ 逐位相同
round4-integrated[0:65536] == artifacts/block16/pack/c256_weights.fp16.bin[0:65536]               ✔ 逐位相同
```

前者是部署内核的 `[n][k]`，后者是 `c256_d4_full.comp`（fixture 实际跑的模块）的 `[N16][K16][N16][K16]`（`coopMatLoad(b, pack, wo + (n0/16)*4096 + (k0/16)*256, 16, LCOL)`）。所以 §4.2 用部署 pack 得出的"int8 pack = 该矩阵的量化"与 §5 用 fixture pack 做的参考是**同一块矩阵**，可以互相对照。

### 5.1 先证明模拟器就是父算术（否则后面没有意义）

| rel_L2 / SNR | 7.579e-06 / 102.41 dB |
| **负对照：把 shift 当 (0,0)** | 逐位相同 **0.0084%**、rel_L2 **1.349** → ABI 的 `shift=(-1,-1)` 读法被反向证实 |

### 5.2 INT8 臂（同一 T/Y、同一权重矩阵，同一 shift）

内核顺序：逐 tile（64×256）求 `amax` → `invC=127/amax`、`sC=amax/127`（f32）→ `code=clamp(roundEven(T·invC),±127)` → 8×K32 `int8×int8→int32` → `acc = seed + float(iacc)·(sc[n]·sC)`（f32）→ 舍入 half。

| 指标 | INT8 vs 父 FP16（同一模拟器） | INT8 vs GPU 抓取 `image_out.bin` |
|---|---|---|
| rel_L2 | **0.4977%** | 0.4977% |
| SNR | **46.06 dB** | 46.06 dB |
| absmax | **0.01221** | 0.01221 |
| RMS | 1.765e-03 | 1.765e-03 |
| 相关 | 0.99998762 | 0.99998762 |
| 逐位相同 | 10.23% | 10.23% |

辅助量：逐 tile 激活 `amax` 0.7778 … 1.6025（**动态、逐 workgroup**）；激活码饱和 80/1,032,192 = **0.0063%**；`int32 == int64` 在 77 个 tile 上**全部成立**；最坏 `|dot| ≤ 256·127·127 = 4,129,024 < 2³¹`（不会溢出），也 **< 2²⁴**（int32→float 转换精确，`dequant` 前的 `MAT_C(iacc)` 无损）。

**这些是 CPU 模拟数字，不是数值门。** 它们说明：机制在真实数据上可算、可对齐、误差量级是 8 bit 权重量化 + 逐 tile 激活量化的正常水平（0.5% rel_L2），并且 int32 累加在 K=256 上确实够用。它们**不**说明内核在设备上行为正确（见 §7）。

## 7. 具名缺口（按诚实口径分类）

**已完成**：待实施 → 编译 → 接线 → 静态零残余（模块级 0 FP16 MMA）→ pack 身份 → CPU 整数参考。

**未完成（不得声称通过）**：

1. **GPU 单帧未测量（本卡）**：没有任何 plan 级 GPU 执行，因此**没有本卡的 PSNR、没有 fixed-input 门、没有反馈门、没有 ordinary**。`run/gpu/WO-SWEEP.json` 的 45.95 / 46.02 / 39.25 dB 是别人对**另外三份单用途 plan**的单帧测量，其中两支跑的是 `C256_QX_HALF_MODE=0` 的模块（与部署 qX 语义不同），qx_last 那支还有 §1 的 binding 缺陷，**都不是本卡结果，也不是验收**。
2. **数值通过 / 质量通过：均无**。本卡只给出 CPU 模拟参考（§5）；仓库内没有既定的 INT8 容差（`run/codex-sol-int8-pilot-20261018/v3/QUALITY-FOUNDATION-AND-PROPOSAL.json`），0.4977% rel_L2 / 46 dB 只是本臂与父 FP16 的距离描述。
3. **qX 外延未被数值覆盖**：`emit_qx` 逐字继承（含 mode=1 的 precise-half 语义），但夹具只带 T/Y/image_out，**没有 qX 参考**。所以"这 13 个 PASS 仍给下游 FFN 正确的 qX"目前是**代码身份 + 静态布局**论证，不是数值论证。
4. **scale 资格**：`sc.f32` 是**从 FP16 权重矩阵按 `max|W[n,:]|/127` 重算**的逐输出通道步长（本卡已证明与已发货码逐码一致），它是**权重**量化器，不是激活标定；激活步长是每 workgroup 动态求的 `amax`。没有做过任何标定流程，也没有多帧统计。
5. **设备行为**：`M8N16K32 signed int8 → int32` 在这个模块 + 这版驱动 + 32 子组上的实际行为，本卡未验证；`PRECISE`/`ROBUST` 语义、`coopMatLoad` 的 int8 LCOL 步长在设备上的实现都只有源码与 SPIR-V 依据。
6. **native 资源**：没有任何 GRF / SLM / occupancy 数据。`shared 17416` 是 **SPIR-V 静态声明值**（从 Workgroup 变量类型算出，与 plan 一致），不是 native 分配。
7. **性能**：无。静态上每输出 tile 的 MMA 步数由 16×K16 变 8×K32（动态次数减半），但没有一次真实计时，因此**不写毫秒、不下性能结论**。
