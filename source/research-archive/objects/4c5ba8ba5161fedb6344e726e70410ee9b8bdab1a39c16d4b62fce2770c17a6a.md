## 3. 动态 scale 合同（Q/K/V/P 四类）

`evidence/SCALE-CONTRACT.json`。先说清**已有的两个 scale 不是**本卡的动态 scale：

| 已有 scale | 资源 / offset | 轴 | 产生点 | 实测（block23） |
|---|---|---|---|---|
| QKV 输出 scale（`wsc`） | binding 10 = `wqkv + 786432`，6144 B = 1536 float | per（head, 输出通道） | 离线权重包 `split16_bNN_wqkv.int8.bin`（792576 B = 786432 int8 + 6144 scale） | 1.585e-4 … 3.397e-4 |
| 注意力 scale（`aux[p4.y+h]`） | binding 1 = `aux + 262144 B`（float 索引 65536+h） | per head（16 个） | 离线 aux 包 `split16_aux.bin` 尾部 | 0.0145 … 2.446 |

本卡新增（全部在 WG 内推导，**不新增 binding、不新增 push 字**）：

| scale | 从哪来（资源/offset/产生点） | 范围 | 消费者 |
|---|---|---|---|
| **V**（已实施） | 无资源；`shared uint shVMax`（4 B）。256 线程扫 `qkv[4096..6144)` 全部 2048 个 half，`atomicMax(floatBitsToUint(abs(float(V))))`；由父已有的 **post-score barrier** 发布 | **per workgroup = per (head, window)** | `sV=|V|max/127`；`sv8[f]=i8code(V[f],1/sV)`；反量化因子写进 `shPsf` |
| **P**（已实施） | 无资源；`shared float shPsf[1024]`（4 KB）。行 owner 线程（`lid<64`）在自己已经做 `sp[e]=sp[e]*inv` 的那个循环里顺便取该 query 64 个 P 的最大值 | **per query（per token, head）**，每 WG 64 个 | `sP=pmx/127`，`pInv=127/pmx`；P8 写进 `sy8`；`shPsf[q*16+c]=sP*sV` |
| **Q**（合同，未实施） | 无资源；应在写 `Q(e)=qs` 的同一个 norm pass 里取每行 32 通道 absmax | per token per head（64 行） | QK 的 A 侧 dequant（见 §9 GAP-QK） |
| **K**（合同，未实施） | 同上，取 `K(e)=kn` 每行 absmax | per token per head（64 行） | QK 的 B 侧 dequant |

**证明没有借用 QKV 权重 scale**（五条，逐条可查）：

1. **资源不同**：QKV scale 在 binding 10（`wqkv+786432`），注意力 scale 在 binding 1
   （`aux+262144 B`）；新 Q/K/V/P scale 只在寄存器与 `shared`（`shVMax`、`shPsf`），
   一个描述符都不读。SPV 侧证据：候选的 opcode 差集里**没有**新增对 buffer 的
   `OpCooperativeMatrixLoadKHR`/`OpLoad`（新增的 4 条 coopmat load 全部来自 `sy8`/`sv8`；
   新增的 `OpLoad` 47 条是循环临时量与两个 shared 变量的标量读写）。
2. **轴不同**：QKV scale 是 per（head, 输出通道）——一个按通道索引的数组在数学上
   无法表达 per-token 或 per-query 的 absmax；注意力 scale 是 per head 的单一标量。
3. **量级不同**：1.585e-4…3.397e-4（QKV）与 0.0145…2.446（注意力）对比本臂实测
   `sP` 2.06e-4…3.79e-4、`sV` 2.84e-2；互相顶替会让反量化后的乘积差 2–4 个数量级。
4. **寿命不同**：QKV scale 在 QKV store **之内**、任何 norm 之前被消费；norm 会重新
   缩放整行，所以 norm 之前的 scale 不可能描述 QK 消费者看到的 norm 之后的量级。
5. **数学位置不同**：`wsc` 作用于 int32 QKV 累加器（→half 之前），是"投影输出"的
   dequant；QK 的动态 scale 必须作用在 **norm 之后、QK 的 int32 累加器之上**，
   两者不是同一个乘积的两个因子。

**P 的归一化时机（split vs ViT，逐条）**：

| 条目 | R12 split16（本卡） | ViT（r15） | 后果 |
|---|---|---|---|
| P 归一化位置 | **PV 之前**：`sp[e]=sp[e]*inv`，`inv=1/max(total,2^-14)`，行 owner 线程写，然后 WG barrier，再 PV | PV **之后**：P 未归一化进 PV，`1/max(den,6.198883056640625e-05)` 在全部 key chunk 之后对 context 分子用一次 | split 的 int8 码量化的就是 FP16 PV 会乘的那个 half；ViT 的 int8 累加器里必须只有分子 |
| P 是否落地 | 落地：`phase[4096]` half 矩阵（父为分母树已有），量化搭现有 barrier | 不落地：寄存器交接（`sp[4096]`/`den[64]` 已删） | split 可以"读回 half 再量化"；ViT 必须在寄存器里量化 |
| P 上界 | `P<=1` 恒成立（`exp>0`，`inv=1/max(Σexp,2^-14)`），所以 `pmx*(127/pmx)=127` 永不饱和 | P=exp(·)，只受 exp 域约束（1.03125…1.5693），行和未归一 | split 可证不饱和；ViT 需按 chunk 取 max 且不能假设 ≤1 |
| per-query max 的成本 | 0 次 shuffle：一行 64 个 P 全在同一个线程（`lid<64`）手里 | 需要 `subgroupShuffleXor(16)`（一个 query 的 4 行在 `lane^16` 上） | 不能把 split 的"无交换"结论搬到 ViT，也不要把 ViT 的 shuffle 搬回 split |
| 反量化因子的位置 | PV 出口一次 `CF(acc)*sfm`，`sfm=sP*sV`，再一次 `CH` 窄化 | 反量化/倒数在 PV 循环之外，作用在 context 分子上 | 两者的 int32→half 窄化点不同，不能共用一份 epilogue 参考 |
| 分块 | 64 query × 64 key / WG，8 个 SG 各 8 query；K=64 分 2 个 K32 片 | 32 头 × 32 维、288 token；4 个 dim 片段、每片 N=16 query，16-key chunk | owner 与 K 顺序都不同；本卡不照搬 ViT 的 P 时机 |

## 4. 实施的段：PV（两个模块各一份候选）

**改法（C1–C8，`evidence/CHANGE-SET.json` / `CHANGE-SET-b30.json`，脚本化应用，
每个锚点必须出现且仅出现一次）**：

- **C1** 新增 `shared int8_t sv8[2048]`、`shared float shPsf[1024]`、`shared uint shVMax`；
  P 的 int8 码复用 `sy8[4096]`（QKV staging 在 QKV 循环结束后已死，尺寸正好 4096）。
- **C2** `i8code(half v, float invs)`：与 R04 实测 adapter 同一算术（一次 FP32 缩放、
  一次 `roundEven`、一次 clamp[-127,127]）。
- **C3** `if(lid==0u) shVMax=0u;` 放在 main 首部——由父已有的 post-QKV barrier 发布。
- **C4** V absmax 扫描放在 **post-norm barrier 之后、QK `j` 循环之前**（256 线程 × 8 元素，
  与 `qkv[4096+f]` 同一个线性索引）。
- **C5** 在已存在的 norm 相（post-score barrier 与 PV barrier 之间）读 `shVMax` 得
  `sV`/`sVinv`。
- **C6** 行 owner 线程在归一化循环里顺便取 `pmx`，算 `pScale=pmx*(1/127)`、
  `pInv=127/pmx`，写 `sy8`（P 码）与 `shPsf`（16 列广播的 dequant 因子）。
- **C7** 同相内 `sv8[f]=i8code(V[f],sVinv)`（stride-1 拷贝，`sv8[f]` 与 `qkv[4096+f]` 同址）。
- **C8** PV：`CA acc0,acc1` 两个 K32 片（keys 0–31、32–63，父的 K 顺序），
  每片 `CIA a`（`sy8`，`m0*64+32s`，LROW stride 64）+ `CIB b0,b1`（`sv8`，`32s` 与
  `16*64+32s`，LCOL stride 64）；出口 `CF sfm=load(shPsf, m0*16, 16, ROW)` 后
  `CH narrowed=CH(CF(acc)*sfm)`——**只有一次窄化**，与父一致。
  `#if !ROW_OWNER` 的 ticket 归因路径（G3 不 dispatch）保留父 FP16 PV 不动。

**为什么这样对齐 ABI**：`shPsf` 是一张 8×16（每 WG 64×16）的 float 表，第 r 行 16 列全
等于 `sP*sV`，用 `coopMatLoad(..., m0*16, 16, ROW)` 载入——**行索引由地址给出**，
因此不需要假设 int32 累加器的 lane/component 映射（R04 用的是"同一 lane 的 4 个分量
同列"，在 R12 的朝向下行才是 query，per-query scale 不是 lane 均匀的）。
代价是 4 KB shared 和每 SG 一次 coopmat load，换来"只依赖一个已存在的 load 语义"。

**多重集差分全归因**（`evidence/SPV-DELTA.json`、`SPV-DELTA-b30.json`，
opcode 表经 `TOOL-DEFECTS.md` D2 修正并带 grammar 自检：4 个模块

- 10 个函数里 **8 个 opcode 多重集完全相同**（`tile/blk_/wind/expo/norm/qdbg/ldbg/v_ra/wq8_`）；

| PV | **0** | **0** | 已换成 4 处 i8×i8→i32：15 号模块 12663（2382）、12685（2386）、12783（2406）、12805（2410）；b30 模块 12552、12574、12672、12694 | 本卡移走 32 处静态 FP16 |
| 合计 | 8（2 FP16 + 6 int8） | 128（32 FP16 + 96 int8） | 由 4 FP16/模块降到 2，int8 由 6 升到 10 | |

动态次数（源级，非 FLOPs、非时间）：每帧 16 个 PASS 共 **5376** 个 workgroup
（8 个 6×3×16 = 288，8 个 6×4×16 = 384）。计数口径：**每 SG** = 单个子组自己的指令执行
次数，**每 WG** = 8 个 SG 之和。PV 每 SG 8 → 4（每 WG **64 → 32**）；QK 每 SG 8 = 每 WG 64
不变；QKV 每 WG 768 不变（每 SG 96 = 6 站点 × 2 k × 8 kc）。

| 每 WG | 父 | 候选 |
|---|---:|---:|
| FP16 MMA（QK 64 + PV 64 → QK 64） | 128 | **64** |
| int8 MMA（QKV 768 → QKV 768 + PV 32） | 768 | **800** |

每帧（×5376）：FP16 矩阵乘指令 **688128 → 344064**，int8 **4128768 → 4300800**。
MAC 数守恒：PV 每 WG 仍是 64 query × 32 dim × 64 key = 131072 次乘加，只是由 64 条
K16 FP16 改成 32 条 K32 int8（每条 8×16×32 = 4096 MAC）。

`scalar_float_bypass_check`：模块里没有用标量浮点乘加绕过矩阵段——
QK/PV 之外唯一的 K 归约就是 QKV 的 int8 MMA；`dot`/标量乘加计数为 0。

## 7. 本臂 INT8 参考状态

`evidence/ORACLE-PV.json`——**本卡**在 CPU 上按 shader 的同一公式生成
（stdlib Python，`run/python312` 无 numpy；seed 20261024；64 query × 64 key × 32 dim，
P 取父的 `H(P*inv)` half 值，V 取父的 half slab）：

- **非零**：P、P8 非零率 1.0，V8 非零率 0.989；`all_three_nonzero=true`。
- `P<=1` 成立；`P8` 最大值正好 127（不越界）；`V8` 最大 127；
  int32 累加最大 |acc| = 61090，理论不可能越界值 64×127×127 = 1032256，余量 3.5e4 倍。
- 与父 FP16 路径（half 操作数、FP32 累加）比较：`max_abs` 0.0039（半个 half ulp 量级）、
  `mean_abs` 8.9e-4、RMS 1.12e-3、相对 RMS **0.82%**；解析界
  `(sP/2)Σ|V| + (sV/2)Σ|P| + sP·sV/2` 的最大值 0.0257，**全部落在界内**

- **没有过任何设备侧门**：这是本臂参考，未在 GPU 上验证；`GATE` 未跑。

## 9. 未解决阻碍（具名）

- **GAP-QK（最重要）：QK 仍是 2 处 FP16 MMA/模块，每帧 344064 条。** 未实施的原因是
  dequant 形状：score = `sQ[row]·sK[col]·Σ Q8·K8` 是**秩 1 外积**，不是标量，
  而 score 累加器随后要加 bias、做 exp、写 debug 回显。可行方案（**已定合同、未实施**）：
  ① 把 Q/K 的 INT8 片写进 shared（Q 8×32、K^T 32×16，LROW/LCOL，stride 32 正好是
  现有 half 布局的 stride），② QK 出口用两张广播 float 表做两次逐元素乘：
  `sfmQ`（64 query × 16 列，行广播，与 PV 的 `shPsf` 同一技巧、可复用同 4 KB）与
  `sfmK`（每个 `n0∈{0,16,32,48}` 一张 8×16，列广播，共 2 KB），
  ③ 然后走父原有的 bias 加法与 `CH` 窄化。**代价**：logits debug 回显（`ldbg(0)`）的语义
  会从"原始 f32 累加"变成"dequant 后的 f32"，需要单独定一版 debug 语义；
  Q/K 的动态 scale 还要从 norm pass 发布进 shared（每 head 64 个 float，两次写）。
  本卡没有做，也没有用任何"等价"说法替代它。
- **GAP-V：V 的 half slab 现在只剩 debug 回显一个读者。** 生产 SPV 里
  `qkv[4096..6144)` 的 half V 已经没人读（PV 读 `sv8`），删它还会牵动 QKV 段的
  `STORE_QKV_I8`（本卡明确不碰 QKV）。登记为后续"QKV store 按 debug 开关裁剪"的工作项。
- **GAP-S（scale 粒度）：** P 的 scale 是 per-query、V 的 scale 是 per（head, window）。
  若门判定 0.82% 的局部 RMS 不可接受，**同一 ABI 内**可做的是 V 细到 per-dim
  （32 个 float 的 shared 发布，多一次 barrier）或 P 细到每 32-key 片内一致
  （数学上两片必须共用一个 sP，否则 int32 累加不能再合并——这条限制要写进任何后续尝试）。
  两者都未实施。
- **GAP-B（block30 的出口）：** 本卡只把 block30 的 PV 段 INT8 化，**没有**碰它的 T half
  出口，也没有套普通 15 个的 qT 内联出口。block30 的 l3（`split16_b30_l3` → S24，2 处
  FP16 MMA）与 pool/head 仍按原样，属于 R13/R14 的范围；R13/R14 的孤立 INT8 候选合并时
  必须重新对 block30 的 l2 出口身份，不能拿本卡的 T 值直接当已验收输入。
- **GAP-G：没有 GPU 时段。** gate（fixed/fb2）、per-pass capture（qT/T 目前都不是 plan
  OUTPUT，需要加 resident OUTPUT 或翻 debug 位）、ordinary 3×30、画质全部未跑；
  `run/r12-split16-l2/jobs.json` 只列不跑。
- **GAP-X：4 KB 额外 shared 与单地址 `atomicMax` 的代价未测。** 30724 B 是否仍能维持
  原来的 occupancy、2048 次单地址 atomic 是否比 R04 的 64×32 更糟，都要设备数据；
  更省的做法（每 SG 先 redux 再一次 atomic，共 8 次）留给性能阶段，本卡先用与 R04 同款的
  已验证写法。
