## 1. 期望在 ISA 里看到的可观察变化（逐条）

| # | 观察点 | 期望 | 为什么必须是这样 |
|---|---|---|---|
| P1 | `dpas.8x8` 计数 | **= 256** | 段循环只是重新排列发布时序；每个窗口仍是 16 ki × 2 acc。若 IGC 把 loop 保持为滚动形式，DPAS 会少于 256（循环体只有 1 份），这就是 A 类 |
| P2 | `sync.bar` | **dynamic 1 → 4**，static 仍 **2** | 1 道序言 barrier + 1 道循环内 barrier（j=1,3,5 执行）；debug 分支里的 barrier 消失 |

## 2. 「若看不到就等于未实现」的判据（预登记，先写下再测）

- **A 类（实现未落地）**：`dpas.8x8 ≠ 256`，或 `sync.bar` dynamic 仍为 1，或 `load.slm.d32x8t ≠ 1024`（A 读被改动）。→ 记"实现未落地"，**不是**方向无效。
- **B 类（有副作用）**：`scratch > 0`，或指令数 > 7 400，或 `workgroup memory ≠ 32 768`。→ 列增量账，优先怀疑段循环没展开导致的代码膨胀/寄存器压力。
- **B′ 类（消息收益没拿到但时序收益在）**：P3/P4 未达成（仍是 `d16u32`）而 P2 达成。→ 说明 32 B 连续块没被合并；此时只能读 resources 判断时序收益，方向仍未被否定。
- **C 类（当前身份无净收益）**：全部 P1–P8 达成、gates 逐位相同，但 15 PASS 逐 PASS 不变慢也不变快（<1 µs/PASS）。→ 归因到"staging 驻留不是该 kernel 的瓶颈"这一形状结论，并指向 RESUME §5.1 的 A 读布局卡。
- **E 类（数值失败）**：gates 不同。→ 首先查段下标算术 `e_ = seg*4096 + t_local*16`（发布覆盖面已穷举证明，故更可能是 barrier 位置/段-窗口对应错），或 debug 路径。

## 3. 与 native 无关但必须一起看的资源侧

- `pipeline-statistics`：Instruction Count 应落在 P9 区间；**Workgroup Memory Size 必须仍是 32 768**，`Scratch Memory Size` 必须 0，`Loop Count` 应为 4（父）→ 若变成 5，说明段循环没被展开，P1 也会失败。
- `resources` 逐 PASS GpuTime：父 15 PASS = 30.0–37.0 µs（单样本 base 臂，见 COST-LEDGER.ceiling）。候选若在 **30 µs 以下** 才算组内变快；逐 PASS 同向率是比整帧更有分辨力的量。
