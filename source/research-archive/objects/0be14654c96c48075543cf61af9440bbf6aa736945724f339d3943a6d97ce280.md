Both modules contain **two different matrix stages**, and the GUIDE requires both to become
INT8 in the same card:

* **WO** — the front-end output projection inside `nr_body_stage()`
  (`y = x·W_woᵀ + residual_scale·Y`). A = the window's context tile (`gT`, and for C256 its
  shared copy `shT`), B = the module's own `pack` (binding 0) WO region. 2 static MulAdd
  sites, executed 4× (C128) resp. 8× (C256) per workgroup.
* **DS** — the post-pool down-sample projection in `main()`
  (`d = pooled_tile·W_dsᵀ`), A = `nrf_mean` (the 2×2-pooled tile), B = `nrf_w`
  (binding 8) at `whalf`. 4 static sites (C128: one round × 4 channel blocks;
  C256: two rounds × 4 channel blocks).

The C64 sibling card (`candidates/r09-r11-f3ds`) implemented only its WO and left exactly
these two cards at 6 FP16 sites each. This card closes both.

## 3. The implementation

Sources: `source/candidate/r10_f3c128_body_ds_wo_ds_i8.comp` (20520 B, sha256
`9c51de5e607d0036bec251a56e8d2b80b3cdfa9ca97acfe6e5d86750185ac829`) and
`r11_f3c256_body_ds_wo_ds_i8.comp` (20780 B, sha256
`f3302264b47e059ebd7870ae846f7e1ce1fe27052b55e92cdd6846fd9a7f4336`), both derived from
their own parent (the parent text is kept verbatim wherever it is not listed below).

### 3.1 WO → INT8 (both widths)

1. the parent's fp16 A stream out of the window context tile is replaced by a
   **workgroup-private int8 staging tile**: pass 1 computes the amax of this window's own
   context tile from the same `gT` half values the fp16 arm multiplies, a serial reduction
   over `shMax[256]` publishes `inv = 127/amax` and `sC = amax/127`, pass 2 writes one code
   per (token, channel) with `roundEven` + clamp to ±127. Layout: element (token t,
   channel k) at `((t/32)*K + k)*32 + (t%32)`, so an 8-token × 32-channel K32 A fragment is
   a column-major stride-32 view (the measured I8A layout).
2. the fp16 B stream (`pack`) is replaced by the int8 pack at binding 10 with the I8B K32
   layout, plus the per-output-channel scale table at binding 11.
3. the K16 loop becomes a K32 loop (C128 8→4 steps, C256 16→8 steps) and the accumulator
   flips f32 → i32.
4. the parent's seed-before-K is impossible with an i32 accumulator, so the residual is
   loaded immediately before its own epilogue: `seed = widen(H(gY × pack[ars+n]))`, then
   `prod = MAT_C(acc) × (MAT_C(fsc) × sC)`, `sumv = prod + seedc`, one `MAT_H` narrowing.
   The residual value is never rescaled, requantised or dropped, and the *set* of
   `gY`/`pack[ars+n]` loads keeps its address expressions and strides (0 and 64/128/256).
5. all stores are the parent's: debug echo, `imgout` with the original
   `c128_img_half_index`/`c256_img_half_index` + OOB rule + stride 16, and the `nrf_pair`
   staging store with the original `(sg*2+acc)*128` stride-16 row-major layout.

Diagnostics: `NR_D4_MODE` is kept with the parent's meaning (0 full, 1 seed only,
2 mma only), applied to the INT8 epilogue.

### 3.2 DS → INT8 (the post-pool stage)

**Decision: the quantisation is applied AFTER the pool, and the pooling stays fp16.**

Evidence that the parent's DS activation domain is the pooled value, i.e. post-pool:

* the parent's DS A operand is `coopMatLoad(aa, nrf_mean, rowbase*K + k, K, RowMajor)` —
  `nrf_mean` is written by the pooling tree at the *end* of every `j` iteration and is the
  pooled 2×2 mean, not the WO output;
* `nrf_mean`'s only writer is the pooling block (`nrf_mean[(4*ly+lx)*K + kk] = v`, `v` from
  the four `nrf_pair` reads `(a+b)+(cc+dd))*0.25`); its only reader is the DS loop. There is
  no other consumer, and no second quantisation point anywhere in the parent;
* therefore the honest INT8 replacement is: keep the parent's half pooling writer
  **textually unchanged**, quantise the 16×K pooled tile **once** afterwards, and let the
  DS read the codes.

Implemented as: `nrf_mean[2048/4096]` half (staging, writer unchanged) +
`nrf_mean8[K*32]` int8 (DS A operand, element (slot s, channel k) at `k*32 + s`) + one
`barrier()` + a second amax reduction over the pooled tile + one code write per element.
The measured alternative (quantise the WO output, dequantise, pool, requantise) is worse in
both widths — see §6 D/E — which is the reference for the choice, not an assertion.

DS B is the new int8 pack at binding 12 with the same I8B K32 formula, `whalf` folded into
the pack (so the kernel no longer adds `pc.p6.y`; the FP16 DS pack stays bound at BIND 8
and is simply unread). Dequantisation is folded once per fragment:
`MAT_H(MAT_C(acc) × (MAT_C(fsc) × sD))`, then the parent's own `nrf_stage` staging store and
`nrf_write_group()` — both byte-identical text.

### 3.3 What is provably untouched

`nrf_pair`, the four pooling reads, the pooling writer (including the `precise` qualifiers
and the `M8COL8`/`nrf_mean` address), `nrf_ds_at()`, `nrf_write_group()`, the `main()`
prologue, the push-constant ABI (all 32 words), the grid, the workgroup size, and the owner
(subgroup-local 8×16 fragments; the staging tiles and the two scale slots are
workgroup-private, so no cross-subgroup or cross-workgroup contract is created).

(the I8B K32 column-major stride-32 view the kernel loads at
`(n0/16)*(K/32)*512 + ki*512`).

| pack | N×K | rel L2 (W round-trip) | max abs err | saturation | zero channels | decode bijective |
|---|---|---|---|---|---|---|
| R10 WO | 128×128 | **0.701513 %** | 0.001953 | 181 / 16384 = 1.105 % | 0 | yes |
| R10 DS | 256×128 | **0.735223 %** | 0.001953 | 320 / 32768 = 0.977 % | 0 | yes |

| R11 DS | 512×256 | **0.764359 %** | 0.001953 | 663 / 131072 = 0.506 % | 0 | yes |

`decode bijective` means the set of FP16 element indices the formula touches is exactly
`[base, base + N*K)` — a wrong tile formula would address a wrong range. Both DS regions
end exactly at the end of their pack (`180736+32768 = 213504` halfs = 427008 B;
`656128+131072 = 787200` halfs = 1574400 B), which is a second independent confirmation of
`whalf`.

**One layout trap, documented rather than glossed.** The C256 WO region is `n*K+k` in the
deployed module, while the C64/C128 WO (and both DS regions) use the blocked form. During
the reference work I proved this by experiment (`build/probe_wo_layout.py`): the
`s1-output-complete` "full" captures were fed a **WO-only re-laid pack** whose WO region is
*blocked*, and their modules (`c128_d4_full.spv`, `c256_d4_full.spv`) read blocked. Only the
matching pairing reproduces the captured output (99.989 % / 99.983 % bit-identical); the
mismatched pairing drops to 0.06 %. So the two pack files in that tree hold the **same
weights in the two layouts**. `make_packs.py` therefore uses each *deployed* module's own
formula — blocked for R10, `n*K+k` for R11 — because the pack must match what the deployed
kernel reads, not what the capture's kernel reads.

| R11 candidate | **37896 B** | `sT8` 16384 (`[16384×i8]`), `nrf_mean` 8192, `nrf_mean8` 8192 (`[8192×i8]`), `nrf_pair` 4096, `shMax` 1024, `shScale` 8 |

**R11's capacity problem and how it is actually resolved.** The parent already declares
45056 B of a 49152 B ceiling, so a 64×256 int8 context tile (16384 B) cannot be *added*.
`shT[16384]` exists for exactly two reasons — the WO A operand and the debug echo — so it is
**re-declared as the int8 staging tile itself** (same element count, 1 B per element instead
of 2). That frees 16384 B instead of consuming it. The debug echo, the only other reader, now
reads `gT` directly: identical bytes, because the parent fills `shT` from `gT` verbatim and
never writes either. Net: **45056 → 37896 B, i.e. 7160 B below the parent and 11256 B below
the ceiling**, with no second staging buffer and no streaming loop needed.

These are declared SPIR-V bytes. **Native SLM/occupancy/GRF are not measured and are not
claimed.** Note also that the DS A staging tile uses only 16 of the 32 lanes of each column
(`nrf_mean8` is `K*32` for 16 slots), i.e. half of it is padding — deliberate, because
stride 32 is the measured I8A layout of this family; a 16-stride variant would have to be
measured on a device before use.

| | post-pool (implemented) | pre-pool (alternative) | end-to-end (INT8 WO + post-pool DS) |
|---|---|---|---|
| R10 rel L2 | **1.432 %** | 1.989 % | 1.504 % |
| R11 rel L2 | **1.223 %** | 1.509 % | 1.340 % |

and pooled-tile code differences between the two placements: R10 `{0: 478768, 1: 37206,
2: 122}` (37 328 of 516 096 codes differ), R11 `{0: 257008, 1: 58378, 2: 6}`. So the two
placements genuinely differ, and the implemented one is the closer of the two in both
widths — which is why the post-pool reading is the one shipped. The pooling itself is *not*
re-quantised and no second post-pool scan was added beyond the single code pass.

**E — DS arm.** With the pooled tile held at the parent's values, the INT8 DS (new pack,

## 8. Where C128/C256 differ from their C64 sibling (`f3c64_body_ds`)

Same family, one block earlier; the mechanism is reused, but four things are genuinely
different and were not copied blind:

1. **Two stages to convert, one accumulator shape.** C64 had 4 FP16 WO sites and its DS was
   already INT8 with a deployed post-pool scale (`entry_sc[4]` from the upstream `entry_q`
   path). C128/C256 have **2** WO sites and **4 FP16 DS sites**, and they have **no
   post-pool scale anywhere in their bindings** — the pooled value is written unquantised
   into a `shared float16_t nrf_mean`. So this card had to *define* the post-pool scale
   (per-workgroup amax of the module's own pooled tile) and *create* the DS pack; nothing
   could be inherited.
2. **WO tile shape.** C64/C128 WO B uses `(n/16)*(K/16)*256` (blocked); C256 WO B uses
   `n*256+k` (plain). C64 needed 2 K32 steps, R10 4, R11 8.
3. **Shared memory.** C64 needed +5128 B and had room. R11 starts at 45056/49152 B and
   cannot add a 16 KiB tile, so the resolution is a *retype* of the existing `shT`
   (frees 16384 B) rather than an addition — the C64 pattern (add `sT8` and a reduction)
   does not transfer.
4. **Pooling index maps.** The three epilogues differ in which fragment rows the 2×2 block
   comes from: C64 uses `(sg>>2, (sg>>1)&1)` with `ly = 2*sy1 + h`; C128 uses
   `R = sg>>2`, `ly = 2*sy1 + R`, `py = 4wy−2+2sy1+R`; C256 uses `q = j>>1`,
   `ly = 2*(1−sy1)+dy` (note the `1−sy1` inversion) and a *different* validity test
   (`px < p7.x && px < p5.y`, no `tile_ok`). Each candidate keeps its own parent's map
   verbatim; only the operands' dtype and the quantisation were added.

Per-workgroup matrix-step counts (source level, not time):

| | WO parent → candidate | DS parent → candidate |
|---|---|---|
| R10 | 4 j × 2 frag × 8 K16 = 64 → 4 × 2 × 4 K32 = **32** | 4 frag × 8 K16 = 32 → 4 × 4 = **16** |
| R11 | 8 j × 2 × 16 = 256 → 8 × 2 × 8 = **128** | 2 rnd × 4 × 16 = 128 → 2 × 4 × 8 = **64** |

## 9. Named gaps (nothing hidden)

1. **No capture of PASS 14 / PASS 22.** The numeric reference is a neighbouring block of the
   same width with the capture module's own pack. The deployed arm's own frame reference
   does not exist yet; producing one needs a `--dump-intermediates` diagnostic job for each
   pass (which changes residency and therefore cannot itself be a production gate).
2. **Deployed pack layout is an inference for R11's WO only.** The deployed C256 body reads
   `pack[wo + n*256 + k]`, and that source replays byte-identically, so the deployed
   `swin_22_weights` must be stored in that form; the *capture* tree's C256 pack is stored
   blocked. Because `make_packs.py` uses the same formula the kernel uses, the INT8 pack
   inherits exactly the deployed arm's semantics — if the deployed pack were in the other
   layout, the deployed FP16 arm would already be wrong (a pre-existing defect, not one this
   card introduces), and the reference numbers in §7 would be unchanged because they are
   measured in weight space.
3. **R11 debug echo reads `gT` instead of `shT`.** Content-identical by construction
   (`shT` was filled from `gT` and neither is written), but the store is now issued after the
   quantiser instead of after the copy. No byte of the debug buffer changes; named because a
   reader diffing the sources will see it.
4. **`nrf_mean8` padding.** Half of the DS A staging tile is unused padding (16 of 32 lanes),
   a consequence of using the measured stride-32 I8A layout. Recoverable only after a device
   measurement of a 16-stride variant.
5. **BIND 8 (the fp16 DS pack, 427008 / 1574400 B) stays bound and unread** so that no parent
   BIND moves and rollback stays trivial. A release-grade plan can drop it.
6. **`NUMERIC`, `QUALITY`, `ORDINARY`, `NATIVE` not run.** No GPU slot was allocated; no
   pipeline was created, so native SLM/occupancy/scratch and any millisecond or PSNR figure
   remain unmeasured and unclaimed.
7. **No-tolerance statement.** §7 reports relative L2, bit-identical shares and saturation
   rates as *measurements*. No threshold is proposed, and none of it is a pass/fail claim.
