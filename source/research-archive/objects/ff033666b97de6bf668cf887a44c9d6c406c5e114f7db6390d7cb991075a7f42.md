## 1.（Q1）映射：每个 (lane, component) 代表哪个 (token, channel)

### 1.1 内核几何（父与候选完全相同）

| 量 | 值 | 依据 |
|---|---|---|
| WG | 256 线程 = **8 个 SG**（subgroup 32 lane） | `layout(local_size_x=256)` |
| SG 通道 owner | `n0 = (sg % 4) * 32` → 4 个通道四分之一 × 32 通道 | 源码第 40 行 |
| SG token 相位 | `p = sg / 4 ∈ {0,1}` | 父 `m0=(p+2j)*8`；候选 `m0=p*32+16jp` |
| 每 WG 覆盖 | 64 token × 128 channel（8 个 8-token 块 × 8 个 16-channel 块） | grid `21×12`，42×24 tile 图 = 42×24×4 quad |
| 输出元素 | 64×128 = **8192 / WG**；8192×252 = 2 064 384 = 全图 half 数 | PROOF.mapping |
| K | 128 = 8 步 × 16 | `ki<8`，`k0=ki*16` |

### 1.2 输出 tile 的 owner 表（可枚举）

父：`(sg, j, h)` → tile `(m0=(p+2j)·8, nblk=n0+16h)`，`j∈0..3, h∈{0,1}` ⇒ 8 SG × 4 × 2 = **64 tile / WG**。
候选：`(sg, jp, blk, h)` → tile `(m0 = p·32+16jp+8blk, nblk=n0+16h)`，`jp∈0..1, blk∈{0,1}` ⇒ 8 × 2 × 2 × 2 = **64 tile / WG**。

| SG | p | 父的 4 个 m0（j=0..3） | 候选的 4 个 m0（jp=0..1, blk=0..1） |
|---|---|---|---|
| 0,1,2,3 | 0 | 0, 16, 32, 48 | (0, 8), (16, 24) |
| 4,5,6,7 | 1 | 8, 24, 40, 56 | (32, 40), (48, 56) |

- 8 个 m0 值集合相同（0,8,…,56），每个 SG 仍持 4 个 8-token 块，通道 owner 不变。
- 变化只在**同一 SG 拿到的是哪两块**：父取跨度 16 的棋盘格，候选取**相邻两块**（`m0` 与 `m0+8`）。
- 通道方向完全不变（`h∈{0,1}`，`n0` 与 `ars`、`scale0/scale1` 一一对应）。

**覆盖证明（PROOF.json，穷举 8192 元素）**：父/候选各恰好 1 个 owner/元素（duplicate 0、missing 0）；
store 地址逐元素相等（mismatch 0）；seed tile 相等（0）；scale 索引相等（0）；tile 集合完全相同（0 差集）。
四个 store 的 `(m0,nblk)` 区间两两不重叠（父 0 冲突、候选 0 冲突）。

### 1.3 尾块

**无尾块**：64 token、128 channel 都是 8×16 tile 的整数倍；`grid 21×12` → `tx=2wx+shift+(q&1)`、`ty=2wy+shift+(q>>1)` 覆盖 42×24 quad 图。
shift≠0 的 PASS 由 `c128_img_half_index` 的 **oob 判定 + clamp** 处理，该函数与调用点逐字未改，因此 oob 域、skip 域、clamp 地址都与父相同（这是布局等价，不是新证明）。

## 2.（Q2）删了什么真实工作（正常执行路径，不计 debug 声明）

候选把 `j` 循环换成 `jp`（2 次），把 **一对权重 tile 提到两个 M 块之上**：

| 工作 | 父（每 SG / 每次派发） | 候选 | 变化 |
|---|---|---|---|
| B（权重）tile 全局读 | 4j × 8ki × 2nblk = **64 次**，每次 512 B | 2jp × 8ki × 2nblk = **32 次**，每次 512 B | **−32 次 / −16 KiB 逻辑** |
| 每 WG 的 B tile 读 | 512 次 = **256 KiB** | 256 次 = **128 KiB** | −50% |
| 每 WG 的 A+B+seed 逻辑读字节 | 344 064 B | 212 992 B | **−131 072 B（−38.1%）** |
| 第二 n-block 基址算术 | 每 (j,ki) 重算 `wo+(n0/16)*2048+(k0/16)*256` 两次 | 每 jp 一个 `bBase`，第二块 `+2048`（常量） | 少一条 mul/add 流 |
| M 循环次数 | 4 | 2 | −2 次循环开销（K 循环仍 8 次） |
| coop matrix load（动态 / SG） | 104 | 72 | −32 |
| DPAS | 64 | 64 | 0 |
| A tile 读 | 32 | 32 | 0（每 A 仍供 2 个 acc） |
| seed 读 | 8 | 8 | 0 |

**native 层面的“真实工作”**（父的只读采集 `CS_asma558554d30105096_…_b_10_orig.asm`）：

- `send.ugm` 共 **481**：`load.d32x8t` **320**（A+seed 的跨行转置读，每 256 B tile 8 条）、`load.d32x8` **64**（权重 512 B tile，1 条/tile）、`store.d32x8t` **64**（每 store tile 8 条）、`d16u32` 10、其他 9。
- 即：**被删掉的是 64 条 512 B 的权重 `load.d32x8` 中的 32 条**（主路径）；A/seed 的 320 条转置读与 64 条 store 不变。
- 这不是“删指令数”的收益，而是**每 SG 少 32 条 512 B 全局请求**（并顺带少一条基址算术流）。

**没有删**：`sync.allwr`（13）、`sync.bar`（1，仅 debug 复制用）、`mov`（484）、任何 dpas、任何 store。
也没有动 `exp/倒数/FMA 收缩/clamp/saturate`（本 kernel 不含这些）。

## 3.（Q3）重叠：原来如何重叠，现在是否被破坏

本 kernel **没有 SLM、没有 barrier、没有 WG 内归约**：8 个 SG 只共享 L1/L2 上的 gT 与 pack 流，输出 tile 两两不相交。
因此重叠只发生在 **每 SG 内的“供料—DPAS—退休”** 上。

| 值 | 生产者 | 首个消费者 | 最后消费者 | 覆盖者 | 危险 | 父/候选 |
|---|---|---|---|---|---|---|
| A tile `a`（8×16） | `coopMatLoad(gT)` @ (m0,ki) | DPAS acc(n0) | DPAS acc(n0+16) | 下一次 ki 的同名 SSA 值 | RAW→WAR | 父 2 DPAS；候选 **2 DPAS（不变）** |
| 权重 tile `b0/b1`（16×16） | `coopMatLoad(pack)` @ (nblk,ki) | DPAS acc(m0,nblk) | DPAS acc(m0+8,nblk) | 下一次 ki 的同名 SSA 值 | RAW→WAR | 父 **1** DPAS；候选 **2** DPAS（**唯一被拉长的寿命**） |
| `acc00..acc11`（f32） | seed 初始化 | 8 次顺序 muladd | `MAT_H(acc)` 窄化 | 无（每次 jp 新建） | RAW 链 | 父 2 个 acc → 候选 4 个 |
| `seed`（f16 8×16） | `coopMatLoad(gY)` | `seed*scale`（half） | `MAT_C(seed)` | 每次 jp 重载 | WAR（跨 jp） | 父 2/j、候选 4/jp，总数不变 |
| store tile（8×16 half） | 窄化结果 | `coopMatStore(imgout)` | — | 无 | 无 | 地址集合与父完全相同、两两不交 |

- **被保护的重叠**：A 仍然“一次读、两个 N 半区用”；权重仍然“最后一条 DPAS 发出后才允许被下一次读覆盖”。
- **唯一变差的危险**：权重返回窗口的 WAR 距离 1 DPAS → 2 DPAS。源序特意排成 `b0(2 DPAS) → b1(2 DPAS)`，让每块权重在下一块被需要之前退休；这正是 F10 的教训（`$token.src/$token.dst` 不能互换解释，必须追到最后真正消费者）。
- **没有把所有东西串起来**：仍然 8 个 SG 并行、252 WG、每 SG 独立；没有新增同步点，也没有把 A/B 流合并成单链。

## 4.（Q4）新增成本（全账）

| 项 | 量 | 依据 |
|---|---|---|
| f32 累加器 | 2 → **4** MAT_C（8×16 f32） | 每个 4 GRF/lane ⇒ **+8 GRF/lane** |
| 瞬时 seed | 2 → 4 MAT_H（每 jp 4 个，立刻转 acc） | 峰值 4 acc + 1 seed |
| 权重返回区寿命 | WAR 1 → **2 DPAS** | 见 §3 |
| SPIR-V 指令数 | 834 → **1011**（+177，+21%） | `build/spv-stats.json` |
| SPIR-V 字节 | 3386 → **4098** words（13 544 → 16 392 B） | 同上 |
| coop 静态计数 | load 5→8、store 4→8、muladd 2→4 | 循环体静态展开不同；**动态** muladd=64、store=8 不变 |
| 整数地址 ALU（SPIR-V，模块级静态） | IAdd 59→82、IMul 37→28、UDiv 10→7、ISub 2→2 | 循环体改为“每次 2 个 M 块”：设共享序言为 P，`P+Bp=59`、`P+Bc=82`，按块归一 `(Bp+23)/2 < Bp`（Bp>23）⇒ **每输出地址 ALU 下降**；乘除因“一对一个 bBase”而减少 |
| Function 局部变量（SPIR-V OpVariable） | 52 → **75（+23）** | 同时存活的 coop matrix 值（+2 acc + pair A/B），即 +8 GRF/lane 的源码侧视图 |
| 有效 lane / WG 数 | 不变（256 线程、252 WG、8 SG、全 lane 有效） | 无 predication 变化 |
| scratch / SLM | 仍要求 **0 / 0**；无新 barrier、无新 buffer、无新派发 | 若 scratch>0 即拒绝（见 §5） |
| 代码体积 | +21%（+2 848 B） | 4 个 acc 的 store/seed 序列 |
| 活值峰值 | +8 GRF 数据（acc）+ 2 GRF（第二个 A）+ 4 GRF（第二个 B）≈ **+14 GRF 瞬时** | 父已用到 r127（scratch 0），**这是本卡最大风险** |

**逻辑字节 ≠ DRAM 字节**：权重区只有 **32 KiB**（C128 段），被 252 WG × 8 SG 反复读取，几乎必然驻留 L1/L2；所以 −38% 是**请求字节/请求条数**，不是 DRAM 流量。**片段字节 ≠ 实际 GRF**：跨行 A tile 在 native 是 8 条 32 B 转置消息，不能按 256 B/tile 折算成 1 条 send。

**接口与浮点核对（`SPV-INTERFACE.json`，逐项相等）**：
capability / extension / entry point / execution mode 全同；**非 Function 存储类**全同（Uniform/StorageBuffer/PushConstant/Private 计数一致）；
装饰直方图全同（**NoContraction = 0**，两侧都空）；**FP 动态计数全同**——`OpFMul` 8→8（half `seed*scale`）、
`OpFConvert` 16→16（8 次 MAT_H→MAT_C 加宽 + 8 次 MAT_C→MAT_H 窄化），**无** OpFAdd/OpFSub、**无** OpQuantizeToF16。
即：舍入点数量、类型与位置（seed 乘、加宽、窄化）逐点不变。

## 5.（Q5）是否真落到 native（预测 + 判据，**未证明**）

父的只读 native 采集（同身份，`kernel_hash=a558554d30105096`）：

```
instructions 2257   send.ugm 481   dpas.8x8 64   mov 484   sync.nop 298
sync.allwr 13       sync.bar 1     scratch 0     workgroup mem 0
r0..r127 (max_r 127, distinct 126)  first dpas @0x1030
```

候选预期（详见 `NATIVE-PREDICTION.md`）：

1. `dpas.8x8` **=64**，每 acc 的 K 序仍是 `k0=0,16,…,112`；
2. `load.ugm.d32x8`（512 B 权重）**64 → 32**；
3. `load.ugm.d32x8t`（A+seed）**320 不变**；`store.ugm.d32x8t` **64 不变**；
4. `send.ugm` 总数 **481 → ≈449**；
5. `scratch = 0`、`workgroup memory = 0`、无新 barrier；
6. 指令数 **2150–2320**（父 2257）；`max_r` 仍 ≤127。

**判据**：若权重 send 仍是 64 条 ⇒ **实现未落地（A）**，不能写“方向无效”；
若 `scratch>0` 或指令数 >2400 ⇒ **副作用（B）**，优先怀疑 +8 GRF 累加器压力；
若一切成立但 ordinary 不显著 ⇒ **D**（单卡作用域 198 µs / 18.2 ms = 1.08%，天花板就低）。

**实测（主代理串行作业的回执，本卡只读引用，见 `GPU-RECEIPTS-READONLY.json`）**：

| 观察点 | 父 | 实测候选 |
|---|---|---|
| 内核 hash | `a558554d30105096` | **`e662a7728e588f29`**（不同内核） |
| 权重 512 B `load.d32x8` | 64 | **32** |
| A+seed `load.d32x8t` / store `d32x8t` | 320 / 64 | **320 / 64** |
| `send.ugm` 总数 | 481 | **449** |
| `dpas.8x8` | 64 | **64** |
| scratch / workgroup mem / blocks | 0 / 0 / 50 | **0 / 0 / 50** |
| 指令数 | 2257 | **2005**（预测区间 2150–2320 **偏低**，好方向） |
| `max_r` / 首个 DPAS | 127 / `$0x1030` | **127** / `$0x14e0`（序言 +81 条：首 DPAS 前 4 个 seed） |

⇒ **机制落地，非 A；无 spill，非 B（压力轴）；不是 E**。两条修正：①指令数不能按“acc 变多 ⇒ 指令变多”线性估
（M 体数减半省下更多）；②“相邻 DPAS 共用权重寄存器”不能当复用证据（寄存器号会重载复用——
父的 63 个相邻对里也有 48 对共用 B 寄存器，而父的 B 每 tile 只用 1 次），唯一可靠证据是
512 B 权重载入 64→32 且 DPAS 仍 64。

## 6.（Q6）整体是否更快（本卡不能测，写清怎么测）

- **先门**：`fixed`（frame0 gold `1755e9c2…`）、`fb2`（末帧 gold `9c3e511e…`，`--warm 0 --reps 2 --feedback --save-frames`）。数值预期**逐位相同**（地址/seed/scale/K 序已穷举证明），不同即 E。
- **主判据（可分辨的那一层）**：`resources` 作业的**逐 PASS GpuTime**。父的 11 个 C128 PASS 各 **16.8–18.9 µs**（f06-scale-fragments 资源作业实测），11 PASS 合计 **197.7 µs**，占 18 228 µs 帧的 **1.08%**。逐 PASS 分辨率约 1 µs，足以看到 10–30% 的组内变化。
- **整帧**：`ordinary`（warm1/reps30/feedback，两臂 6 组交替）。**天花板 198 µs = 1.1%**，低于 ordinary 的 CI 分辨率（≈±0.1 ms），所以**预期就是 D/INDISTINCT**；它在这里的作用是**回归守门**，不是收益证明。
- **归因**：plan 只改 11 条 PASS 的 SPV 路径，其余 221 条逐字不变 ⇒ 这 11 个 PASS 的逐 PASS 差是单链归因；其余 221 PASS 是天然对照。**不跨批相减毫秒，不与 F10 0.422 ms 相加**。
- **上界估算**：若组内请求字节 −38% 能换来 10–30% 的组内时间，则是 **20–60 µs/帧**（0.1–0.3%），仍在 ordinary 噪声内。
- **已有回执（主代理作业，只读）**：`resources` 单样本两臂 → F06 C128 组 **195.10 → 166.61 µs（−28.49 µs，−14.6%）**，
  **11/11 同向**（−1.30…−3.96 µs/个）；同一对样本的整帧求和 17 577 → 17 443 µs（−0.76%）**不可归因**，
  因为 40 个非目标 PASS 也变化 >3%（单样本噪声）。`gates` fixed/fb2 两臂逐位相同。
  **ordinary 已完成（主代理作业）**：两臂 6 组交替 × 30 样本，180+180 全留；末帧 gold `2b63d4ba…` 全中。
  配对均值差 **+0.040454 ms**，sd 0.037381，se 0.015261，t(0.975,5) ⇒ 95% CI **[+0.001225, +0.079682]**，
  **5/6 组同向**，组均值 19.18320 → 19.14274 ms（**0.211%**）。
  ⇒ 整体是**边缘但非零的正收益**（下界 +1.2 µs）；与 resources 单样本组内 −28.49 µs（−14.6%）同向、
  且与“组内约 21% 的收益”量级一致，不是 D。
  **主代理已判 ADOPTED_CHAIN_HEAD**（RESULTS.json / NOTES-main.json）：接受并进入接受链（链长 3），
  但明确要求后续 family 包带一条**不含本改动的消融臂**，因为 CI 下界只有 +0.0012 ms。

## 7. C256 的下一条改动（只写草案，本轮不实施，不删 shT）

现状（`f06-scale-fragments/family/c256/candidate.comp`，15 PASS）：`shared float16_t shT[16384]`（**32 KiB**）+ 一次 256 线程整块复制 + 1 道 `barrier()`，8 个 SG owner 从 SLM 读 A。

**下一条具体改动**：把 shT 按“当前消费窗口”**分段发布/退休**（例如按 16-token slab：每段 4096 half = 8 KiB，4 段），保留 shT 本体与 A 的 LROW 读，只把“整块 barrier”换成每段的 publish/consume 协议或按寿命复用 arena；**不直接删 shT**。

**必须留在台账上的成本（删 shT 的代价）**：现在是一次 32 KiB 全局读（16 384 half）由全 WG 分摊；若改成每个 owner 直接读 gT，则每 SG 需读 8 个 M 块 × 8 行 × 256 half = 16 384 half = **32 KiB**，8 个 owner 合计**最多 256 KiB 逻辑全局请求/WG（8×）**。cache 效果未知：这块 tile 被 8 个 owner 共享，很可能命中 L1/L2，因此**不能把 256 KiB 当 DRAM 流量**，必须实测。已写入 `COST-LEDGER.json.c256_note`。

**寿命证明草案**（下一卡必须先做）：
1. 每个读该段的 owner 都在段被覆盖前完成（publish/consume epoch；每段 barrier 必须覆盖**所有** owner）；
2. 段的写域与任何仍存活的读者不重叠（旧值仍被读时不能删 WAR 屏障）；
3. 退休点取**最后一个读者之后**，不是最后一个生产者 store 之后；
4. 任何 owner 无法定界时保留整块读路径作为回退。

**严格线禁令（已遵守）**：跨 head 的 partial output 再归约会改变加法顺序 → 不采用；owner 融合只允许改放置，不允许改归约树。

## 8. 未决项 / 风险排序

1. **GRF 压力（最高）**：父 max_r=127、scratch=0，候选 +8 GRF 累加器。若 IGC 选择 spill ⇒ 直接判 B 并按 RESUME §5.1 降级（把 scale 载入下沉到 jp 内以释放 4 GRF）。
2. **权重复用是否被 rematerialize**：若 IGC 在压力下把共享 B 载入复制成 2 条，权重 send 仍是 64 ⇒ 判 A（实现未落地），方向未证伪。
3. **组内收益是否可测**：即便落地，198 µs 的天花板决定整帧大概率 D；需要逐 PASS GpuTime 才能给出组内结论。
4. CARD.txt 的 33 PASS 宽度拆分（11/11/11）与证据（7/11/15）不一致；本卡只用 C128=11。
5. 本卡没有验证 INT8 分支、没有部署、没有换装；GPU 与游戏侧一律未触碰。
