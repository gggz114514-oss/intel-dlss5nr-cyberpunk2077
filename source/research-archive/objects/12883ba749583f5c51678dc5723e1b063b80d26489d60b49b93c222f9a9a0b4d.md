## 0. 实测答案（回填，回答本卡唯一问题）

**删掉永不执行的 `if (debug)` 路径后，IGC 让出了 10 个寄存器，不是 32 个。**

| 量 | 父臂（实测） | 候选（实测） | Δ |
|---|---:|---:|---:|
| 静态指令 | 1947 | **1720** | **−227** |
| `send` 静态条数 | 429 | **364** | **−65** |
| 其中 `store.ugm.d32x8t` | 128（生产 64 + dbg 64） | **64** | **−64** |
| `dpas` | 64/线程 | **64** | 0 |
| `sync` | 265 | 264 | −1 |
| `first_dpas` 偏移 | 3712 | 3488 | −224 |
| **`max_r_any`** | 127（`r127` 是 `and` flag 暂存） | **127** | **0** |
| **`max_r_data`** | **124** | **114** | **−10** |
| **不同寄存器数** | **104** | **94** | **−10** |
| 高位寄存器带 | `r118/r120/r122/124` 各 3 次 | **全部消失**（带下移到 ≤114） | — |
| `scratch` | 0 / 1024（两种口径见 §1 注） | 同 | 0 |
| 门控 store 的 `dbg` 消息 | 64 条静态、0 条动态 | 0 / 0 | — |

**读出（对后续卡有用的一条）**：门控死路径**不是**寄存器水库，但它确实“占着名字”：
它的 f16 staging 与地址料需要约 10 个寄存器宽度，删掉后 IGC 把整条高位 band 往下挪了同样的宽度
（`r118..r124` → 消失，峰值 124→114）。**腾出量 = 这条路径自己占用的宽度，不会更多**；
`+32 GRF` 的 M4 因此**仍然被挡**（114 + 32 = 146 > 128，且 `scratch` 未变）。

**我预测错了一条**：我预测 `max_r_data` 不动（Δ0，允许 ±4），实测 **−10**。
错因见 §2 末尾（门控区确实不拥有**专属**寄存器，但它把生产段的 band 顶高了 10 格，
删掉后 band 整体下移；我当时把“没有专属寄存器”误推成“峰值不受影响”）。

## 2. 当初的判据（写死）与这次裁定

| # | 观测量 | 基线 | 判据 | 本次实测裁定 |
|---|---|---|---|---|
| N1 | **`max_r_data`** | 124 | `≤92` ⇒ 腾出 ≥32 GRF ⇒ 进 step B；`93–123` ⇒ 记实际量、按可用量选形态；`≥124` ⇒ A 类结论收工 | **114 ⇒ 落在 `93–123`：腾出 10，M4（+32）不够，B 不建** |
| N2 | `max_r_any` | 127 | 只看 N2 变而 N1 不变 ⇒ 按“没腾出”处理 | 127 未变；但 N1 自己降了 10，故按 N1 计 |
| N3 | `scratch` | 0（driver）/1024（捕获） | 变 `>0`/变大的 ⇒ 有 spill 副作用 | 两臂相等 ⇒ 无 spill |
| N4 | `dpas` | 64/线程 | 变了 ⇒ 实现错误 | 64 ✅ |
| N5 | `send` | 429 | 不变 ⇒ 删除未落地 | 364 ⇒ 落地 |
| N6 | `store.ugm.d32x8t` | 128 | 同上 | 64 ⇒ 落地 |
| N7 | 运行时发射消息 | — | `debug == 0` 时两臂应相同 | 门控 64 条静态消息在两臂都**不发射** |
| N8 | 静态指令 | 1947 | 1761 ± 20 | 1720（见上表） |
| N9 | 基本块 / `r` 仍展开 | 49 / 是 | — | 是（dpas 仍 64） |
| N10 | `first_dpas` | 3712 | ≈3712 | 3488 |

**裁定（CONTRACT §6 分类）**：这是 **“实现完整落地 + 当前身份无净收益”的 C 边界情形，按 INDISTINCT 记 D**，
同时**关闭“从 debug 路径腾寄存器”这条杠杆**：它只能腾出自己占的 ~10 GRF，永远到不了 M4 要的 32。
与主代理 `RESULTS.json` 的 `MEASURED_INDISTINCT_LEVER_CLOSED` 一致。

### 我当初为什么预测 Δ0（错因，供后人校准模型）

三条 ISA 事实我读对了：
1. 门控路径**没有专属寄存器**（`registers_only_in_dbg = []`）；
2. 它最高只碰 `r96`，`r96..r124` 全在生产段；
3. 峰值来源是 mB 的 Y 行地址 `r118/r120/r122/r124`（跨整个 kernel 的活值）。

**错在推理跳步**：从“门控区不拥有专属寄存器”推出“峰值不受影响”，漏了另一条通道——
门控区**延长**了 f16 staging（`r12..r15`）与部分地址料的活值区间，把整条高位 band 顶高了。
删掉后带整体下移 10 格（`r118..r124` 消失，峰值 124→114）。
→ 教训：**判“死代码是否占寄存器”，不能只看它有没有专属寄存器，要看它是否延长了别人的活值区间。**

## 3. 若 A 腾出 ≥32 GRF：step B 的形态与前置条件（本卡未建）

- **形态 M4**：8 累加器，`4m × 2n`，`r` 折进 acc 组。每 WG：权重消息 **256→128**、权重字节 **128→64 KiB**、
  load 总字节 **208→144 KiB（−31%）**、总消息 2880→2752（−4.4%）；代价 **+32 GRF**（32→64 GRF 累加器）。
- **硬前置**：`scratch` 不增 且 `max_r_data + 32 ≤ 124`。**本次实测的 114 + 32 = 146 > 128 ⇒ 不满足**，
  所以 B 不开；这也是 `RESULTS.json` 判 “M4 与 F05-12acc 保持关闭”的依据。
- 若将来能从别处（减少同时活跃的 acc/片段、或换 shape）腾出 32 GRF，M4 的形态与判据仍见本节。
