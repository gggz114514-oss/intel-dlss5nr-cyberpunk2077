##  2. 六条（实际是八条）排除理由 —— 为什么判 BLOCKED 而不是出候选
################################################################################

  R1 expand A 4×→2×（hidden 块 32→64，8 个 expand acc）
     会删 −16 msg / −4096 B / −64 mov / −16 jmpi
     ✗ **就是 n03(C128) / n03b(C256) 已测的同一机制**，CARD 明令禁止重复
     ✗ 而且 C64 是它**最弱**的一档：−6.6% 消息 / −9.6% 字节 / 帧上界 0.033 ms
       （C128：−8.5% / −11.2% / 0.056 ms；C256：−9.9% / −12.2% / 0.098 ms）
     ✗ 它的整个作用面（A，占字节 19.2%）够不到主导成本（权重，占 67.3%）

  R2 seed 复用 expand A（−4 msg / −1024 B）
     ✗ 要把 4 个 MAT_H 从 expand 段跨整个 middle 段活到 barrier 之后
       = **+8 GRF/lane**，而文件 max_r = 127/128 + 1 就是硬件顶（L4 禁止抬活值）

  R3 `scale` 去重（源码 4 次读 2 个 tile）
     ✗ **编译器已经做了**：ISA 实测 load.ugm.d32x8t 只有 16 条 = 2×8 行，
       源码 4 次读已 CSE 成 2 次 ⇒ 源码层冗余在 native 已到下界（L18 同型）

  R4 跨 SG 权重去重（−96 / −48 / −24 条，三宽度冗余倍数 4×/2×/1× 的来源）
     ✗ 走 SLM 广播：消息 128→160 = **+25%**，另加 +1 barrier、+96 SLM 读、
       +32 SLM 写、+64 KiB SLM 流量 ⇒ 违 L2（消息数下降才付钱）、L12/L19（SLM 往返是要删的）
     ✗ 改 owner/几何：需 8 个互异 g = 256 个 M 通道，**C64 只有 64** ⇒ 数学无解
     ✗ 而且 shared = 8192 B 已被 mLocal[4096] 占满，SLM 暂存无处可放

  R5 权重读加宽（换更宽的消息）
     ✗ L20 在本身份上复现：d32x8 只在 exec16 出现（16×8×4=512 B 顶格），
       d32x16t/d32x64t 只在 exec1 广播出现，**exec16/32 上不存在 x16/x32/x64 形式**
     ✗ 一个 16-hidden tile 的权重 slab 是 1024 half = 2048 B 连续，现读 4 条
       512 B，**已在 512 B/条的下界**

  R6 SLM 发布 / 合约 A / gY 省消息
     ✗ mLocal 行跨距 64 half = 128 B，一个 MAT_H/MAT_A 行只 32 B
       ⇒ 每片段必 8 条 32 B 消息 = 行粒度下界；加宽 store 形式不存在（L14/L20）

  R7 gY 布局跨 PASS 折叠
     ✗ L19 已把全局 store→load 折叠轴判 D（机制可表达但 site 亚阈）

  R8 去掉 debug 路径（−192 msg / −6144 B）+ 静态算术/地址折叠
     ✗ L17 实测 +0.005 ms INDISTINCT（227 条指令剥离），不是帧成本
     ✗ L1/L3：静态指令削减在 8–16 PASS 内核里低于检出下限；
       n04a 在 F05 C64 同型已测 −0.098 ms SLOWER_95

  补充证伪：对三宽度做了全量 send 签名普查，**相邻同址重复消息对 = 0**，
  签名重复全是 a0 相对寻址暂存寄存器 r2/r3 的文本巧合 ⇒ ISA 里没有被编译器漏掉的重复读。

##  3. 同步轴观察（主代理点名要的一条）
################################################################################

  sync.allwr：C64 = 10，C128 = 37，C256 = 70         （C64 只有 C256 的 1/7）
  send 返回窗最高寄存器：C64 117，C128 113，C256 117
  屏障：三宽度都恰好 1 个 sync.bar
  mLocal 消费多重度：C64 2×，C128 4×，C256 8×
  sync.nop：C64 196，C128 307，C256 541

  读法：**C64 的返回区/同步压力在三宽度里最健康**。宽度越窄，每个 SG 要等的
  返回区越少（合约 K 只有 64，即 4 个 ki × 2 个 tile），allwr 自然最少。
  所以"同步轴"在 C64 上已经几乎无东西可删 —— 这排除了"先删同步"的直觉路线，
  而 L12 恰好也说过：并发内核里的消息/同步删除可能完全被隐藏
  （F20 删 32/64 条片段传输消息，帧只动 ±0.02 ms 且不显著）。
  注意：这是**观察，不是定价**。本卡没有 resources 臂，不做任何因果断言。

##  4. 若将来放开寄存器预算，C64 的哪一条会最先变得可行
################################################################################

  先看清余量：max_r = 127，硬件上限 128 ⇒ **只有 1 个 GRF 的空隙**。
  所以"放开预算"不可能来自现有余量，只能来自**把寄存器腾出来**（如 L17 的
  debug 剥离只回收 10 个，而 F18 的 6-acc 形态还差 2 个）。

  按"所需 GRF 从少到多"排序，三条会依次解锁：

  ① **seed 复用（R2）—— 第一个解锁，只需 +8 GRF/lane**
     删 −4 msg / −1024 B（占生产字节 2.4%）。
     仍然亚阈（单 PASS 上界远小于 0.03 ms），**单独不成卡**。
     但它是最便宜的验证：如果哪天有人腾出 8 个 GRF，这是唯一"只删不增"的改动。

  ② **expand A 4×→2×（R1）—— 需要 +32 GRF/lane（4 个新 acc）**
     删 −16 msg / −4096 B（9.6%），帧上界 0.033 ms。
     但它是**已测机制的重复**，且实测两宽度都 INDISTINCT、成包 −0.040 SLOWER。
     ⇒ 即使解锁也不该再单独成卡。

  ③ **跨 SG 权重（R4）—— 再多寄存器也解锁不了**
     它的约束不是 GRF，是"C64 只有 2 个不同 g"这个**数学事实**。
     ⇒ **寄存器预算是 C64 的错误杠杆**：放开它也只会让①②这两条本来就
       亚阈/被禁的改动变得"可支付"，不会让 C64 变得值得开卡。

  一句话结论：**C64 的约束是形状（256/C 的权重冗余），不是寄存器。**
  想真正动 C64，必须改 WG 形状（2 个 WG 合作，或 local_size 128 让每个 g
  只有 2 个 SG），那必然改 grid/owner/shared，属新卡，且要先回答
  "8 KiB shared 已满，权重暂存放在哪"。
