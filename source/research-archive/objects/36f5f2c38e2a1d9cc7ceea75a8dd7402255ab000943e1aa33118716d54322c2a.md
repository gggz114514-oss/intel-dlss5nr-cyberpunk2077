# ANALYSIS — n12-vit-qkv (F14 ViT QKV / fragment norm owner)

卡：`n12-vit-qkv`，族 F14，ordinal **95 / 100 / 105 / 110 / 115 / 120 / 125 / 130**
（PASS 58/63/68/73/78/83/88/93，`vit_block31_qkv … vit_block38_qkv`，grid `3 × 96 × 1`，256 线程）。
八个位置共用同一个 SPV（`72e2df7c…`）与同一份源码，所以本卡是一个 shader、一类机制、一次改动。

父身份（只读）：

| 项 | 值 |
|---|---|
| parent SPV | `candidates/zcode-fp16-b5-global-expansion-20261020/vit-qkv-norm-owner-v2/spv/vit_qkv_norm_owner_v2.spv` = `72e2df7c7b1e542f375f5c7c2bdc572433a08c5f1a1a0d706026efa54b9a1e87` |
| parent source | `…/source/b3_04_vit_qkv_norm_owner.comp` = `2c6a1993…` |
| 父字节复现 | 本卡 `parent-rebuild.spv` 字节相同（raw compile，见 BUILD.json；与 RECIPES/PARENT-BYTE-VERIFIED 的 F14 `mode=raw, nc_count=7` 一致） |
| 基线 plan | `f10-weight-return-separation-20261027/plan.txt` = `a024c3c5…` |
| 本卡 plan | 8 行 PASS 路径替换，`9a3c7c06…`；cpu-check 与基线逐字相同 |

候选：`candidate.spv` = `d008f8fefca9e8fa881713302bb45fab4c23a5d4c8258a4b1cbca07e8577e4c7`
（源码 `candidate.comp` = `b3c6e215…`，`SOURCE-DIFF.patch`：+2 个 helper、4 行调用点）。

**一句话改动**：norm 的倒数不再「只在 column-0 owner 里算 + 跨 lane 广播」，改成**每个 lane 各自跑完整棵 xor 归约树并在原地求倒数**。
前提正是 N12 卡面写的 AMD NO_BCAST 条件：先逐节点证明原树同序/同值（第 2 问 + `evidence/TREE-PROOF.json`），再删广播。
**没有新增独立 norm 核，没有第二份镜像，没有改 A/B 供料、K 累加序、半精度舍入点、写域。**

## 1. 映射：生产者 (lane, component) 到底代表哪个 (token, channel/head/k)，消费者要什么

### 1.1 生产者一侧（F14，`b3_04_vit_qkv_norm_owner.comp`）

```
gx = gl_WorkGroupID.x (0..2)      gy = gl_WorkGroupID.y (0..95)     sg = gl_SubgroupID (0..7)
n0  = gy*32                        mA = gx*128 + sg*8               mB = mA + 64
输出：qkv[p6.x + m*3072 + n0 + c]   （3072 = 32 head × 32 channel；Q=0..1023，K=1024..2047，V=2048..3071）
```

Intel B580 sealed CH 的 8×16 half 累加器 lane 映射（本候选**没有改**它，只依赖它）：

| 量 | 表达式 | 含义 |
|---|---|---|
| lane 内的 (row, col) | `row = 2*ci + lane/16`, `col = lane%16` | `ci` = 累加器组件序号 0..3 |
| token | `t = m + row` | `m ∈ {mA, mB}`，一个 subgroup 覆盖 16 个 token（两组各 8 行） |
| channel | `n = n0 + col`（`h0` 侧，+0..15）；`n0 + 16 + col`（`h1` 侧，+16..31） | 一个 workgroup 的 32 个 channel 正好是一整个 head |
| head | `head = n0 / 32 = gy mod 32`（Q）；`gy-32`（K）；`gy-64`（V） | 96 个 gy = 3 段 × 32 head |

norm 用的配对：`f16vec2 vq_pair_sum(f16vec2(h0[ci],h1[ci]), …)`，即
`s[d] = z[d]² + z[d+16]²`，`d = lane%16`，token 由 `ci` 与 `lane/16` 决定（4 个 token/ lane）。
归约轴是**行内 16 个 column（lane 的低 4 位）**；`xor 8/4/2/1` 不跨 16-lane 半区，所以两个行奇偶各自独立。

枚举结论（`evidence/LAYOUT-PROOF.json`，逐元素生成，不是抽样）：

| 检查 | 结果 |
|---|---|
| 生产者写入元素数 | 884,736 = **288 live token × 3072 channel** |
| 消费者（F15）读取元素数 | 884,736 |
| 两个集合相等 | **是**（`producer_only = []`，`consumer_only = []`） |
| 重复写 | **0**（每个元素恰好 1 个 `(gx,sg,group,row,n0,c)`） |
| 行外写（`n ≥ 3072`） | **0** |
| 写入 token 区间 | 0..287（288 = 36 个 8 行组，整组存活） |
| padding token 288..383 | **0 次写** |

### 1.2 消费者一侧（F15 `vit_attention_pden_register.comp`，只读核对）

| 用途 | 读取式 | 需要的元素 |
|---|---|---|
| Q | `coopMatLoad(qf, qkv, p6.x+(q0+qg)*3072 + h*32 (+16), 3072, columnMajor)` | `qkv[t*3072 + 0 + h*32 + c]`，column-major 的 16 列 = 16 个 token，每列 16 个连续 half = 该 head 的 channel |
| K | `sk[e]=qkv[p6.x+(j0+key)*3072 + 1024 + h*32 + c]`，`e=key*32+c` | `qkv[t*3072 + 1024 + h*32 + c]`（32 个连续 half = 64 B） |
| V | `sv[e]=qkv[p6.x+(j0+key)*3072 + 2048 + h*32 + c]` | `qkv[t*3072 + 2048 + h*32 + c]` |

所以消费者要求的唯一形式是 **`qkv[token*3072 + S + head*32 + c]`，`S ∈ {0,1024,2048}`，c = 0..31 连续**。
生产者 `n0 = 32*gy` 且 `h0/h1` 分别落在 `n0+0..15` / `n0+16..31`，**逐字节就是消费者要的方向**。
本卡因此**没有**输出打包改动可删（详见 2.4 与 5）：任何"更宽的 store"都要求消费者改布局或加第二份镜像，两者都被卡面禁止。

### 1.3 边界枚举（历史事故点，逐条给数）

| 边界 | 值 | 判定 |
|---|---|---|
| V 区末端 | `n0=3040, c=31 → n=3071`，行宽 3072 | 行内，`next n=3072` 才会越界 |
| head 31 | Q `[992,1023]`、K `[2016,2047]`、V `[3040,3071]` | 三个 chunk 各自贴边但不越界 |
| chunk 基址 | Q 0 / K 1024 / V 2048 | 漏 `+1024` 或 `+2048` 会读到**同一行另一段**（`reads_not_written=0`，但 294,912 个元素指向别的区）——即"不报错但语义错"，这是必须枚举而不能"看末帧"的原因 |
| K/V key chunk | `288 = 4×64 + 32` → F15 走 **TAIL** 体，读 key 256..287 | `FULL` 4 块 + `TAIL` 1 块，尾块 32 key |
| 生产者 8 行组 | `288 % 8 == 0` | `if(m>=pc.p0.x) continue` 与父的逐行 `t<p0.x` **等价**（不会出现半组） |
| head 索引 | `head = n0/32`，与 `(n0%1024)/32` 的 scale 索引同源 | Q 段 `n0<1024` 时 `scale = scales[p2.z + head]` |

## 2. 删的是什么"真实工作"

全部计数来自 `evidence/SPV-STATICS.json`（glslang 产出的 SPIR-V，本卡实编译）与
`evidence/ISA-ACCOUNT.json`（基线 plan 同身份的 native 捕获，**只读引用**，不是本卡采集）。
按正常执行路径计，不计 debug 声明（`if(pc.p0.w!=0u)` 的 dbg store 一律不算，也没有删）。

### 2.1 树：4 个条件步 → 4 个无条件步（每步 1 条 `OpFAdd` + 1 条 `OpGroupNonUniformShuffleXor` 不变）

父 `vq_tree_xor`（每次调用，SPIR-V 指令数 **84**）：

```
if((lane&15u)<8u) s=s+unpackFloat2x16(subgroupShuffleXor(pack(s),8u));   ← 4 组
```

父实现里每一步都带：结构化分支头 `OpSelectionMerge` ×4、`OpBranchConditional`+`OpBranch`（合计 8 条）×4、
`lane&15` 掩码抽取 ×4、以及 `pack/unpack` 的 `OpBitcast` ×8、`OpLoad` 21、`OpStore` 12。
候选 `vq_tree_all`：**42** 条，`OpGroupNonUniformShuffleXor` 仍是 4，`OpFAdd` 仍是 4，
但 `OpSelectionMerge / OpBranchConditional / OpBranch / 掩码抽取 = 0`。

> 关键一点：**算术指令一条没多、一条没少**。SPIR-V 里父的每步只有 1 条 `OpFAdd`（向量 half2），
> 候选也是 1 条。删掉的是"这个 lane 该不该加"的判定与重汇聚机械，不是加法本身。

### 2.2 倒数：owner + 跨 lane 广播 → 就地求（每次调用 35 → 17 条）

父 `vq_norm_rcp`（**35** 条）：`if((lane&15u)==0u)` 分支 → `OpExtInst FMax` ×2 → `OpExtInst InverseSqrt` ×2
→ `pack` → `OpGroupNonUniformShuffle(pack, lane&16u)` → `unpack`；else 路径写 `f16vec2(0)` 再 join。
候选 `vq_rcp_own`（**17** 条）：`OpExtInst FMax` ×2 → `OpExtInst InverseSqrt` ×2 → 构造 f16vec2，无 shuffle、无分支。

native 侧这条广播的落地形式已定位（`evidence/ISA-ACCOUNT.json`）：编译器把值**先落到一个 GRF**，
再用 `a0` 间接读按源 lane 索引取回：

```
add  (16|M0) a0.0<1>:uw  r2.0<1;1,0>:uw  0x580:uw      ← 每次广播 2 条地址 setup（M0/M16）
mov  (16|M0) r4.0<1>:d   r[a0.0]<1,0>:d                 ← GRF 间接读
```

基线 ISA：`r[a0]` 间接读 **8** 次（4 次广播 × 2 个半区），`a0` setup **8** 次。
这 8+8 条与那 4 条 `subgroupShuffle` 是本候选唯一要"在 ISA 里消失"的指令。

### 2.3 逐项清单（每次 work-item 执行）

| # | 删除项 | 每次调用 | 调用数 | 小计 | 依据 |
|---|---|---|---|---|---|
| 1 | 树步的条件分支/select/重汇聚 | 84−42 = 42 条 | 4 | **168** | SPV-STATICS helper 计数 |
| 2 | owner-only 倒数 + 广播 | 35−17 = 18 条 | 4 | **72** | 同上 |
| 3 | else 路径零填充（2 条 f16 mov / 调用） | 2 | 4 | 8 | 同上（含在 35→17 内，单列） |
| 4 | native 广播 GRF 间接读 + 地址 setup | 8 读 + 8 setup | — | **16** | ISA-ACCOUNT（静态） |
| 5 | native 的重汇聚 `goto`/`join` 对 | 4 步×4 调用 + 1×4 调用 = 20 对 | — | **20 对 = 40 条** | ISA 直方图 `goto=20, join=20`，与 SPIR-V 的分支数**一一对上** |

第 5 项是本卡最强的可核对项：父的 SPIR-V 里恰好有 `4 个树调用 × 4 步 + 4 个 rcp 调用 × 1 分支 = 20` 个发散结构，
native 恰好 `goto 20 / join 20`。候选这两个数应归零。

### 2.4 没有删、也不该删的（如实记账）

- **没有删加法**：4 步 half add 每组件仍是 4 条（父的谓词形式在硬件上本来就是 SIMD-32 掩码执行）。
- **没有删 `math.rsqt`**：父 `math.rsqt (32|M0)` 8 条（= 4 次调用 × 2 组件），候选仍是 8 条。
- **没有删 `packFloat2x16`/`unpackFloat2x16`**：GLSL 的 `subgroupShuffle*` 只接受 32-bit 类型，
  这是把 `f16vec2` 变成可交换值的最小手段；删它需要换交换通道（另一张卡）。
- **没有删 store 次数/宽度**：4 次 `coopMatStore`（2 组 × 2 侧）就是 1.77 MB 输出本身。
  每个 8×16 RM store 落在 8 行 × 32 B（行距 3072 half = 6144 B），这是布局的必然结果，
  而 F15 的 Q 读是同样 32 B 段、K/V 填充是同样的 64 B/token 连续——**已经是消费者方向**。
  想"更宽 store"只有两条路：改消费者布局（F15 已定案）或加第二份镜像（禁止）。
- **没有动 debug 路径**：`if(pc.p0.w!=0u)` 的两次 dbg store 原样保留，不计入收益。

## 3. 重叠：独立工作原来怎么并行，本改动保护了什么

矩阵之间（A/B 供料）本卡**完全不碰**；下面只列 norm 尾段及其上游，标出 RAW/WAR/WAW。

| 值 | 生产者 | 最后消费者 | 退休/覆盖者 | 冲突 |
|---|---|---|---|---|
| `y`（A 片段 `af`） | `coopMatLoad(af,y,…)`，每 k0 一次 | 同迭代 2 条 MMA（mA/mB 各自） | 下一迭代再 load 同一个 `af` | **WAR**（每迭代一次，未被本卡改变） |
| `w`（B 片段 `b0/b1`） | 每 k0 两次 load | 同迭代 **4 条 MMA**（两组 × 两侧共享） | 下一迭代 load | **WAR**；这是既有的"一 B 供两 M"复用，保留 |
| `accA0/A1/B0/B1` | 64 次 `coopMatMulAdd` 链 | `MH(acc…)` 收窄（每组的 h0/h1） | 收窄后即死，寄存器可被 norm 复用 | **RAW**（长链）→ 之后 **WAR** |
| `h0/h1`（MH 收窄结果） | `MH(acc)` | ①dbg store ②`vq_pair_sum` ③（缩放后）qkv store | qkv store 后死 | ②③ **RAW**；①与②③无冲突（只读） |
| `s01/s23` | `vq_pair_sum` | 4 步树（本候选：**每个 lane 自己**） | 树完成后被倒数消费 | **RAW** 链 4 级 |
| `inv01/inv23` | 倒数（父：lane 0/16 + 广播；候选：每 lane） | 8 次 `vq_scale_q`/`vq_scale_k` | 下一组的倒数覆盖 | **RAW**；组间 **WAR** |
| `scale`（`scales[…]` 标量） | 一次 scalar load（uniform 地址） | 8 次乘法（`r9.0<0;1,0>` 广播操作数） | — | 只读，无冲突；与树**独立**，本可更早发出（留给下一张卡） |
| `qkv` 元素 | 本 dispatch 的 store | F15 下一次 dispatch 的 load | — | 跨 dispatch **RAW**；地址互不相同 → 无 WAW |
| debug `dbg` 元素 | dbg store | 外部读 | — | 不参与（p0.w=0） |

原来怎么重叠、本改动保护了什么：

- 树的两个 `f16vec2`（`s01`/`s23`）与两个 group 的尾段是**四条独立链**，可以交错；
  但父实现每一步都有一次**按 lane 的发散分支 + 重汇聚**，把 32 个 lane 的进度绑在一起，
  并且倒数还要**等一个 GRF 写完再按 a0 间接读回**（写→读串行）。
  候选把这两处串行点去掉：梯级只剩"shuffle ↔ add"的纯数据依赖，四条链可以真正交错。
- `scale` 的全局标量在 Q 段被夹在"倒数"和"第一次乘法"之间（native 0x172F0 / 0x17390 两处 scalar
  load），它本来不依赖树；本候选没有把它前移（避免一次改动两件事），但树变短后它相对更早可用。
- 累加器寄存器在 `MH()` 之后即死，norm 的临时值可以复用它们（**WAR**）；候选的临时值更少
  （不再需要给广播暂存一份 GRF），所以这条 WAR 只会更松。

目标始终是"删工作 + 保护供料"，不是"把东西串起来"：A/B 读次数、MMA 顺序、屏障数量都没动。

## 4. 新增成本（全部入账）

| 项 | 增量 | 说明 |
|---|---|---|
| 重复权重/A 读取 | **0** | K 循环、`coopMatLoad` 数、MMA 数完全不变（`OpCooperativeMatrix{MulAdd,Load,Store}KHR` 4/4/4 → 4/4/4） |
| 地址计算 | **0**（−8 组 `a0` setup 在 native） | 源码地址表达式未改；SPIR-V `OpIAdd 42 / OpIMul 19 / OpUDiv 4` 父候相同 |
| 选择/分支头 | **−4**（每次调用，树内） | `OpSelectionMerge` 只在父的树里出现（rcp 里 1 条），候选两处均为 0 |
| shuffle | **−1 次调用**（`OpGroupNonUniformShuffle` 1 → 0）；`ShuffleXor` 4 → 4 不变 | 删的是"广播"，保留"归约" |
| 复制/mov | 源码无新增；native `mov` 应下降（8 条 `r[a0]` 读 + 重汇聚前的搬运） | 预测值见 NATIVE-PREDICTION |
| 同步/屏障 | **0** | 源码无 `barrier()`，`OpControlBarrier` 两臂都是 0，shared 0 B；模块级 `OpFunctionParameter` 15→13 只是 helper 参数少了两个（`vq_tree_xor(s,lane)`→`vq_tree_all(s)`、`vq_norm_rcp(s,lane)`→`vq_rcp_own(s)`），不是执行屏障 |
| 有效 lane | **上升**：父的 rcp 只有 2/32 lane 有效，候选 32/32 | 同一 lane 集合随后被 8 次乘法使用，不改变结果 |
| WG 数 / grid | **不变** | 288 workgroup、2304 subgroup |
| 活值峰值 | **不增**：每 lane 持有自己的 4 个 half 倒数，替代广播来的 4 个 half；省掉广播暂存 GRF | 无 scratch 需求论证依据：父 scratch 0，候选去掉暂存而非新增 |
| 代码体积 | **下降**：module words 4871 → 4567，bytes 19484 → 18268（−1216 B） | SPIR-V 事实；native GEN 数留待 GPU 核 |
| 数值 | **0 变化** | 见第 2 问 + `evidence/TREE-PROOF.json` |

逻辑字节 ≠ DRAM 字节、片段字节 ≠ 实际 GRF：本卡**不释放任何内存对象**，省的是尾段的控制流与一次跨 lane 交换。

## 5. 是否真落到 native（预测 + 判据，不声称已实现）

完整清单在 `NATIVE-PREDICTION.md`；这里只给三条硬判据（看不到就等于没实现）：

1. **`goto` 20 → 0、`join` 20 → 0**。基线 native 恰有 20 对，正好等于父 SPIR-V 的发散结构数
   （4 树调用 × 4 步 + 4 倒数调用 × 1 分支）。这是最锐利的判据：树谓词如果还在，这两个数不会动。
2. **`r[a0]` 间接读 8 → 0，`a0` setup（`add a0 … 0x580/0x600`）8 → 0**。这是 `subgroupShuffle(lane&16)`
   的落地形式；广播删掉后不应再出现。
3. **不变项必须真的不变**：`dpas.8x8 == 256`、`send.ugm == 1224`、`math.rsqt == 8`、`scratch 0`、
   `workgroup memory 0`。任何一项动了都说明改动越界或编译器重排，需要按 B 类重新归因。

## 6. 整体是否更快（要测什么、用哪条臂、怎么归因）

- **先看 native（A 类）**：按合同落锤顺序，先确认上面三条判据，再谈毫秒。
- **数值/资源**：`fixed`（frame0 = `1755e9c2…`）、`fb2`（frame0 同、末帧 `9c3e511e…`）、
  `ordinary`（末帧 `2b63d4ba…`）。本卡预期**逐位相同**（证明见 PROOF.json），任何差异＝E 类实现错误。
- **计时**：两臂 `base`/`cand`，6 组交替顺序，每组 30 帧（warm 1、feedback），540 样本全留，
  按进程组均值差算 t(df5) 区间；不剔尖峰、不补跑。
- **归因边界**：本卡只改 8 个 F14 位置，而且只改尾段控制流。
  单个 F14 dispatch 是 7633 条静态指令、256 条 DPAS 的 kernel 里的一小段，**预期变化在普通分辨率附近**；
  不得把结果与 F10 的 0.422 ms 相加，也不得用整体毫秒倒推"广播删除有效"。
  若 native 已落地而 ordinary 不动 → **D**（同族 8 个 PASS 已成包，不挑单点），
  这条方向（每 lane 自持归约结果）在本 shader 上的**上界就是这个尾段**，不存在"再多删一点广播"的余量。

## 7. 分诊（先按 A 预写，待 GPU 改判）

- **A（实现未落地）**：native 里 `goto/join` 仍 20、`r[a0]` 仍 8 → 说明编译器没有按源码重排，
  记"实现未落地"，不得记"方向无效"。下一个具体动作见 RESUME 第 4 节。
- **B（有副作用）**：`goto/join` 归零但 `mov` 上升 / 出现 spill / 首个 DPAS 推迟 → 列增量账再修一版。
- **C（无净收益）**：ISA 落地、门通过、整体仍慢 → 归因形状/编译器/候选身份，不推广成方向禁令。
- **D（INDISTINCT）**：ISA 落地、门通过、整体不可分辨 → 本族按包记 D。
- **E（数值失败）**：先定位首差 token/channel；本卡若失败首选怀疑点按概率排序为
  ①广播值未逐 lane 一致（已被穷举证伪）②`precise`/NoContraction 差异（NC 集合一一对应，已核）
  ③num 门用错 gold（fixed/fb2/ordinary 三套别混用）。
