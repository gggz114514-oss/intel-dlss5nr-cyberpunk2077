## 3. 已核实的 CPU 计时边界：聚焦关键切分，不在 0.66ms 内过度切碎

主文件 `R/source/bridge/src/deferred_identity.cpp`（注意 Vulkan 侧源码直接位于 `R/source/vulkan/` 根目录，无 `src/` 子目录），行号是当前阅读版本的导航锚点，修改后用符号定位。

| 字段/区间 | 当前锚点 | 实际含义 |
|---|---|---|
| record_started → record_finished | 约 413、748 | CPU 创建/获取资源、HDR/SR 录制；不属于当前面板 total |
| retire_previous_for_reuse | 约 816，started 之前 | 前帧退休/复用等待，位于面板 total 之外 |
| started → nr_prepared (`prep`) | 831→880 | Signal prepared、能力判断、bypass=false 时的 CPU 等待和有限次数 motion readback；不是 GPU prepare 执行时间 |
| nr_prepared → nr_modeled (`host`) | 880→932 | 构建 NRB_Frame 和 `processor->process`（含前网络 fence 检查、D3D 拷贝录制提交、Vulkan 录制提交）；不是网络 GPU 时间 |
| nr_modeled → nr_pre_sr (`composite submit`) | 932→981 | `queue->Wait(nr_ready)` 的 CPU 调用、描述符堆获取/重写、`composite` 录制/Close/提交；不是合成 GPU 时间 |
| nr_pre_sr → ended (`tail`) | 981→1063 | 后续 `deferred`/SR 提交、其余游戏列表提交、最终 `completion` fence 的 CPU 阻塞等待、`processor`/resource retirement |
| total | 1076 | `started → ended` 的 CPU 墙钟包络；不是 Present 帧间隔，也不是纯 NR GPU 时间 |

特别核查：约 1019 的 `deferred` 提交、1023 的 `if(begin<count) original_execute(...)`，发生在 `completion` fence Signal（1027）之前。最终等待包括 NR 之外的 SR 与游戏工作。多个 `matched` 项的 `completion` Signal 均在该提交批次之后；记录 `matched` 数与 `ordinal`，禁止把同一批次等待重复计为多个独立帧的 GPU 工作。

实施 CPU 事件：固定大小的帧记录，记录绝对 QPC tick 与 frequency，不只存差值。由于 `frame.frame_id` 在 `submit_deferred_identity`（898行）才分配，在 `record_deferred_identity` 创建 `Pending` 时分配单调递增的 `pending_seq`，用 `pending_seq + frame_id + control_epoch + route` 关联录制与提交阶段，禁止只凭相近时间配对。

**只做有判别力的关键切分（已知 `prep + host + composite submit` 合计仅 ~0.66ms，占 2.5%；`tail` 占 ~25.4ms 即 97.5%，不在 0.66ms 内切几十个微秒级碎段）**：

1. **`started` 之外的账目**：
   - 复用已有 `RecordTimingWindow` 的 6 个通道（`record`、`resources`、`hdr_initialize`、`xess_record`、`record_to_submit_gap`、`record_to_retire_span`）；厘清包含关系，不重复相加。
   - 单列 `retire_previous_for_reuse` 起止耗时（816行）。
2. **`started → nr_pre_sr`（~0.66ms 区段）**：
   - 保留原有 `started`、`nr_prepared`、`nr_modeled`、`nr_pre_sr` 四个边界点；
   - `host` 内部仅需单列 Vulkan `WaitForFences(network_fence_pending)` 起止（验证前帧网络是否已在前帧 `completion` 等待中完成，即此处等待是否接近 0）。
3. **`tail`（`nr_pre_sr → ended`，~25.4ms 区段）内部必拆三段（核心判别项）**：
   - `tail_submit_cpu`：`nr_pre_sr`（981行）→ `completion` fence `Signal` 完成（1027行），覆盖 `deferred_list`（XeSS/SR）提交 + 剩余游戏列表 `original_execute` + `queue->Signal(completion, 1)` 的纯 CPU 提交时间；
   - `tail_wait_cpu`：`SetEventOnCompletion` / `WaitForSingleObject(completion)` 起止（1043→1049行），记录阻塞等待 GPU 跑完流水线的纯 CPU 等待时间、wait 返回码与 `completed_value`；
   - `tail_retire_cpu`：等待完成（1050行）→ `ended`（1063行），覆盖 `pool_terminal_proof` / `processor.retire` 耗时。

在现有池统计上增加最小诊断计数：pooled private composite 次数、unique composite heap 创建次数、pool hit/miss。每帧只写内存，窗口结束导出。必须用计数证明 C 实际走复用路径、B 实际走每帧新建路径。

## 4. GPU 时间戳：分阶段、小数量、不新增等待

禁止用 CPU stopwatch 包住异步 API 当 GPU 耗时；禁止 GPU 逐帧同步读取查询；禁止用 GTPin 全密度块计时作真实等待分配。不要全网 266 PASS 逐个插桩，本轮只做粗阶段分解。

### 4.1 D3D12：本队列的时间轴

初始化时建立 timestamp query heap、readback buffer，槽位与现有 Pending/资源退休关联。用该队列 `GetTimestampFrequency` 转毫秒。只在原有最终完成已确认后读取，不新增 `WaitForSingleObject`/`Signal`/fence 来等诊断。复用查询槽前必须确认旧 GPU 写和 CPU 读已经结束；计时开关切换也不提前销毁在飞资源。

**跨模块实现注意**：锚点 1/2/4/5/6 位于 `CyberpunkNRBridge.asi`（`R/source/bridge/src/`），而锚点 3 位于 `nrvk_bridge.dll`（`R/source/vulkan/nrb_vulkan_processor.cpp`）。由于 `NRB_Frame` ABI 已冻结（`nrb_vulkan_processor.cpp:555` 校验 `sizeof(NRB_Frame)`），不得修改 `NRB_Frame` 跨 DLL 传递查询堆；应在 `nrvk_bridge.dll` 内用同一个 `c->d3d` 和 `game_q` 独立维护拷贝阶段的 D3D12 query heap + readback buffer（在既有完成确认后读取），窗口结束后用 `(frame_id, control_epoch)` 与 ASI 侧记录对齐。两边均在同一个 `ID3D12CommandQueue`（`game_q`）上执行，属于**完全相同的 D3D12 队列时钟域**，ticks 可直接相减。

插入锚点：

1. `deferred_identity.cpp` 的原始 `color_copy` `CopyResource` 前/后：单独量初始身份复制，不能混进 prepare。
2. `HdrProxy::record_prepare`（`nr_hdr_proxy.cpp`）：外包前后两点（包含状态转换与 Dispatch）。
3. `nrb_vulkan_processor.cpp::record_and_submit_copies`（482起）：整段 `do_copy` 前/后两点，包含完整状态转换与 color/motion/depth/exposure 中实际存在的复制。首轮不逐纹理插点。
4. `HdrProxy::record_composite`：外包前后两点，包含准备与恢复状态；保留原调度。
5. `deferred`/SR 列表（`deferred_identity.cpp:714-738`）：`entry.deferred_list` 由桥接自己 Reset、录制前后 barrier、调用 `original(list, ...)` 并 `Close()`，可直接在该列表开头（719行前）与结尾（738行 `Close()` 前）插入 D3D12 timestamp，直接测出 XeSS/SR 的真实 GPU 耗时！
6. `completion` fence 前的 GPU 末端标记：若 `begin == count`（即 `deferred_list` 后无剩余游戏列表），锚点 5 的末尾即为 `completion` 前的最后一个桥接 GPU 锚点；若 `begin < count`（有剩余游戏列表，且外部列表已 Close 不可编辑），则记录 `remaining_game_lists_count = count - begin`，不强行插空 marker list。

为了衡量跨 API 服务/等待包络：取同一帧在同一个 D3D12 队列上的“锚点 3（copy 结束）→ 锚点 4（composite 开始）”时间差 $\Delta T_{\text{D3D\_handoff}}$。它包含 Vulkan 侧执行、跨 API 信号量传递与队列调度间隙，不得为收紧此区间额外插入强制同步或拆提交。

### 4.2 Vulkan：同一个命令缓冲内分解

文件 `R/source/vulkan/nrb_vulkan_processor.cpp` 与 `port_network_bridge_backend.cpp`（在同一个 `slot.cb` 内）：

- V0：输入 acquire 屏障前（`nrb_vulkan_processor.cpp:759` 前）。
- V1：acquire 屏障后、`nrvk_backend_frame` 内 history copies + controls update 前（`port_network_bridge_backend.cpp:290` 前）。
- V2：上述操作及其后 transfer→compute barrier 后、gather 前（305行）。
- V3：gather 及其后 barrier 后、首个 network PASS 前（317行）。
- V4：最后 network PASS 及其后 barrier 后、scatter 前（325行）。
- V5：scatter 及其后 barrier 后（329行）。
- V6：外部所有权 release 屏障后（`nrb_vulkan_processor.cpp:828` `EndCommandBuffer` 前）。

`V1-V0` = acquire 包络；`V2-V1` = 历史/控制准备包络；`V3-V2` = gather 包络；`V4-V3` = 完整网络包络（266 PASS）；`V5-V4` = scatter 包络；`V6-V5` = release 包络；`V6-V0` = Vulkan 命令缓冲总执行包络 $\Delta T_{\text{VK\_exec}}$。

使用队列支持的 timestamp 查询，检查 `timestampValidBits`、`timestampPeriod`，处理有效位回绕。查询结果只在对应既有网络 fence（`network_fence_pending` / `slot.cb_fence`）完成后用 `vkGetQueryPoolResults`（不带 `VK_QUERY_RESULT_WAIT_BIT`）读取；不在当前帧同步等待结果、不新建一次提交获取结果。`vkCmdResetQueryPool` 放入同一个 `slot.cb` 开头（V0 之前）。

### 4.3 跨 API 等待计算（不做跨 API 时钟校准）

D3D12 和 Vulkan 的原始 ticks 不可直接相减，且当前 `create_vulkan`（`nrb_vulkan_processor.cpp:264`）严守 T5 契约仅启用 3 个设备扩展，**不要去开启 `VK_EXT_calibrated_timestamps` 或做跨时钟域零点拟合**。

直接用各自时钟域内的同帧区间差计算跨 API 净开销：
- D3D12 同队列包络：$\Delta T_{\text{D3D\_handoff}} = \text{ms}(T_{\text{composite\_start}} - T_{\text{copy\_end}})$
- Vulkan 同队列包络：$\Delta T_{\text{VK\_exec}} = \text{ms}(T_{V6} - T_{V0})$
- **跨 API 信号量唤醒与调度等待净包络** = $\Delta T_{\text{D3D\_handoff}} - \Delta T_{\text{VK\_exec}}$

（注：V0 位于 `slot.cb` 开头，在 `copy_ready` timeline semaphore wait 满足后才执行，因此 $\Delta T_{\text{D3D\_handoff}} - \Delta T_{\text{VK\_exec}}$ 恰好捕获了 D3D copy 完成 → Vulkan 队列唤醒，以及 Vulkan 完成 → D3D `nr_ready` 唤醒 + CPU 提交 composite 之间的全部非重叠等待/间隙。）

## 5. 低扰动实现要求与同进程 B/C 切换开关

- 三种诊断模式：`OFF`、`CPU_ONLY`、`CPU_GPU`。
- **同进程 B/C 切换开关**：对比 `R/descriptor-reuse/before/nr_hdr_proxy.cpp` 与当前 `nr_hdr_proxy.cpp`，B（对照）与 C（候选）的唯一实质代码差异仅在 `HdrProxy::record_composite`（596行）是否复用 `resource_lease_->bundle().composite_heap`（B 每帧调 `CreateDescriptorHeap`，C 从池中取 `bundle().composite_heap`）。在诊断版 ASI 中将该分支做成运行期可切换开关（`composite_heap_reuse = 0/1`，同时保留独立编译的 B/C 对照能力），以便在同一游戏进程、同一静止画面下直接做 `B ↔ C` 窗口切换，彻底消除重启游戏的跨进程方差。
- **每帧采集，不搞 1/8 帧抽样**：在预分配 ring buffer 和既有 fence 完成后异步读取的前提下，每帧写十几个 timestamp 仅微秒级开销；`CPU_GPU` 模式下直接**每帧记录**，避免 1/8 抽样与引擎偶发帧周期混叠，也省去额外的相位检查窗口。若偶发遇到查询未就绪，单列 `query_unavailable` 计数，绝不阻塞等待。
- 固定容量内存记录，预分配查询和 readback；不逐帧创建诊断对象、不逐帧 flush 文件、不加新线程轮询 fence。容量到限停止采集并计数，不覆盖数据假装完整。
- CPU 热点内只记录时间与整数计数；hash、CSV/JSON、统计在窗口结束后做。原有日志保持两臂一致，不顺手静默或改频率。
- 完成一次正常窗口后再切换模式/臂，可通过已有安全配置入口（如每秒轮询一次的轻量控制文件，绝不每帧读盘）控制切换。
- 不修改 shaders、运算次序、history 更新、descriptor binding 内容、图像状态转换、外部 semaphore 等待阶段、现有完成验证。
- 编译后做最小受影响 CPU 测试；GPU 验证直接进游戏，不把缺失 debug layer 当成虚构的通过或无限阻塞。

## 6. 执行顺序与预算

### D0 身份和源码边界（CPU）

先交付短版 `CLOCK-MAP.md`：上述每个字段的源码锚点、包含关系、漏在 `total` 之外的区间、能与不能相加的量。用实际编译代码验证，特别清理认知上的旧注释：`nrb_vulkan_processor.cpp`（如第 8、683 行）仍有“CPU 已等待 copy fence”的陈旧注释，实际当前版本（695、840-844 行）是 `copy_ready` timeline semaphore GPU 等待。注释不是执行证据。

### D1 测量扰动验证与 26ms 阶段拆解（第 1 次游戏启动）

使用诊断版（默认置为 B 对照分支，或先验 B），同一静止场景，在同一进程依次执行：`OFF → CPU_ONLY → CPU_GPU → OFF`，每窗口 30 秒、前 5 秒标 settling。全保留；分开报告首次初始化和稳态。诊断阶段不改网络、风格、后端、视角。

**判据脱钩（严禁因自然热漂移误熔断）**：
1. **针对“26ms 花在哪”（毫秒级 GPU/CPU 阶段拆解）**：比较 `CPU_GPU` 与前后 `OFF` 窗口的 `total` 均值/中位数。只要插桩引入的系统性偏移 `< 0.5 ms`（约 2%），`CPU_GPU` 测出的各阶段耗时（`color_copy`、`prepare`、`staging_copy`、`vk_acquire/history/gather/network/scatter/release`、`composite`、`XeSS/deferred`、`tail_wait_cpu`）即完全有效，**不得因为前后 `OFF` 窗口存在 `0.2~0.4 ms`（~1%）的自然帧耗漂移就触发 `MEASUREMENT_LIMIT` 停工**。
2. **针对“0.261ms CPU 下降去哪了”**：在 D1 数据中直接核查 `tail_wait_cpu`（`WaitForSingleObject`）占 `tail` 的比例，以及 `nr_modeled` 时 GPU 是否仍在执行前置异步工作。

最低正确性：身份一致、feedback 连续、无 timeout/device removed，用户画面正常。

### D2 B/C 两臂对照（优先同进程 ABAB 切换，最多 1~2 次启动）

- **主对照（同进程 ABAB 窗口切换，可在 D1 同一进程内紧接着执行，或单独第 2 次启动）**：
  固定同一存档/视角、分辨率、设置、风格、帧率上限和 stock clocks。在 `CPU_GPU` 模式下，同一进程内按 **`B → C → B → C`** 顺序采集 4 个 30 秒窗口（前 5 秒标 settling）。
  直接检验同进程内切换到 C 时：
  1. `composite submit`（`nr_modeled → nr_pre_sr`）是否稳定下降约 `0.26 ms`；
  2. `tail_wait_cpu`（`WaitForSingleObject`）是否反向增加约 `0.26 ms`（直接证明：GPU 瓶颈未变，`composite` CPU 录制提早结束只是让 CPU 提早 `0.26 ms` 进入 `completion` fence 等待，因此 `total` 不变）；
  3. 同帧 GPU 各阶段（特别是 `composite` 与 `network`、`XeSS`）耗时在 B 与 C 之间是否无变化。
- **独立二进制核验（可选补充，最多 1 对独立进程 B→C）**：
  若同进程 `B → C → B → C` 已闭合解释，仅需核对独立编译的 B/C ASI 符号与行为一致（或最多跑 1 对独立进程确认），**无需机械重启 6 次游戏**。

统计每窗口原始帧分布和窗口均值/中位数/p90/p99；完整展示每个窗口及相邻 B/C 差值，不用几千相关帧伪造窄 CI。面板只用于身份与趋势，主账用逐帧 CPU 记录和同帧 GPU 查询。若目标是游戏 FPS，还需单列 Present 帧间隔；没有它只能称桥接延迟，不称 FPS 收益。

总预算默认 **1~2 次游戏启动**（同进程完成 D1+D2，必要时补 1 对独立进程）。不要额外做多种优化候选。

### D3 对账和终态

从原始数据重算，检查CPU分段之和=旧total、扩展边界与record计时覆盖一致。GPU各阶段只在同一个时钟域和同一帧内加总；计算GPU未覆盖间隔，不把CPU与GPU重叠时间再加一次。所有 unmatched、query unavailable、切epoch、读失败、非steady帧单独计数保留。

结束后恢复原ASI、DLL、bridge INI、panel INI并逐文件验SHA，锁FINISHED且无游戏进程。禁止部署、改最新链头指针或替换Small。

## 7. 竞争解释：每条都给支持与反证

| 假设 | 必须看到的证据 | 不能据此声称什么 |
|---|---|---|
| 只是计时边界移动 | C 的 `nr_pre_sr` 提前约 0.26ms；`tail_wait_cpu`（`WaitForSingleObject`）反向增加约 0.26ms；同帧 GPU 各阶段耗时与 `total` 不变 | 仅凭 `composite submit` 减少不能说整帧更快 |
| GPU实际工作增加 | 同一进程 ABAB 场景下某个同域 GPU 阶段在 C 窗口持续增大；身份与插桩扰动闭合 | 不能仅凭跨进程 `tail` 墙钟增加判网络或合成变慢 |
| CPU提交/队列等待成为关键 | CPU 提交时间、$(\Delta T_{\text{D3D\_handoff}} - \Delta T_{\text{VK\_exec}})$ 跨 API 等待净包络显著或变化 | 长 send 或 fence 存在不是暴露等待证据 |
| 提交更早导致并发争用 | 同进程切换到 C 时提交时机提前与某个 GPU 阶段变长共同出现 | 本轮观察只能支持；未做可判别对照不能归因确定 |
| 场景/频率/跨启动波动 | 同进程 B↔C 无差异，仅跨进程重启时漂移 | 不得以“噪声”丢弃不利样本；无频率观测则写 unknown |
| 描述符复用未生效 | C 仍有每帧 unique 创建、pool miss/未走 private 路径 | 未触发实现不能否定复用方向 |
| 桥接total漏算关键CPU段 | 前帧 retire 或录制明显耗时且位于 `started` 之前 | 修正账目不是性能优化 |

本轮不为了证明某条链插sleep、busy wait、fake consumer或新增barrier。若观察还不能区分，提交一个具名的下一步最小诊断，说明变量、混杂和停止条件，不擅自开启新优化。

## 8. 后续优化只能按实测触发

1. 若shared staging copy占比显著：下一轮才研究prepare直接写共享可导入纹理，证明状态、跨API所有权、最后消费者与复用，不先改shader数值。
2. 若history/gather占比显著：下一轮才核对pre/post字段消费者和别名，区分复制payload与实际DRAM；不能因为源级MB大就宣称瓶颈。
3. 若原图CopyResource占比显著：证明合成全覆盖和失败回退，用受控路径处理；不得无条件删除。
4. 若主要在SR/游戏剩余列表：报告它不属于NR核心，不能再用它指导网络kernel优化。
5. 若CPU提交真实缩短而端到端没有变化：保留描述符复用资产，解释其不在关键路径的证据；不称方向失败，也不以删指令数冒充收益。
6. 若原有终端等待才是问题：先说明谁拥有输出、history、staging以及何时最后使用；不能用“稳定一会儿”替代每帧完成证明。
