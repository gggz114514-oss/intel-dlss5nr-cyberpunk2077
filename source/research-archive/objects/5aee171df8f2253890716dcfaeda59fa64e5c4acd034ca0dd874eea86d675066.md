## 2. 实施：三处同一算法（R17 修复版）

### 2.1 复用的是修复后的算法，不是通道常量

`candidates/r17-fix-a-dequant/source/c3x_pre_c256_i8mma.comp` 相对 R17 首臂的**唯一**算术差异：

```
首臂 : if ((tid%32)==0) nr3_srow[r3] = inv3;            // inv3 = 127/amax   <- 错
修复 : if ((tid%32)==0) nr3_srow[r3] = 1.0/inv3;        // = amax/127       <- 对
```

即**码点是 `roundEven(x*127/amax)`，所以反量化必须乘 `amax/127`**；首臂把量化步长当反量化
尺度，造成约 127 倍过尺度（同帧 20.19 dB → 修复臂 34.47 dB，`run/gpu/WO-SWEEP.json`）。
本卡三处**逐字**沿用修复后的形式：

```glsl
inv3 = (m3 > 0.0) ? 127.0 / m3 : 0.0;             // 量化步长
code = int8_t(clamp(roundEven(float(h) * inv3), -127.0, 127.0));
srow = (inv3 > 0.0) ? (1.0 / inv3) : 0.0;          // DEQUANT，R17-FIX-A
f[c] = f[c] * (rowF[c] * colF[c]);                 // 一次乘，f32
```

`rowF`/`colF` 用 **stride-0 协作矩阵载入**实现行/列广播（`LCOL`+0 取行、`LROW`+0 取列），
与 R17 已部署手法相同；不是新语义（登记为 N1 风险，需 native/数值门确认）。

### 2.2 各卡的 A 路径（三处各不相同，这是本卡的主要工作量）

| 卡 | 父的 A 来源 | 本卡的量化方式 | 每行尺度覆盖 |
|---|---|---|---|
| R16 | **全局** binding 2，规范 NHWC，行步长 `p1.x=1024`（8 行连续） | 32 线程；每行 4 lane × 256 通道 → shared int8 `t3a[8][1024]`（8192 B） | 每 token（每投影行） |
| R18 | **shared gather** 瓦片 `nr3_gbuf[16][256]`（父自己的 oob 零填） | 256 线程；每行 16 lane × 16 通道 → shared int8 `nr3_a[16][256]`（4096 B） | 每 gather 行 |
| R19 | **全局瓦片** `[tile][k16][row][16]`，行步长**常量 16** | **显式转换桥**：256 线程；每行 16 lane；按 `abase+row*16+(k/16)*256+(k%16)` 读半精度 → shared int8 `nr3_a[16][128]`（2048 B） | 每桥接行 |

### 2.3 R19 的 stride-16 陷阱：实现了显式转换桥，并给出逐元素证明

父的 A 片段载入是 `coopMatLoad(a, x65, abase + (kc/16)*256 + rh*128, 16, LROW)`，
即全局 `[tile][k16][row][16]`（每 tile 2048 half），**行步长常量 16**。K32 int8 片段要求
同一行 32 个连续 k，而该布局里同一行的 k=0..15 与 k=16..31 相隔 256 half（中间是另外 15 行）。
**直接把 K32 跨 stride-16 读会把 16 个不同行混进 K 维**——本卡没有这么做。

选的是卡面允许的两条路里的**转换桥**（生产者改布局留作后续优化，见 §7 第 7 条）：

```
bridge:  half_index = abase + row*16 + (k/16)*256 + (k%16)
         abase = p4.x + tile*(K/16)*256,  tile = wy*p1.x + wx
parent:  abase + rh*128 + (kc/16)*256 + i*16 + j,  row = rh*8+i, k = kc+j
```

因为 `kc` 是 16 的倍数、`j<16`，所以 `(k/16)=kc/16`、`(k%16)=j`，两式**恒等**。
`evidence/R19-BRIDGE-PROOF.json` 对全部 `16×128` 个 `(row,k)` 对逐元素比较，`identical=true`；
又因为两式都是 `abase + 相对量`，**对 1008 个 tile 一次证明即覆盖全部**
（`tiles_dispatched = tiles_available = 1008`）。

尾部：`K=128=4×32`（无 K 尾）、`rows=16=2×8`（无行尾）、`channels=64=2×32`（无列尾）、
**没有 OOB 行**（父本来就没有 guard，桥也没有；唯一隐含要求是 `K%32==0`，部署的 `p5.x=128` 满足）。

其它读者：`block61_swin_body_1..4` 都绑 241（`evidence/RESOURCE-USERS.json`）。
本卡**不改** binding 11 的全局布局、也不写它（源级 0 处 `x65[...] =`，SPV 里也没有到该变量的
OpStore），所以其它读者不需要改，也没有"静默改布局"。

   （`dump_block38_out` absmax 5.589e-4、rms 1.75e-5；`dump_vit_block38_T/A/QKV` 甚至全 0），
   而 skip 的 absmax 是 32.5，所以 `main` 项在 f16 加法里被完全吃掉——FP16 臂逐位等于 gold，
   INT8 臂也落在 1 ulp 级（8.9e-7）。**这不是"数值通过"**，只是"该帧不可判别"。
   投影级 3.4 % 是这堆近零张量的相对误差（同一行内动态范围极窄），不可外推。
   → 需要一次**有判别力**的抓取（见 §7 第 1 条）。
3. `dump_ioport_39_ioport_projection.bin` 在该 run 里**全 0**（G3 中未融合的投影 pass 已退役），
   所以不能拿它当 R16 的投影 gold。

## 6. 连接成本（次数/字节推导，不写毫秒）

全部是**源级计数**，不是实测 DRAM，也不是耗时。单位：每个 MMA 片段流 = 一个 subgroup。

| 项 | R16（1 SG/WG，576 WG/帧） | R18（8 SG/WG，264 WG/帧） | R19（4 SG 投影，1008 WG/帧） |
|---|---|---|---|
| 权重全局读 / 每个片段流 | 64 步 ×2 ×512 B = 65,536 B → 32 步 ×2 ×512 = 32,768 B（−50 %） | 16 步 ×2 ×512 = 16,384 → 8 ×2 ×512 = 8,192（−50 %） | 8 步 ×2 ×512 = 8,192 → 4 ×2 ×512 = 4,096（−50 %） |
| 每 WG 权重读（含 SG 间重复） | 1 × 65,536 = 65,536 → 32,768 B；×576 = 37.75 → 18.87 MB/帧 | 8 × 16,384 = 131,072 → 65,536 B；×264 = 34.60 → 17.30 MB/帧 | 4 × 8,192 = 32,768 → 16,384 B；×1008 = 33.03 → 16.51 MB/帧 |
| A 全局读 / WG | 8192 half = 16,384 B → 同量（另 +8192 B int8 shared 写+读） | 4096 half = 8,192 B → 同父（gather 不动；另 4096 B int8 tile） | 2048 half = 4,096 B → 同父（桥读同一批 half） |
| MMA 指令 / WG | 64 → 32 | 256（8 SG × 32）→ 128 | 64（4 SG × 16）→ 32 |
| shared 声明 | 512 → 8,864 B | 8,192 → 13,376 B | 2,048 → 5,184 B |
| barrier | 3 → 5（+2） | 3 → 5（+2） | 1 → 3（+2） |
| 权重常驻 | 1,048,576 B half → 526,336 B（−49.8 %） | 65,536 → 33,280（−49.2 %） | 16,384 → 8,448（−48.4 %） |
| 新增量化算术 / WG | 8192 元素：1 乘 + roundEven + clamp + int8 存；abs/max 各 8192；`127/amax` 8 次 f32 除 | 4096 元素同构；16 次除 | 2048 元素同构；16 次除 |
| 反量化 / SG | 2×128 元素 × 1 乘 + 1 次 int→f32 | 2×128 同构 | 2×128 同构 |

owner/活区：int8 A 瓦片、abs 部分和、行尺度都只属于本 dispatch 的 workgroup 活区，在 MMA 步内消费；
输出/落盘的写者与地址**与父完全相同**（`evidence/RESOURCE-USERS.json`：三 PASS 的
`write_set_unchanged=true`，写槽分别是 3 / 10 / 10）。
**登记的遗留**：三个 PASS 仍绑定 FP16 pack（binding 0 / 8），但只剩 gain 记录被读；
对应的投影矩阵成为死数据（与 R17 同一条 N2 遗留）。

## 7. 未解决阻碍（具名）

1. **G-R16-1 R16 缺有判别力的输入抓取（本卡最重要缺口）**。已有 `block38_out` 来自一条近乎
   全零的 ViT 分支（absmax 5.6e-4），使 `main` 项在 blend 的 f16 加法里不可见。
   需要的抓取（本卡只提请求，不跑）：对 PASS 96 执行一次，dump `INPUT` = resource 443、
   `OUTPUT` = resource 350 与 resource 341（skip），且**同一帧**要求
   `|projection| ≥ 1e-2`；若网络本身不给这个量级，则改为：追加一个"投影直出"缓冲
   （新增一个只读拷贝 pass 或 `p7.x=1` 诊断分支）并在同一 run 里 dump 它。
   没有这一步，R16 只能停在 `CPU_STRUCT / OFFLINE_COMPILE / PLAN_IDENTITY`。
2. **N1 行/列尺度片段的语义**：`rowF` 用 `LCOL`+stride 0、`colF` 用 `LROW`+stride 0 做广播，
   与 R17 同一手法，本工作区有同族部署代码（`fused_body_ds_keep_anchor.comp`），但三处都
   **没有 native/数值证据**。若门显示行间串扰，回退方案是"整瓦片单尺度"，每处约 5 行改完。
3. **N2 FP16 pack 死数据**：见 §6 末。下一步可把 gain 记录搬进新 pack 并解绑 binding 0/8。
4. **N3 局部数组/散布读**：R16 用 half 元素循环读全局（父也是），R19 桥在全局上做 16 次
   跨步读取；是否被驱动放进 scratch **native 未知**。
5. **NATIVE 未知**：无 pipeline-create 回执 → 三模块的实际 SLM 分配（8864/13376/5184 是
   SPIR-V 静态量）、GRF、DPAS vs 模拟、以及 int8 `M8N16K32` 在本组织驱动上的行为全部未测。
6. **GATE / 数值通过 / 质量通过 / ORDINARY 全未跑**：本卡没有 GPU 时段，`GPU.lock` 未触碰。
   不能把 CPU 双臂参考写成"数值通过"，也不能把 §5 的 rel_L2 当质量结论。
7. **R19 的桥是"正确优先"路线**：它比生产者直写 int8 瓦片多一次 16×128 的散布读；覆盖率
   优先接受这个成本。真正的优化（C64 body 侧直接产 int8 K32 瓦片）要重新证明 `(k,row,col)`
   与所有读者（`block61_swin_body_1..4` 现在都不读 int8 瓦片，所以是"新增边"而不是"换边"）。
8. **registry/manifest 未重生成**：本卡只给 plan 身份，没有重跑 `build_registry_v2.py`，
   任何"registry 已认可"的说法都不成立。
9. **下游 half 读者未逐位对比**：`split16_b40_l0_qx_producer` / `l1` / `l2` / `l3` 读
   resource 350（本卡的 `block39_out`）；读的是同一布局同一写域，但**没有**逐位比对证据，
   属下游 arm，不在本卡范围。
