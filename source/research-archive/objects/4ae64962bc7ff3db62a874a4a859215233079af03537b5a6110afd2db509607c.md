## 1. 六问

### Q1 映射：每个 (lane, component) 代表哪个 (token, channel)？

C256 一个 WG = 256 线程 = 8 SG，负责 **2 个 head（h = 2·WG.z + sg/4）**；每个 head 由 4 个 SG
（sg%4 = t）按 token 块划分。全部 coopmat 形状：`MAT_A`=8×16 half（4 comp/lane）、
`MAT_B`=16×16 half（8 comp/lane）、`MAT_C`=8×16 fp32（4 comp/lane）、`MAT_H`=8×16 half（4 comp/lane）。

**A 操作数（gY）**：`coopMatLoad(a, gY, (w·64 + m0)·256 + k0, 256, LROW)`
→ 元素 (r,c) = `gY[(w·64+m0+r)·256 + k0+c]` = **token (m0+r)、输入通道 (k0+c)**，K = 256 通道，
ki = 0..15 覆盖 k0 = 16ki。

**B 操作数（pack，权重）**：`coopMatLoad(b, pack, wq + (96h + 16·j)·256 + k0, 256, LCOL)`
→ LCOL 步长 256 ⇒ 元素 (i=K, n=N) = `pack[wq + (96h+16j+n)·256 + k0+i]`
= **输出通道 (96h+16j+n)、输入通道 (k0+i)**。j = 0..5 依次是 Q0,Q1,K0,K1,V0,V1，
每个 j 覆盖 16 个输出通道。权重包布局 = `[channel][k]`，k 步长 1、通道步长 256。

**C/H 累加器 lane 映射**（`nrh_coord_C`，已逐位复核）：lane L、component ci
→ x = 4L+ci；z = ((x&3)<<5) ^ ((x&124)>>2) = 32·ci ^ L；row = z/16，col = z%16
⇒ **(row, col) = (2·ci + L/16, L%16)**。即每 lane 持 4 个 token 行（2ci+L/16 ∈ 0..7）、1 个
通道列（L%16）。

**qkv 发布布局（未改）**：
| 区 | 偏移 | 布局 | 写者 | 读者 |
|---|---|---|---|---|
| Q | `base+0` | `[token][32 dims]`（LROW 步长 32；q0→dim0-15，q1→+16） | 4 个 SG | score 的 B（`bq0/bq1`，LCOL 步长 32，base+qg·32） |
| K | `base+2048` | 16 槽 × 128 half：槽 = 2·kb + dimhalf，`[dim][8 keys]`（LCOL 步长 8） | 4 个 SG | score 的 A（LCOL 步长 8，每次取 128 half） |
| V | `base+4096` | `[token][32 dims]`（LROW 步长 32） | 4 个 SG | PV 的 A（LCOL 步长 32，按 key 逐行） |

**一一覆盖（可枚举证明）**：候选把父的两个 row_phase 合并成一次 pass，但两块的 token 基址
仍是 `m0a = 8·t`、`m0b = 8·t + 32`（t = sg%4），与父的 `m0 = 8·t + 32·row_phase` 完全同址：

| t = sg%4 | 父 phase0 token | 父 phase1 token | 候选块 | K 槽（父与候选同） |
|---|---|---|---|---|
| 0 | 0–7 | 32–39 | a / b | 0,1 / 8,9 |
| 1 | 8–15 | 40–47 | a / b | 2,3 / 10,11 |
| 2 | 16–23 | 48–55 | a / b | 4,5 / 12,13 |
| 3 | 24–31 | 56–63 | a / b | 6,7 / 14,15 |

→ token 0..63 每个恰好出现一次（4 SG × 2 块 × 8 行）；Q/K/V 各 2048 half；
per-head `qkv` 区 6144 half = 64 token × 32 dim × 3，两个 head 区 base 0 / 6144 合计 12288 half
= 24,576 B = 声明的 `qkv[12288]`。**无漏读、无重复写、无跨 SG 同址 WAW**。
尾块：C256 的 64 token 正好被 8 个 M8 块整除，**没有半块/尾块**；`pc.p1.z` 的单点模式
（`wx=p2.x, wy=p2.y`）只是把 w 固定，不改变 token/通道映射。

### Q2 删什么真实工作（正常执行路径，不计 debug、不计编译器已消掉）

唯一被删的是**同一 SG 内、同一权重 tile、地址逐字节相同的第二次加载**：
父的 row_phase 循环里 B 地址 `wq + (96h+16j)·256 + k0` **不含 m0**，所以两个 row_phase
发出的权重 load 是同一地址的两次请求。

per SG（整个 64 token 窗口 = 2 个 row_phase）逐条枚举：

| 动作 | 父 | 候选 | 差 |
|---|---|---|---|
| QKV 权重 tile 加载（B，6 tile/ki × 16 ki × phases） | 192 | 96 | **−96（−50%）** |
| QKV A tile 加载（gY，QK 段 1/ki·phase + V 段 1/ki·phase） | 64 | 64 | 0 |
| QKV DPAS（8×16×16） | 192 | 192 | 0 |
| qkv 发布 store（Q/K/V 共 6 条 coopMatStore/块） | 12 | 12 | 0 |
| 屏障 | 1 | 1 | 0 |
| safe 标量 `auxf[pc.p5.x+h]`（每 phase 一次） | 2 | 2 | 0 |

**native 侧这 96 次是真实存在的**（既有 native，SPV 字节相同的父身份，
`f05-k-consumer-tile/c256/captures/native-f20-pixel-owner/ISA/CS_asmfd78c91bb8744f0f_…asm`）：

* QKV 段（`fence.slm` 之前）：192 条 `dpas`，**192 条 `load.ugm.d32x8`（32 B/lane 稠密，
  与"每 DPAS 一个权重 tile"一一对应）**，512 条 `load.ugm.d32x8t`（A 侧，8 条/tile），
  **2 条 `load.ugm.d32x1t`（= 每 phase 一次的 auxf scale ⇒ 证明 row_phase 在 native 完全展开、
  两遍都真的发出）**，64 条 `store.slm.d32x8t` + 4 条 `store.slm.d32x4`（qkv 发布）。
* attention 段（`fence.slm` 之后）：32 条 `dpas`、32 条 `load.slm.d32x4`（K/V 的 A tile 16+16）、
  8 条 `load.ugm.d32x8`（8 个 score block 的 bias）、2 条 `load.slm.d32x8`（`bq0/bq1`）。
  ——与源码模型逐项相等，说明该 ISA 的确对应本 shader 且被完全展开。

所以本卡的"删工作"= **一个帧内 3,514,368 条等址权重 load**（4576 WG × 8 SG × 96），
逻辑请求字节 1.68 GiB（**不是 DRAM 字节**：每 head 权重只有 48 KiB，绝大多数命中 cache；
省的是 issue/send 与返回区，不是显存流量）。

### Q3 重叠：谁生产、谁消费、RAW/WAR/WAW

| 值 | 生产者 | 最后消费者 | 覆盖者 | 依赖 |
|---|---|---|---|---|
| `gY`（F04 写，跨派发） | 上一 PASS；本 PASS 只读 | QKV 的 A load（QK 段+V 段各一次） | 无（本 PASS 不写 gY） | 跨派发 RAW（不在本卡范围，未动） |
| `pack` 权重 | host 上传；本 PASS 只读 | QKV 的 B load | 无 | 只读，无 WAR |
| `accQ0a…accK1b`（8 × MAT_C） | `coopMatMulAdd` ki=0..15 | `MAT_H(...)` 窄化 | 无 | 每 acc 自身 RAW 链，K 序 0..15 |
| `MAT_H q/k` | 窄化 → `nr_norm_qk_pair` | qkv store | 无 | 就地 RAW |
| `qkv`（SLM） | 8 个 SG 各写自己 head 区的互斥 token 槽 | score 的 `bq0/bq1`、K 的 A tile、PV 的 V A tile | 无（本 PASS 之后不再写） | **屏障前 W→屏障后 R**：跨 SG RAW（必需，保留） |
| `gT` | PV 的 4 条 store | 下一 PASS（F06） | 无 | 跨派发 RAW（未动） |

- **屏障**：1 条 `barrier()`，位于 QKV 发布之后、score 之前；父候选都只有这 1 条，候选没有新增。
- 候选改变了 Q/K/V 的**发布顺序**（父：块 a 的 Q/K/V → 块 b 的 Q/K/V；候选：两块 Q → 两块 K →
  两块 V）。三组地址互不相交，屏障覆盖全部写者，故顺序变化不产生新的 RAW/WAR。
- 候选**去掉了**父的 row_phase 迭代边界：父在进入 V 段前可让 4 个 QK 累加器退休；候选要求
  8 个 QK 累加器同时活到 ki 循环结束。这是唯一被拉长的活值区间，已计入 Q4。

### Q5 是否真落到 native（预测 + 判据，见 NATIVE-PREDICTION.md）

关键预测（都以既有 native 的父身份计数为基准，父 SPV 字节相同）：

1. QKV 段 `load.ugm.d32x8` **192 → 96**（这是"落地"的主判据；看不到 96 就是未落地，分诊 A）。
2. QKV 段 `dpas` **192 → 192**、`load.ugm.d32x8t` **512 → 512**、`load.ugm.d32x1t` 2 → 2。
3. QKV 段 DPAS 目标元组 `8 → ≥12`（8 个 QK + 4 个 V），且 8 个 QK 元组必须在**同一段**内同时活。
4. 每条 `load.ugm.d32x8` 与它的**最后**消费者 DPAS 的距离从 ~1 拍变为 ~2 拍；若编译器改成
   "load→dpas→load→dpas" 串行（send 前插 wait/sync），则省了 96 条却换来了等待 → 分诊 B。
5. `scratch` 仍 0、`fence.slm` 仍 1、`store.slm` 计数不变。

### Q6 整体是否更快

* 要测的整体量：**同样的 232 行 plan**，只有本组 16 个 PASS 的 SPV 换成候选；
  两臂（base / cand）同批 6 组交替、每组 30 样本（warm1/reps30/feedback），
  以进程组均值差算 t(df=5) 区间（按 START-HERE 的 ordinary 协议）。
* 归因只允许写：本组 16 个 PASS 的整链时间差 + 同批 native 的 send/dpas 计数差。
  **不得**把"96 条 send/SG"换算成毫秒，也不得跨批次相减（本线上一次 F05 单点收益都在 ±0.1ms 噪声内）。
* 预期上限的量级判断（不作为承诺）：QKV 段 send 数 −96/160 = −60% 的权重 send、总 send −9.5%、
  DPAS 数不变，且 F05 这 16 个 PASS 的 QKV 占本 shader 224 条 DPAS 中的 192 条（86%），
  但它的 send 只占 1014 中的 192（19%）——**A 侧 512 条 `d32x8t` 才是这个 shader 的 send 主体**，
  本卡不动它。这决定了本卡的期望值应低于"权重 send 减半"的直觉。

## 3. 退化会来自哪里（明写）

1. **acc 活值峰值**：QK 段 4 → 8 个 MAT_C（+16 fp32 reg/lane）。既有 native 显示父在 QKV 段
   已经用到 r24…r72 共 8 个 DPAS 目标元组、全 shader 最高 payload 寄存器 r112 / 上限 127，
   **只剩约 15 个寄存器的余量**；+16 有可能直接触发 spill（=STOP）。
2. **B 返回区活值**：父 native 只有 9 个轮转的 B 寄存器，192 条 load 192 条 DPAS 一一对应，
   在途 send 深度约 9。候选让每个 B 跨两条 DPAS，深度可能下降或被调度器改成串行等待
   （F10/F05 已证的"返回区耦合"退化路径，不能当免费收益）。
3. **重复 A 读（本卡刻意没有引入）**：若为压 acc 峰值改成"按权重对分三遍"（S2：Q 对一遍、
   K 对一遍、V 对一遍，每遍 4 个 acc），B 仍减半但 A 从 64 → 96（**+32 条 A load = +50%**），
   净 send 收益从 −96 缩到 −64。本卡选 S1（A 不变、acc +16），把 S2 作为具名备选写进 RESUME。
4. **低活跃 lane**：本卡不引入（QKV 段 32/32 lane、8/8 SG 全活跃）；score/PV 段未动。
5. **代码体积/调度窗口**：SPV 静态 +9.25%，native 段更长，I-cache 与调度窗口都可能变化；
   这是"整体重测"而不是"单链归因"的理由。

  候选未新增 `precise`/NoContraction（`child_own_decorations_outside_pattern = 0`）。
