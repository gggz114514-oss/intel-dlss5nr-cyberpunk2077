## 1. 父核结构（行号 = 父源 `parent_c256_d4_epi_only.comp`）

几何：`gT` 每 workgroup 16384 个 fp16 = 64 行 × 256 列（行 = token，列 = K）；`shT` 与它同布局，`shared float16_t shT[16384]`（L19，= 32768 B）。`local_size_x = 256`（L9）→ 8 个 SG（`sg = t_local/32` ∈ 0..7），每 SG 输出 32 个 C 通道（`n0 = (sg%8)*32`，L45）。

### 1.1 shT 的写点 / 读点

| 站点 | 父源行 | SPV 位置（code# / word#） | token 区间 | 说明 |
|---|---|---|---|---|
| W1 整窗暂存 | L33–L34 | code#131 / word#1530 | 0..63（全 64 行） | `for (e = t_local; e < 16384; e += 256) shT[e] = gT[w*16384 + e]`；每个 lane 固定写列 `t_local` 的 64 行；每元素全 WG 只写一次 |
| R1 M8 的 A tile | L74 | code#285 / word#2146 | 第 j 块 = 8j..8j+7 | `coopMatLoad(a, shT, m0*256 + k0, 256, LROW)`，8×16 tile：行 m0..m0+7、列 k0..k0+15；ki=0..15 覆盖全部 256 列 |
| R2 debug 转储 | L37–L38 | code#159 / word#1624 | 0..63（仅 debug≠0） | `OpLoad shT[e]` → `dbg[425984 + e]`，每 lane 64 个元素 |

R1 与 C 通道的关系：A tile 只由 `(j, ki)` 决定、**与 sg 无关**，所以 8 个 SG 各自读同一块 A tile；每个 SG 用它更新自己的 acc0（C 通道 `n0..n0+15`）与 acc1（`n0+16..n0+31`）。因此 shT 的读不是按 C 通道切分，而是按 token 行（j）与 K 列（ki）切分；全 WG 的 shT 读量 = 8 SG × 16384 元素 = 131072 元素（每元素每 SG 读一次）。**父、候选这一点完全相同。**

### 1.2 barrier（父）

| # | 位置 | 作用 | 动态次数 |
|---|---|---|---|
| B1 | word#1555（L35，暂存循环之后、j 循环之前） | 保证 16384 个 store 全部完成后才读 | 1 |
| B2 | word#1659（L40，`if (debug)` 内、debug 转储之后） | debug-only | debug≠0 时 1 |

父的普通路径动态 barrier = **1**；debug 路径 = 2。

### 1.2b 候选 barrier（静态 3 条；word# 为模块词偏移）

| # | word# | 位置 | 作用 | 动态次数/调用 |
|---|---|---|---|---|
| B1 | 1633 | 每带暂存循环之后（L51，在 strip 循环内） | 本带 4096 个 store 全部完成 → 本带可读 | 4 |
| B2 | 1746 | `if (debug)` 内、每带 debug 转储之后（L56） | debug-only | debug≠0 时 4 |
| B3 | 2946 | 本带两个 M8 完成后、下一带写入前（L119，`if (strip < 3)`） | 本带读完 → 下一带可写 | 3 |

普通路径 4 + 3 = **7**；debug 路径 4 + 4 + 3 = **11**。B3 是唯一"新增语义"的 barrier（读→写 WAR 边界）；B1 是父 B1 的按带版本；B2 是父 B2 的按带版本。三者操作数完全一致（见 6.1）。

### 1.3 8 个 M8 的处理顺序

`for (j = 0; j < 8; ++j)`（L43）：`m0 = (sg/8 + 1*j)*8`（L44）。因 `local_size_x=256 ⇒ sg∈[0,7] ⇒ sg/8 = 0`，故 **m0 = 8j**，j 依次处理 token 行 0..7、8..15、…、56..63。每个 j 内：先做 acc0/acc1 的 seed（gY 的 8×16 tile × pack 的 scale，L48–L71），再 `for (ki = 0; ki < 16; ++ki)`（L72）以 k0 = 16ki 读 A、读 B0/B1、两次 `coopMatMulAdd`（L79–L80），最后把 acc 收窄为 half 写 `imgout`（L83–L100）。**K16 顺序、B 布局、每个输出元素的操作数顺序都不变。**

### 1.4 acc 生命周期

每个 j 新建 `acc0`、`acc1`（`MAT_C` = FP32 coopmat 8×16）：seed → 16 次 MulAdd 累加 → `MAT_H(acc)` 收窄 → 存 `imgout`（debug 时另存 `dbg`）。acc 不跨 j、不跨 SG；候选里也不跨条带。

## 5. SPV 差分归因（多重集 + 结构 + 轨迹）

方法：整模块按 `(opcode, word count)` 做多重集差分；全局段另做一次；类型/常量/变量做 ID 无关的结构差分；代码段做"按 OpName / 常量值归一化后的指令轨迹"差分，逐 hunk 与预期类别比对。**全部差异均已归类，无未归类项**（`evidence/SPV-DELTA.json`，`verdict = CPU_VERIFIED`）。

- 词数：3257 → 3411（+154）；`removed_words = 0`、`added_words = 154`、净增 +154 = 模块词差；15 个变化类的 word-count 加权和也是 +154（`word_delta.consistent = true`）。
- "父有子无" 类：**空**（没有整类指令消失）；"子有父无" 类：**空**（没有整类新指令出现）。也就是说全部差异都是两侧共有指令类的计数变化 + 常量值变化，没有整类增删。
- 变化的 15 类：

| 类 | Δ | 归属 |
|---|---|---|
| OpControlBarrier | +1 | BARRIER：新增"带读完→下带可写"边界 |
| OpLoopMerge / OpSelectionMerge / OpLabel / OpBranch / OpBranchConditional / OpULessThan | +1 / +1 / +7 / +5 / +2 / +2 | CONTROL_FLOW：strip 循环、jj 循环、`if(strip<3)` |
| OpVariable / OpLoad / OpStore | +3 / +8 / +4 | INDEX_SCALARS：Function 存储的 `strip`、`sbase`、`jj` 及其读写（私有标量簿记，不是 SLM/DRAM 流量） |
| OpIAdd / OpIMul / OpConstant | +4 / +2 / +1 | ADDRESS_ARITH：`+sbase`（暂存与 debug 各 1）、`j=strip*2+jj`、`strip++`、`strip*4096`、`strip*2`、常量 2048 |
| OpName | +1(wc3) / +2(wc4) | NAMES：`jj`、`strip`、`sbase` |

- 结构差分：类型图只有 `shT` 链变化（`array(f16,16384)` / `ptr Workgroup` → `array(f16,4096)` / `ptr`）；常量值集合只多 `2048`；变量只有 `shT` 的字节数 32768→8192；执行模式 `LocalSize 256 1 1` 不变；绑定/集合装饰不变。
- 轨迹差分：11 个 hunk，逐个对应"新增 strip 循环头、暂存上界 16384→4096、暂存下标 +sbase、debug 上界与下标、jj 循环上界、j=strip*2+jj、A 下标 256→2048（glslang 对每个 coopmat load 生成两条重复地址链，故两处）、`if(strip<3)` 的 barrier 与 strip 自增"。没有任何 hunk 落在 FP 运算、coopmat 运算、B/scale/seed 载入、imgout/dbg 存储上。
- 不变量：FP 计数 `FConvert 4/4`、`FMul 2/2`；coopmat `Load 7/7`、`Store 4/4`、`MulAdd 2/2`；非 shT 的全局缓冲访问点全部 Δ0（`gT` 1、`YBuf` 2、`PackBuf` 4、`ImageOut` 2、`DbgBuf` 3）；6 个非 A 的 coopMatLoad 归一化操作数文本两侧完全相同（B: stride 16、ColumnMajor；scale: stride 0、RowMajor；seed: stride 256、RowMajor）。A 载入的 stride/列主序不变，只有下标表达式变了。

## 6. 记账（源级静态推导，非实测）

设 15 条受影响 PASS 的派发网格：8 行 11×6 + 7 行 11×7 = **1067 个 workgroup/帧**（读自冻结 plan 的 PASS 记录，不是实测派发）。

### 6.1 barrier

- 静态 `OpControlBarrier` 指令：父 2 条 → 候选 3 条（+1）。静态条数 ≠ 动态条数：候选的一条在 strip 循环里、一条在 `if(debug)` 里、一条在 `if(strip<3)` 里。
- 动态（每 workgroup 调用）：普通路径 **1 → 7**（4 次每带暂存后 + 3 次带间读后，第 4 带后不需要）；debug 路径 2 → 11。
- 全帧（15 个 PASS 各派发一次）：**1067 → 7469 次 barrier 执行，+6402/帧**。
- 三处 barrier 的操作数（执行作用域 2 = Workgroup、内存作用域 2 = Workgroup、语义 264 = WorkgroupMemory|AcquireRelease）与父完全相同。
- 两个条件 barrier 都在**一致控制流**里（`strip` 是有常量界的循环归纳变量，`debug` 是 push constant 标志，256 个调用取值相同）；SPIR-V 校验通过。目标驱动是否接受这种写法属于 pipeline-create 时的 GPU 侧检查。

### 6.2 声明 SLM

`shT` = `array<float16_t, 4096>` × 2 B = **8192 B**（父 16384 × 2 = 32768 B，−24576 B，−75%）。这是 **SPIR-V/plan 的声明值**，不是驱动 native 分配；native 分配、WG 并发度与占用率全部未知（需 pipeline-create 统计）。

### 6.3 global 输入读

暂存读量不变：每 WG 16384 个 fp16 = 32768 B（每 lane 64 个元素），全帧 1067 × 32768 = **34,963,456 B 源级有效字节**（≈33.35 MiB；不是实测 DRAM 字节）。元素次数 17,481,728 次/帧，父 = 候选（Δ0）。**本卡不减少 global 输入读域**，与设计预期一致。

### 6.4 shared 访问量（也未变）

写：16384 元素/WG（每元素一次）；A 读：131072 元素/WG（8 SG × 16384）；debug 读：16384 元素/WG（仅 debug）。三者父 = 候选。改变的只是"整窗一次备好"变成"分 4 带滚动备好"，即**同一块 shared 存储被复用 4 次，而非新增/减少访问**。

### 6.5 地址算术

- 暂存 gT 下标：父 `w*16384 + e`（每元素 1 IMul + 1 IAdd）；候选 `w*16384 + sbase + e`（1 IMul + 2 IAdd）→ **每元素多 1 次 IAdd**，即每 WG +16384 次、每 lane +64 次。
- `sbase = strip*4096`：每带每 lane 1 IMul + 1 Store + 2 Load（暂存下标与 debug 下标各用一次）；4 带共 16 条/lane。
- `j = strip*2 + jj`：每 lane 8 次（1 IMul + 1 IAdd）。
- strip 循环控制与 `strip < 3` 判断：每 lane 数十条整数指令（静态差分已逐条列出，均为 CONTROL_FLOW 类）。
- A 读下标：父 `m0*256 + k0`、候选 `jj*2048 + k0`，**指令条数不变**，只是乘法常量 256→2048（静态差分里这类变化计为"同 opcode、常量值变化"）。
- 静态增量：OpIMul +2、OpIAdd +4、OpConstant +1（2048）。动态上：**主导项是每 WG +16384 条 IAdd**（每元素一条），其余是每 lane 十余条的循环/索引簿记；相对每 WG 256 次 `coopMatMulAdd` 的矩阵运算是小量，但确实存在。

### 6.6 标量簿记

Function 存储局部变量 +3（`strip`、`sbase`、`jj`），静态 +8 Load / +4 Store；动态每调用：`strip` 5 次、`sbase` 2 次、`jj` 5 次 load，`j` −2、`m0` −2。这些是 glslang 的私有标量（通常落寄存器），**不是 SLM 或 DRAM 流量**；是否溢出到 scratch 需 native 统计。

## 7. CPU 结论与资格

- `CPU_STRUCT`：条带映射逐 j 等价（枚举 + 集合哈希相同）；shT 每元素每 WG 写一次、每 SG 读一次；最大存活 4096 元素 = 8192 B（父 16384 元素 = 32768 B）；8 SG、每 SG 两 acc、K16 顺序、B 布局、`m0`/`n0` 表达式均不变。
- `OFFLINE_COMPILE`：glslang 16.5.0 编出 SPV，`spv_validate_cpu result=0`。
- `SPV_IDENTITY`：15 类多重集差异 + 11 个轨迹 hunk 全部归类，无未归类变化；FP/coopmat/全局访存不变量成立。
- 因此本卡**只能**标 `CPU_STRUCT` / `OFFLINE_COMPILE` / `SPV_IDENTITY`；**不是** GATE/ORDINARY/NATIVE/QUALITY 通过，不写 PASS、不写毫秒。

## 8. 未验证项与"可能抵消"

4. **QUALITY**：本卡不改数学，预期无数值差异，但未验证。
5. **驱动接受度**：`if(strip<3)` 与 `if(debug)` 里的一致控制流 barrier 在目标驱动 pipeline-create 时是否被接受（SPIR-V 校验器已接受）。

**可能抵消（如实写）**：普通路径 barrier 由 1 增到 7（每帧 +6402 次），且暂存路径每元素多 1 次整数加法（每 WG +16384 次）。唯一可能的收益来自"声明 SLM 32 KiB→8 KiB 后 WG 并发度上升"，这必须由 native 统计与 ordinary 计时判定；**在拿到 native 与 gate/ordinary 之前，本卡不预支任何收益**，也不排除同步开销完全抵消甚至反超。
