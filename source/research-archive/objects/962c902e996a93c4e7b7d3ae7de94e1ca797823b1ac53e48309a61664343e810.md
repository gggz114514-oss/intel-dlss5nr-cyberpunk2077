# n38-f20-arena-shrink · ANALYSIS（合同 §4 的六个问题）

卡 id `n38-f20-arena-shrink`；F20 = ord 230 `s37_fold_body_r1a_v1`，1 PASS，grid (169,97,1)，local 256 = 8 SG×32 lane。
父 = 链头 `215aca67…`（GROUPS.md：F20 链头 sha = 基线 sha）。候选 `8d697649…`。
本卡只做一件事：**把 `shY[2048]`（4096 B）退役，让 stage-3 的 contract 结果住进 `shX` 已经腾空的窗口**，
使 SPIR-V `shared` 从 24576 降到 20480 B（≤21845），驻留 2 → 3。
全部结论按合同 §0 只做 CPU/静态，**没有 GPU、没有部署、没有金帧**（金帧是 `GPU-REQUEST.json` 的门）。

数字来源：`build/lifetime.json`（寿命/hazard）、`build/spv-check.json`（SPIR-V 结构）、
`build/addr-audit.json`（地址审计）、`BUILD.json`（身份/plan/cpu-check）、`PROOF.json`（证明汇编）。

## Q1 映射：生产者每个 (lane,component) 代表哪个 (token, channel)，消费者要求什么

被搬动的值只有一个：**`vY` = stage 3 contract 的输出 `Y[64][32]`**（64 个 token × 32 channel）。
它原来住在 `shY`，现在住进 `shX`；**偏移、步长、布局、访问形状全部不变**，所以映射是恒等而不是"重新推导"。

### 1.1 生产者（stage 3，源码 322/329）

```
uint m0 = sg * 8u;                                   // 每个 SG 独占 8 个 token 行
coopMatStore(half0, shX, m0*32u,      32u, LROW);    // 8x16 片段 -> rows 8sg..8sg+7, cols 0..15
coopMatStore(half1, shX, m0*32u+16u,  32u, LROW);    // 8x16 片段 -> rows 8sg..8sg+7, cols 16..31
```

* 片段类型 `MAT_H = coopmat<float16_t, Subgroup, 8, 16, UseAccumulator>`，32 lane 上每 lane 4 个元素
  （源码里 `half0[0..3]` 被逐个取用，见 316–320 行的 `handoff0[0..3]`）⇒ 一个片段 = 8×16 = 128 half。
* `LROW` + `stride = 32u` ⇒ 元素 (row i, col j) 落在 `m0*32 + i*32 + j`，即 `t = 8sg + i`、`c = j`。
  `half0` 覆盖 j∈[0,16)、`half1` 覆盖 j∈[16,32)，合起来正好 8 行 × 32 列 = 256 half/SG。
* **8 个 SG 的行是不相交的**（`m0 = 8sg`）⇒ 8×256 = 2048 = 整块，每个 (token,channel) 恰好写一次。

### 1.2 消费者（stage 9，源码 534/543）

```
uint m0 = sg * 8u;
coopMatLoad(seed, shX, m0*32u,     32u, LROW);   // rows 8sg..8sg+7, cols 0..15
coopMatLoad(seed, shX, m0*32u+16u, 32u, LROW);   // rows 8sg..8sg+7, cols 16..31
```

**生产者与消费者用的是同一类片段、同一个 (offset, stride, layout)**，所以 (lane, component)→(row, col)
的分布函数在两侧是同一个（n17 §5.2 已用 SPIR-V 类型证明 `MAT_H` 与 `MAT_A` 只差 `MatrixUse` 一个操作数：
`build/spv-check.json → H_vs_A_type.same_except_use = true` 由 n17 记录）。
⇒ 消费者读的 (t,c) 集合 = 生产者写的 (t,c) 集合，**逐元素相等**（`build/addr-audit.json`
`I4_footprints.candidate.coverage["shX/vY"] = {written: 2048, read: 2048, read_but_never_written: 0}`）。

### 1.3 一一覆盖、无漏读、无重复写、尾块

| 检查 | 结果 | 依据 |
|---|---|---|
| 写者覆盖 = 2048（整块） | ✓ | `I4` footprint：`s3-Y-W` 每 SG 256，8 SG 不相交 |
| 读者覆盖 = 写者覆盖 | ✓ | `read_but_never_written = 0` |
| 重复写 | 0 | 每个 token 行只属于一个 SG（`m0 = 8sg`） |
| 漏读（plane 的某元素从没被任何 SG 读） | 0 | `read = 2048` 且 8 SG 各读自己 256 |
| 尾块 / 部分 tile | 无 | 64 = 8×8，32 = 2×16，余数 0（`PROOF.json P7`） |
| 新的零填充/越界钳制 | 无 | 两条原有的（stage 0 oob→0、stage 9 地址钳制）都没动 |

同一套映射在**父**上也成立（父只是把它写到另一个数组）：
`I2_offset_identity.identical = true` —— 把 32 个共享访问行的数组名抹掉后，两臂的多重集**完全相同**。

## Q2 删掉了什么真实工作

**诚实结论：本卡删的是"空间"，不是算术/搬运指令。** 与 n36 的分类相同：收益来自占用率（更多驻留 WG
去填消息延迟），而不是少发指令。逐条列：

| 项 | 父 | 候选 | 依据 |
|---|---|---|---|
| Workgroup 存储变量 | 3（`shXP` 4096 + `shAr` 16384 + `shY` 4096） | **2（`shXP` + `shAr`）** | `build/spv-check.json.workgroup_variables`、`BUILD.json.workgroup_bytes` |
| Workgroup 字节 | 24576 | **20480（−4096）** | 同上 + `storage_bytes.Workgroup` |
| SPIR-V 指令数 | 4249 | **4247（−2）** | 少 1 个 `OpVariable` + 1 个 `OpName` |
| 模块 words | 16924 | 16916（−8） | 同上 |
| `OpControlBarrier` | 16 | 16 | 不减不加 |
| coopMat 传输（IGC 后） | 29 load / 17 store | 29 / 17 | 源级 38/20 不变 |
| SLM 消息（模型 = 源级传输 × 8） | 464 | 464 | n17 §2.1 的 8 消息/传输常数 |
| 屏障执行数（正常路径） | 5 | 5 | n30 §5 的贴图 |
| mov / add / sel / shuffle | — | **不变** | FP 多重集与整数控制流 opcode 集不变（`opcode_delta` 只有 `OpVariable` 与 `OpName`） |
| 舍入点 / K 序 / 归约树 | — | **不变** | FP 多重集 70 = 70；NC 站点 45 = 45 且多重集相等 |

**没有删、也不声称删**：任何 `send.slm` / `mov` / `add` / barrier。本 PASS 的 464 个 SLM 消息
（≈72 % 的运行消息流）一条都没动——按 n17 的结论，那条路要在 GLSL 里手写 DPAS per-lane 布局，
离线证不了，本卡不碰。

## Q3 重叠：独立工作原来如何重叠（RAW / WAR / WAW 表）

F20 的并行单元是 **(SG × token 行)**：8 个 SG 各拥有 8 个 token 行（`m0 = 8sg`），整条链上**行归属不变**。
下表是 `shX` 这一块内存上三个值的生产者 / 最后消费者 / 覆盖者，逐元素枚举（8×8 个 (writer SG, reader SG) 组合）。

| # | 值 | 生产者（写） | 最后消费者（读） | 覆盖者（下一个写者） | 关系 | 同 owner | 跨 owner | 关闭者 |
|---|---|---|---|---|---|---|---|---|
| 1 | `vX` | `s0-fold-W`（stage 0；SG sg 写 rows 8sg..8sg+7） | `s1-expand-R`（stage 1；**4 个 SG 共享一个行块** `sg/4`） | — | RAW | 1024 | **7168** | **barrier src 215**（父已有） |
| 2 | `vX` | 同上 | `s3-seed-R`（stage 3；本 SG 自己的 8 行） | — | RAW | **2048** | **0** | 不需要（owner 内） |
| 3 | `vX` | 同上 | `dbgX-R`（debug 回声，全部 2048） | — | RAW | 2048 | 14336 | barrier 215 + 225/227 |
| 4 | `vY` | `s3-Y-W`（stage 3；SG sg 写 rows 8sg..8sg+7） | `s9-seed-R`（stage 9；同一个 SG、同一批行） | — | RAW | **2048** | **0** | 不需要（owner 内） |
| 5 | `vY` | 同上 | `dbgY-R`（debug 回声） | — | RAW | 2048 | 14336 | barrier 332（debug 块内） |
| 6 | `vO` | `s9-O-W`（stage 9；SG sg） | `tail-R`（**只有 SG0/SG1 读全部 64 行**） | — | RAW | 256 | **1792** | **barrier src 586**（父已有） |
| 7 | `vO` | 同上 | `dbgO-R` | — | RAW | 2048 | 14336 | barrier 586 |
| 8 | `vX→vY` | — | `s3-seed-R` 读完 → `s3-Y-W` 写 | — | **WAR** | **2048** | **0** | **载荷依赖**（见下） |
| 9 | `vX→vY` | — | `s1-expand-R` 读完 → `s3-Y-W` 写 | — | **WAR** | 0 | **7168** | **barrier src 282**（父已存在的无条件屏障） |
| 10 | `vX→vY` | — | `dbgX-R` 读完 → `s3-Y-W` 写 | — | WAR | 0 | 14336 | barrier 215/225/227/282（4 道） |
| 11 | `vY→vO` | — | `s9-seed-R` 读完 → `s9-O-W` 写 | — | **WAR** | **2048** | **0** | **载荷依赖** |
| 12 | `vY→vO` | — | `dbgY-R` 读完 → `s9-O-W` 写 | — | WAR | 0 | 14336 | barrier 332/334/336（3 道） |
| 13 | `vX→vY` / `vY→vO` | 写写 | — | — | WAW | 2048 | 0 | 同 owner 同 8 行 + 中间的 barrier |

**载荷依赖**（第 8、11 行，这是本卡的合法性命门）：store 的**数据**是
`MAT_H(acc0/acc1)`，而 `acc0/acc1` 的初值就是刚才那次 seed `coopMatLoad` 的结果
（stage 3：`acc0 = MAT_C(seed)`；stage 9：`acc0 = MAT_C(seed)`）。所以
**store 不可能在 load 落地之前发射**（寄存器记分牌依赖），而两边的行集合都只属于本 SG ⇒ 不需要屏障。
这与 n30 用来删掉 stage3→4 屏障的论证是同一个（"每个 store 操作数都派生自它可能冲突的 load"）。

`shArena` 那边（本卡**不动**）：`vM` stage1→3 的 RAW cross = 7168（barrier 282），
stage3 读 → stage4 写 Q/K/V 的 WAR cross = **5376**（barrier 336，n30 的地盘）——
本卡的枚举独立复现了 n30 的这 6 个数字（`PROOF.json P8`，见 Q6）。

**没有把东西串起来**：新增的依赖边只是"同一个 SG 先写后读同一个地址"，没有任何跨 SG 的串行化；
**不动**的 3 道跨 SG 发布（215 / 282 / 586）一条都没删。

## Q4 新增成本（全部入账）

| 项 | 增量 | 依据 |
|---|---|---|
| 重复权重读取 | **0** | 权重站点与循环结构不变；`load.ugm` 计数不变（Q5 的 native 判据） |
| 重复 A(tile) 读取 | **0** | stage 1/3/4/6/8 的 A 片段站点全不变 |
| 地址计算 | **0 条新指令** | 5 处偏移表达式逐字符不变（`I2_offset_identity`） |
| 选择 / shuffle / pack | **0** | 无新增 `OpSelect`/`OpVectorShuffle`（`opcode_delta` 只有 `OpVariable`/`OpName`） |
| 复制 / 搬运 | **0 条新消息** | 源级 coopmat 传输 38/20 不变 |
| 同步 | **0 道新屏障** | 16 → 16，作用域签名 `Workgroup/Workgroup/264` 不变 |
| 有效 lane | **不变** | 没有改 owner 映射、没有改 grid、没有改 token tile |
| WG 数 | **不变** | grid (169,97,1) = 16393 WG，1 PASS |
| 活值峰值 / 寄存器 | **0** | 没有跨 stage 的新值；`max_r` 期望 ≤127（ISA 门） |
| 代码体积 | **−2 指令 / −8 words** | 只少一个 `OpVariable` 与其 `OpName` |

**唯一的未知（已定价）**：合并后 `shY` 与 `shX` 是同一个变量，IGC 若"看不出" stage 3 的
seed load 与 Y store（以及 stage 9 的 seed load 与 O store）是同一数组上的 WAR，可能补一条
`send.slm fence`。父 ISA 的 `fence.slm` = 11。上界代价：+2 条 fence/线程 = 2/747 ≈ **0.27 % 的消息**。
判据 O4：`fence.slm` 必须仍是 11，变 12+ 即 **B 类（实现有副作用）**。

**逻辑字节 ≠ DRAM 字节**：本卡不改变任何 DRAM 访问（不新增、不减少全局读）。
**片段字节 ≠ 实际 GRF**：本卡不动任何片段搬运，GRF 需求不变。

## Q5 是否真落到 native（预测 + 判据，不声称已实现）

没有 GPU，所以这里只写"我在 ISA 里要看到什么，看不到就等于未实现"。完整清单在
`NATIVE-PREDICTION.md`（顶部是硬判据）。摘三条最硬的：

| # | 可观察点 | 父 | 期望候选 | 若不符 |
|---|---|---|---|---|
| O1 | ISA kernel attribute *Workgroup Memory* | 24576 B | **20480 B** | 仍 24576 ⇒ **A 类（未落地）**，禁止用毫秒反推机制 |
| O2 | 驻留 WG / SM（20 KB 工作集在 64 KiB 池里） | 2 | **3** | 仍 2 ⇒ 驻留台阶没吃到（先查 O1，再查池的实际大小） |
| O3 | 消息普查：`load.slm.d32x8t` / `store.slm.d32x8t` / `dpas.8x8` / `send.ugm` | 304 / 160 / 64 / 237 | **304 / 160 / 64 / 237** | 任一上升 ⇒ B 类 |
| O4 | `fence.slm` | 11 | **11** | 12+ ⇒ B 类（编译器补了 fence） |
| O5 | SLM 基址族的个数（flat `[A+…]` 后缀） | 3 个 Workgroup 数组 | **2 个** | 仍 3 个 ⇒ 退役没落地 |
| O6 | `scratch` / `max_r` | 0 / 127 | **0 / ≤127** | scratch>0 或 max_r>127 ⇒ 门不过 |

native 层面**不做毫秒倒推**：即使 O2 成立，帧级收益也要看 ordinary（Q6）。

## Q6 整体是否更快：要测什么、用什么臂、如何归因

**本卡不能测**（合同 §0 禁 GPU）。要测的整体量与臂：

| 项 | 内容 |
|---|---|
| 臂 | base = 链头 `accepted/n36-f05-arena-c64c128-20261027/plan.txt`（`af6c1287…`）；cand = 本卡 `plan.txt`（`3a18df59…`，只换 ord 230 一行） |
| 门（先于任何计时） | fixed 金帧 `1755e9c2…`、fb2 金帧 `9c3e511e…` **逐字节**；不过即 **E 类**，不谈计时 |
| 资源 | GpuTime（该 PASS 单独 1.357 ms，帧份额 7.5 %）、驻留/占用率计数器 |
| 计时 | ordinary 6×30 交替（warm 1 / reps 30 / feedback），末帧 `2b63d4ba…`；单 PASS 作用域小，<0.03 ms 要**两批** |
| 归因 | 只看 ord 230 的 same-PASS GpuTime 与驻留台阶；不把帧级差摊给别的族；stall 计数器（BARRIER 0.219 / ALUWR 0.291）在 `evidence/COUNTER-NOISE.json` 的 ±3.8–4.9 点噪声内，不作为判定依据 |

**预期量级（写清是预测）**：

* 本卡零消息、零屏障、零活值代价，**收益全部来自驻留 2→3**（+50 % 的同核 WG 数）。
* 校准锚点：n36 在 F05 上把 24576→16384（驻留 2→4）实测 **+0.117 / +0.126 ms**，
  而 F05 这族 2.95 ms ⇒ **每步驻留 ≈ 该族自身时间的 4 %**。F20 自身 1.357 ms ⇒ 一步 ≈ **0.055 ms**。
* 反向探针的弹性（F05 2→1 值 1.219 ms、F06 2→1 值 0.364 ms）说明这种台阶是**强不对称**的，
  正向一步不宜按反向一半去推 ⇒ 我给 **0.02–0.08 ms** 的区间，点估计 ≈0.05 ms（帧份额 ≈0.3 %）。
* F20 是消息/发射消费者（n17：84 M 消息、623 M 指令、DPAS 只占 1.3 %），
  多一个驻留 WG 正好填消息延迟 ⇒ 区间上沿并非不可达；但 `<0.03 ms` 的单点作用域按 L13 记 D（INDISTINCT），
  需要两批同向才升级。

**不做的归因**：不把这 0.05 ms 与任何"跨批次"数字相减（合同 §0：不跨批次相减毫秒）。
