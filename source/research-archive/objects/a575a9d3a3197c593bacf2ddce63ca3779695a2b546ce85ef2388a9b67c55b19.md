# n02d-f02-bias-wide — PROBE-DESIGN（第 A 步：8×64 累加器 lane map 的 `if(debug)` 探针）

**一句话**：8×64 累加器片段的 lane→(row,col) 约定**没有任何可引证据**（密封头文件只测到
8×16 与 16×16）。探针只能在 GPU 上跑，所以它是**上 GPU 的第一步**；
**在它出结果之前，本卡候选既不判 E、也不判 A**（数值／native 落地都还不能定）。

---

## 1. 要测的问题（精确到可判真假）

现有实测律（`register_handoff.glsl` `1c4c7489` 的 `nrh_coord_C`，n02c 已 128 项逐项复核）：

```
8x16 累加器： comp c, lane L  ->  row = 2c + (L>>4), col = L & 15
```

候选把 8 个 8×16 站点换成一个 8×64 带（每行 64 个 f32），于是需要知道：

> **问题 Q**：8×64 带的 component k（k=0..15）of lane L 到底持有瓦片的哪个 (row, col)？

**答案是否影响机制生死，取决于一个二值性质**：

- **可判生**：lane L 的 16 个 component 恰好持有它在 4 个 8×16 站点里需要的 16 个元素
  `{(2c + (L>>4), 16b + (L&15)) : c=0..3, b=0..3}`（任意**同 lane 内**排列）。
  这时把 `bias[c]` 换成 `band[π(4b+c)]` 只是**换一个寄存器号**，f32 加、加法顺序、
  随后的 `nrh_narrow()` 半精度舍入点全部不动 ⇒ 零额外指令。
- **可判死**：某些 component 持有的是**该 lane 用不到**的元素（跨 lane 才能拿到需要的值）。
  那时提取必须走 subgroup shuffle：至少 16 条/片段（4 站点 × 4 component），
  而省下的只有 56 条 uniform 消息 ⇒ **净负**，本机制到此为止，不许靠加 shuffle “修好”。

## 2. 探针实现（已交付，可直接跑）

| 文件 | 作用 |
|---|---|
| `probe.comp` | 父源码 + 三处**只在 `if(debug && sg==0u)` 内**的落盘；`debug` 在本工件里硬写为 `true`（它永不进 plan 的计时/门臂，也不部署） |
| `probe-plan.txt` | 链头 plan，只把本组 7 行指向 `probe.spv`（`replaced==7`，`cpu-check` 已过） |
| `probe.spv` | 过 `spv_validate_cpu`（rc=0） |
| `probe_read.py` | 主机侧判读器（含 `--synthetic` 自检） |

**探针写的三个区域**（`dbg` = binding 4 = `swin_1_debug`，float16_t 元素）：

| 区域 | 偏移 | 内容 |
|---|---|---|
| A | `24448 + k*32 + lane`，k=0..15 | band0（行 t0..t0+7，全 64 列）的 component k |
| B | `10240 + k*32 + lane`，k=0..3 | band1（行 t0+8..t0+15）的 component 0..3 抽查 |
| C | `12288 + c*32 + lane`，c=0..3 | 现有 8×16 站点 (h0,b0) 的 component c（对密封律的交叉验证） |

- 偏移选择的依据：`swin_1_debug` 是 50176 B = 25088 half 元素，父源码既有 debug 落盘
  的最大偏移约 24303，故 A 段 24448..24959 是**未被使用的尾部**；
  B/C 段**故意覆盖**父源码的 q00/k00 dump 区（本工件不服务那些取证，且这点已在文件里标注）。
- **`sg==0` 门**：四个 SG 同偏移会互相覆盖到逐元素交错，导致“同一张表但不同 t0”混在一起；
  只让 sg0 写，保证 dump 内部自洽（t0=0，瓦片基址就是 `pc.p2.w`）。
- 探针不改正常路径：所有落盘在 `if(debug…)` 里，`debug` 之外的数值路径与父**逐字相同**；
  探针 SPV 不进任何计时/门/部署 plan。

**运行命令**（主代理的 GPU 槽，单臂，1 rep）：

```
clock_runner.exe --plan cards/n02d-f02-bias-wide/probe-plan.txt \
                 --out <fresh dir> --pool --warm 0 --reps 1 --dump-intermediates
# 产出：<out>/dump_swin_1_debug.bin  （float16，dbg 全量）
# 参考表：plan 的 BUFFER "swin_1_aux" = fb（float32，4100 元素）
python cards/n02d-f02-bias-wide/probe_read.py \
        --dump <out>/dump_swin_1_debug.bin \
        --fb   @NR_WORKSPACE@/src/project/artifacts/parallel-port-20261013/swin/network/block1/pack/c32_aux.bin \
        --out  cards/n02d-f02-bias-wide/LANE-MAP.json
```

## 3. 判读规则（`probe_read.py` 的方法与判据）

不做“按值反查坐标”（bias 表里有重复值，会多解）。改用**角色一致性测试**：
对每个 component k 与每个候选角色 (b,c) ∈ 4×4，问“**全部 32 个 lane** 上
`band[k][lane] == fb[W + tile(row=2c+(L>>4), col=16b+(L&15))]` 是否成立”。
错误角色只有在“同一张表在 32 个不同位置重复同一个值”时才可能通过 ⇒ 16×16 矩阵基本是对角的。

基址 W 由扫描确定（不需要信任 plan 的 PUSH 字）。

| 判读结果 | 含义 | 动作 |
|---|---|---|
| **H1** | `k = 4b + c` 成立（16 个 component 全一致、双射） | `candidate.comp` **已按此写**；若探针回报 H1，则候选的 f32 加与舍入点**按构造精确**，可直接进数值门 |
| **PERM** | 另一个**同 lane 内**双射 | 改 `NRH_C64_AT(b,c)` 一行、重建；零指令代价，数值精确 |
| **PERM-NONBIJECTIVE** | 两个 component 争同一角色 | 实现错误，先修索引 |
| **CROSS-LANE** | 有 component 持有该 lane 用不到的元素（dump 的值都在 `fb` 里，但没有 lane-局部的角色解） | **机制死**：提取需跨 lane，净负；按 C/BLOCKED 报，不许加 shuffle “补救” |
| **NO-BASE** | dump 的值根本不在 `fb` 里 | 探针臂没跑（`--dump-intermediates` / `debug` / 偏移）——不是布局结论 |

**判读器已自检**（CPU，未花 GPU 槽）：

| 合成 dump | 期望 | 实测 |
|---|---|---|
| `--synthetic H1` | H1，base=0，双射，密封律 128/128 | ✅ `_probe-selftest-H1.json` |
| `--synthetic NAIVE`（自然延伸 `z = 32k+lane`） | CROSS-LANE | ✅ `_probe-selftest-NAIVE.json`（`dumped_values_present_in_fb = 512/512`，无 lane-局部解） |
| 人为置换（k → 角色 `(5k mod 16)`） | PERM，且能还原该双射 | ✅ 一次性脚本，见 `RESUME.txt` §5 |

## 4. 预期（写清“看到什么算对”）

- 若实现按其 8×16 律“按列块重复”扩展（最可能的实现方式）：
  `component k = 4b + c` 持有 `(2c + (L>>4), 16b + (L&15))` ⇒ **H1**，判读器会给 16/16 对角。
- 若实现按“瓦片行主序线性摊到 32 lane × 16 component”（`z = 32k + lane`）：
  每 lane 只拿到 cols {L, 32+L}（或类似），**拿不到它 4 个站点要的 16 个元素** ⇒ **CROSS-LANE**。
  这一条是**必须先测的负分支**：它正是“不做探针就动手必然判 E”的形态。
- 中间形态（列块内互换、b 与 c 交换等）：**PERM**，一行修正，仍然零代价。

## 5. 与候选判定顺序的关系（硬约束）

1. 探针臂先跑，产出 `LANE-MAP.json`（本卡已交付判读器与自检，只差 GPU 一分钟）；
2. 判读 = `H1`：候选数值**按构造精确**，可直接进 `fixed`/`fb2` 两套末帧 gold 门（合同 §8.1）；
3. 判读 = `PERM`：先改一行索引再编译，仍先过数值门；
4. 判读 = `CROSS-LANE`：**候选作废**，本卡按“定价否掉”收尾（不判 E，不判 A，属于 C/机制不可行）；
5. 无论哪种，`load.ugm.d32x16t 64→0` 是否在 native 里出现，仍按 A 类判据单独看。

> 因此本卡 `candidate.spv` 的数值身份是**条件身份**：它对齐的是 H1，不是“已证实的实现”。
> 这也是本卡不声称 E/A 的原因。
