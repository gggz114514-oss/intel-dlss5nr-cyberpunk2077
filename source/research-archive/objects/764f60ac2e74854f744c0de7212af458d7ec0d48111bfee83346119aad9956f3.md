# n08b-f08-order — NATIVE-PREDICTION（第 5 问：期望在 ISA 里看到什么，以及判据）

本卡**没有 GPU**，以下全部是**预测 + 判据**，不是“已证明”。采集由主代理串行执行（`GPU-REQUEST.json`）。

## 0. 参照物：n08 批次的实测（旧批次，仅作方向参考，不作当前身份）

n08 卡 `RESULTS.json:layer2_native`（同一批次内两臂对比，F08 kernel 的 ISA 文件名唯一变化）：

| 项 | base (66,2,1) | n08 cand (33,4,1) |
|---|---|---|
| F08 kernel ISA 文件 | `CS_asm3b9ac75d…` | `CS_asm3de9ecb0…` |
| Instruction Count | 4672 | 4673（+1 地址准备） |
| send / dpas / sync | 534 / 132 / 231 | 534 / 132 / 231 |
| max_r | 127 | 127 |
| first DPAS addr | 1056 | 1072（晚 2 条） |
| 观察到的变化 | — | token 的 `shl 4→5`；group 的 `shl 2→1`；`and 1 → bfn.0xEA`（subgroup 掩码 1→3）；末尾 `mov` 的 hash 常量 |

**这些数字属于旧批次**：当前链头含 n05a/n06，其他 39 个 kernel 的字节已经变了。本卡只允许把“同批 base 臂”当参照物，禁止拿 n08 批的绝对计数当当前身份（合同第 8 节第 7 条）。

## 1. 本卡期望看到的（逐条可观察点）

本卡的每 WG 内容与 n08 候选**完全相同**，只把两条 grid 轴互换。所以：

| # | 可观察点 | 期望值 | 若是别的值 |
|---|---|---|---|
| 1 | dispatch grid（capture/派发记录里的 F08 PASS） | **(4,33,1)**，132 个 WG、1056 个 SG | 仍是 (66,2,1) → plan 的 16 行没进 manifest（不是实现问题，是装配问题） |
| 2 | token 步长的 ×32 | 作用在 **WorkGroupID.y**（ISA 里 `mul/shl 5` 的源 = `sr0.1` 的那条 `mov`） | 仍作用在 `sr0.0`（x）→ **实现未落地**（A 类） |
| 3 | group 步长的 ×2 | 作用在 **WorkGroupID.x**（`shl 1` 的源 = `sr0.0`） | 仍 `sr0.1` → 未落地 |
| 4 | subgroup 位运算 | `and 3`（或 n08 里那条 `bfn`）与 `shr 2`，与 n08 相同 | 出现 `and 1` / `shr 1` → 还是父映射 |
| 5 | 指令数 | 与**同批 n08 臂**相同（n08 批次 `RESULTS.json` 记 4672/4673，其 `GPU-REQUEST.json` 却写 4669——两个数字在本卡不采信，只要求同批两臂自洽） | 差 ≥2 且无法归到 sr0 分量互换 → 代码生成变了，必须单独记账，不能当“预期” |
| 6 | send / dpas / sync / max_r | 534 / 132 / 231 / 127（与同批 n08 臂相同） | 任一变化 → 说明不只换了轴，先查是否混进别的机制 |
| 7 | SLM / scratch | Workgroup Memory 2048 B、Scratch 0 | 变化 → 实现有副作用 |
| 8 | 分支/尾块 | 无新增分支、无新增尾块处理 | 出现新分支 → 计划外 |
| 9 | 其他 39 个 kernel | 与**同批 base 臂**逐字节相同（本卡只动 F08 的 16 行） | 有不属于 F08 的变化 → plan 装配错误 |

## 2. 判据（“若看不到就等于未实现”）

- **A 类（实现未落地）的判据**：ISA 里 ×32 仍跟 x、×2 仍跟 y，或 `and 1`/`shr 1` 仍在，或 grid 不是 (4,33,1)。→ 记“实现未落地”，**不得**用整体毫秒倒推机制。
- **落地判据**：第 2、3 条同时成立且第 4–9 条无计划外差异。落地之后，整体计时才是对本卡问题的回答。
- **失败判据（装配）**：F08 PASS 行仍指向父 SPV（`32291c7e…`）→ plan 没生效；此时任何计时都无意义。

## 3. 不能观察的（写清楚，不用它支撑结论）

| 项 | 为什么不能 | 本卡怎么写结论 |
|---|---|---|
| cache 命中率 / 每 slab 是否真的驻留 | gtpin mode0 只给 ISA/基本块；zprof 只给 GpuTime；无 cache 计数器 | 只写“整体计时显示…”，不写“cache 命中率提高/下降” |
| 并发 WG 数、每 core 的 wave 组成 | 无 occupancy/launch trace；只能由 SLM 2048 B 的分配语义**推测** 8 个 SG 同 core | 写 unknown |
| driver 实际发射顺序是否等于 `x + gx*y` | 同上 | §4 的“并发窗口足迹”只是模型，只能作为**事前声明差异方向**，不能当证据 |
| lane→(row,col) fragment 约定 | Intel DPAS 实现定义，本工作区无引证 | 三臂在该层一致（同 opcode 序），不影响判别 |

## 4. 与整体计时的衔接（判别逻辑，不预测毫秒）

- 本卡与 n08 的每 WG 内容、每 PASS 请求量完全一致；两臂唯一变动是“一排 WG 共享权重（n08）还是共享 token 块（本卡）”。
- 若 native 落地且整体 (4,33) 回到基线：退化归到**发射顺序/并发足迹**。
- 若 native 落地且整体仍慢 ~0.18 ms：退化归到两臂**共有的每 WG 内容属性**（32 KiB 输入足迹 或 WG 内 4 条同 slab 流），本卡**不能**在两者之间再分。
- 若 native 未落地：上面的计时一律不解释。
