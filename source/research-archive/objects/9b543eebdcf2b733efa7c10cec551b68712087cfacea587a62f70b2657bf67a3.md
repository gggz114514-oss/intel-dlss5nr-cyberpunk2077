## 1. 映射：每个 (lane, component) 到底代表哪个 (token, channel)

### 1.1 域与几何（可从源码逐行推出）

| 量 | 值 | 出处 |
|---|---|---|
| grid | 66 × 4 × 1 = 264 WG/pass | plan header `66 4 1`；`BUILD.json:group.grid` |
| local_size | 256 → 8 子组（sg=0..7，lane=0..31） | `candidate.comp` 第 7、58 行 |
| `token_at(s)`（KIND0） | `gl_WorkGroupID.x*16 + s` | `candidate.comp` 第 54 行 |
| `tiled(T,c,512)` | `((T/16)*32 + c/16)*256 + (T%16)*16 + (c%16)` | `split16_common.glsl` |
| m0 / n0 | `m0=(sg/4)*8` ∈ {0,8}；`n0=(sg%4)*32` ∈ {0,32,64,96} | `candidate.comp` 第 70 行 |
| 真实 token 数 | 66×16 = 1056 = 44×24 | 无 padding token |
| channel 数 | 512 | K 环 `k=0..511` step 16 |

### 1.2 生产者 ↔ 消费者 一一覆盖（父，`sx` 路径）

- 生产者（staging）：`for (e=lid; e<8192; e+=256)`，`t=e/512`、`c=e%512`，
  `sx[e] = gf[tiled(token_at(t), c, 512)]`。
  ⇒ 槽位 `e = t*512 + c`，写入者 = 线程 `lid = e mod 256`。**8192 槽位、每槽恰好写一次**。
- 消费者（A 片段）：`coopMatLoad(a, sx, m0*512 + k, 512, ROW)`，ROW 行主 → 元素 (r,cc) 读槽
  `m0*512 + k + r*512 + cc`，即 `t = m0+r`、`c = k+cc`。
- 等式：`consumer_slot ≡ staging_slot`，**逐 (token, channel) 全枚举 0 不匹配**
  （`PROOF.json:coverage.slot_mismatches=0`；本轮 `SELFCHECK.json:address_algebra.staging_slot_mismatches=0`）。

### 1.3 候选直接地址（本轮独立重推 + 复算）

`abase = tiled(token_at(m0), 0, 512) = (token_at(m0)/16)*8192 + (token_at(m0)%16)*16`，
直接读地址 `abase + (k/16)*256 + r*16 + cc`。

代数（`q = k/16`，`k` 必为 16 的倍数，`T = token_at(m0)+r`）：

```
tiled(T, k+cc, 512)
  = ((T/16)*32 + (k+cc)/16)*256 + (T%16)*16 + (k+cc)%16
  = (token_at(m0)/16)*8192 + q*256 + ((token_at(m0)%16)+r)*16 + cc      // T/16 不变、T%16 = (m0%16)+r
  = abase + q*256 + r*16 + cc
```

前提 `token_at(m0)%16 ∈ {0,8}` 且 `r < 8`（由 `m0 ∈ {0,8}` 保证）：`(m0%16)+r ∈ [0,16)`，不跨超块；
`c = k+cc` 满足 `(k+cc)/16 = q`、`(k+cc)%16 = cc`（因 `cc<16`）。三项前提全部由父自身 launch 几何给出，
不引入新假设。

**验证规模**（本轮 `selfcheck.py`，独立于 PROOF.json 重算）：

| 检查 | 规模 | 结果 |
|---|---|---|
| 直接地址 vs 父 staging 后地址（逐 (gx,sg,k,r,cc)，含 4× 冗余读者） | 2,162,688 次 | mismatch **0** |
| 消费者槽位 vs 生产者槽位 | 2,162,688 次 | mismatch **0** |
| 直接地址去重后的不同地址数 | — | **540,672** = 1056×512 = 整个 `gf` 相关域（连续，min 0 / max 540671） |
| 每 WG 覆盖的地址窗口 | 66 个 WG | 形状全同；每 WG 8192 个不同地址 |
| 越界 | — | 最大读索引 540671 < 缓冲范围；`sx` 最大读 8191 < 8192 |

**尾块**：`grid.x*16 = 1056` 恰为真实 token 数，`tiled()` 的最大 token 超块 = 65 (<66)，无 padding，
无半 tile，故"尾块正确"是**空真**（没有尾块）而不是被忽略。

**重复写/漏读**：`sx` 8192 槽位全部被写且只写一次（`PROOF.json:coverage.duplicate_writes=0`，
`uncovered_slots=0`）；读侧每个槽被同 WG 的 4 个子组各读一次（`subgroup_readers_per_slot=4`），
这是父也有的 4× 冗余（见 §4）。

### 1.4 (lane, component) 层：谁写哪个槽、消费者怎么拿到

**生产者（父 staging，逐 lane 可枚举）**：线程 `lid` 写槽 `e = lid + 256*i`（`i = 0..31`），
每次写 **1 个 half（单 component，未向量化）**。故：

- 线程 `lid` 负责的 32 个槽 = `{ e : e mod 256 = lid }`；
- 槽 `e` ↔ `(t = e/512, c = e%512)` ↔ `(token = WG.x*16 + t, channel = c)`；
- 即 `(lane, component) = (lid, i)` 精确对应
  `(token, channel) = (WG.x*16 + (lid+256i)/512, (lid+256i)%512)`；
  `i` 走 32 次覆盖 8192 个 (token, channel)，**无重叠、无遗漏**（`slots_written_exactly_once`）。

**消费者（`coopMatLoad`）**：矩阵元素 `(r, cc)` 读槽 `m0*512 + k + r*512 + cc`，
即值来自 `(token = token_at(m0+r), channel = k+cc)`。
A 片段的 `(lane, component) ↔ (r, cc)` 指派由 IGC 的 cooperative-matrix 降级决定、源码不可见，
但这不妨碍证明等价：

> 父与候选用的是**同一个** `coopMatLoad`（同类型 `MA`、同 `ROW`、同 8×16 形状、同 component 数），
> 所以"哪个 lane 的哪个 component 装 (r,cc)"在两侧**按定义相同**；变的只有"这个 (r,cc) 的字节
> 从哪里取"，而这一点由 §1.3 的逐元素地址等式覆盖。⇒ 不需要知道 B580 的 A-fragment CH/C 映射，
> 也能断定两侧语义等价。

**（对照）seed 块确实显式依赖 CH/C 映射**：`component ci of lane lv = (row = 2ci + lv/16, col = lv%16)`
（`candidate.comp` 第 20–23、82–93 行）。这段代码**本次未改一个字**，不属于本 diff 的证据面。

**本卡不声称**：A 片段的具体 (lane, component) 排布与 DPAS 的寄存器 bank 分配 —— 属驱动行为，
只能由 native 采集观察（见 `NATIVE-PREDICTION.md` 不变量 W4/§1.2）。

## 3. 重叠：原来谁和谁重叠，删了之后靠什么供料

单 WG 的时间轴（父）：`序言 → [staging 32 次散列读 + 32 次 SLM 写] → fence+barrier → seed 块 → K 环（32 × 2 DPAS，全展开）→ 末次 store`。

| 边 | 生产者 | 最后消费者 | 覆盖者 | 类型 | 候选里的处置 |
|---|---|---|---|---|---|
| E1 | staging `sx[e]`（任意 warp） | A 片段读（**另一个 warp** 的 `coopMatLoad`） | 无 | **RAW（跨 warp）** | 整条边删除：A 直接从 `gf` 读，无中转 |
| E2 | staging `sx[e]`（本 warp） | 同 warp 的 A 读 | 无 | RAW（同 warp） | 同上，删除 |
| E3 | 上一 WG 的 staging 写 | 下一 WG（**不同** WG）的 staging 写 | 硬件按 WG 分 SLM | WAR（跨 WG，非本次 kernel 内） | 不变：`sx` 是 Workgroup 存储类，按定义每 WG 私有；`PROOF.json:no_cross_workgroup_reader` 给出 `sx` 引用数 4（1 变量 / 1 store / 1 access chain 进 A 读 / 1 入口点接口） |
| E4 | 同 WG 内 staging 写 | 同 WG 内 staging 写（同槽） | 无 | WAW | 不存在：8192 槽每槽恰好写一次 |
| E5 | seed 块（寄存器直写 acc0/acc1，本 kernel 已无 `scratch`） | 第一个 DPAS | 无 | RAW（同 warp，寄存器） | 不变 |
| E6 | A/B 片段 | `acc0/acc1` | 后续 DPAS 链 | RAW（寄存器） | 不变；`a` 一次读供同 k-step 的 2 个 DPAS（与父同），B 双 bank 各供 1 个 MulAdd（与父同） |
| E7 | `acc0/acc1` → `MH` 收窄 → `gy` | 本 PASS 的 2 次 `coopMatStore` | 无 | RAW（寄存器） | 不变 |

**barrier 真正保护的是什么**：只有 E1/E2（同 WG 内跨 warp 的 `sx` RAW）。
它**不**保护 B 权重（`weights` 是 `readonly buffer`，本 kernel 不写）、不保护 A 的 global 源
（`Ffwd` 在 GLSL 里没有 `readonly` 限定符，但 KIND0 路径对 `gf` **只读不写**：本 PASS 唯一的
global 写是 `gy`，见 `candidate.comp` 第 129 行）、也不承担跨 WG 顺序（SLM 私有）。
因此删除它不改变任何**跨 WG** 语义，只删掉"本 WG 8 个子组必须等彼此"这一个同步点。

**供料保护**（删除后靠什么保证顺序）：
1. A 的元素与地址逐项相等（§1，2,162,688 次枚举 0 错）⇒ 读数等价；
2. A 与 B 的指令顺序、`acc0/acc1` 两条链、K 序、收窄点、末次 store 全部逐字未动
   （`PROOF.json:order_invariance`：`k_sequence` 32 项逐值相同，`a_load_sites=1`、`b_load_sites=2`、`dpas_sites=2`）；
3. 单个 lane 之内不存在"读到别人还没写完的数据"：候选没有任何对 A 源的写，A 源在整个 kernel 内只读。

**边界（不夸大）**：若 pool 把 `Ffwd`(binding 3) 与 `Residual`(binding 4) 映射到同一底层内存，
则"本 PASS 写 `gy` / 别的 WG 读 `gf`"的别名危险在**父里就存在**（父的 barrier 也只是 WG 级），
本卡既不新增也不消除它。plan 里它们是两条独立 BUFFER 行（`SELFCHECK` 未改 buffer 行），
cpu-check 的 `502 buffers` 与父逐字相同。

## 5. 是否真落到 native（预测 + 判据，不写"已证明"）

详见 `NATIVE-PREDICTION.md`（含父 ISA 实测计数与候选期望值/不变量）。三条最关键的：

1. **判据 1（落地铁证）**：`sx` 相关 SLM 消息必须归零 —— 父静态 `store.slm 4`（4 宽体）、
   `load.slm 256`（8/k-step × 32）、`fence.slm 1`、`signal barrier 1`、`sync.bar 1`；
   候选期望 `0 / 0 / 0 / 0 / 0`。任何非零残留 ⇒ **A 类未落地**。
2. **判据 2（A 供料确实换源）**：K 环内 8 次/k-step 的 A 读从 `send.slm(0x0210C500,
   load.slm.d32x8t.a32)` 变为 `send.ugm(load.ugm.*)`。**次数可能变**（这是最可能偏差的一项），
   但**通路必须变**；通路不变而 barrier 也没了 ⇒ 说明 A 被常量/垃圾替代（会先在数值门炸掉）。
3. **判据 3（数学不动的硬不变量）**：`dpas.8x8 = 64`（32×2）不变，权重 `load.ugm.d32x8` 仍 64 条
   （2/k-step），末次 `store.ugm.d32x64t` 仍 2 条，seed 块 13 条 d16u32 读不变。
   → 若 dpas ≠ 64 或权重读 ≠ 64，先按 E 类（数值/结构）处理，而不是当性能结论。

**scratch**：父 0（无 spill，无 `send.gtwy` 承载 scratch；2 条 gtwy 分别是 named-barrier 信号与 end-of-thread）。
候选期望仍 0；若出现 gtwy 承载 scratch 或 spill/fill，判 B 类。

## 6. 整体是否更快（本卡要测什么、怎么归因；本卡测不了）

**测什么**（已写入 `GPU-REQUEST.json`，主代理串行执行）：

| 臂 | 用途 | 命令形态（来自合同 §8.1 与 COMMON） | 判据 |
|---|---|---|---|
| gates `fixed` | 正确性 | `--pool --warm 0 --reps 1` | 末帧 `1755e9c2…29d6` |
| gates `fb2` | 正确性 | `--pool --warm 0 --reps 2 --feedback --save-frames` | 末帧 `9c3e511e…fd36` |
| native `base` / `cand` | 落地判据 | gtpin + nativemap `--dump_isa` | §5 三条判据 |
| resources | GpuTime | zprof `--metrics GpuTime` | 只作旁证 |
| ordinary | 整体量 | `two-arm-6-alternating, reps 30, warm 1, feedback` | 末帧 `2b63d4ba…658d`，成对差 + CI95 |

**如何归因**（顺序按合同 §8.5：先 native 落地 → 再数值/资源 → 最后整体计时）：

1. 若 native 三条判据都成立：本卡只对**这 16 个 PASS 的差**负责；整体 ordinary 的差可以归因到
   "16 PASS 的 staging+barrier 删除"，但**不能**外推到其他族。
2. 若 native 判 A：写"IGC/驱动仍保留 SLM 往返"，方法未证伪；不许用整体毫秒倒推机制。
3. 若 native 落地但 ordinary 不显著：先算天花板——本卡可触范围是 16/232 PASS（6.9%）内的
   一次 16 KiB 往返 + 1 barrier；父每 WG 访存 98304 B 里只有 32768 B 被删。
   分母（整帧）不可知，故只能给"≤ 父 F09 份额"的上界，不能给绝对值。
4. **禁止**：把本卡收益与 F10 的 0.422 ms 相加或相减；跨批次比毫秒。

**本卡没有 GPU，因此本节只登记"要测什么/如何归因"，不含任何时间数字。**

## 7. 本轮发现的三处口径问题（如实登记，均不改变结论）

1. **CARD.txt 写"直接以 stride-512 读 gt"，实际是读 `gf`**：KIND0 的 staging 源是
   `gf`（binding 3, `Ffwd`），`gt`（binding 5, `Context`）是 `KIND==2/4/3` 分支用的。
   被删掉的是 `gf` 的那次往返；源码未改错，是 CARD 措辞与实现不一致。
2. **plan 的 `PASS` 值 ≠ ordinal**：16 行被替换的 PASS 值是
   `{24,28,32,36,40,44,48,52,98,102,106,110,114,118,122,126}`，对应 ordinal
   `{61,65,…,89,135,…,163}`（`pass_label` 字段）。合同 §8.2 已要求用 ordinal+name+SPV sha+行号定位，
   本卡自检同时核对了两套编号与 16 个 name。
3. **plan 里 `shared=16384` 是簿记字段，不分配 SLM**：`clock_runner.cpp` 只做
   `parse / shared>49152 断言`（3 处命中，无其它使用），SLM 大小由 SPV 模块决定
   （候选 Workgroup 0 B）。因此候选**不会**因 plan 仍写 16384 而被保留 16 KiB SLM，
   也**不需要**为此改 plan（改它属于第二变量）。若 native 报表按 plan 回填 `shared_bytes=16384`，
   那是标签值，不是驱动事实。
