# AMD FP8 reference: transferable methods and limits

Reference scope: local project AMD reference, not a claim about all AMD FP8 software. Read implementation and pipeline defines separately; optional branches and historical timing comments are not active-pipeline performance evidence.

## Transferable methods
- Consumer-shaped fragments: choose score/P/V orientation and owner together; retain the existing FP16 reduction order and narrowing points. A globally uniform matrix direction is not required.
- Streaming expand -> activation -> contract: retain output accumulators and consume one hidden tile at a time. The optional NR_STREAM_C32 implementation demonstrates this organization; it is not enabled by the inspected pipelines.json definitions.
- Weight reuse versus live range: more M tiles reuse weights but keep more accumulators live. Optimize the total cost, not just SLM bytes.
- Conversion packing: quad_quant_glsl.py groups AMD FP8 conversion and packing operations. This is target-specific native lowering, not an Intel FP16 instruction recipe.
- Prefetch distance: the optional NR_WPF implementation preserves MMA order while moving independent loads; native changes require end-to-end verification.

## Verified limits
- Inspected fswinimagepost32/fswinimagepreds32 pipelines use NR_FWAVES=2 and NR_K_REGS=0. Do not generalize this to every C32 pipeline: fswinfusedup32 uses NR_FWAVES=1.
- ACT_F32, NORM_F32 and RESIDUAL_F32 are enabled in those reference configurations. Their numerical path cannot be copied under our bit-exact FP16 contract.
- For 64x32 K and V, logical payload is 8192 B in FP16 versus 4096 B in FP8. At 32 lanes that is 256 versus 128 B/lane before Q/P/accumulators; these are payload counts, not measured GRF allocation.

## F20 stream1m verification
- Parent: P03. No baseline update.
- Fixed/fb2 gates pass; six ordinary final frames all match expected gold.
- Native static counts (including debug): instructions 4531 -> 4008, SLM 622 -> 429, mov 1402 -> 1312, UGM 237 -> 245, DPAS 64 -> 64, scratch 0.
- Source cost: hidden activation SLM write/read removed; expansion weight reads increase 32 KiB/WG. This tradeoff is real; its causal timing contribution is unmeasured.
- Three process-pair savings: +0.380564, -0.308830, -0.089122 ms. Mean -0.005796 ms, CI95 [-0.880634,+0.869042]. INDISTINCT; all 180 samples retained. Do not claim zero benefit or that extra weight reads caused the result.
- Candidate retained, not adopted. No extra GPU repetitions authorized by this finding alone.

Next evidence-based analysis: count M-tile weight reuse and peak overlapping live fragments together, then identify whether a balanced owner schedule can remove publication without doubling expansion weight traffic. No claim of an implemented solution yet.
