## 3. What was implemented (closure rule 3, rule 2): R21 output segment

**Choice and why.** The R21 output projection is the smallest self-contained segment in the
two cards (2 of 14 sites, K = 32 exactly one K32 step, one operand is a static 32×32 weight
matrix, the other is an in-kernel activation tile that is already subgroup-local, and the
epilogue is the untouched residual seed). It exercises the whole INT8 chain (pack → activation
quantisation → integer MMA → folded dequant → single narrow) with the least new risk, and it
delivers a *measured* segment reference instead of another contract. The R20 projection was the
alternative, and it is deliberately **not** done here: its input `x65` is a cross-tile gather
and its output feeds a genuinely cross-subgroup blend (section 4), so it needs a new pack *and*
a new activation-scale contract *and* a decision about the blend-input identity before any code
is worth writing.

## 4. The R20 cross-subgroup boundary, from the SPIR-V (deliverable 4)

`evidence/CROSS-SG-SETS.json` + `evidence/CROSS-SG-nrf2_proj.json`.

**Who writes.** The projection is one `coopMatStore` at parent word **11987** with index
`nrf2_proj[((rh*8)*32)+(cg*16)]`, stride 32, RowMajor, where `rh = sg2>>1`, `cg = sg2&1` and
`sg2 = gl_LocalInvocationID.x/32` (local size 128 → exactly four subgroups). SG `(rh,cg)`
therefore writes the half set
`S(rh,cg) = { rh·256 + cg·16 + 32r + c : r<8, c<16 }` (128 halves). The four sets are disjoint
and their union is exactly `[0,512)` — **proved by construction here, `partition = true`**.

**Who reads.** The blend loop reads `nrf2_proj[(ct*32)+ch]` at words **12285/12319**, with
`ct = (2rh + sy>>1)·4 + (2cg + sx>>1)` and `ch ∈ [0,32)`. So SG `(rh,cg)` reads the four coarse
tokens `{8rh+2cg, +1, +4, +5}` — *all 32 channels*, i.e. 128 halves of which **64 are produced
by the sibling subgroup `(rh, 1−cg)`** (its 16-column block). Cross-subgroup fraction of the
blend reads: **50 %** for every subgroup.

**Which barrier publishes it.** Word **11994**, `OpControlBarrier(Workgroup, Workgroup, 264)`
(= `Workgroup` execution scope, `Workgroup` memory scope, `AcquireRelease|WorkgroupMemory`),
i.e. the source's plain `barrier()` at `c32_f2_i8.comp:220` between the projection store and
the first blend read. It is a *workgroup* barrier, which is what a cross-subgroup handoff
requires and what the code already had.

**The second handoff is not cross-subgroup.** The blend writes `nrf2_blend[((sg2*512)+(slot*32))+ch]`
(words 12725/12781) and `nr_body_stage` reads `nrf2_blend[(sg*512)+{0,8,16,24}]` (words
16188/16386/16584/16782) — the same `gl_LocalInvocationID.x/32` value on both sides, so each
subgroup consumes only its own 512-half slab (`cross_subgroup = false` for all four). The
`memoryBarrierShared(); barrier();` pair at words 12806/12809 is therefore stricter than needed,
not a cross-subgroup publication.

**Did this card's change fake any of that with a shuffle?** No. Both modules contain **zero**
`OpGroupNonUniform*` instructions (`diff21.py` → `subgroup_ops: {}` for parent and candidate;
the parent has no shuffle at all, and the candidate adds none). The R21 change communicates only
inside a subgroup and only through shared memory, and its three new barriers are
`Subgroup`-scope `OpMemoryBarrier` + `OpControlBarrier` at candidate words
10661/10664, 10845/10848, 11091/11094 (`evidence/R21-SG-LOCALITY.json`):

* activation codes: store `shC8[((sg*1024)+(lane*32))+i8]` (word 11066), load
  `shC8[(sg*1024)]` (word 11371) — **the same `sg` expression on the writing and the reading
  side**, and 8 × 1024 B fills the declared 8192 B exactly, so no subgroup can reach another's
  tile;
* the reduction: `shLmax[t_local]` (10656) / `shLmax[((sg*32)+l8)]` (10746) and
  `shSgScale[sg]` (10836/10861) — partitioned by `sg` on both sides;
* the weight tiles (`w8`) are read-only static data; the scales (`wsc`) are read-only.

So the R20 projection/blend remains a genuine workgroup-barrier handoff (which this card
documents but does not modify), and the R21 output segment introduced no cross-subgroup
communication at all.

## 8. Named blockers and next steps (closure rule 6)

1. **R20 projection (1 site)** — not attempted. It needs (a) a static INT8 pack of the
   `PROJECT_PAIR` variant weights (`pw`, K = 64 in 16-wide steps, N = 32) with a per-channel
   scale, (b) an activation scale for `x65`, whose tile is a **cross-tile gather**
   (`abase = p4.x + tile65·(p5.x/16)·256 + rh·128`), so the 8-token ownership cube used here
   does not apply unchanged, and (c) a decision on the post-blend `qX` identity: the blend adds
   `skip_in·skip_gain` **after** the projection, so the projection output cannot be quantised in
   place of the blend output (GUIDE R20 blocker). The consumer side (`nr_body_stage`) already
   quantises its own X copy with `nr_i8_put_x(final, fsc[1])`, so the blend output is the only
   place an INT8 identity may be created — and that is exactly the value that the F2 half path
   still needs for the `skip4` half-ish readers. Next concrete step: capture one `nrf2_blend`
   tile with a diag plan, then define `sQx` and an INT8 `x65` gather.
2. **R20 QKV/QK/PV/output (64 sites)** — the R02 contracts (`candidates/r02-c32-body/contracts/`)
   apply verbatim in shape, but R02's QKV switch is gated on the `invY` calibration for six
   blocks; block66 is not one of R02's passes, so it needs its own `invY` (a captured `Y` tile,
   same diag mechanism) plus the 12 extra tile packs. Named blocker: `invY` uncalibrated for
   block66; no code written.
3. **R21 expand (4) / contract (2) / QKV (2) / QK (2) / PV (2)** — `candidates/r20-r21-tail/contracts/GAPS.md`
   lists each one with its concrete missing piece. In short: expand/contract are the same
   M8N16K32 shape as this segment and need the `nr_act_h` fusion to stay half (the parent's
   activation is a half function between the two GEMMs), QKV needs a 96-channel pack and the
   post-contract `Y` quantisation, and QK/PV have **both** operands dynamic, so the dequant is a
   rank-1 outer product (`sK[key]·sQ[query]`) that needs per-token amax — a cross-lane reduction
   the parent does not have.
4. **Pipeline feature risk (native, unverifiable here).** The candidate needs `shaderInt8` and
   `StorageBuffer8BitAccess`. Seven deployed passes already use both, so the runner plainly
   creates such pipelines, but whether it enables the features for *this* pass's pipeline is only
   observable at pipeline creation. If it does not, the pipeline fails and the plan falls back to
   nothing — that is a **hard, named** risk, not a numeric one.
5. **Layout confirmation (native).** The I8A/I8B byte layouts (`k·32+m`, `n·32+k`, stride 32,
   `LCOL`) are inherited from the deployed C32-I8 modules and validated on the host by the pack
   round trip, but the device-side mapping is only proven by a gate. The 4× shared waste of the
   I8A tile (1024 B for 256 codes) is a direct consequence of that inherited stride; a stride-8
   variant is a stage-2 candidate that needs its own native proof.
6. **No GPU.** Gate/ordinary/quality un-run. `run/r20-r21-tail/jobs.json` lists 5 gate arms
   (parent fixed/fb2, candidate fixed/fb2, candidate diag) and 6 ordinary arms
   (3 process pairs × 30 samples). Following R02's rule, the jobs assert **no numeric tolerance**
   between candidate and parent frames: the candidate replaces 2 FP16 K32-equivalent steps with
   INT8, so byte equality is asserted only between two runs of the *same* candidate plan
   (self-determinism), and the frame delta is recorded for the coordinating entry to judge
   against the segment reference in section 5.
