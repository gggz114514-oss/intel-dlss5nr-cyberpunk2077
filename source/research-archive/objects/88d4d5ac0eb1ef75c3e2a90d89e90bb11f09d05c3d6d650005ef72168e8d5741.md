## 三、P1：C256误用了baseline的权重格式

候选：ROOT/candidates/amd-layout-fusion-resume-fix-20261016/f3-c256-fused-half-patch-v1/。

错误在 source/fused_c256_body_ds.comp:222-232。四片B fragment均按下式读取：

```text
offset = whalf + (nb0+r)*16*K + k
stride = K                     // K=256，ColumnMajor
```

build_f3_c256.py明确使用f19-paired/baseline/source/ioport_t03_ds_pair_fp16.comp作DS来源。它不是当前父实际执行的权重合同。当前父pass83绑定的是：

```text
ROOT/candidates/amd-map-20261015/round4-integrated/candidate/spv/ds-f19-paired.spv
SHA256 2f4cc7a621086fe62254db6218d2fd935eae0ade94626e7908099f17e3968c7f
```

解析该已绑定SPIR-V可直接确认，两片权重coopMatLoad均为16×16分块格式、stride=16。当前对应源码是f19-paired/source/ds_complete_fp16.comp。其片起址为：

```text
offset = whalf + ((n0/16)*(K/16)+k/16)*256
stride = 16                    // ColumnMajor
```

保存的父SPIR-V权重load位于word offset 2217/2390，stride常量16；融合SPIR-V的四个权重load位于2805/2928/3051/3174，stride为load K。差异不只是旧注释或证明文字。

### 同一个真实pack的反例

两者都绑定resource465（ioport_22_ioport_pack），weight_half=656128，没有做权重重排。按同一逻辑W[n,k]展开地址：

```text
父：whalf + ((n/16)*(K/16)+k/16)*256 + (n%16)*16 + k%16
新：whalf + n*K + k
```

例如n=0、k=16：

| | half地址 | 保存的FP16值 |
|---|---:|---:|
| 当前父 | 656384 | -0.005859375（bits 0x9e00） |
| C256候选 | 656144 | 0.0234375（bits 0x2600） |

独立对全部131072个逻辑权重坐标核对：122880个地址不同，实际pack中120998个FP16位值不同。这是已保存文件的读取结果，不是GPU数值测试或最终输出差异计数。它足以否决当前投影的权重合同。

旧静态证明C2只核候选是否符合baseline公式，未核baseline是否与父绑定SPV一致，因此“C2权重等价PASS”必须撤回。body源码/raw SPV身份一致不能推出另外一个DS模块的来源也正确。

### 最小整改

保留已经证明的body、mean、重分块、输出store、skip22和padding；在新C256 v2中把四个B load改为父实际的分块地址：

```glsl
// r分别为0、1、2、3；nb0已经是16通道组号。
uint woff = whalf + ((nb0+r)*(K/16u) + k/16u)*256u;
coopMatLoad(bb, nrf_w, woff, 16u,
            gl_CooperativeMatrixLayoutColumnMajor);
```

K仍按16递增，四个accumulator的运算顺序不变。无需为此增加repack派发或改父pack。修真实源码和生成器，保存新SPV/运行表/argv，补“实际父SPV→逻辑n/k→物理地址→实际pack值”的检查。至少包括n/k跨16边界的已复现反例；可用全部131072项整数地址等价检查，成本很小。不要覆盖本次v1封存后复用原标签。

## 四、C256重分块可以保留，成本口径需纠正

本次确实回答了报告18的owner问题：父DS采用8个连续raster token；保持原body WG范围时，这些token可能来自不同body WG。融合核转为自己4×4池化patch内的4列×2行M8，再经标准coopMatStore到subgroup专用暂存、按真实layout1地址逐元素写出。此适配不要求跨WG通信。

均值用真实physical_py，暂存用ly；每个j的32通道由本subgroup暂存求均值，subgroupBarrier保护复用。body完成后WG barrier才允许projection读取其他subgroup产生的K通道；输出暂存按sg分区，继续使用subgroup屏障。没有在原body j循环内新增WG barrier。这些组织证据可采信。

独立检查输出覆盖1056×512=540672 half，各写一次；有效1008 token、视图padding48 token、分配尾部96 token的合同保留。尾部49152 half不由融合视图写入，仍依赖既有clear。由于权重合同失败，当前不能将这些几何结论扩写成投影值正确；修后仍需GPU数值门。

需修正的静态成本记账如下，避免后续误解XMX和停摆：

| 项目 | 正确口径 |
|---|---|
| C32 DS每subgroup MMA | K32/16×2片=4次，回执“2×16”不适用于本核。 |
| C32 DS整段MMA | 父64512，新65856；新保留边界WG，包含被抑制store的计算，增加约2.08%。 |
| C256 DS整段MMA | 父67584，新78848，增加约16.67%；不能把新增边界计算当利用率改善。 |
| C256 projection暂存屏障 | 4片×每片前后2次×2轮=16次subgroupBarrier，不是8次；body均值暂存另有2×8=16次。 |
| C256标量输出store | 全段540672；首尾边界patch各4096，内部patch8192。7021是截断平均值，不能称每patch固定store数。 |

上述MMA是SPIR-V cooperative运算的循环工作量，不是实测ISA指令数、硬件槽数或耗时。原生计数器须在数值通过后采集，按真正有用工作与实际工作共同解释。父DS没有baseline里的输出暂存屏障，其实测停摆不能由baseline源码的barrier个数代替。

还有一处文案残留：C256构建脚本开头仍写skip22被192/270读取；当前父真正读者是83和192，270读的是skip4。输出写回本身已经正确保留，文案须与修正版访问表同步。

## 五、真实访问修正有效，完整施工还剩六项

L1/L2/F1/F2/C64/C128仍没有新实现候选，不能以来源定位或访问表交付代替完整AMD方法尝试。保持报告15/17的范围，并纠正回执中的缩项口径：

- F1目标是0 features→1 lift→2 body→3 pool。features/lift的中间物化是完整融合的消除对象；skip0及供pass4使用的block0_out保留。回执“only block0_out could be elided”不符合本票范围，不据此改图。
- F2目标是269 projection→270 blend→271 body，完整融合可消除内部projection与blend，仍保留skip4和block66_out。只做270+271是分段候选，不能记作完整F2。
- L1要尝试block30→ViT→block39全条公共外部激活接口及全部真实消费者。仅保持现有canonical不改，不是新的布局统一实现。
- L2的b47 KIND4→KIND1、pass191 src_layout3→1可作为具名局部候选：该swap源的算术主体相同、分支差异在输出store，但仍须验证逻辑字节置换、padding/clear与同批收益。它只消除一个planar接口，不能记作整条L2或layout0公共接口完成。

新确认的C64/C128来源可以复用，但未建核仍写未实施。无GPU时段继续限制GPU验收，CPU施工按原授权继续。
