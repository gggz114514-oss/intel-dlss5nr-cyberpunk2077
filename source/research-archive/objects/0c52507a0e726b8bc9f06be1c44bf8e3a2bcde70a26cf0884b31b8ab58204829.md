## 1. 映射：生产者每个 (lane,component) 代表哪个 (token, channel)？消费者要什么？

### 1.1 生产者（F20 ord 230，`main()` 尾核）

```glsl
if(sg<2u) {                                    // 8 SG 里只 2 个 SG 执行尾核
    uint t=sg*32u+lane, q=t/16u, r=t%16u;
    int px=(2*int(wx)+shift+int(q&1u))*4+int(r%4u);
    int py=(2*int(wy)+pc.p3.w+int(q>>1u))*4+int(r/4u);
    if(px>=0 && px<1280 && py>=0 && py<720) {  // 窗口钳制：只写 1280x720 内
        vec4 value=boundary_project(t);        // 4 个 FP32 累加器
        …写回…
    }
}
```

| 维度 | 取值 |
|---|---|
| 每条 lane 产出的单位 | **一个像素的整条 4 通道记录**（不是单通道） |
| token | `t = sg*32 + lane`，`t ∈ [0,64)`（sg∈{0,1}） |
| 像素 | `q = t/16`（0..3，选 8x8 块内的 2x2 个 4x4 象限之一），`r = t%16`（4x4 内位置） |
| x | `px = (2*wx + shift + (q&1))*4 + r%4` |
| y | `py = (2*wy + p3.w + (q>>1))*4 + r/4` |
| 通道 | `component 0..3 → residual_out[(py*1280+px)*4 + 0..3]`，即 `value.x/.y/.z/.w` |
| 通道语义 | x/y/z = 投影残差 rgb；w = blend logit（F21 用 `residual.w` 过 sigmoid 得 blend，见 §1.3） |
| 每个 WG 覆盖 | 一个 8x8 像素块：`x ∈ [8wx-4, 8wx+3]`，`y ∈ [8wy-4, 8wy+3]`（shift=shift_y=-1，来自 plan push） |

### 1.2 可枚举覆盖（`build/addr-proof.json`，CPU 全枚举，不是抽样）

用 plan 里真实的 push（`tiles_x=336, shift=-1, shift_y=-1, single_flag=0`）和真实 grid（169,97,1）复算每一条线程：

| 项 | 值 |
|---|---|
| 总线程（2 SG × 32 lane × 16393 WG） | 1,049,152 |
| 通过窗口 guard、真的发 store 的 | **921,600** = 1280×720 |
| 被 guard 挡掉（窗口外） | 127,552 |
| 不同像素数 | 921,600（**无重复**） |
| 重复写 | 0 |
| 每 WG 内 lane 映射是否单射 | 是（64 个 (q,r) → 64 个不同 (px_off,py_off)） |
| 尾块 | 无：921,600 就是整窗，且块间步长 8、块内 8x8，块之间的并集覆盖 `[-4,1348)×[-4,772) ⊇ 窗口` |
| warp 活跃度 | 32,786 条 warp 到达该站点；3,806 条 32 lane 全被挡（mask=0）；360 条 16 lane；28,620 条满 32 lane；均值 28.11 lane |

> 一一覆盖的论证不依赖"父做过所以对"：上面 921,600 个不同像素 + 0 重复 + 块结构互不相交，是把
> `(wg, sg, lane) → (px,py)` 逐点枚举出来的结果（`_addr_proof.py`）。

### 1.3 消费者（F21 ord 231 = n02 卡的候选，同一条交接的另一端）

```glsl
uint i=gl_GlobalInvocationID.x, W=pc.p0.z;     // W=1280
vec4 residual=vec4(residual_in[i*4u],residual_in[i*4u+1u],residual_in[i*4u+2u],residual_in[i*4u+3u]);
```

- 消费者要求：**每像素 4 个连续 float32，基址 `i*4`（i = py*1280+px）**，一次 16 B 读（native 已是 `load.ugm.d32x4`）。
- 本卡写出的正是 `(py*1280+px)*16` 起的 16 B，通道序 0..3 不变 ⇒ 消费者读到的每一个字节与父完全相同。
- 两端对称：生产端 4×4 B message → 1×16 B message；消费端本来就 1×16 B load。

### 1.4 本卡改了什么、没改什么

| | 父 | 候选 |
|---|---|---|
| 每条 lane 写多少字节 | 16 B（4 条 4 B store） | 16 B（1 条记录 store） |
| 写哪些字节 | `(py*1280+px)*16 + {0,4,8,12}` | 同左（枚举逐字节比对 3,686,400 对，0 不符） |
| 通道序 | x,y,z,w | x,y,z,w（SPIR-V 里 4 个分量字面量 0,1,2,3，候选是同一个向量局部变量的整读） |
| 覆盖 / 尾块 / 有效 lane | 见表 1.2 | **完全相同**（本卡不动 px/py/guard/sg 条件） |

## 3. 重叠：原来哪些独立工作重叠？本卡是否把它们串起来？

### 3.1 相关资源与责任者

| 资源 | 生产者 | 最后消费者 | 覆盖者 | 冲突 |
|---|---|---|---|---|
| `shX[t*32+c]`（SLM，24576 B 中的 2048 half = 4096 B） | stage 9 投影尾声（8 个 SG 全部写：`coopMatStore(half0, shX, m0*32, …)` / `half1` 到 `m0*32+16`，m0=sg*8 ⇒ 行 8sg..8sg+7，列 0..31） | `boundary_project`（尾核 warp 0/1 的 64 lane 读全部 64 行） | 下一次派发 stage 9 重写 | RAW（stage9→尾核）；**跨 SG**，由 line 586 的 `barrier()` 保护；WAR/WAW 同一个 barrier 保护 |
| `value` = 4 个 FP32 累加器（寄存器） | `boundary_project` 的 32 步循环（c=0,2,…,30，每步先 c 后 c+1） | **本卡的 store**（每条 lane 一次） | 无（lane 私有） | RAW（累加→store）；**本卡不改变这条依赖**，只改变"4 条 store 消费同一个向量" |
| `residual_out`（binding 3） | **只有本卡这一处**（父：4 条标量 store；候选：1 条记录 store） | F21 ord 231（同派发下一次 dispatch 读 `residual_in[i*4+k]`） | 下一次派发整体重写 | 4 条标量 store 之间是**同一 buffer 的 WAW，但字节不相交**（0/4/8/0xC），本来就没有序要求 |
| `dbg`（binding 4） | debug 块 | 无人 | — | debug=0，不执行 |
| 权重 `wb[17024..17121..]`（binding 0 的常量 pack） | host（常量 buffer，plan 外） | `boundary_project` 的 4 通道乘加 | — | 只读；本卡不动读侧 |

### 3.2 本卡的时序影响（这是唯一的"新串行风险"，必须写清）

父 ISA 尾部（实测）：

```
0x100C8  shl  r12.0 :d  r6.0 :d  4:w              // r12 = 像素记录基址 = r6*16（IGC 本来就按 16 B 步长算）
0x100E8  add  r20.0 :f  r24.0  r30.0              // z 的最后一次加
0x100F0  send.ugm ... store.ugm.d32 ... r10:2     // 先发 x 的 store
0x10100  add  r4.0 :f  r28.0  r32.0               // w 的最后一次加（在第一条 store 之后！）
0x10110  send.ugm ... store.ugm.d32 [A+0x4]  r18:2
0x10120  send.ugm ... store.ugm.d32 [A+0x8]  r20:2
0x10130  send.ugm ... store.ugm.d32 [A+0xC]  r4:2
0x10140  join
```

- 父：x 的 store 在 w 的最后一个 `add`（0x10100）之前发出，编译器已经把第 4 通道的收尾与第 1 条 store 重叠了。
- 候选：一条 16 B store 必须等 4 个分量都在 payload 里就绪 ⇒ **第 4 分量（w）的最后一个 add 变成这条 store 的硬前置**。
  代价是"一条消息晚发 ~1 个 add 的延迟"，收益是"4 条消息变 1 条"；不能离线量化，但在 1 PASS 作用域里是噪声级（见 §6）。
  这条用 `NATIVE-PREDICTION.md` 的观察点 7（store 相对最后一个 `add`/`dpas` 的位置）去证实/证伪。
- 不改变的：barrier 位置、SLM 往返、WG 数、有效 lane（同一 mask）、4 个累加器的活跃区间（父也是同时活到 store）。

## 5. 是否真落到 native（预测 + 判据，不声称已实现）

基线身份（已读，只作对照）：pipe 38、kernel `76902ef344609c8a`、ISA sha `121a38aa…`、4754 指令、
`send.ugm` 237、`dpas.8x8` 64、`sync.bar` 12、`scratch` 0、workgroup 24576 B。
**为什么这不是"期待编译器做没做过的事"**：同一条交接的消费端（F21，ord 231）源码写了 4 条标量
`residual_in[i*4u+k]`，native 是**一条 16 B `load.ugm.d32x4`**；F21 卡的写侧同型改动（4 条标量 store → 1 条记录 store）
已经在 native 落地（`store.ugm.d32` 8→0、`store.ugm.d32x4` 0→2、`send` 35→29，见 `n02-f20-f21-tail/RESULTS.json`）。
本卡的站点形状与之一致（同一基址 + 立即数 0/4/8/0xC 的 4 个 dword），且基址寄存器在基线里已经是
`shl r12, r6, 4`（×16）——16 B 步长本来就算好了。若这样仍得到 4 条 4 B store，那是一个**明确的可观察事实**（A 类），
不是预测错了。

必须看到（任一不成立即按 A 类记，详见 `NATIVE-PREDICTION.md` §2）：

| # | 观察点 | 父 | 候选预测 | 判据 |
|---|---|---|---|---|
| 1 | `store.ugm.d32.a32.bss`（4 B/lane） | 4（0/4/8/0xC） | **0** | 仍 4 ⇒ A 类 |
| 2 | 16 B 记录 store | 0 | **1**（16 lane 拆分则 2） | 0 ⇒ A 类；2 也可接受但收益打折 |
| 3 | `send.ugm` 总数 | 237 | **234**（拆分则 235..236） | 237 ⇒ A 类 |
| 4 | `dpas` / `send.slm` / `sync.bar` | 64 / 497 / 12 | **不变** | 任一变化 ⇒ 调度副作用 |
| 5 | `mov` | 1687 | **1687..1695** | >1695 ⇒ B 类（拼装过多） |
| 6 | `scratch` / workgroup | 0 / 24576 | **0 / 24576** | 非 0 ⇒ B 类，停 |
| 7 | store 相对最后一个 `add`/`dpas` 的位置 | 见 §3.2 | 移到 4 个分量都就绪之后（仍在 kernel 尾、`join` 之前） | 位置乱序 ⇒ 记调度副作用 |
| 8 | kernel hash | `76902ef344609c8a` | 必须变化 | 不变 ⇒ 模块没换（A 类） |

看不到 1/2/3/8 ⇒ **A 类：实现未落地**；不允许用整体毫秒倒推"机制有效"（合同 §8.5）。

## 6. 整体是否更快（测什么、怎么测、怎么归因）

- **必须测的整体量**：整车 `ordinary`（`--pool --warm 1 --reps 30 --feedback`，gold `2b63d4ba…`），
  6 组交替 base/cand；以及 `fixed`（`1755e9c2…`）与 `fb2`（`9c3e511e…`）两个门；`resources` 臂给单 PASS 的 `GpuTime`。
- **归因边界**：候选与父的差异只有 ord 230 这一行的 SPIR-V；native 臂必须落在 **pipe 38**（不要去读 pipe 39 = F21）。
- **预期**：本卡只把 1 个 PASS 尾部的 4 条消息合成 1 条（每派发 −98,358 条消息，字节不变，指令 −3..+5）。
  参照同型改动（F21，2 组记录、每像素消息 10→4）实测 **+0.004986 ms，CI[−0.0104,+0.0203] INDISTINCT**，
  本卡的作用域只有 1 组记录（F21 的一半），**单点几乎不可能出显著性**。
  因此本卡的点估计只作方向参考，**判决交给 §7 的 2 PASS 包**（合同 §6 D 类 + L8：包的结果不能由成员递推，必须实测一次）。
- **不能声称的**：不能说"消息减少 4:1 所以一定更快"；逻辑字节不变，收益只可能来自消息发射/占用，而非 DRAM 流量。

## 7. 成包依据（F20 + F21 = 2 PASS）

- 该形状（一条四通道 FP32 记录被拆成 4 条 4 B 标量 store）在基线 40 条 pipeline 里**只出现两次**：
  F20 ord 230（1 组 4 条，pipe 38）与 F21 ord 231（2 组 8 条，pipe 39）——正是同一条 `residual_out` 交接的两端
  （`n02-f20-f21-tail/PROOF.json` 的 `same_site` 扫描 + 本卡 `build/native-base.json` 复核）。
- 其他族的标量 store 形状不同（散写或 0/0x20 交错），**不并入**本包。
- 成包做法（主代理执行）：在链头 plan 上同时替换 **第 2987 行（ord 230 → 本卡 candidate.spv）** 与
  **第 2995 行（ord 231 → `cards/n02-f20-f21-tail/candidate.spv` 5b14b9a3…）**，其余行不动。
- 本卡 `GPU-REQUEST.json` 只声明 **1 个 PASS**（ord 230），包由主代理合并。
