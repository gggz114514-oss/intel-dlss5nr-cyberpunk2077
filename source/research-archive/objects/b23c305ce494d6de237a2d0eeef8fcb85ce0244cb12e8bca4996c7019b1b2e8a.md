## 0. 先说方向：为什么本轮不做 M/N tile 重排，也不做 WG 顺序重排

施工卡建议的首个候选是 shape-specific M/N tile 或 WG 顺序重排。本卡**先用合同允许的自由度把它算到底**，
再落到 native 已经量出来的真实供料冲突上。两个静态结论（都可复核）：

**(a) 4 累加器下，当前 tile 已经在最优等值线上。** 逻辑读取量（half 元素 / 派发）：

    A = M·K·(N/N_sg)        B = N·K·(M/M_sg)
    A+B = M·K·N·(M_sg+N_sg)/(M_sg·N_sg)

每个 SG 的累加器数 = (M_sg/8)·(N_sg/16)，4 个累加器 ⇒ M_sg·N_sg = 512。于是 A+B 只由
(M_sg+N_sg) 决定：当前 (16,32) 与对称的 (32,16) 都是 48，**并列最优**；
(8,64)/(64,8) 是 72，更差。M=288、K=1024、N=4096 时：A=37.7M、B=75.5M、合计 113.2M half。
所以“换 tile 形状”在 4 累加器预算内**不可能减少任何读取量**，只能改变 A/B 的比例。

**(b) 唯一能减读取量的办法是把面积翻倍（8 累加器），而这已经被测过。**
`work/dsh-fp16-same-family-20261023/RESULTS.md` §41/§42/§45 的六次实测：
S32/K11 expand **+0.2109 ms（唯一正向，已进现役）**、S64/K11 expand +0.1375（一对为负，“噪声”）、
S32/K09 −0.0435、S32/K14 −0.0832、S32/K23 −0.0294、S64/K09 −0.4103。
8 累加器（S64 = M64×N128，每 SG 4 个 M8）把权重读取量砍半，但每 SG 活值从 4 块涨到 8 块，
实测吃掉了收益。**原样重做 S64 属于“已做过且已测”的候选，合同 §1 禁止。**

**(c) WG 顺序重排在这个 plan 上没有可换的东西。** grid=(9,32)，x 最快 → 同一 N 片的 9 个 M 块
在派发序上相邻，共享同一块 128 列权重 slab（128×1024×2 B = 256 KiB）；若把 N 放快，相邻 WG 会跨
32 个不同权重 slab（8.4 MiB 常驻）而只共享一块 32 行 A slab（64 KiB）。现有顺序已经是权重局部性
更好的一侧；再换就需要动 plan 的 grid 字段，而收益只是“可能更好”的猜测，不值得开候选。

**(d) 因此本卡改的是 native 里已经存在的真实工作：每个 k0 步的 24 条累加器搬运。**

## 1. 映射：每个 (lane,component) 代表哪个 (token, channel)

### 1.1 形状（从 plan 的 PUSH/BIND 反推，非猜测）

PASS 56…91 的 `PUSH`：`p0=(288,320,0,0)`、`p1=(0,4194304,8388608,11534336)`、
`p2=(12582912,12583936,0,31)`。⇒ live=288、stage=0、block=31；K=1024（`VIT_STAGE 0`）。
BIND：`x`=589824 B=294912 half=288×1024；`aHidden`=2359296 B=1179648 half=288×4096。
grid `9 32 1`、`local_size_x=256`（8 SG）。

每 WG：M 32 行 × N 128 列。每 SG：**16 行 × 32 列**（两个相邻 M8 × 两个相邻 N16），4 个累加器。

    sg = gl_SubgroupID (0..7)      sg_m = sg/4 (0..1)      sg_n = sg%4 (0..3)
    mA = wg.x*32 + 16*sg_m         mB = mA + 8              n0 = wg.y*128 + 32*sg_n

| 累加器 | token 行 | channel 列 |
|---|---|---|
| accA0 | mA..mA+7 | n0..n0+15 |
| accA1 | mA..mA+7 | n0+16..n0+31 |
| accB0 | mB..mB+7 | n0..n0+15 |
| accB1 | mB..mB+7 | n0+16..n0+31 |

### 1.2 生产者 / 消费者映射（driver 自己的 tuple 表背书）

`run/.../nat-k11-s32-native-000/compile/coopmat-properties.json`（本卡只读引用）报告设备支持
`M=8,N=16,K=16, A=0(row-major), B=1(column-major), C=1, Result=1`。因此一条
`dpas.8x8`（= 8×16×16）在本机上就是：

* **A 片段** `MA af`：8 行 × 16 个 K，row-major，`x[pc.p5.x + row*K + k0]`，行距 K=1024 half（2048 B）。
  一个 lane 拿 4 个 half。8 行共 256 half = 512 B，但**行不连续**，所以 native 是 8 条 32 B 单 lane 消息。
* **B 片段** `MB b0/b1`：16 个 channel 行 × 16 个 K，column-major 打包，行距 16 half（32 B）⇒
  **一个 16×16 tile 是 512 B 连续**。native 用 1 条 `(16|M0)` 宽消息（16 lane × 32 B）取完。
* **C/Result** `MC acc`：8×16 fp32，lane 内 4 个 float。

Epilogue（stage 0）：`MH`(half 累加器视图) → 可选 debug store → `vit_cubic` → `coopMatStore` 到
`aHidden[m*4096 + n0 + side*16]`，stride 4096，row-major。

### 1.3 一一覆盖证明（枚举，不是抽样）

`_tools/proof_map.py` 对 grid (9,32)、每 WG 8 个 SG、每 SG 两个 M8 做全枚举：

* (token, channel) 覆盖 **1,179,648 = 288×4096**，重复 0、漏 0（`PROOF.json.mapping`）。
* 行：wg.x∈0..8 → 基址 0,32,…,256；sg_m∈{0,1} → +0/+16；mA 与 mB=mA+8 各 8 行 ⇒ 每 WG 32 行，
  9 WG = 288 行，无重叠。
* 列：wg.y∈0..31 → 128·wg.y；sg_n∈0..3 → +32k；每 WG 128 列，32 WG = 4096 列，无重叠。

### 1.4 尾块与不同 M（单独验证，contract 要求）

`PROOF.json.store_domain` / `read_domain`：

| live | 写入行数 | 期望 | 越界写 (live 之后) | 运行 K 循环的 SG | 触发 clamp 的 SG | 越界读 |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0 | 0 | 0 | 0 | 0 | 0 |
| 7 | 8 | 8 | 1 | 128 | 128 | 0 |
| 8 | 8 | 8 | 0 | 128 | 128 | 0 |
| 16 | 16 | 16 | 0 | 128 | 0 | 0 |
| 255 | 256 | 256 | 1 | 2048 | 0 | 0 |
| 257 | 264 | 264 | 7 | 2176 | 128 | 0 |
| **288（本 plan）** | **288** | 288 | **0** | 2304 | **0** | **0** |
| 289 | 288 | 288 | 0 | 2304 | 0 | 0 |

两条必须说清的事实：

1. **本 plan 的 8 个派发都是 live=288 = 9×32**，没有任何尾部行，也没有任何 clamp 被触发。
   因此候选的**读集合与父逐字节相同**（`read_domain[288].sgs_with_clamped_row = 0`）。

   对 live=288 为 0）。

## 2. 删什么真实工作（正常执行路径，不计 debug 声明）

native 证据：`run/dsh-fp16-same-family-20261023/nat-k11-s32-native-000/gtpin/ISA/CS_asm48ac0230660a2c52_simd32_...asm`
（sha256 `f5f655b1…`，837450 B，`Instruction Count 7231 / Basic Block Count 272 / Loop Count 0 / Scratch 0 / SLM 0`）。
K 循环**完全展开**（0 回边，64 个相同的 106 指令步）。一个 k0 步（`0C90..120F`，并与下一周期核对一致）：

| 类 | 条数 | 占比 | 说明 |
|---|---:|---:|---|
| int/addr/br | 30 | 28.3% | 8 条 A 行地址 + 4 条 B lane 地址 + 指针推进 |
| **mov(32)** | **24** | **22.6%** | **8 存 accA 组 + 8 存 accB 组 + 8 取回** |
| sync.nop | 16 | 15.1% | 送/收记分板等待 |
| send.narrow1 | 16 | 15.1% | 2 个 A tile × 8 行，exec-1、32 B/条 |
| mov(8) | 11 | 10.4% | A tile 行数据→lane 布局重排（8 条）+ 3 条地址 |
| dpas.8x8 | 4 | 3.8% | 4 个累加器各 1 次 |
| mov(1) | 3 | 2.8% | |
| send.wide16 | 2 | 1.9% | 2 个 B tile，各 512 B 连续 |

**要删的真实工作 = 那 24 条 mov(32)。** 它不是源级的“搬运变量”，而是 IGC 为了在
K 循环里保留两个 live 判定产生的 **join 点**，被迫给 4 个累加器准备一个稳定“家”
（`r52..r66` / `r68..r82`），每步先存后取：

* 证据 1：紧跟在 2 条 DPAS 之后就是 8 条 `mov (32|M0) r58←r3.0 / r56←r5.0 / r54←r7.0 / r52←r9.0 /
  r66←r11.0 / r64←r13.0 / r62←r15.0 / r60←r17.0`（`0A30..0A68`），随后 `0A70 jmpi`。
* 证据 2：`L1072`（`0430..0468`）是**同一条判定的另一条边**，把 `r66,r64,r62,r60,r58,r56,r54,r52`
  清零。同一个寄存器组在两条边上都被定义 ⇒ 它是 join 的 phi 落地寄存器。
* 证据 3：`L3488`（`0DD8`、`0EE0..0F18`）把 `r58…r60` 再取回 `r3,r5,r7,r9,r11,r13,r15,r17`，
  正好是 DPAS 的 4 个累加器操作数（`r3/r11/r36/r44` 的 dword 0 位）。
* 全核 `mov(32)` 共 1568 条，24×64 = **1536 条在展开步内**，剩 32 条在序言/尾声。

### 2.1 同族自然对照（本卡最关键的 native 证据）

本仓库里同族、同编译器、同 SPIR-V 生成器的三个 CURRENT 捕获可以直接对照
（`VIT-FFN-NATIVE-COMPARISON.json`，全部只读引用、本卡自算）：

| 核 | live 判定位置 | 累加器 | 展开 | instr | dpas | mov(32) | **mov32/dpas** | instr/dpas |
|---|---|---|---:|---|---:|---:|---:|---:|---:|
| **expand**（本卡父） | 循环**内** | 4 | 完全展开 | 7233 | 256 | 1568 | **6.12** | 28.25 |
| **contract**（94..129） | 循环**外**（`if(mA<live&&mB<live)`） | 4 | 卷回 | 3460 | 152 | 345 | **2.27** | 22.76 |
| **projection**（F16） | 循环**内** | 2 | 完全展开 | 5407 | 128 | 797 | **6.23** | 42.24 |

三条读法：

1. 判定在循环内的那两个核（expand、projection）**mov32/dpas 都是 6.1–6.2**，与累加器个数
   （4 vs 2）无关 ⇒ 搬运是**按 DPAS 组**付的，不是“每个累加器一份”的固定开销。
2. 判定已经提到循环外的 contract 只要 **2.27**（低 2.7 倍）；它剩下的那部分发生在
   **回边**（循环卷回、跨迭代存活），展开直体里没有回边。
3. 所以本卡候选在 expand（完全展开）上应该把“按组搬运”整块去掉；contract 的残留给出
   一个保守下界：若 IGC 仍保留部分搬运，mov32 大约落在 **100–600**，而不是 1568。

这条对照是“先查 native 真实供料冲突”的直接结果：**冲突在循环内的判定 join，不在预取数量**，
所以本卡不加任何预取。

另外删掉 2 条/步的 `jmpi`（全核 136 条 = 2×64 + 8）与对应的谓词判定。`cmp` 只有 4 条——
说明**谓词早就算到循环外了，只有分支留在循环里**；这正是本卡候选的工作：把分支也移出去。

**不删**：任何 send、任何 DPAS、任何 SLM 往返（本核 shared=0）、任何屏障（本核无屏障）。

## 3. 重叠：原来的独立工作如何重叠（RAW/WAR/WAW）

| 值 | 生产者 | 最后消费者 | 覆盖者 | 关系 |
|---|---|---|---|---|
| B tile b0/b1 | `send.ugm (16|M0)` 宽消息（1 条/tile） | 本步第 2 个 DPAS | 下一步的同一条宽消息 | **RAW**（DPAS←send）；**WAR** 被双缓冲吸收：操作数在 `r106/r98` 与 `r86/r118` 之间**每步交替**，send 写另一组 |
| A tile（mA 行） | 8 条 `send.ugm (1|M0)` | 本步 2 条 DPAS（配 b0、b1） | 下一步的 8 条 narrow 消息 | **RAW**；**WAR**：原始返回区 `r11..r18` 与累加器组**同号**，这就是冲突源 |
| A tile（mB 行） | 8 条 narrow（下一半） | 另 2 条 DPAS | 下一步 | 同上，原始返回区 `r27..r35` |
| 4 个累加器 | DPAS | epilogue 的 `MH` 转换/存储 | 下一步 DPAS（原地累加） | **RAW** 跨 64 步；**WAW**：join 迫使每步写回 `r52..r82` 再取回 |
| 残差 / 系数 | stage 0 不涉及（expand 只写 aHidden） | — | — | 本族 expand 无残差读，无 norm/den 树 |
| epilogue 的 `MH` → `vit_cubic` → store | 累加器 | `aHidden` store | 下一步（m 前进） | **WAR**：`result` 局部复用，父已如此 |

结论：**本核没有被“串起来”的独立工作可以重叠**（每步就是 2 个 B、2 个 A、4 个 DPAS 的紧链）；
唯一可删的是被 join 逼出来的累加器搬运。候选**不增加任何预取**：
B 宽消息的条数、A narrow 消息的条数、发送顺序都不变。

## 5. 是否真落到 native（预测 + 判据，不写“已证明”）

详细可观察点见 `NATIVE-PREDICTION.md`。一句话：**如果候选 ISA 里 `mov(32)` 从 1568 掉到
100–600（保守下界取自同族 contract 的 2.27/dpas，理想为 ~30），`Instruction Count` 从 7231 掉到
5400–6200，而 `dpas.8x8` 仍 256、send 仍 1216、`Scratch 0`、`Loop Count 0`、
`Basic Block Count` 不暴涨，就算实现落地**；若 `mov(32)` 仍 ≈1568，就是“实现未落地（A 类）”，
说明搬运不是 join 造成的，下一个改动改走“给两个 A tile 各自独立变量 + 把 clamp 变成地址选择”
（见 RESUME 的 next-2）。同族 contract 的 2.27 mov32/dpas 是这条预测的实测锚点，不是外推。

## 6. 整体是否更快：本卡要测什么、怎么归因

* 族内单位：F13 expand 8 个派发；atlas 的**同帧族和**口径（不是逐行中位相加）：
  `fullnet-connection-atlas-20261027/PROFILE-REPORT.txt` 记 F13 ViT FFN 族 fixed 首帧中位 **1.222440 ms**、
  fb2 第二帧 1.223170 ms（expand+contract 共 16 个派发；本卡只动其中 8 个）。
* 要测的整体量：**ordinary 双臂 6 组交替 ×30 样本**（`warm 1 / reps 30 / feedback`，
  末帧 gold `2b63d4ba…`），因为这是唯一能变成帧收益的量；gate（fixed/fb2）只做数值门，
  不做性能归因。
* 归因：单链只能声称“删掉了 24 条/步的寄存器搬运 + 2 条/步的条件跳转”，
  **不能**声称某条 mov 值多少毫秒。若整体不动，也要先看 native 是否落地（合同 §8.5）。
* 语句级上限：每步 106 条里删 26 条 ⇒ 单派发最多 −24.5% 指令发射量；F13 expand 的
  8 个派发在整个 profile 里同帧和为 1.2224 ms（含 contract），**帧级上限明显小于 0.3 ms**，
  不能承诺更多。
* 分开测：`native`（判落地）、`resources`（GpuTime/占用）、`gates`（数值）、`ordinary`（收益）。
  见 `GPU-REQUEST.json`。
