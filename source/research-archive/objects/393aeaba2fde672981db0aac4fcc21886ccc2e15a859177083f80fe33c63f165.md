# n23-f05-shape / MESSAGE-WIDTH — evaluation of the "wide message = contiguous" hypothesis

**Verdict: the hypothesis does not survive the ISA. Blocked for a shader-only delta, and the
blocker is arithmetic (512 B per message ceiling × 48 KB of weights per subgroup), not the layout
and not the asset.** Stage-1's measured `96 -> 96` is therefore the expected result, not an
implementation miss by the layout.

## 1. What the hypothesis claims

"The driver only emits wide messages for contiguous column-major weight blocks: F19 has 48
`load.ugm.d64x64t`, F05 has none, and n24's seed load merged into `d32x64t` because stride 16 +
contiguous. So make the 32-channel block truly contiguous and one load will cover it."

## 2. What those wide instructions actually are

Two instruction pairs, copied verbatim from the captures.

**(a) our weight B load** (`.../n04b-f05-c128-feed/native/captures/native-native-base/ISA/
CS_asmf98d5ab4e239dd54_simd32_..._9_orig.asm`, the parent identity):

```
(W) send.ugm (16|M0)  r19  r7  null:0  a0.2  0x22804500  {I@2,$1} // wr:1+0, rd:8;
                                                     load.ugm.d32x8.a32.bss[a0.2]
```

exec **16**, **per-lane addresses** (`a0.2`), **8 GRF returned** = 16 lanes x 32 B = **512 B**, which
is exactly one 16x16 fp16 tile. The message is already *saturated* by one tile.

**(b) the "wide" class the hypothesis points at** (`.../n01b-f02-load-side/.../
CS_asmf5bd1d41164ade43_..._8_orig.asm`, ordinal 18 = `block9_swin_body_1`, same block, same pack):

```
(W) send.ugm (1|M0)   r3   r2  null:0  a0.0  0x2240F500  {I@1,$7} // wr:1+0, rd:4;
                                                     load.ugm.d32x64t.a32.bss[a0.0]
    mov (32|M0)       r7.0<1>:hf  r3.0<1;1,0>:hf        {$7.dst}      <- broadcast to 32 lanes
```

exec **1**, **uniform address** (`a0.0`, i.e. one address for the whole warp), **4 GRF**, then a
broadcast `mov`. That is how IGC implements a **uniform/broadcast read**, e.g. the
`coopMatLoad(scale, pack, rs + cg, 0u, LROW)` stride-0 scale loads in that shader. It carries the
same bytes to every lane, which is exactly what a weight *operand* fragment never does: the B
operand's lane map gives each lane a different column (`col = lane & 15`, `row = 2c + (lane & 1)`,
`register_handoff.glsl` `nrh_coord_B`).

F05's remaining classes agree: `d32x8t ... (1|M0) ... rd:1` = uniform 1-GRF reads (address setup,
debug paths); `d32x8.a32.bss[a0.2]` with `rd:8` = the 512 B per-lane tile reads; `d32x4` = the
score-stage 16x16 B tiles. There is no per-lane message wider than 512 B anywhere in either kernel.

## 3. The arithmetic that decides it

Per subgroup, the QKV projection reads

```
6 channel tiles x 8 k-steps x 2 row phases x 512 B = 48 KB
```

and the ceiling for a per-lane `send.ugm` is

```
8 GRF x 32 B = 32 B/lane x 16 active lanes = 512 B
```

so the **static message count floor is 48 KB / 512 B = 96** — the parent number, and exactly what
stage-1 measured after merging the V pair into one 1 KB load. A 1 KB fragment load is still
**two** 512 B messages; making the fragment wider cannot change that. Only reading *fewer bytes* can.

## 4. So is the requested layout already in place? Yes, and stage-1 measured it

`packed/*.reblocked.fp16.bin` store output channel `n` of pair `p` at

```
wq + h*12288 + p*4096 + ki*512 + n*16 + k          (halves)
```

i.e. element `(k, n)` at `base + n*16 + k` = **ColumnMajor with stride 16 halves** for all 32
channels, and the eight k-tiles of a pair are 1 KB apart, so the pair region is **8 KB contiguous**.
That is precisely "one `coopMatLoad(..., stride 16, LCOL)` covers 32 channels", and the proof that
the bytes are the parent's is `build/PERMUTATION-PROOF.json` (589824/589824 coordinates). The
stage-1 GPU run is the measurement *of that layout*: gold byte-exact, messages 96 -> 96.

## 5. What could still reduce the 96, and what each costs

| route | effect on messages | price | status |
|---|---|---|---|
| merge the V/Q/K pairs (B1) | **0** (2 x 512 B -> one 1 KB = still 2 messages) | 0 GRF (NESTED law: 3 x 16 = 48) | measured on the V pair: 96 -> 96 |
| break the 2x duplication across the two row phases (weights are identical for both) | 96 -> 48 | both phases' accumulators live = 12 x 8 GRF = 96 GRF | measured by n05e: **-0.349 ms** |
| stage the 24 KB head weights in SLM once per WG | 96 -> 96 + 48 staging messages | SLM traffic priced by n17 | worse |
| 16-token M-tiling (one phase) | 96 -> 48 | acc GRF doubles to 96 (3 acc x 32 GRF) | same occupancy wall |
| a 1 KB per-lane message (`rd:16`, `d32x16` class) | 96 -> 48 | none, if the driver emitted it | **not emitted for per-lane loads; not requestable from GLSL** |

## 6. Falsifier for a future attempt

If any candidate ever shows a per-lane load with `rd:16` (or a `d32x16`/`d64x…` class with
`(16|M0)` and `a0.2` addressing), the ceiling argument changes and 96 -> 48 becomes reachable.
Until then, the weight-load count is fixed by the tile bytes, and any card claiming to reduce it by
reshaping the fragment is measuring the compiler, not the mechanism.

## 7. Consequence for this card

* B1 (Q/K merge on the NESTED law) is **not built as an arm**: it cannot reduce messages, and on
  NESTED it does not reduce accumulator GRF either (3 x 16 = 48 = parent). It would only shave
  static instructions (stage-1 already showed -108 of 4813 for the V pair alone) which is below the
  detection floor of this campaign (n04b: -20 instructions, indistinct).
  The source is kept compiled-but-unshipped in `b1-unbuilt/` (validated, NC 73 = 73, spv
  `b0876934...`) so the work is not lost if the ceiling ever changes.
* The card's remaining honest value: the shape probe (A), the NESTED law, the pure-reorder asset
  proof, the element-access negative result, and this ceiling argument.

## 8. Corpus statistic that settles it (2038 ISA captures, read-only scan)

Every `send.ugm ... load.ugm.*` in `fullnet-continuous-20261027/queue/**/ISA/*.asm`, grouped by
message class, address mode and exec size:

| class | addr | exec | rd | count |
|---|---|---|---|---|
| `d32x64t.a32.bss` | a0.0 | **1** | 4 | 20280 |
| `d32x16t.a32.bss` | a0.0 | **1** | 1 | 14856 |
| `d64x64t.a32.bss` | a0.0 | **1** | 8 | 9892 |
| `d32x64t.a32.bss` | a0.2 | **1** | 4 | 7005 |
| `d32x32t.a32.bss` | a0.0 | **1** | 2 | 50 |
| `d32x8.a32.bss` | a0.2 | 16 | 8 | 32767 |
| `d32x8t.a32.bss` | a0.2 | 1 | 1 | 21984 |
| `d16u32.a32.bss` | a0.2 | 32 | 2 | 4702 |
| `d32x4.a32.bss` | a0.2 | 16 | 4 | 104 |

**No wide class (x16 / x32 / x64) occurs at exec 16 or 32 anywhere in the corpus.** The wide
messages are all exec-1 reads of a contiguous block of at most 8 GRF / 256 B; the operand loads
(the ones that feed `dpas`) are `d32x8` at exec 16 with 8 GRF, i.e. 512 B, which is exactly one
16x16 fp16 tile. Fragment width therefore cannot change the message count, and no storage layout
can either: the ceiling is a property of the message, not of the data.

The only way the wide class could ever be used for weights is to read a block uniformly and then
redistribute it with shuffles — the trade-off n17 priced as net-negative.
