* The **unit** is the workgroup: `q0 = gl_WorkGroupID.x*64`, `h = gl_WorkGroupID.y`.

* The absmax is taken over this tile's 64 query tokens x **32 head dims** (`d = h*32 + e%32`).
  That is exactly the Q operand block of the QK MMA for this tile.
* `qkv` is `binding 6` (`layout(set=0,binding=6,std430) buffer QKV { float16_t qkv[]; }`,
  `vit_common.glsl` L77); offset base `pc.p6.x` = 0 (plan PUSH word 20 = 0), stride 3072

* **The scale is NOT stored in any buffer.** `shQMax` is `shared`, i.e. `Workgroup` storage
  class. There is no write-back, no plan row, no bounce to memory. This is why the deployed
  module needs no extra binding for the dynamic scales, and why the static version needs one
  carrier that already exists (see Â§4).

## 4. The 128 B scale table: what it is, and why it is the right carrier

### 4.1 The table itself

`BUFFER "vit_block31_scales" 128 "E:/…vit/block31/vit_scales.fp32.bin"` (plan line 402).
128 B = **32 float32** = one per head, `scales[h]`. It is written by the QKV producer and read
by every ViT kernel of the block through binding 1:

```
vit_common.glsl L68:  layout(set=0,binding=1,std430) readonly buffer Scales { float scales[]; };
```

The attention kernel reads the **already scaled** QKV: the producer applies
`scales[h]` and an L2 normalisation before the values land in `qkv[]`, so `scales[h]` never
appears in the attention source. What the attention kernel needs is a *different* per-head
number (the int8 step), and binding 1 is the per-block, per-head, already-bound carrier for
exactly that kind of data.

### 4.2 Proof that binding 1 is in the deployed module's interface but unused

```
 18: OpEntryPoint GLCompute %main "main" …%__2 %__3 %__4 %__5 %__6 %__7 %__8
241: OpName %Scales "Scales"
350: OpDecorate %__4 NonWritable
351: OpDecorate %__4 Binding 1
352: OpDecorate %__4 DescriptorSet 0
530: %__4 = OpVariable %_ptr_StorageBuffer_Scales StorageBuffer
```
and `%__4` has **exactly these six occurrences** - there is no `OpAccessChain` into it, i.e.
the descriptor is declared, decorated and listed in the entry point, but never read.
Consequence for the implementation: **using it adds no binding, no descriptor-set-layout
change, no push word**; the descriptor is already created and bound by the plan
(`BIND 1 400 0 128` in all six passes of the block).

## 5. The static substitution contract (what changes, and what must not)

### 5.1 Exactness: why a per-head scalar is legal here at all

For one query row `t` and one key `j`:

```
score[t,j] = sum_d Q[t,d]*K[j,d],  d = 0..31 (head dim = 32, one MMA K-step)
Q_hat = sQ * q,  K_hat = sK * k,  q,k integer codes in [-127,127]
=>  sum_d Q_hat*K_hat = sQ*sK * sum_d q*k = sQ*sK * acc
```

This is an identity **iff `sQ` and `sK` are constant along `d`** - which holds in both the
dynamic and the static version. Changing *how* the scalar is obtained (per-tile absmax vs a
pack constant) changes only its value, never the algebra. No rank-1 approximation is
introduced. That is the whole licence for this edit.

### 5.2 Invariants that the edit must not touch (and does not)

| invariant | where it lives | state after the edit |
|---|---|---|
| QK dot product runs over **K = 32 head dims**, int8 x int8 -> int32 | `MA8/MB8/AC8`, `coopMatMulAdd(kf,qf,…` source L187-193 | unchanged (no line touched) |
| **one** dequant multiply per score element, by the scalar `sQ*sK`, after the accumulator | L196-197 / SPV 1179-1188 | unchanged; `sQK = sQ*sK` keeps the same expression and the same product order |
| clamp/exp position: `MF8 -> *sQK -> MH (f16 narrow) -> vit_exp2` | L195-213 | unchanged |
| padding keys keep `exp(0)` in den, are zeroed only in the P fragment | L229-233 | unchanged |
| den: original 64-key half tree, per chunk accumulation, in-lane parity exchange | L224-248 | unchanged |
| `pad = (320-288)*vit_exp(0)` subtracted once per query; `inv = 1/max(den, 6.198883056640625e-05)` once per query after all 5 chunks | L296-303 | unchanged |
| PV: P unnormalised, `sV*sP` per (query,chunk) table, K=64 as two K32 slices | L255-285 | unchanged |
| context epilogue: `*inv`, then `vit_code(*, ws[10])` int8 store | L325-364 | unchanged |
| ABI: 9 bindings, 32 push words, grid 5x32x1, subgroup 32 | plan row | unchanged |

### 5.3 The edit, exactly

```glsl
// ---- was (dynamic) ----------------------------------------------  // ---- is (static) ----
if(tid==0u) shQMax=0u; barrier();                                    const float sq_pack=scales[VIT_SQ_OFF+h];
float qmx=0.0; for(...) qmx=max(qmx,abs(float(v)));                  const float sQ=(sq_pack>0.0)?sq_pack:1.0;
atomicMax(shQMax,floatBitsToUint(qmx)); barrier();                   const float sQinv=1.0/sQ;
const float sQ=(shQMax==0u)?1.0:(bitcast*1/127);                     for(...) q8[e]=int8_t(vit_code(float(v),sQinv));
for(...) q8[e]=int8_t(vit_code(float(v),1.0/sQ));                    barrier();

if(tid==0u){shKMax=0u;shVMax=0u;} barrier();                         if(tid==0u) shVMax=0u; barrier();
float kmx=0,vmx=0; for(...){… kmx=max(...); vmx=max(...);}          float vmx=0; for(...){… vmx=max(...);}
atomicMax(shKMax,…; atomicMax(shVMax,…; barrier();                 atomicMax(shVMax,…; barrier();
const float sK=(shKMax==0u)?1.0:(bitcast*1/127);                     /* sK hoisted before the key loop: */
const float sV=(shVMax==0u)?1.0:(bitcast*1/127);                     const float sK =(sk_pack>0.0)?sk_pack:1.0;
const float sQK=sQ*sK;                                               const float sKinv=1.0/sK;  /* + sV as before */
for(...){ sk8=vit_code(sk,1.0/sK); sv8=vit_code(sv,1.0/sV);}         for(...){ sk8=vit_code(sk,sKinv); sv8=….0/sV; }
```

Three properties worth stating explicitly, because they are what make the CPU numbers
transferable:

1. **`1.0/sQ` and `1.0/sK` are still evaluated in fp32 at run time from the same step value**
   (not shipped pre-reciprocated). So for a head whose pack value equals its dynamic value the
   Q/K codes are **bit-identical**, and no second rounding is introduced anywhere.
2. `sQK = sQ*sK` is the same expression, same operand order, same place (once per chunk).
3. The `>0.0 ? : 1.0` select reproduces the parent's `(shQMax==0u)?1.0:…` degenerate-tile
   fallback, so an unset pack slot can never produce a division by zero or an inf code.
   The pack builder asserts all 64 constants per block are `> 0`.

Two side effects, both reductions and neither claimed as measured: two workgroup barriers per
kernel launch disappear (the Q reduction no longer needs them) and shared memory drops from
20492 to 20484 B (`shQMax`, `shKMax` removed).

Calibration (one frame, F1 = 34189, no eval frame touched):

```
sQ[h] = float32(max_t,d |Q_h(t,d)| over all 288 live tokens) * float32(1/127)
sK[h] = float32(max_t,d |K_h(t,d)|)                          * float32(1/127)
```
The max over all tokens equals the max of the five per-tile dynamic values (the tiles
partition the 288 tokens), so **on the calibration frame the static scale can never clip and
each head's static value is bit-identical to the largest of its five dynamic values**. The
multiplier is the same fp32 constant the shader uses (`0x3C010204`), so a head whose dynamic
value happened to be that max gets *literally the same fp32 step*.

All eight packs keep the original 128 B prefix byte-identically (verified: `prefix128_identical=True`),
so nothing about the producer side moves.

## 8. What this contract closes, and what it explicitly does not

Closed (2 sites, 8 dispatches each -> 16 dispatch-site pairs, 8 buffers):

* `sK` - ViT attention, per-head pack constant, no `OpAtomicUMax`.

**Not closed, and not claimed closed:**

| site | instances | why it stays dynamic |
