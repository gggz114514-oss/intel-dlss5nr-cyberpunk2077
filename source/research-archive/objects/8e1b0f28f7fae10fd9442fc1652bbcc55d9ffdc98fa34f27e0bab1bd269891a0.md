## 1. 源码结构（先钉死数学，再谈成本）

`candidate.comp`：`Y = W·M + imgin·gain`（1×1 contract，K=128 全通道），epilogue 只有 fp16 窄化 + store。

- 每个 subgroup `sg∈[0,8)`：`n0=(sg%4)*32`（4 个列组 × 32 列），`q=sg/4∈{0,1}`（2 个行组）。
- `r∈[0,2)` 循环：`mA=(q+4r)*8`，`mB=mA+16` → 8 个 8 行片段全被 **恰好一次** 覆盖（m=0,8,…,56）。
- 每个 (m,n) 8×16 片段：先 `seed=imgin[m,n]`（f16）→ `seed*=gain[n]` → `acc=MAT_C(seed)`；
  再 `ki∈[0,8)`：`wb0,wb1`（16×16 f16，n0 与 n0+16）、`a`（8×16 f16，k=16ki），
  `accA0+=a·wb0`、`accA1+=a·wb1`、再载 `a'`（mB）、`accB0+=a'·wb0`、`accB1+=a'·wb1`。
- 收尾：4 个 `MAT_H(accX)` 窄化 + `coopMatStore` 到 `gY[(w*64+m)*128+n]`；`if (debug)` 再存一份 `dbg`。
- **共享内存 0、屏障 0**：SPIR-V 里 `OpVariable` 的 storage class 统计 = `{PushConstant:1, Input:2, StorageBuffer:7, Function:75}`，
  Workgroup=**0**；`OpControlBarrier`=**0**，`OpMemoryBarrier`=**0**；driver `Workgroup Memory Size`=**0**。
  该族历史"shared 44 KiB 接近上限"是 **C256 body** 的形态，contract 段一个字节 shared 都没有。

### 2.3 放大的成因（这是本卡唯一"有冗余"的地方）

- **A 4×**：`n0=(sg%4)*32` 让 4 个列组各自重读同一 (m,k) tile。去重只能跨 subgroup → 需要 SLM 或改 tile 归属（见 §5）。
- **权重 4×**：两层叠乘——①`r` 循环两个 body 内 `bbase0/bbase1` 与 r 无关，同一权重 tile 被载两次（2×）；
  ②`q=sg/4` 的 2 个行组各自重读同一 (k,n) tile（2×）。
- **seed / Y store 都是 1×**：seed 每个 (m,n) tile 只读一次；Y 每个元素只写一次（§3 有覆盖证明）。

## 3. 一次写、多次读的往返（roundtrip）审计

| 往返类型 | 结论 |
|---|---|
| SLM 写→读往返 | **不存在**：Workgroup 变量 0、`send.slm` 0 条。N14/F07 删的那种 `coopMatStore→subgroupBarrier→读回` 在本 PASS 没有对应结构。|
| 全局写→读往返 | **不存在**：本 PASS 只写 `gY`（+门控 `dbg`），从不读回 `gY`/`dbg`。|
| 生产者末次 store 被消费者重读 | 存在但**跨 PASS**：本 PASS 读 `gM`（ord 193 写）、`imgin`（上游 body 写）；折进消费者布局要改 ord 193/上游的 SPIR-V，不在本卡"只替换 ord 194 一行"的授权内。|
| 同 PASS 内重复计算 | `c128_img_half_index()` 的 t 相关链（q/s/tx/ty/两级 clamp/oob/index ≈10 条标量 op）在 seed 的 4 个子块里按 (t,c) 各算一次，而同 r 下只有 2 个不同 t → 每 r 冗余 2 条链、每线程 4 条链 ≈ **40 条指令（2%）**，无消息变化。按 `CONTRACT.md` L1（地址算术折叠在 ISA 上不减少工作）不作为机制。|

## 4. DPAS 与有效 lane

- DPAS：`dpas.8x8 (16|M0)`，每线程 64 条（4/ki × 8 ki × 2 r），× 8 subgroup = 每 WG 512 条，
  每条约 8×16×16 = 2048 MAC → 512×2048 = **1,048,576 = 64×128×128**，与 tile 精确相等 → **DPAS 数没有冗余**（不可删）。
- 有效 lane：DPAS 的 exec 是 `(16|M0)`，即 32 lane 里 **16 lane**（50%）参与矩阵；
  A 行/seed/Y store 消息是 `(1|M0)`（单 lane 发地址的块消息），权重消息是 `(16|M0)`；
  标量索引数学是全 32 lane。**这是该 kernel 既有形态**，不是本卡引入；"有效 lane 低"在这里换来的是每 lane 更大的累加器份额（MAT_C 8×16 = 8 GRF/acc）。
- 同步：265 条全是寄存器依赖型（`sync.nop` 238、`allrd` 19、`allwr` 8），**没有一条是内存/工作组屏障**。

## 5. 可删工作的穷举与代价（本卡的裁定依据）

在 4 个累加器（=32 GRF）、8 subgroup、64×128 满 tile 的约束下，穷举出来的删法只有四条（M1–M4）：

代数（`proof_cover.py` 可复算；A tile 256 B、W tile 512 B、seed/Y tile 256 B、每 tile 8 行消息）：

```
每 WG A 字节 = 131072 / n   （n = 每次迭代的 n 片段数）
每 WG W 字节 = 262144 / m   （m = 每次迭代的 m 片段数）
每 WG 消息  = A/32 + W/512 + seed 64 + store 512
```

| # | 机制 | 实测工作量变化（每 WG）| 新增代价 | 裁定 |
|---|---|---|---|---|
| M1 | 互斥阶段 arena 退休复用（N14 方向）| 无可删：该段 shared 0、屏障 0、`send.slm` 0 | — | **不适用**：没有 arena 可退休；要"复用"必须先引入 SLM 暂存（card 明令禁止继续堆融合暂存）|
| M2 | 生产者末次 store 折进消费者布局（N16 方向）| `gM` 的 A 4× 重读（-48 KiB/WG）或 seed 的 oob/clamp 链（≈40 条/线程）| 需改 ord 193 / 上游 body 的 SPIR-V | **越权**：plan 只替换 ord 194 一行 |
| M3 | 4 acc 重划分 2m×2n → 1m×4n | A 2048→1024 消息（64→32 KiB）；总消息 2880→**2112（-27%）**；静态约 -15% | 权重 256→**512 条 / 128→256 KiB**；load 字节 208→**304 KiB（+46%）**；4 块权重同时活跃 **+12 GRF** | **不是删除，是交换**：拿字节换 issue 槽；且在 r124 的核上再抬活值 |
| M4 | 8 累加器 4m×2n（r 折进 acc 组）| 权重 256→128 条、128→**64 KiB**；load 字节 208→**144 KiB（-31%）**；总消息 2880→2752（-4.4%）| **+32 GRF**（4 acc=32 GRF → 8 acc=64 GRF）| **预算不足**：现 kernel 用到 r124、104 个不同寄存器、`Scratch Memory Size = 0`；+32 GRF 必然溢出，违反本卡 native 不变量 `scratch 0` |

M4 的账（为什么"字节最优"必须抬 acc 数）：
固定一次迭代 m×n 个 acc，A 放大 = 8/m、W 放大 = 8/n（WG 共有 8 个 m 片段、8 个 n 片段，8 个 SG 分摊）。
总 load 字节 = 131072/n + 262144/m。m·n = 4 时最小点 m≈2.83/n≈1.41，整数格点 **m=2,n=2 与 m=4,n=1 同为 192 KiB**
→ 现布局已是 4 acc 下的字节最优；只有把 m·n 抬到 8 才能到 128 KiB，代价就是 +32 GRF。
换消息则相反：m=1,n=4 给 2112 条，但字节 304 KiB。**两条路都无法同时降消息与字节。**

## 6. 结论

1. contract 段是**纯 GEMM + 单点 epilogue**：0 SLM、0 屏障、0 往返、DPAS 数精确、store 精确、seed 精确。
2. 唯一的真实冗余是**跨 subgroup 的 A/权重重复读**（A 每 WG 64 KiB vs 应 16 KiB；权重 128 KiB vs 应 32 KiB），
   而它的两种消除法分别被"禁止新增共享暂存"和"+32 GRF 溢出"挡住。
3. 唯一在规则内可实施的重划分（M3）是**消息换字节**的交换，不减少工作量（load 字节 +46%），
   按 L4（任何抬高另一项成本的候选都亏）与 L2（要的是在常量寄存器压力下**同时**降字节和消息）不构成本卡的合格机制。
4. 因此本卡判 **BLOCKED**：contract 段没有可删的矩阵外工作，也没有在 4-acc/8-SG/寄存器天花板下同时降消息与字节的矩阵内机制。
   细节与反证见 `ANALYSIS.md`、`PROOF.json`、`COST-LEDGER.json`。
