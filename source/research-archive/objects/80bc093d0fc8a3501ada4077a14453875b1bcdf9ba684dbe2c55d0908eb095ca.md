## 1. 映射：每个 (lane, component) 代表哪个 (token, channel)，消费者要什么

### 1.1 几何（C128 F04，父与候选相同）
- WG = 256 线程 = 8 SG（`local_size_x=256`）；grid `(21,12,2)` 类；`gl_WorkGroupID.z` 走 window 内的 slab 号 `t0 = 32z`。
- window = 64 token；token `t` → `q=t>>4, s=t&15`，`tx = 2wx+shift_x+(q&1)`，`ty = 2wy+shift_y+(q>>1)`（`nb05_swin_c128_common.glsl:35-44`）。
  即 token = (window 内 2×2 像素之一, 16 个 slot 之一)，每 token 128 个 channel。
- `g = sg%4` → M channel `32g..32g+31`；`pair = sg/4` → slab 行 `16·pair..16·pair+15`。
- 每 SG 4 个 8×16 `MAT_C`：行组 A=`slA=16·pair`，行组 B=`slB=slA+8`；列 tile `cg0=32g`，`cg1=cg0+16`。
- `mLocal[4096]` = `[32 slab token][128 C]`，8 KiB（`Workgroup Memory Size` native = 8192，父与候选同）。

### 1.2 mLocal 生产/消费映射（本卡不改）
| 元素域 | 生产者（唯一） | 消费者（多重度） |
|---|---|---|
| (row 0..31, ch 0..127) | SG(`g=ch/32`, `pair=row/16`) | 4 个 SG（同 `pair`，`g=0..3`），每个元素被读 4 次 |
| 生产元素数 | 8 SG × 512 = 4096 = 32×128 | 无重复写、无漏写 |
| 消费元素数 | 4 × 4096 = 16384 half = 16 KiB/WG | 与父相同（本卡未动） |
| 尾块 | row 32 = 2×16，8 行 A tile 整除；K=128 = 8×16；N/SG=32 = 2×16 → **无残块** | 图像越界只在 `c128_img_half_index` 的 `oob` 与 clamp，父与候选同一函数、同一字节 |

### 1.3 middle 的 A 输入（expand 的 A tile）映射 —— 本卡改这里
| 项 | 值 |
|---|---|
| 元素 | (token ∈ SG 的 16 个 row, 输入 channel 0..127) |
| 被谁读 | 同 `pair` 的 4 个 `g` SG 都读**同一批 token 的全部 128 channel**（每个 SG 必须算自己的 32 个 middle channel，K=128 全要） |
| 每 SG 每次需要 | 2 个 token 组 × 128 channel × 2 B = 4 KiB（16 个 8×16 tile） |
| 父的实际读取 | `hb` 外循环 4 次 × `ki` 8 次 × 2 组 = **64 个 tile = 16 KiB**，地址只与 `ki`、token 组有关 → **4× 重复** |
| 候选的实际读取 | `hb` 2 次 × `ki` 8 次 × 2 组 = **32 个 tile = 8 KiB**，地址逐条相同 → **2× 重复** |
| 覆盖性 | 两次读的是同一批 16 个唯一 tile；候选不增加也不减少任何被读地址，只减少每地址的重复次数 |

native 侧独立证据（父 SPV 的 ISA，见 §5）：`(1|M0) load.ugm.d32x64t` 共 **68** 条 = 64（A tile：4 hb × 8 ki × 2 组）+ 4（残差 seed），
**按 barrier 拆分实测：barrier 前 64 条、后 4 条**，与源码结构逐条吻合；若编译器已把 A tile 提出 `hb` 循环，前面应为 16 条。
每条 A 读后面紧跟 4 条 `mov (32|M0) …:hf` 的散布和 1 条 oob `jmpi`，所以**重复读一次要付 1 条消息 + 4 条 mov + 1 条分支**。
**所以 4× 重复读确实落到 native，不是源码错觉。**

### 1.4 候选改动的映射等式（逐条）
- hidden tile 编号：父 `(8g + 2·hb + T')·2048`（`hb∈0..3, T'∈0..1`）；候选 `(8g + 4·hb + T)·2048`（`hb∈0..1, T∈0..3`）。
  两者都覆盖 `8g + 0..7`，且按 hidden 索引升序消费 → **middle 的 K 序列 0,16,32,48,64,80,96,112 不变**。
- expand 累加器：父每 32-hidden 块 4 个（2 token 组 × 2 hidden tile），块末 act+窄化+middle；
  候选每 64-hidden 块 8 个（2 token 组 × 4 hidden tile），块末同样 act+窄化+middle。
  每个输出元素的 K 累加仍是 `ki=0..7` 升序，一条不差。
- act（`c128_act_h`）作用在同一个 `MAT_H` 窄化点上，参数、顺序、次数（每元素 1 次）不变。

## 2. 删掉了什么真实工作（正常执行路径，不计 debug 声明）

| 工作 | 父（每 SG 每次 dispatch） | 候选 | 依据 |
|---|---|---|---|
| expand A（输入）UGM 读 | 64 条 256 B = 16 KiB | **32 条 = 8 KiB（−32 条 / −8 KiB）** | 源码 `coopMatLoad(xa, imgin, xA + ki*256u, …)` 现只在 `hb` 之外被复用一次；父 ISA 的 64 条 `d32x64t` 全部在 barrier 之前、正好 4 hb × 8 ki × 2 组 |
| A tile 的半字散布 mov | 64 × 4 = **256 条 `mov (32|M0) …:hf`** | 128 条（−128） | 父 ISA：每条 A 读之后紧跟 4 条 `mov (32|M0) rX<1>:hf rY<1;1,0>:hf`（把 256 B 线性块摊成 DPAS A 片段），再跟 1 条 oob 跳过 `jmpi` |
| A 的 oob 条件跳转 | 64 条 `jmpi`（每读 1 条） | 32 条（−32） | 同上，`if (!oobA) coopMatLoad(...)` 每次读一份谓词分支 |
| expand 权重 UGM 读 | 64 条 512 B = 32 KiB | 64 条（不变） | 每 (hb,ki) 仍是 4 个 hidden tile 各 1 条，total 2×8×4 |
| middle 权重 UGM 读 | 16 条 512 B = 8 KiB | 16 条（不变） | 2 hb × 4 hidden tile × 2 channel tile |
| contract 权重 UGM 读 | 16 条 512 B = 8 KiB | 不变 | 段外，源码文本相同 |
| 残差 seed UGM 读 | 4 条 256 B | 不变 | 段外 |
| mLocal 发布（SLM store） | 4 次 × 8 条 = 32 条 | 不变 | 段外 |
| contract A（SLM load） | 16 tile × 8 条 = 128 条 | 不变 | 段外 |
| DPAS | expand 128 + middle 32 + contract 32 = 192 | 192 | 逐 acc K 序相同 |
| barrier | 1 | 1 | 单 WG `barrier()` 保留 |
| 全局存储 | gY 4 次发布 | 不变 | 段外 |

删除的**不是**“编译器已消掉的源码”：父 native 里 64 条 A 读真实存在（§5 计数），候选源码把同一地址的读从 4 次降到 2 次。
删除的**不是** debug 声明：候选在 `if (debug)` 里多写 4 条 dbg store（hidden tile 从 4 变 8），生产路径上线被谓词关掉，不记入删除也不记入新增收益。

**逻辑字节 ≠ DRAM 字节**：省下的 8 KiB/SG 是 L1/L2 层请求，同一 4 KiB 在短时间内被 4 次（候选 2 次）读取，
大概率命中 L1，因此不能声称 DRAM 流量减少 12 KiB/SG。可在 resources 臂看 L1/L2 命中与 UGM 请求数，但不宣称因果。
**片段字节 ≠ 实际 GRF**：+16 GRF/lane 是逻辑值，物理分配由分配器决定，必须由 native 的 scratch/占用率确认。

## 6. 整体是否更快：本卡要测什么、用什么臂、怎么归因

- **臂**：`base`=现役基线 plan（`a024c3c5…`），`cand`=`cards/n03-f04-middle/plan.txt`（`f6ad8f00…`，只换 11 个 C128 F04 PASS）。
- **门**：fixed（gold `1755e9c2…`）、fb2（末帧 gold `9c3e511e…`）、resources（zprof GpuTime）、native（上面那张表）。
- **ordinary**：warm1 / reps30 / feedback，6 组交替独立进程对，全部 360 样本保留，t(df5) 于对均值差，报告 95% 区间；
  不删峰、不补跑、不追显著。两臂交替顺序在启动前固定（`GPU-REQUEST.json`）。
- **归因边界**：只有 232 个 PASS 中的 11 个（C128 F04）改变，且每个 PASS 只删掉 409 条 UGM 中的 32 条（7.8%），
  这段在全部 F04 上的历史占比（子组时钟探针）是 expand/act/middle ≈75–79%，publication 3–7%，contract 17–20%。
  按 F04 族 2.17 ms（冷单帧诊断，不是 ordinary）粗算，本卡可测上限约 0.02–0.05 ms，**低于本 runner 6 对的检出下限（约 ±0.10 ms）**。
  因此：**即使机制完全落地也可能 INDISTINCT（D），这不能反过来证明“输入重复读不贵”**；反过来若出现 −0.2 ms 级变化，
  必须先排除分配/绑定差异（本卡 plan 的 buffer 数、pool 字节、PASS 行参数与父逐字一致，可用 receipt 核对）。
- 单链归因：本卡只做“A 输入重复读的 4→2”这一条，不做权重/发布/contract 的混合包（`f04-family-package` 的教训）。

## 7. 未决项与下一条具体改动

1. **C256（15 PASS，ordinal 36/39/42/45/48/51/54/57/171/174/177/180/183/186/189）**：`c256/candidate.comp:67-78` 同样是
   `for hb<4 (h0=hb*32) { for ki<16 { wh0, wh1, A } }`。下一条改动 = 同一变换（块宽 32→64，8 个 acc，`ki` 仍 0..15）。
   该宽度每 SG 的 A 读是 4×16×2 = 128 条 → 64 条，**收益面是 C128 的 2 倍**（−64 条 UGM/SG），但 8 个 acc + C256 已有 352 条 DPAS，
   寄存器压力更大：先在 native 上确认 C128 的 scratch=0 再推 C256。
2. **C64（7 PASS，ordinal 6/9/12/15/217/220/223）**：`c64/candidate.comp:64-75` 同结构，`ki<4`（K=64）。A 读 4×4×2 = 32 条 → 16 条，
   **收益面最小**（−16 条/SG），留到最后做，或与 C128 一起成包但要单独消融。
3. **同族更值得做的下一处（不属本卡，需新卡）**：C128 F04 的权重读取有 2× 的 pair 冗余
   （`pair=0` 与 `pair=1` 的 SG 读同一批 `Wm`/`WC` tile：96 条 UGM/SG 中，middle 16 + contract 16 各有一半是重复的）。
   它需要改 owner/几何（更多 token 每 SG 或 pair 合并），会动 WG 映射与权重读取总量，必须独立成卡。
4. **seed 与 expand A 的重复**：contract 的 4 个 seed tile 就是 expand 在 `ki=2g/2g+1` 上已经读过的同一批输入
   （同 token、同 16 channel）。保留它们可以删 4 条 UGM/SG，但要把 4 个 half 片段跨整个 middle 段存活（+8 GRF/lane），
