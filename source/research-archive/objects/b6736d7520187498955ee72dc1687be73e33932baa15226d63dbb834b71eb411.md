Card `n28-f20-barrier-alu`, task A. Everything below is read-only analysis plus one candidate
that is described at the end; **no GPU was used and nothing was deployed**.

Identity of the audited parent (all hashes in `BUILD.json`):

Two independent counts disagree at first sight and both are right: the **SPIR-V contains 16
`OpControlBarrier`**, the **dispatched ISA contains 12 `sync.bar`**. The 16 → 12 step is IGC
merging four pairs of adjacent barriers; the 16 → 5 step is `debug = 0`. This audit proves
both steps.

## 1. The 16 `OpControlBarrier` and what each one publishes

All 16 are identical in scope and semantics: execution scope **Workgroup (2)**, memory scope
**Workgroup (2)**, semantics **264 = 0x108 = AcquireRelease | WorkgroupMemory**
(constant ids resolve to `(2, 2, 264)` in both the parent and the candidate — see
`tools/barrier-split.py` output in `tools/barrier-split.json`). There is **no subgroup-scope
barrier anywhere in this kernel**, so "relax the scope" is not an available move here.

Line numbers are the parent source; "runtime" is the `debug = 0` path.

#7 are *merged* barriers that still execute: IGC hoisted the conditional `barrier()` out of
the uniform `if (debug)`, which is legal because the condition is uniform and the following
barrier is unconditional, so the merged barrier runs in both paths.)

## 2. The five runtime barriers: writer / reader intervals and the decision

Sets are integer intervals in half (2-byte) units of the three shared arrays
(`shXP[2048]`, `shY[2048]`, `shArena[8192]` = `A[64][128]` | Q | K | V | Ctx), built from the
SPIR-V index expressions (`tools/spv_sites.py` → `tools/spv-sites.json`: 13 shared-source
`OpCooperativeMatrixLoadKHR` sites) and the loop bounds in the source. The decision procedure
is interval overlap split into same-subgroup and cross-subgroup pairs
(`tools/proof_barriers.py` → `tools/proof-barriers.json`).

| barrier | writer set (per subgroup) | reader set (per subgroup) | same-SG overlap pairs | cross-SG overlap pairs | verdict |
|---|---|---|---|---|---|
| B1 `0x0ED0` (215) | stage 0: `shX` rows 16q..16q+16 for subgroups {2q, 2q+1} | stage 1: `shX` rows 8·(sg/4+4r) and +16, 8 rows × 32 cols, r = 0,1 | 8 | **128** | **required** |
| B2 `0x4490` (282) | stage 1: `shArena` rows mA, mA+8, mB, mB+8 × cols [32(sg%4), +32) | stage 3: `shArena` rows 8sg..8sg+8 × all 128 cols | 4 | **32** | **required** |
| B3 `0x6270` (334+336) | stage 4: `shArena` [2048r + 256sg, +256) for r = 0,1,2 (Q, K, V) | stage 3: `shArena` [1024sg, 1024sg+1024) — the whole A block | 8 | **24** (WAR) | **required before this card** |
| B4 `0x8C00` (394+396) | stage 4 as above | stage 6: Q [256sg, +256) and the whole K region [2048, 4096); stage 8: the whole V region [4096, 6144) | 8 | **136** | **required** |
| B5 `0xE9D0` (586) | stage 9: `shX` [256sg, +256) (O rows 8sg..8sg+7) | tail: `shX` [0, 1024) for sg 0 and [1024, 2048) for sg 1 | 8 | **8** (56 of 64 rows cross-SG) | **required before this card** |

Readings:

* **B1, B2, B4 are publications.** The writer owns a column band (B2) or a row block (B1) that
  the reader needs in full, so the transport is cross-subgroup by construction and the barrier
  is the only ordering primitive. Nothing in the source can remove them without changing who
  computes what (the owner map), which is the algorithm.
* **B3 is a WAR barrier over arena reuse**, not a publication: stage 3 reads all 8192 halves of
  the A block and stage 4 then overwrites 6144 of them with Q/K/V. The *data* does not have to
  cross subgroups — only the memory does. See §4.
* **B5 is a publication only because the tail is not owner-aligned**: `if (sg < 2)` makes two
  subgroups read the 64 rows that all eight subgroups wrote. 56 of the 64 rows are read by a
  subgroup that did not write them. See §5 — this card's candidate.

## 3. The three classes the card asks for

### (a) Both sides are the same subgroup only

* `shY` (stage 3 writes rows 8sg..8sg+7, stage 9 reads rows 8sg..8sg+7): **identical
  intervals for all eight subgroups**, i.e. the `shY` half of B3 needs no barrier at all. It is
  B3's *arena* half (the WAR above) that keeps the barrier alive. Verified:
  `proof-barriers.json → shy.writer == shy.reader`.
* The Q plane of stage 4 → stage 6: writer SG = reader SG (rows 8sg, `n0 = 32·(sg%4)` vs
  `score_q0/1` at `sg*8*32`), i.e. same-subgroup. It is *not* removable on its own because the
  barrier is shared with the K/V publication of the same stage (B4), and `n17c` already
  measured the Q register hand-off (32 messages removed) as INDISTINCT.
* The tail (stage 9 → stage 11): **not** same-subgroup in the parent (56/64 rows cross-SG),
  but it can be made same-subgroup by re-owning the tail — §5.

### (b) No write between the two barriers

Four pairs of adjacent barriers have nothing between them but a uniform guard or a debug dump:
`(225, 227)`, `(334, 336)`, `(394, 396)`, `(599, 601)`. All four pairs are already collapsed by
IGC into one `sync.bar` (that is the 16 → 12 step), so there is **no runtime redundancy left to
delete**: every remaining pair is separated by real work. The only *source-level* redundancy is
`if (debug) barrier();` following a `barrier()` that closed an `if (debug)` block — dead code at
`debug = 0`, and removing it changes nothing the XVE executes (L17: the gated debug path is
neither a frame cost nor a register reservoir).

### (c) Hoistable out of a loop

**None.** All 16 `barrier()` calls sit at function scope in `main()`; there is not one barrier
inside the `for (round)`, `for (ki)`, `for (step)`, `for (j)` or `for (c)` bodies. The
"sync every iteration of the same data" pattern does not exist in this kernel, so class (c) is
empty by construction (verified by reading the 16 call sites: lines 215, 225, 227, 282, 332,
334, 336, 391, 394, 396, 519, 521, 523, 586, 599, 601 — none inside a loop body).

## 4. What is left for B3: the arena, and why this card does not take it

B3 disappears if stage 4 no longer writes into memory that a *different* subgroup read at
stage 3. The arena is `A[64][128]` = 8192 halves = 16 KB and stage 3 reads **all** of it, so any
placement of Q/K/V inside `shArena` collides with some other subgroup's read window:

| plane | parent placement | overwrites A rows | stage-3 reader of those rows |
|---|---|---|---|
| Q | `shArena[0..2047]` | 0..15 | sg 0, 1 |
| K | `shArena[2048..4095]` | 16..31 | sg 2, 3 |
| V | `shArena[4096..6143]` | 32..47 | sg 4, 5 |
| Ctx | `shArena[6144..8191]` | 48..63 | sg 6, 7 |

Two ways out, both already spoken for:

1. **Column-interleave the four planes into the A block** (`plane p = A columns 32p..32p+31`,
   stride 128). Then stage 4 subgroup sg stores exactly A rows 8sg..8sg+7 — the rows it read
   itself at stage 3 — and B3's cross-SG WAR becomes intra-owner. This needs **zero** extra
   memory and is the candidate of the sibling card `n30-f20-arena-rotate`
   (its module: 15 `OpControlBarrier`, scopes still (2, 2, 264), sha `5abad855…0544a4`).
   This card does not duplicate it.
2. **Add 8 KB for a dedicated K/V plane** (24576 → 32768 B per workgroup). Rejected on the
   campaign's own budget rule: F20 already sits at 29184 B of workgroup memory (L23), and
   raising it to 32 KB cuts the resident workgroup count, which is exactly the L4/n05e
   failure mode (−0.349 ms) — a 3 % barrier gain cannot pay for that.

## 5. What this card implements: B5 / the pixel-owner tail (owner alignment)

`if (sg < 2)` gives 64 rows of output to two subgroups while six subgroups idle, and it is the
only reason B5 exists. Stage 9 subgroup sg already stores exactly the O rows 8sg..8sg+7
(`coopMatStore(half0, shX, m0*32, 32, LROW)` with `m0 = 8*sg`). Re-owning the tail so that each
subgroup projects **its own** eight rows (four lanes per row, one output channel per lane)
makes the read set equal to the write set for every subgroup:

| | rows read per SG | cross-subgroup rows |
|---|---|---|
| parent (`sg < 2`, `t = sg*32 + lane`) | 32 | **56 of 64** |
| candidate (`row = 8*sg + lane/4`, `ch = lane&3`) | 8 | **0** |

(`tools/tail_model.py` → `tools/tail-model.json`, computed over 25 `(wx, wy)` samples.)

B5 is therefore removed, the tail's four serial FP32 channels per lane become one per lane
(the per-element operation sequence is unchanged: `c` ascending, one multiply then one add per
term, `precise`), and the 75 % of lanes that were idle in the last 8.8 % of the kernel now
carry work. Numerics, the block map and the remaining four barriers are untouched; see
`ANALYSIS.md`, `PROOF.json` and `NATIVE-PREDICTION.md`.

Barrier bookkeeping for the candidate: **16 → 15 static `OpControlBarrier`**, **12 → 11
`sync.bar`**, **5 → 4 executed per workgroup at `debug = 0`**, scope/semantics still
`(Workgroup, Workgroup, 0x108)` — the kernel is not buying the removal by relaxing any barrier.
