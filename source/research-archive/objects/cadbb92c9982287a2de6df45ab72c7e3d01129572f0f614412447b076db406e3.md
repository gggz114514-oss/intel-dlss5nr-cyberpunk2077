## 1. 映射：每个 (lane, component) 实际代表哪个 (row, col) → 哪个 `fb` 下标

### 1.1 两侧各自的坐标律

- **消费者（不变）**：8 个 `NRH_C`（8×16 f32 累加器）片段，component `c` of lane `L` 必须持有
  `row = 2c + (L>>4)`，`col = L & 15`（密封头文件 `nrh_coord_C` 的实测律，n02c `PROOF.json.P1` 128 项逐项复核）。
  站点 `(h,b)` 的瓦片基址是 `fb + pc.p2.w + (t0 + 8h)*64 + 16b`，行跨度 **64 f32 = 256 B**。
- **生产者（本卡改成宽读）**：8 个站点合并成 2 条 **8×64 f32 累加器带**，
  带 `h` 的基址 = `pc.p2.w + (t0 + 8h)*64`，行跨度 64 ⇒ **8 行 × 64 列 = 2048 B 连续**。
  带的 component `k` of lane `L` 持有哪个元素由实现决定（**探针问题**）；
  候选按 **H1** 写：`k = 4b + c` 持有 `(2c + (L>>4), 16b + (L&15))`。

### 1.2 站点 → 表坐标 → `fb` 下标（可枚举，机器已核）

```
fb_index(lane, comp, h, b) = pc.p2.w + (t0 + 8h + 2*comp + (lane>>4))*64 + 16*b + (lane & 15)
带内线性下标             z = (2*comp + (lane>>4))*64 + 16*b + (lane & 15)
```

| 量 | 父（8 站点 × 8×16） | 候选（2 带 × 8×64，H1） |
|---|---:|---:|
| (lane, component) 项数 | 8×4×32 = **1024** | 2×16×32 = **1024** |
| 覆盖的瓦片元素 | **1024 / 1024，重数 1** | **1024 / 1024，重数 1** |
| 元素集合是否同一 | — | **是**（`PROOF.json.P3.identity_with_parent_element_set = true`） |

**一一覆盖**（`PROOF.json.P2/P3`，机器枚举）：两侧都是 1024 项对 1024 个瓦片元素、最大重数 1。
**无漏读**：带 `h` 的 `rows_touched = 8h..8h+7`、`cols_touched = 0..63`，两带拼成整块 16×64。
**无重复写**：bias 路径只有 `coopMatLoad` 写这两个带变量，之后只读；随后 `sc[c]` 是唯一被写回的累加器
（`precise float biasedN=sc[c]+band[...]` 与父同形），带变量本身不被写第二次。
**尾块**：基址只含推送常量 `pc.p2.w` 与 SG-均匀 `t0 = 16*sg`，**不含 WGID、不含 token 基址**；
瓦片恰好 16×64 f32 = 4096 B/SG，与 8 站点读的 4096 B 完全一致 ⇒ 任何 dispatch 边缘都没有半带。
（`imgin`/`imgout` 的 8 处 `if(!tok_oob_u)` 逐字未动。）

**消费端要求**：bias 必须是与累加器**同布局的 f32 片段**，按 component 逐元素相加，**加完才窄化**
（`p0b = nrh_narrow(sc0)`）。候选严格保持这一点：加的仍是 `sc[c]`（左操作数逐项未变，见 §4.3 的
`bias_add_operand_pairs.left_operand_unchanged = true`），右操作数从"站点局部 component c"变成"带内 component 4b+c"，
在 H1 下是**同一元素的另一个寄存器号**。

## 2. 删什么真实工作（只算正常执行路径）

| 类别 | 删掉的量 | 依据 |
|---|---:|---|
| `load.ugm.d32x16t`（uniform、rd:1、64 B，一条一行） | **−64 条 / −4096 B**（每 SG） | 8 站点 × 8 行；候选把 8 个 `coopMatLoad(bias,fb,…,64u,LROW)` 站点整体删掉（SPIR-V 侧 `(8,16,ACC) stride=64` 由 8 → 0） |
| 每站点的 uniform 行地址 `add (1\|M0) r4 = base + {256,512,…,1792}` | **−8 条链 × 7 条** | ISA 实测（n02c `bias-clusters.json`）；候选只剩两条带的基址 |
| bias 的 f32 加 | **0（不可删）** | 8 片段 × 4 component = 32 条，是数学 |
| bias 的窄化 `mov …:hf ← …:f` | **0（不可删）** | 64 条，是 `nrh_narrow()` 的半精度舍入点 |
| 重复读 | **0（本来就没有）** | n02c `PROOF.json.P3`：64×16 = 1024 = 表元素数，重数 1 |
| SLM 往返 / 屏障 / fence | **0** | 本候选没有引入任何 SLM 中转（这正是相对 n02c 方案 N/T 的全部优势） |
| 交织 mov（528 条 zip 块） | **0** | 本候选不动任何 `NRH_B` 块读 |

**净删的真实工作**：每 SG **56 条消息发射**（64 → 8）与 8 组 uniform 地址递增；
不算 debug 声明（388 条 dbg 存储本就不执行），也不算"编译器已消掉的源码"。

## 3. 重叠：原来怎么重叠，改动后谁等谁

阶段与 owner（每个 dispatch：4 SG/WG，128 lane；grid 由链头 PASS 行字段读得，未经 GPU 复核）：

| 阶段 | 生产者 | 片段 | 最后消费者 | 覆盖者 |
|---|---|---|---|---|
| 入口 | `coopMatLoad(imgin)`（WG 相关基址） | `x`(CH) | A 转换 / scale 种子 | `if(debug)` dbg |
| expand G1/G2 | `wb` 块读 48 条 | `e`,`y` | 激活 → A；`y*scale` | 同块 next |
| QKV | `wb` 12 条 | `q/k/v` | norm / 写 shK,shV | — |
| score | `shK`(SLM) 8 条 | `sc0/sc1` | den 树 + PV A | **bias 加** |
| **bias（本卡）** | **`fb` 2 条带读 → 8 条宽消息** | `bias64a/bias64b`(8×64) | `sc0/sc1 + band[...]` → narrow → exp | 无 |
| PV | `shV`(SLM) 8 条 | `tc` | narrow → ctx | — |
| output | `wb` 4 + `y*scale` | `oc` | narrow → imgout | — |

| 值 | 关系 | 说明 | 本卡影响 |
|---|---|---|---|
| `fb[…]` → 带片段 | **RAW** | 只读表、dispatch 不变、跨 WG 同一 16 KiB | 读同样 4096 B/SG，**只改发射槽** |
| 带片段 → `sc[c]+band[…]` | **RAW** | 逐 component | 不变（顺序、配对逐项核对） |
| `sc`（DPAS 写）→ bias 加 | **RAW**，跨 8 个片段串行 | 片段是 DPAS 出口 | **不变**：仍按列块 b 依次消费，两带在同一列块内并排 |
| 带变量 `bias64a/b` 与后续片段 | **WAW/WAR** | 分配器视角 | 峰值 8 GRF → 32 GRF（见 §4、`BUDGET.md`） |
| `shK`/`shV`（8192 B SLM） | **WAR**（屏障 `0xb520` 前写、后读） | 不变 | **未动**（不复制 shK 读、不加屏障） |
| 唯一 `barrier()` | — | 输入侧全在前、bias 全在后 | **仍 1 道**（`OpControlBarrier` 1 → 1） |

**目标不是把所有东西串起来**：本候选保留"每列块 2 条 shK 块读 + 4 条 DPAS + 2 处 bias 加 + 2 次窄化 + exp"
的原有交错节奏，只把"8 条一组的 64 B gather"换成"2 条一次的 2048 B 连续读"，
所以片段 i 的等待仍由片段 i+1..7 的 DPAS 覆盖（n02c §3.3 实测的那种覆盖形态**没有被破坏**）。

## 4. 新增成本（全部入账，`COST-LEDGER.json`）

### 4.1 消息与字节

| 项 | 父 | 候选（最好） | 候选（现实） |
|---|---:|---:|---:|
| bias 消息条数 /SG | 64 | **8**（`d64x64t` 512 B） | **16**（`d32x64t` 256 B） |
| bias 字节 /SG | 4096 B | 4096 B | 4096 B |
| 执行路径 UGM 读 | 182 | **126（−30.8%）** | 134（−26.4%） |
| 执行路径总消息 | 209 | **153** | 161 |

逻辑字节 **守恒**（4096 B 还是 4096 B）：本卡买的是**发射槽**，不是带宽 —— 这点必须写在归因里。

### 4.2 寄存器（唯一真正的新增）

一条 8×64 f32 带 = 2048 B = **16 GRF/线程**；两条带同时在场 = **32 GRF**；
今天 bias 峰值 8 GRF（8 站点串行复用 `r21..r28` 那批）⇒ **+24 GRF**。
bias 段（屏障之后）实测寄存器水位 **r108**，整核 r127。
三种写法与退路的峰值、代价、判据见 `BUDGET.md`（W1/W2/W3 三张表）。

### 4.3 其他逐项

| 项 | 量 | 依据 |
|---|---|---|
| 地址计算 | **−8 组 uniform 递增**（8 站点 × 7 条 `add`），新增 2 条带基址 | `BUILD.json.opcode_census.changed`：`OpIAdd 421 → 381` |
| f32 加 | **0 变化**（32 条，左操作数逐项相同，右操作数 = 4b+c） | `BUILD.json.bias_add_operand_pairs` |
| 窄化 / 舍入点 | **0 变化**（`OpFConvert` 26 → 26，bias 窄化仍 8 处） | `PROOF.json.P5` |
| 交织 mov | **0 变化**（`NRH_B` 块读 64 个 `(16,16,B)` 站点未动） | `shape_census`：`(16,16,'B') stride=16` 64 → 64 |
| SLM / 屏障 / scratch | **0 / 0 / 0**（预期） | `OpControlBarrier` 1 → 1；无 `shared` 增项 |
| 有效 lane / WG 数 | **不变**（128 lane、4 SG，`if(sg<4u)` 恒真） | 源码结构未动 |
| 活值峰值 | **+24 GRF**（见 §4.2） | 算术 + 实测水位 |
| 代码体积 | **−2244 B**（128448 → 126204） | `PROOF.json.P5` |
| 跨 lane 传输 | **0**（前提：探针判 H1/PERM） | `PROBE-DESIGN.md` §3 |
| 片外 DRAM 字节 | **0 变化**（表 dispatch 不变、L1/L2 常驻） | n02c §0.3 `PROOF.json.P4` |

### 4.4 片段字节 ≠ 实际 GRF（这条必须点明）

一条带 2048 B 是**逻辑**字节，落到寄存器就是 16 GRF；两条带 32 GRF **不是** 4096 B 的"顺带"——
它就是本卡最大的新增成本。反之，父路径 8 条 64 B 消息总共只 512 B，却因为落地粒度占 8 个 GRF
（半 GRF 一个），所以"片段字节 → GRF"两边都不是 1:1。

## 5. 是否真落到 native（预测 + 判据，本卡无 GPU）

完整清单在 `NATIVE-PREDICTION.md`，要点：

- **N1**：`load.ugm.d32x16t`（fb bias）**64 → 0**。看不到 ⇒ **A 类（未落地）**，不换写法重跑。
- **N2**：新增 `load.ugm.d64x64t` **+8**（512 B）或 `load.ugm.d32x64t` **+16**（256 B），**类型与条数必须成对报告**。
  若出现 `d32x1t`/逐 lane 64 B 读 ⇒ IGC 把 coopmat 载入标量化，同样记 A 类。
- **N3**：地址形状 —— 每组 4（或 8）条消息以 **+512 B（+256 B）连续**递增，两组基址相差 **+2048 B**；
  **不再出现** 8 条一组、256 B 步长的 gather 模式。
- **不变量**：`dpas.8x8` **128**、`sync.bar` **1**（`@0xb520`）、528 条交织 mov **528**、
  `add :f,:f,:f` **32**、bias 窄化 mov **64**、`shared` **8192 B**、`scratch` **0**、最高寄存器 **≤127**。
- **前置**：`LANE-MAP.json` 判读必须是 `H1` 或 `PERM`；`CROSS-LANE` ⇒ 机制判死（不做计时）。
- 静态指令预期 4958 → **≈4850±60**。

**这一节全部是预测**：本卡没有 GPU，没有任何"已落地"的声称。

## 6. 整体是否更快（本卡不能测，写清测什么、怎么归因）

- **要测的整体量**：`ordinary`（`--pool --warm 1 --reps 30 --feedback`）两臂 **6 组交替**的组均值差，
  配对 95% CI（df=5），不剔除不重跑；臂 `base` = 链头 `719f100b…`，`cand` = 本卡 `4c41368b…`。
- **门的顺序**（合同 §8.5）：`native` 先看是否形成处理 → `resources`（scratch/max_r/WG）→ 数值 `fixed`+`fb2` → 最后 ordinary。
- **归因上限**：F02 族 7 PASS 合计 1.366038 ms，占 18.1637 ms 的 **7.52%**（`PASS-TIME-RANKING.json`）⇒
  整核 ms 的变化必须按族占比读，不能把整核 delta 当机制收益。
- **先验参考（同身份同 7 PASS）**：n01b 省 **32** 条消息（−17.6% 执行路径 UGM），
  实测 **+0.012712 ms，CI[−0.006922,+0.032346] = INDISTINCT**。本卡 **−56**（−30.8%）是同一链上更大的步长，
  但那是**另一个机制**（scale 的 stride-0 去重），不是本机制的外推；协议分辨率够不够只能实测。
- **机制归类**：n02c 已证重复读 = 0、表 dispatch 不变、已与 12 条 DPAS 交织 ⇒ 属 **L12（被并发隐藏的消息）**，
  不是 L2（重复消息删除）。因此"删了 56 条消息"不等于"省了 56 条消息的时间"。
- **三种可能的落点**：显著 ⇒ 归因写"bias 段发射槽 −56/SG"；INDISTINCT ⇒ 按 **D 类**记，并说明
  "这是该族唯一还没被测过的形状，不是方向禁令"；E ⇒ 先查 `LANE-MAP.json` 与 component 映射。
