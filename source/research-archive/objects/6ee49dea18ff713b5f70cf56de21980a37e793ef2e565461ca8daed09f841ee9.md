## 本卡改什么（两个 hunk，都在 QKV 的 kc 循环，都只动整数/地址）

| hunk | 位置 | 内容 | 语义 |
|---|---|---|---|
| H1 地址递推 | kc 循环前 + 循环尾 | 四个 staging base 从「每 slice 用 `tiled()` 重算」改为「循环前算一次、每 slice +1024 half」 | 见下式，恒等 |
| H2 slice 生命周期 | 循环体 + 尾部 | 一个 10240 half 的共享 arena，A slice 在 `[0,4096)` / `[4096,8192)` 两个窗口间交替；删掉每 slice 尾部 retire barrier，只保留 staging 后的 publish barrier | WAR 距离从「同 slice」变成「跨 1 个 slice」，最后一个 slice 落在非 handoff 窗口 |

H1 恒等式（对 `tiled(token,c,512)`，`kc=64i`、`c0<64`）：
```
tiled(t, kc+c0, 512) = ((t/16)*32 + (kc+c0)/16)*256 + (t%16)*16 + (kc+c0)%16
                    = tiled(t, c0, 512) + (kc/16)*256 = tiled(t, c0, 512) + 1024*i
```
穷举 1024 token × 8 slice × 64 c0 = **524288** 组全部相等（`BUILD.json: proofs.address_hoist_identity_checks`）。

H2 窗口序列（`kc = 0,64,…,448` → i = 0..7）：
```
i    : 0 1 2 3 4 5 6 7
abase: 4096 0 4096 0 4096 0 4096 0     (末尾 slice 7 在 [0,4096)，与 QKV handoff 不重叠)
```
窗口 w 的使用序列是 {0,2,4,6} / {1,3,5,7}；同一窗口两次使用之间至少隔一个 publish barrier（slice 1/3/5/7 的 barrier）——
**这就是删除 retire barrier 的全部前提**，见第 3 问 WAR 行。

## 1. 映射：每个 (lane, component) 到底代表哪个 (token, channel)，消费者要什么

### 1.1 生产者（staging，每 slice 一次）

每 slice（`kc = 64i`）由全部 256 个线程写 4096 个 half，两侧都可枚举：

```
lid ∈ [0,256)         q = lid>>6 ∈ [0,4)      c0 = lid&63 ∈ [0,64)
tx,ty                 窗口 tile 的 2×2 位置（本 WG 内一致）
w4 = p0.x/4, h4 = p0.y/4
quadrant g ∈ {0,1,2,3} = (dx,dy) ∈ {(0,0),(1,0),(0,1),(1,1)}
   T_g = (ty+dy)*w4 + (tx+dx)          B_g = 16*T_g
   v_g = (0 ≤ tx+dx < w4) && (0 ≤ ty+dy < h4)          ← 逐 WG 一致
i' ∈ [0,4)
   token  t = B_g + q + 4*i'
   channel c = kc + c0
   全局 half： gy[ tiled(t, c, 512) ]   （v_g 为假时取 0，且不产生读）
   SLM 落点： abase_i + qkv_a_offset(lid + 256*i' + 1024*g)
             qkv_a_offset(e) = ((e/64/8)*4 + (e%64)/16)*128 + ((e%64)%16)*8 + (e/64)%8
             ⇒ 行 r = 16*g + q + 4*i'，列 k = c0
```
**一一覆盖**：对固定 g，(q,i') ∈ 4×4 ⇒ `q+4i'` 恰好取遍 0..15；四个 g 的 token 基址 `B_g` 互差 16/32/48 ⇒ 四组 16 token 互不相交。
故 `(token, channel)` 对 = 64 token × 64 channel = **4096** = 256 线程 × 16 次 STAGE，**无重复写、无漏写**。
`qkv_a_offset` 对 4096 个 (r,k) 是双射（`BUILD.json: proofs.staged_slice_bijection = 4096`，地址集合 = 0..4095）。

### 1.2 消费者（A 片段，每 k-step 一次）

```
SG sg ∈ [0,8)      p = sg/2 ∈ [0,4)      s = sg%2
mA = 16*p          mB = mA+8             n0 = 48*s
k-step j ∈ [0,4)   k = 16*j
a0 = 行 16p..16p+7 的 8×16 片段：  coopMatLoad(a0, smem, abase+((mA/8)*4+j)*128, 8, COL)
a1 = 行 16p+8..16p+15：            coopMatLoad(a1, smem, abase+((mB/8)*4+j)*128, 8, COL)
元素 (行 m+r', 列 16j+c') 位于 base + c'*8 + r'
```
穷举校验：8 SG × 2 个 abase × 2 个 M8 块 × 4 个 k-block × 8×16 分量 = **16384** 个地址全部还原同一 (r,k)
（`proofs.fragment_addresses_checked = 16384`）。

**"两个 M 块共同消费"的准确含义**：同一 SG 的 a0（行 16p..+7）与 a1（行 16p+8..+15）是**同一片 16 token** 的上/下半，
同一对 SG（p 与 s=0/1）读**完全相同的 16 token**、只在 N 方向分工（n0=0 / n0=48）。
所以一个 staged slice 的消费者集合是「每 SG 2 个 A 片段 × 2 个 SG」，一个 publish 就对全部读者可见——
这正是本卡把 publish+retire 合并成 publish 的依据（不是"少同步一次也无所谓"，见第 3 问）。

### 1.3 尾块

- channel 尾：无。K = 512 = 8 × 64，slice 恒定 64 通道。
- token 尾：由 `v_g`（逐 WG 一致）决定整个 16-token 象限是否为 0；本卡不改变零填充的取值、位置与数量。
- 非法 tile 的**读地址**：父在 `v_g=false` 时把 base 置 0；候选在 H1 之后 base 会随 slice 递增到 `0+1024*i`，
  最大 `1024*7+192 = 7360` half < 输入缓冲 589824 half（`proofs.address_hoist_max_invalid_address`），
  且落点值仍由 `(V)?gy[A]:0` 选 0 ⇒ **被存储的字节不变**。

## 3. 重叠：谁生产、谁最后消费、谁覆盖，RAW/WAR/WAW

| 对象 | 生产者 | 首个消费者 | 最后消费者 | 覆盖者 | 父的约束 | 候选的约束 |
|---|---|---|---|---|---|---|
| staged slice 窗口 `w_i`（4096 half） | 8 个 SG 全部（各 16 次 STL） | slice i 的 barrier 后第一条 A 读 | 第 4 个 k-step 的 a1 读 | slice **i+2** 的 staging 写同一窗口 | publish(B) + retire(B/尾部) | **publish(B) 一个**；WAR 由 slice i+1 的 publish 关闭 |
| A 片段 a0/a1（寄存器） | A `coopMatLoad` | 同 k-step 第 1 条 DPAS | 同 k-step 第 6 条 DPAS | 下一 k-step 的 A 读 | 自然重叠 | 不变 |
| 权重 b0/b1/b2（三个 8-GRF 返回区） | 3 条 UGM（`coopMatLoad`） | 各自 2 条 DPAS | 各自第 2 条 DPAS | 下一 k-step 的权重读 | 三块独立返回区、都在首 DPAS 前 | **不变（本卡禁改）** |
| acc00..acc12（6 个 8×16 F32） | DPAS 累加 | 首个 k-step | `STORE_QKV` | — | 跨 8 slice 存活 | 不变 |
| QKV handoff `[4096,10240)` | `STORE_QKV`（循环后） | debug echo → norm → score bq0/bq1 → PV A | PV 第 4 对 | **偶数 slice 的 staging**（窗口 4096） | 无（父无读者竞争） | 由 slice 7 的 publish 关闭 WAR（末 slice = 7 为奇 → 在 `[0,4096)`） |

hazard 结论：

- **RAW**（staging 写 → A 读）：每 slice 仍有 1 个 workgroup barrier，覆盖全部 8 个 SG 的写者。未削弱。
- **WAR**（A 读 → i+2 的写）：同一窗口的两次使用之间必有 slice i+1 的 publish barrier；
  barrier 是 WG 级，故 slice i 的所有读者在 slice i+1 的 barrier 之前完成，写者在 barrier 之后 ⇒ 顺序成立。
- **WAW**（slice i 写 → slice i+2 写）：同上被 slice i+1 的 barrier 隔开。
- **handoff WAR**：偶数 slice 最后一次使用是 i=6；i=7 的 publish 之后才会执行 `STORE_QKV` ⇒ 不需要额外 barrier。
  这也是"窗口从 4096 开始（偶数 slice 用 handoff 窗口）"的唯一原因——若从 0 开始，末 slice 会用 handoff 窗口，
  必须在 `STORE_QKV` 前再加 1 个 barrier，净收益从 8 降到 7。

**没有把所有东西串起来**：B 的三块仍在首 DPAS 前发出，A 读仍在同一位置，DPAS 顺序未变；只是发布了「一个 slice 一次」而不是「一次 + 一次回收」。

## 5. 是否真落到 native：预测 + 判据

完整清单见 `NATIVE-PREDICTION.md`。摘要（**这是预测，不是已证**）：

1. 整个 PASS 的 `sync.bar` **5 → 4**，kc 循环体内 **2 → 1**；若仍为 5/2 ⇒ **A 实现未落地**。
2. QKV 阶段动态 barrier+fence 消息 **16 组 → 8 组**。
3. staging 段不再出现 4 组 `shl 8`+`bfn.0xFE` 基址重算；改为 4 个循环携带 base + 每 slice 4 条 `add …0x800`。
4. **B 资产不回退**：三条 UGM 权重 send 仍返回到三个互不重叠的 8-GRF 区，仍都早于该 k-step 的首个 DPAS；
   每 k-step 权重读仍 3 次。若 W1/W2 落到首 DPAS 之后、或两块返回区重叠、或多出第 4 次权重读 ⇒ 判"牺牲已接受资产"，直接否。
5. A 片段组装仍是 2 条向量 SLM 读 + halfword 重组；scratch 必须 0；shared 20480；指令数 ≈ 4613±40。

## 6. 整体是否更快：测什么、怎么归因

- 臂：`base` = 基线 plan（`a024c3c5`），`cand` = 本卡 plan（`f01e0cf8`）。**只有 16 个 F10 PASS 不同**（`plan.differing_lines=16`，逐行核对非 F10 行完全相同）。
- 顺序：gates `fixed`（末帧 `1755e9c2…`）→ gates `fb2`（`--warm 0 --reps 2 --feedback --save-frames`，末帧 `9c3e511e…`）→ native（两臂 ISA）→ resources → **ordinary**（`--warm 1 --reps 30 --feedback`，末帧 `2b63d4ba…`）。
  **协议更正已按合同执行：fb2 末帧与 ordinary 末帧不是同一个 gold，不得混用。**
- ordinary：两臂 6 组交替（ABABAB…），每臂每组 30 样本，共 360 样本全留；按组均值差做配对 t(df=5)，报 95% CI。
- 归因边界：本卡只改 F10 的同一条 A 供料链（地址 + 发布/退休），**不跨批相减毫秒**、不重算 0.422ms。
  F10 单 pass 的 GpuTime 参考值 ≈0.1428ms/派发（`INTEL-ROWS[62]`，**旧身份**测量，既不是当前身份也不是端到端承诺）；本卡在上限上只可能贡献其中的
  8 个 barrier + ~160 条整数地址指令每 WG，因此**明确预测量级偏小**，出现 INDISTINCT 时按合同 D 类记录，不写成方向禁令。
- 若整体为负：先看 native 是否只落了 H1/H2 之一（可分臂判断），再按第 4 问最大增量项修一版（见 `RESUME.txt` 的下一步）。
