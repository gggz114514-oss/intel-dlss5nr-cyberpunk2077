## Q1 — Mapping: what every (lane, component) is, on both sides

### 1.1 Geometry of the transferred tile

| item | value | source |
|---|---|---|
| logical tile | `Y[64, 32]` fp16 — 64 tokens × 32 channels = 2 048 halfs | `shY[2048]`, stage 3 → stage 9 |
| owner | subgroup `sg` owns token rows `8*sg … 8*sg+7`, both channel halves | `uint m0 = sg * 8u;` in stage 3 and stage 9 (`m0` identical on both sides) |
| fragments | `yhalf0` = rows `8*sg..`, cols `0..15`; `yhalf1` = rows `8*sg..`, cols `16..31` | `MAT_H` = `coopmat<float16_t, Subgroup, 8, 16, Accumulator>` |
| elements per fragment | 128 halfs = 4 components per lane × 32 lanes | `MAT_H` component count = 4 |
| transfers | 2 stores (stage 3) + 2 loads (stage 9) = **4 fragment transports** | `build/spv-check-candidate.json` |

### 1.2 Producer → consumer, component by component

| component `d` of `yhalf0` | writer | parent path | candidate path | consumer |
|---|---|---|---|---|
| d = 0..3 | stage 3, `MAT_H(acc0)` after 8 DPAS k-slices, same lane | `coopMatStore(y, shY, m0*32+0, stride 32, LROW)` → `coopMatLoad(seed, shY, m0*32+0, stride 32, LROW)` | `yhalf0[d]` stays in the register file | `seed = seed * scale` → `MAT_C(seed)` = the stage-9 accumulator init |
| component `d` of `yhalf1` | stage 3, `MAT_H(acc1)` | `coopMatStore(…, m0*32+16, …)` → `coopMatLoad(seed, shY, m0*32+16, …)` | `yhalf1[d]` | same, second column half |

**Why the handoff is the identity — and what it does *not* assume.** The parent's round trip is
`store(value, base, stride 32, LROW)` followed by `load(…, base, stride 32, LROW)` at the *same*
base and stride. A cooperative-matrix store/load pair with identical layout, stride and offset
is, by construction, the identity on the logical `(row, col)` index: whatever per-lane component
map the layout induces, the load inverts the store's own map. The candidate therefore takes the
value that was *args* of the store (`H(Y)` itself) and passes it on. Consequences:

* no assumption about the `MAT_H` component→(row, col) map is needed at all (we never re-map
  lanes, never convert between matrix uses, never touch the `scale` broadcast);
* the values are **bit-identical**: the same `MAT_H` object that was stored is the one consumed,
  and `seed = seed * scale` keeps its operand order, its rounding point and its `precise` status;
* the same accessor `fragment[d]`, `d = 0..3`, appears on both sides, so a different map could
  only be introduced by also breaking the `handoff0/handoff1` copies to stage 4, which are
  unchanged and still consume `yhalf0/yhalf1` from the same registers.

### 1.3 Coverage enumeration

| check | result |
|---|---|
| element writes per handoff | 256 (2 fragments × 128), exactly one writer lane per element (`sg`, component `d`) |
| element reads per handoff | 256 — every element is read exactly once into the seed (2 fragments × 4 components × 32 lanes) |
| duplicate writes / dropped reads | 0 / 0 |
| tail / partial fragment | none: `Y` is exactly `8 SG × 8 rows` and `2 fragments × 16 cols`, no bounds test, no predicated lane, no partial tile |
| pixel-level boundary (`oob` in stage 0, `px<1280 && py<720` in the tail) | untouched (not in the diff) |
| debug path | `if (debug)` store keeps `shY` identical, so the `dbg[8192…]` Y dump is bit-identical; `debug == 0` at runtime (`p0.z = 0`) so the store is not issued |

| hazard | parent | candidate | change |

| RAW `shY`: stage-3 store → stage-9 load | cross-SG through 6 barriers | **removed** (the load is gone) | −1 long-range dependency |

## Q6 — Will it be faster? What to measure, and how to attribute it

This card cannot measure, so it commits to a measurement plan instead of a claim.

* **What the arm is**: one PASS of 232; the candidate removes 32 of 640 runtime messages (5.0 %)
  and ≈14 instructions of 4 754. Under the strictly-message-throughput model
  (`1.367 ms × 32/640`) that is **≤ 0.068 ms** on this dispatch — i.e. *at* the ordinary CI95
  half-width (0.068 ms, measured on this campaign's own harness), and exactly the same message
  profile as n17's Q candidate, which measured **+0.0257 ms, CI [−0.042, +0.094]** (INDISTINCT).
* **Primary instrument**: `resources` per-PASS `GpuTime` of ordinal 230 (isolated 1.36651 ms
  fixed / 1.359166 fb2; the parent's own frame-to-frame spread on this PASS is 7.1 µs = 0.52 %).
  A 5 % message cut is 5 % of the dispatch *if* message-bound, 0 % if not: this instrument is the
  only one that can see the difference at all, and both outcomes are informative.
* **Secondary**: the whole-frame `ordinary` two-arm 6-alternating design, 30 reps, single batch,
  no rerun. Attribution rule: a loop-level win of ≤ 1 % of one dispatch does **not** have to
  appear here; per L3/L8 an INDISTINCT single point is not evidence that the removed work was
  worthless, and it is not evidence that F20 is message-bound either (the probe in
  `PROBE-ANALYSIS.md` is the instrument for *that* question — it amplifies 16 transfers).
* **Attribution, stated conservatively**: if N1–N4 land and the per-PASS number improves by
  ≳ 0.02 ms, the improvement is attributable to the deleted transport (the diff contains nothing
  else). If N1 lands and nothing moves, the honest statement is "this dispatch does not scale
  with fragment-message count at 5 % amplitude", which is exactly what the probe then tests at
  20 % amplitude.
* **Package rule (L8)**: the same mechanism is worth twice as much in the same SPV — Q (n17's,
  32 messages) + Y (this card's, 32 messages) = 64 messages = 10 % of the stream in one PASS.
  If Y lands and the single point is INDISTINCT, the next card should build Q+Y in one candidate
  (both edits are independent hunks on the same parent) rather than stop the mechanism.
