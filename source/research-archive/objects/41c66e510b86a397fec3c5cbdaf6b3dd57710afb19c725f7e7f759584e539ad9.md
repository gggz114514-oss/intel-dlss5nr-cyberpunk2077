# ANALYSIS — n31-f01-dpas-chain（F01 / ordinal 0 / `f1c32_image_pre`）

方案：删掉 4 个 softmax 分母归约块与 `nr_pool_natural` 里的**操作数交换恒等选择**

```
(lower ? x : peer) + (lower ? peer : x)   ->   x + peer        // 加法交换律，逐位恒等
```

共 29 处源码行 → ISA 68 个 `add acc,acc` 对 → **136 条 `sel`**。
父 = n29 链头 `c12c0f9d…`；候选 `8c9119270eb63360c7ba6dc2afadc81b45f9a5748b2db2a737bb89d9cbd9ee8e`；
plan `42bdaa0691a3079bb308e86a1561c30503e5e0f2d178f5b9b59fa98eba781ce9`（只换第 504 行）。

## 问 1 — 映射：每个 (lane, component) 到底是谁，消费者要什么

后段的张量身份（`docs` 侧参考：`DPAS-CHAIN-AUDIT.md` §2 的分段图）：

| 片段 | lane 是谁 | component 是谁 | 生产者 | 消费者 | 覆盖证明 |
|---|---|---|---|---|---|
| `p00..p03`（NRH_CH，4×half/lane） | 子组内 token：`t0+(lane&15)`，`t0=sg*16` | 4 个注意力列（exp 分子） | `qa·shK` dpas（8×8 累加）→ `+bias` → `nrh_narrow` → `nr_exp_h2` | ①分母归约块；②`nrh_to_A(p0x)` → `·shV` dpas | 16 lane × 4 分量 = 64 槽，等于一个 8×8 tile；`nr_exp_h2` 逐元素 |
| `d`（分母，f16vec2） | 与上同，但**半组内 16 lane 广播后相同** | `d.x` = 列(0) 的 16-token 和；`d.y` = 列(1)；第二块给列(2)(3) | 本卡 4 个归约块 | `inv=1/max(d,eps)` → `p0x[j]*inv` | 每个 (列, 16 token) 组合只被一条链求和一次：块 A 覆盖列 0/1、块 B 列 2/3（p0x），块 C/D 同（p1x） |
| `tc00..tc11` | 同 token | PV 输出的 4 分量 | `nrh_to_A(p)`·`shV` dpas ×4×2 | `nrh_narrow` → `ctx00..ctx11` | 4 组 × 2 = 8 dpas，与 A 片数一致 |
| `oc00..oc11` | 同 token | 输出通道 4 分量 | `nrh_widen_exact(y*scale)` 作初值 → `·w` dpas ×4×2 | `nrh_narrow` → `nr_pool_natural` → `pooled[]` / `imgout` | 尾块：`tok_oob_u` 决定是否写 `imgout` |
| `nr_pool_natural` 的 `a,b` | `lane` 与 `lane^16` 配对 | `a=(x0,x1)`、`b=(x2,x3)` | `oc` 窄化结果 | `pooled[(tile*2+ch/16)*256 + slot*16 + (ch&15)]/2` | `if((lane&17u)==0u)` 只让 2/32 lane 写，`f16vec2` 一次两个通道 |

本次改动**不改任何映射**：`(lower?x:peer)+(lower?peer:x)` 与 `x+peer` 在**每个** (lane, component)
上取同一个值；被删的只是「谁写在加号左边」这一顺序信息。逐位证明见 `PROOF.json` P1/P2
（全 65536 个 half 编码 × 16 个代表 peer，1,048,576 组，0 反例）。

尾块：`nr_pool_natural` 的 `if((lane&17u)==0u)` 与 `tok_oob_u` 未动；`imgout` 的
`tok_base+0/128/256/384` 未动。

## 问 2 — 删了什么真实工作（只算正常执行路径）

| # | 删的东西 | 数量 | 位置 | 依据 |
|---|---|---|---|---|
| 1 | `sel acc0..acc3`（操作数交换） | **136 条 ISA sel**（SPV `OpSelect` 61→1，−60） | 4 个分母块 28 步 × 4 + `nr_pool_natural` 12 | `tools/sim_delete.py`：68 个 `add acc,acc` 对，每对 2 条 sel；`tools/spv-delta.json` |
| 2 | `bool lower=(lane&N)` 谓词与其掩码 | 29 处（SPV `OpIEqual` 32→3，`OpBitwiseAnd` 45→16） | 同上 | 每个块 4 个不同掩码（8/2/4/1）+ pool 的 16 |
| 3 | 29 个局部 `bool` 在 SPIR-V 的变量流量 | `OpVariable −29`、`OpLoad −149`、`OpStore −29` | 同上 | glslang 把 `bool lower` 降到局部变量；IGC 已把它 SSA 化，故**ISA 侧预计 0 收益**（见 COST-LEDGER 的 unknown） |

**不计入**的东西（避免虚报）：

* 376 条 `if(debug) coopMatStore` 的调试转储：本夹具 `debug=0`，早就不执行（`tools/exec-mask.json`）。
* `sync.nop` 177 条：调度提示，源码不可控。
* 任何除法/开方：8 `math.inv` + 16 `math.rsqt` **一条都没删**（§3 冻结）。

**必要性核验**：68 对里每一条 sel 的定义到对应 add 之间**没有第二个读者**（`tools/acc_check.py`：
`sels with an extra reader before the add: 0`），所以删掉后 IGC 不可能把选择搬到别处重建。

## 问 3 — 重叠：原来靠什么并行，改完还剩下什么

| 工作块 | 生产者 | 最后消费者 | 覆盖者（谁保护供料） | 依赖类型 |
|---|---|---|---|---|
| 4 个分母块 A/B/C/D | `p00..p13`（已 exp） | `inv` → `p*inv` | 彼此**完全独立**（A/B 读 p0x，C/D 读 p1x；写不同分量） | A/B 与 C/D 之间无 RAW；块内 `d.x`/`d.y` 两条链独立 |
| 每块 7 步归约 | 上一步的 `d` | 本步 `d` | 步间是**串行 RAW**（这不可避免，是求和本身） | RAW；本次删除只把每步的 `sel→add` 变成 `add` |
| `nr_pool_natural` | `oc` 窄化 | `pooled[]` 写 | 与分母块无关（不同阶段） | WAR：`pooled[]` 槽位互不重叠 |
| PV dpas 16 条 | `p*inv` | `tc00..tc11` | 8 个累加器并行 | RAW（每个 acc 一条链） |
| 输出 dpas + `nrh_narrow` | `tc` → `ctx` → `oc` | `pooled`/`imgout` | 4 个 oc 累加器 | RAW |
| shK/shV 往返 | `store.slm`（16） | `load.slm`（16） | 唯一 `sync.bar`(0xEFE0) + 4 `sync.allwr` | 跨 lane WAR，本次不动 |

要害：**每 lane 独立链数 26 → 26**（`tools/sim-delete.json`）。删除的 sel 全部是
「一条链内部的串行选择」，不是并行链本身，因此不会出现 n28 的 4→1 塌陷（L25）。

## 问 5 — 是否会真落到 native（只写预测与判据）

见 `NATIVE-PREDICTION.md`（逐条可观察点 + 「看不到就等于未实现」的判据）。
一句话：`sel` 必须从 **376 掉到 240±8**，且 `math.inv`=8、`math.rsqt`=16、`dpas`=128、
`send.slm`=27、`max_r`≤127、scratch=0 必须**不变**。

已在本机用 CPU 工具验证的落地证据（不是预测）：

* 父字节复现：`parent-rebuild.spv` = `c12c0f9d…`（与链头 SPV 逐字节相等，`decorated_match=true`，NC 189/189）。
* 候选 SPV 过 `spv_validate_cpu.exe`：`result=0`。
* SPV delta：`OpSelect 61 → 1`，浮点 opcode 313 → 313（**没有一条浮点运算变化**）。
* plan 只换 1 行，`cpu_check` = `CPU_PLAN_OK 152 rows, 232 passes, 502 buffers`。

## 问 6 — 整体是否更快：要测什么、用什么臂、怎么归因

* **测什么**：PASS 0 的 `XVE_STALL_ALUWR`（父 0.385039 ms，全帧最大单项）折算毫秒 + ordinary 帧时。
* **用什么臂**：`base` = `accepted/n29-f01-alu-chain-20261027/plan.txt`；`cand` = 本卡 plan。
  两臂只差 PASS 0 的 SPV 路径（`GPU-REQUEST.json` 的 `plan.diff_rows=[504]`）。
* **归因顺序（合同 §8.5）**：先看 `sel` 是否 376→240±8（A 类判据），再看两个金帧，最后才看毫秒。
* **预期**：链上 ALU 当量 −128/1256 = −10.2%，加权链深 −44 周期；折算到 ALUWR 约
  **−0.01…−0.04 ms**（`DPAS-CHAIN-AUDIT.md` §4 的份额模型）。**没有删任何除法**，
  所以不应期待 n29 那种 +0.080。
* **门槛**：<0.03 ms 按 L13 需第二批平衡批次复现；本卡不因单批次的毫秒数被采纳或否决。
