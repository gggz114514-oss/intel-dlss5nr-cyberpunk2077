派发形状 `grid=(3,32,1)`、`local_size=256`、`live=pc.p0.x=288`（8 个 PASS 的 `PUSH` 全部为 `288 320 0 0`，`p0.w=0` 无 debug store）。

|---|---:|---:|---:|---:|---:|---:|

* **A 侧逻辑读 = 72 MiB / 派发**（唯一 2.25 MiB ⇒ 被 32 个 N 片各读一遍，32× 重复）；
* **B 侧逻辑读 = 191 MiB / 派发**（唯一 8 MiB ⇒ 24× 重复：3 个 wg.x × 同一 WG 内 8 个 SG 读同一块 32 列 × 4096 K = 256 KiB）；
* 每派发 **13.2 M 指令槽 / 160 个 SIMD32 = 82.6 k 周期 ≈ 0.041 ms @2.0 GHz**，而 `PASS-TIME-RANKING` 的单派发隔离时间是 **0.0833–0.0864 ms** ⇒ 这个核约有一半时间在等，不是纯发射受限。

### 0.3 预设方向逐条定价（按卡要求先定价再动手）

**(1) 双 B bank / 权重复用 —— 有三条实现路径，全部按证据否掉**

* 现状已经复用了：快速路径里同一个 B 片喂 **2** 个 A 片（mA 与 mB），即 M 对偶 2× 复用。
* 想再翻倍只有三种做法：
  a) **每 SG 更多 M 行**（S64 形态）：+4 个累加器 = +16 GRF，活值从 16 涨到 32 GRF。`work/dsh-fp16-same-family-20261023` §41/42/45 六次实测：S32/K11 +0.2109（唯一正向）、S64/K11 +0.1375、S32/K09 −0.0435、S32/K14 −0.0832、S32/K23 −0.0294、S64/K09 −0.4103；n11 §0(b) 已判“原样重做属已测候选”。
  b) **K=32 的 coopmat**（设备 tuple `M8 N16 K32, A=7 B=7 C=9 Result=9` 存在）：权重布局 `W[N/32][K/16][32][16]` 使 (32 n × 16 k) 的 1024 B 连续块正好覆盖 bA0+bA1 与 bB0+bB1 两组 ⇒ 可把 2 条 512 B 消息并成 1 条 1024 B。**否决：K=32 的 DPAS 把 32 个乘积累加进 C 的顺序与 2×K16 串接不同，直接违反合同 §3“每个输出的 K 累加顺序不变/舍入点不变”。**
  c) **跨 SG 用 SLM 交换权重片**：按 n17 教训，1 片片段走 SLM = 8 条消息；本核现在 **SLM=0、barrier=0**（SPIR-V 无 Workgroup 变量、ISA 无 `barrier`），加了就是新增 2 个 WG 屏障 + 每片 8 条消息；n13-vit-attn 在反方向上实测 −0.113 ms。
* 结论：**寄存器预算不是瓶颈（父已用到 r254），瓶颈是数值顺序与已测负结果**，本卡不动权重侧。

**(2) 累加器/片段的 SLM 往返 —— 已经不存在，定价后无事可做**
`native-capture.json`：`Workgroup Memory Size 0`、`Scratch Memory Size 0`；SPIR-V 存储类普查（`build/spv-census.json`）无 Workgroup、无 Private 变量；ISA 无 `barrier`/`fence`。T2 direct-epilogue 变体（2026-10-18，见头注释）已把 128 条 shared store + 128 条 shared load + 每 (group,side) 2 个 workgroup 屏障删掉，`scratch` 4096 B 消失。父已经站在这条路线的终点。

**(3) 交织 mov 的来历 —— 用 ISA 定位，不猜源码**
`_tools/movcensus.py`：345 条 `mov(32)` 的源分三类 ——
(i) **218 条**源在 send 返回窗口里（`:hf` 96 + `:f` 122 的一部分）：把 B 片返回值搬进片段槽；
(ii) 快速路径**回边**处的 32 条 `:f`：DPAS 结果搬进长寿“家”寄存器（每迭代 96 条 = 64 `:hf` + 32 `:f`）；
(iii) 受护循环里每 16-K 步 **16 条**：8 条“家→工作”（`r3..r17 ← r130..r136,r122..r128`）+ 8 条“工作→家”，即 **循环内判定造成的 join**。
动态合计 **956,416 条 mov(32)/派发**，其中 **529,408 条（55%）集中在 128 个受护 SG**（每 SG 4,136 条，8.08 条/DPAS；快速 SG 只要 824 条，0.80 条/DPAS）。

**(3′) 卡的前提要修正（L10）**：卡写“contract mov32/dpas 已经 2.27（判定已在循环外）”。
这个 2.27 是**静态**比值，把三条代码路径混在一起；**动态**比值是 1.62，而且 55% 的动态 mov(32) 长在那条**判定仍在循环内**的受护路径上。判定在循环外只对快速路径（2/3 的 WG）成立。
所以本卡**不做** join 消除（那是 n11/n11b 已测的机制，卡与合同 §1 都禁止重做），而是**把跑那条路径的 SG 整批消掉**。

### 0.4 因此选中的搬运：M 对偶跨距 64 行 → 8 行（pair compaction）+ 全死对偶早退

父的对偶是 `(mA, mA+64)`：一个 WG 管 128 行，8 个 SG 各拿一段 8 行（覆盖 64 行）+ 一段 +64 的 8 行（覆盖另 64 行）。
`live=288` 时最后一个 WG 片（行 256…383，grid.x=2）里有 **4 个“半活”对偶**（mA=256…280 活、mB=320…344 死）和 **4 个“全死”对偶**。后果是：
* 32 个 WG（1/3）必须走受护循环：34.1 instr/DPAS（快速路径 19.6），每 16-K 步 16 条 join mov + 2 条谓词跳转；
* 128 个 SG（1/6）**一条 DPAS 都不做**，却把整个 K 循环的宽消息发完：每 SG 512 条 × 512 B = 256 KiB，每派发 32 MiB。

候选把对偶改成 `(mA, mA+8)`：一个 WG 仍然是 128 行，由 8 个**相邻 16 行**对偶铺满；`live=288 = 18×16` 恰好整除，于是**没有任何 SG 半活**，最后一片只剩 2 个完整对偶 + 6 个全死对偶，后者在 K 循环外 `return`。
这不是 join 消除（受护循环源码一行未动，仍作为非 16 对齐 live 的回退路径），而是**让那条路径在本 plan 下不可达**，并删掉空转 SG 的全部发射。

## 1. 映射：每个 (lane, component) 代表哪个 (token, channel)

### 1.1 形状（plan 的 `PUSH`/`BIND` 反推 + 源码）

`PUSH 288 320 …` ⇒ `live=288`、`p0.w=0`；`BIND 4 = 2359296 B` = 1,179,648 half = 288×4096（`aHidden`）；`BIND 5 = 589824 B` = 294,912 half = 288×1024（残差 `y`）。
`grid=(3,32,1)`、`local_size_x=256` ⇒ 96 WG × 8 SG = 768 SG。
stage 1：`K=4096`、`N=1024`、`M=288`；`n0 = wg.y*32`，每 WG 32 列；每 SG 两个 8 行块 × 32 列。

    sg = gl_SubgroupID (0..7)        n0 = wg.y*32
    父： mA = wg.x*128 + sg*8 ,  mB = mA + 64
    候选：mA = wg.x*128 + sg*16,  mB = mA + 8

| 累加器 | 行 | 列 |
|---|---|---|
| accA0 / accA1 | mA … mA+7 | n0…n0+15 / n0+16…n0+31 |
| accB0 / accB1 | mB … mB+7 | n0…n0+15 / n0+16…n0+31 |

`coopmat-properties.json`（同捕获目录）：设备支持 `M=8,N=16,K=16, A=0(row-major), B=0(column-major), C=1, Result=1` ⇒ 一条 `dpas.8x8` 就是 8×16×16；`(16|M0)` 执行掩码意味着 **16/32 lane 有效（50% 通道利用）**，这是父的既有形状，本卡不动。

### 1.2 epilogue 的 (lane, component) → (row, col) 一一映射（未改，逐条枚举）

`vit_direct_epilogue`：`col = n0+side*16 + (lane&15)`，`row0 = m + (lane>>4)`，`t = row0 + 2*ci`，`ci = 0..acc.length()-1 = 0..3`。

| lane>>4 | ci=0 | ci=1 | ci=2 | ci=3 |
|---|---|---|---|---|
| 0 | row m+0 | m+2 | m+4 | m+6 |
| 1 | row m+1 | m+3 | m+5 | m+7 |

* 行：8 个值各出现一次（`(lane>>4, ci) → row` 是双射）；
* 列：`lane&15` 覆盖 16 列各一次；
* 单元数：32 lane × 4 component = 128 = 8 行 × 16 列，**重复 0、漏 0**；
* store：`coopMatStore(res, y, p5.y + m*1024 + n0 + side*16, 1024, RM)`，`side=0/1` 各写 16 列。

### 1.3 grid 级覆盖（枚举，不是抽样；`_tools/proof.py`）

48 个行块（384 行 / 8），每个块恰好被一个 SG 写一次（两种映射都是双射）：

| live | 映射 | 覆盖行 | 重复 | 漏 | 越界写行 |
|---:|---|---:|---:|---:|---:|
| **288（本 plan）** | 父 | 288 | 0 | 0 | **0** |
| **288（本 plan）** | 候选 | 288 | 0 | 0 | **0** |
| 289 | 父 / 候选 | 288 | 0 | 0 | 289…295（继承父行为） |
| 287 | 父 / 候选 | 288 | 0 | 0 | 287…295（继承父行为） |
| 16 | 候选 | 16 | 0 | 0 | 0 |
| 8 | 候选 | 8 | 0 | 0 | 0 |

`live=288 = 18×16` 是候选的关键性质：18 个**完整**对偶；父在该值下产生 4 个半活对偶（见 §0.4）。

### 1.4 尾块

* 本 plan 8 个派发全部 `live=288`，无尾部行、无 clamp 被触发、无越界写；
* 若 live 不是 16 的倍数，恰有 **1 个**部分对偶，它照旧走父的受护循环（源码原样保留），读集合与写域与父逐条相同；
* live 不是 8 的倍数时 `coopMatStore` 仍按整 8 行切片写（父行为，epilogue 未改）。

## 5. 是否真落到 native（预测 + 判据，不写“已证明”）

**信号很弱，必须先说清**：本卡的机制是“某些 SG 不再执行那条路径”，**静态**计数几乎不动（没有消息/DPS 被删出模块，受护循环源码原样保留）。所以静态 ISA 只能证明“候选确实被编译进去了”，不能证明“动态省了”。逐条判据见 `NATIVE-PREDICTION.md`，摘要：

1. **落地判据（可证伪，静态）**：`shl (1|M0) …, 3:w`（`sg*8`）必须变成 `4:w`；`add3 … 64:w`（`mB = mA+64`）必须变成 `8:w`。若 ISA 仍是 `3:w`/`64:w`，说明跑的不是候选 SPV（A 类实现未落地）。
2. **不回归判据（静态）**：`dpas` 仍 152、`load.d32x8` 仍 76、`load.d32x8t` 仍 608、`store` 仍 32、`Scratch 0`、`Workgroup Memory 0`、`Basic Block Count` 30→31、`Instruction Count` 3458→3462…3466（+2 cmp +1 and +1 jmpi，允许 ±2）。
3. **机制判据（静态可达性 + 动态资源）**：用 ISA 里的 `live` 比较对象（`p0.x` = 288）与新的行公式可枚举出 **24 个 (wg.x,sg) 组合里 0 个半活、6 个全死**（PROOF.q1.enumeration）；配 `resources` 臂的每派发 GpuTime 与 `ordinary` 判收益。
4. **看不到即 A**：若上一批 `shl`/`add3` 立即数没变，或 `Basic Block Count` 反而暴涨（>40），或 `Instruction Count` 涨 >200，判 A 类（实现未落地/被 IGC 重构反噬），不做毫秒倒推。

## 6. 整体是否更快：本卡测什么、怎么归因

* **族内规模**：F13 contract 8 个派发，`PASS-TIME-RANKING` 求和 fixed **0.677131 ms** / fb2 **0.678070 ms**，占 19.145 ms 帧的 **3.54%**（对照：F13 expand 8×0.0689=0.551 ms、F16 projection 8×0.0284=0.227 ms —— contract 是 ViT FFN 三块里最大的一块）。
* **要测的整体量**：`ordinary` 双臂 6 组交替 × 30 样本（`warm 1 / reps 30 / feedback`，末帧 gold `2b63d4ba…`）。gate（fixed/fb2）只做数值门，不做性能归因。
* **归因上限**：模型给的是 **每派发指令槽 −12.42%**、**宽消息 −25.2%**、**B 侧逻辑字节 −25.2%**。若派发是纯发射受限，−12.4% ⇒ 每派发 −0.0105 ms ⇒ 每帧 −0.084 ms；但实测 IPC 只有 ~0.49（0.041 ms 的发射下界 vs 0.0846 ms 实测），一半时间在等，所以**帧级预期显著小于 0.084 ms**，落在 0.02–0.08 ms 区间，与 n11 测到的 +0.0386 ms 同量级。
* **不能承诺**：不能把 12.4% 指令折算成毫秒，也不能说“删了 48 MiB 就一定快”（L12：被并发隐藏的消息不付钱）。
* **若 INDISTINCT**：按 L8 成包，与 n11（expand 8 PASS，已建）合成 **16 PASS 包**再判一次；两者机制独立（n11 去 join，本卡去半活/空转 SG），符合“同族同形状成包”的口径，且不与 pkg-vit-16pass（expand+projection）重复。
* **反证观察（判 B 类副作用的抓手）**：若 `resources` 显示每派发 GpuTime **上升**而指令数确实下降，则原因是第三片 WG 的自身延迟 +14.9%（17,474→20,072 条/SG）没被空闲槽位吸收；此时按 B 类改用“第三片仍做单块、但不进受护循环”的变体（需要第三条 K 循环，本卡未做）。
