## 0. The transformation in one paragraph

The parent produces the 128 hidden channels of the C32 FFN expand into
`shared int8_t sE8[8192]` (16 `nr_i8_put_e` calls, 64 int8 byte stores per lane), publishes them
with `subgroupMemoryBarrierShared(); subgroupBarrier();`, and only then runs the contract as a
4-iteration `kg` loop that loads `B32x16` int8 fragments back out of `sE8` with `coopMatLoad`
(16 `coopMatMulAdd` in total). C2 deletes the staging: every 32 hidden features are produced as
four `CH8x16` half fragments, quantised once each into four `uint` code words, permuted into one
in-register `B32x16` int8 fragment, and consumed immediately by the four long-lived INT32
accumulators. The int8 values the MMA sees, the A operands, the accumulation order and the
epilogue are unchanged.

## 1. Coordinate / component graph (contract item 1)

Proof: `evidence/COORD-PROOF.json` checks **C1, C1b, C2, C3, C3b, C4, C5, C6, C7**.

### 1.1 The two sealed maps

`CH8x16` (`coopmat<float16_t, Subgroup, 8, 16, Accumulator>`), from the sealed
`register_handoff.glsl` formula `nrh_coord_CH`, verified against the measured B580 map
(128/128):

```
component c of lane L  ->  row = 2c + (L >= 16),  col = L % 16
```

`B32x16` (`coopmat<int8_t, Subgroup, 32, 16, B>`), from the measured map
`I8-ABI-MEASURED.json` (512/512):

```
component c of lane L  ->  source lane  ((L & 1) << 4) | (L >> 2)  +  8 * (c & 1)
                           source byte  (c & 2) | ((L >> 1) & 1)
                           source word  c >> 2          (0..3 = the four CH fragments)
```

Lane bit 0 is the measured *feature parity* bit: it travels as the 16s bit of the source lane and
therefore selects which of the two CH rows of a pair (`2b` vs `2b+1`) the byte carries. Lane bit 1
selects the byte's high bit (row group 0..3 vs 4..7); lane bits 1..2 carry the token's low half.
The destination component index decomposes exactly as
`frag = c>>2`, `byte = (c&2)|((L>>1)&1)`, `half = c&1`, so the whole permutation is 8 shuffles
(two per word) plus 16 local byte extracts, and it is a **bijection** over the 512
(word, lane, byte) triples (C3b).

The sealed generated helper `generated_i8_adapter.glsl` (sha `5f6db8b4…`) is table-driven with
exactly this content — `I8B_FRAG`/`I8B_LANE`/`I8B_BYTE` agree with the closed form on all
512 × 3 entries (C3). C2 uses the closed form because the table form indexes `const uint[16][32]`
with a dynamic index, which forces a function-scope copy of a 6 KB constant table; the
closed form is the same permutation with no table.

`A8x32` is a **different** map (only 16 of 128 (lane, component) pairs coincide with CH — C1b), so
an A fragment can never be assembled from CH code words. C2 never does; all A operands stay
`coopMatLoad` from `w8`.

### 1.2 What each fragment means

For K32 step `kg`, fragment `j` (0..3) carries hidden features `32kg + 8j … 32kg + 8j + 7` for all
16 tokens: byte `b` of that lane's word is the code of
`E[32kg + 8j + 2b + (lane>=16)][lane % 16]`. Therefore the two halves of the K32 dimension are
fragments `{4kg, 4kg+1}` (features `32kg … 32kg+15`) and `{4kg+2, 4kg+3}` (`+16 … +31`) — the same
two expand feature groups the parent computed for that K range (FULLK K3).

### 1.3 Parent shared layout, and the equality that matters

The parent writes (C4, 2048/2048):

```
nr_i8_put_e(feature f, token t)  ->  sE8[(f/32)*512 + t*32 + (f%32)]
coopMatLoad(xb8, sE8, sg*2048 + kg*512, stride 32, LCOL) element (k,n)
                                 ->  sE8[kg*512 + n*32 + k]  =  E[kg*32+k][n]
```

The contract's B matrix is therefore `B[k][n] = E[kg*32+k][n]`. C6 compares the matrix the join
builds with the matrix `coopMatLoad` reads, **in the parent's own `sE8` address space**, for all
4 × 512 elements: 0 mismatches. C7 confirms the accounting is exact — 128 hidden × 16 tokens are
produced once and consumed once, no duplication and no dropped channel.

**Conclusion item 1: closed. The register B32x16 is the same logical matrix, element for element,
as the one the parent loaded from shared memory.**

## 2. Quantisation direction, scale source and rounding points (contract item 2)

Proof: `evidence/SCALE-ROUND-PROOF.json` checks **S1..S5**.

### 2.1 Scale source

One resource, unchanged: `layout(set=0,binding=6) readonly buffer C32I8Scales { float fsc[]; }`,
656 B / 164 f32 per position.

| index | meaning | used by |
|---|---|---|
| `fsc[0]` | `sX` | dequant taps only, indirectly |
| `fsc[1]` | `invX` | **X quantiser** `nr_i8_put_x` (unchanged) |
| `fsc[2]` | `sE` | contract dequant through `fsc[132+o]` |
| `fsc[3]` | `invE` | **E quantiser** — `fsc[3]` in both parent and candidate |
| `fsc[4..131]` | `sX*sWe[f]` | expand dequant, `nr_i8_deq(..., 4)` with `mbase = 8*frag` |
| `fsc[132..163]` | `sE*sWc[o]` | contract dequant, `nr_i8_deq_add(..., 132)` with `mbase = 8*o` |

`invS` for the E path is `fsc[3]`, fetched from binding 6 at offset 3 — the same resource, the same
offset, the same value as the parent's `nr_i8_put_e`. The candidate even hoists that one fetch
(`const float c2_inv_e = fsc[3];`) across the 16 pack calls; the parent re-read it per call. Both
read a `readonly` buffer that the shader never writes, so the value is the same in every read.
The X path (`fsc[1]`) is not touched at all.

`sE`/`invE` therefore remain **same-source, same-value** in the two modules: nothing in C2 moves,
rescales or reinterprets them.

### 2.2 Rounding points, in order

| # | operation | parent | candidate |
|---|---|---|---|
| 1 | int32 accumulate | MMA | MMA (same operands, same order) |
| 2 | int32→f32 | exact (|v| ≤ 2,064,512 < 2^24) | same |
| 3 | × dequant tap | one RN mul, single multiply so no contraction is possible | same tap, same expression |
| 4 | f32→half narrow | `nrh_narrow` (NRH_CH conversion) | same |
| 5 | activation `nr_act_h` | clamp + 2 fma + 1 mul in f16, one rounding per op | same, same order |
| 6 | `float(v) * invE` | `precise float c = float(v) * inv;` inside `nr_i8_code` | identical, the same function |
| 7 | `roundEven` | `nr_i8_code` | identical |
| 8 | clamp to ±127 | `nr_i8_code` | identical |
| 9 | f32→int8 | `int8_t(...)` truncation of an already-integral value | `int(...)`, then `& 0xFF` byte insert |
| 10 | transport | byte store to shared / byte load by `coopMatLoad` | int→uint byte insert, shuffle, byte extract, sign extend |
| 11 | contract epilogue | `f*scale` mul, `+ seed` add, then one narrow | identical call `nr_i8_deq_add(ca_o, 8o, 132, seed_o)` |

Steps 6–8 are the *same function* `nr_i8_code` on the *same* `float16_t` values with the *same*
scalar; steps 9–10 are integer bit transport. `int(v) & 0xFF` and its inverse
`v >= 128 ? int(v)-256 : int(v)` are exact inverses for every value in `[-127,127]`, so the byte
that reaches the MMA has the same bit pattern and the same value as the parent's stored `int8_t`.

The 64 quantisations per lane are unchanged in count and in order (16 fragments × 4 components,
component order 0,1,2,3 — the same order `nr_i8_put_e` used).

**The seed is not moved.** `NRH_C seed0..seed3` are still computed before K0 from the *original*
FP16 `x0..x3` widened by `nrh_widen_exact`, still survive the whole K=128 accumulation, and are
still added exactly once, after the full-K dequant, by the same `nr_i8_deq_add`, with the same
`precise` two-step (`p = f*scale; q = p + seed`) and the same single narrow afterwards (K6).

### 2.3 Observation on the frozen parent's scale units (recorded, not repaired)

`evidence/SCALE-ROUND-PROOF.json` check **S5** records an arithmetic relation in the *frozen*
scale pack, for the record only:

```
sX*invX = 127.00000219      sE*invE = 127.00000923
```

The dequant taps fix the convention unambiguously: `fsc[4+f] = sX*sWe[f]` with
`sWe[f] = absmax_We[f]/127` is the standard 127-scaled pair dequant, which pairs with
`invX = 127/absmax_X = 1/sX`. The buffer instead holds `invX = 127/sX`. Under the stored value any
`|E| ≥ sE = 0.03617127` (and any `|X| ≥ sX = 0.06625246`) saturates at ±127.

This is a property of the **parent's** frozen pack (`c32_b1_scales.f32.bin`, sha `f3053c8c…`,
`sx/invx` cross-checked against `C32-I8-PACKS.json` and `C32-I8-SCALE-STEPS.json`). C2 is
scale-blind: it copies `fsc` verbatim with the same indices, so **C2 ≡ parent for every input
regardless of this relation**. Whether the frozen parent's numeric gates pass under it is a GPU
question and is *not* adjudicated here. Repairing it would change numerics and is out of card
scope.

**Conclusion item 2: closed. Same resource, same offset, same value, same rounding points, same
seed position.**

## 3. Full K = 128 (contract item 3)

Proof: `evidence/FULLK-PROOF.json` checks **K1..K6**.

```
K = 128 hidden features = 4 K32 steps x (4 CH8x16 fragments x 8 features) x 16 tokens
step kg      : features 32kg .. 32kg+31, produced by parent expand groups 2kg and 2kg+1
A operand    : w8[16384 + (o*4 + kg)*1024], o = 0..3   (identical index expression, K1/K2)
accumulators : ca0..ca3, one per output group o; each receives exactly 4 MMA terms (K4)
order        : kg outer 0,1,2,3; o inner 0,1,2,3 — the parent's `kg` loop order, kept (K2)
epilogue     : one dequant multiply + one seed add per accumulator, after all 128 terms
```

The parent's `kg` loop is one SPIR-V body executed four times; C2 emits four straight-line step
blocks with the same constants. The *dynamic* counts are therefore identical: 16 expand MMA +
16 contract MMA, 16 expand A loads + 16 contract A loads, in both modules.

C2 does **not** re-associate the accumulation even though it is entitled to: the int32 bound is
`127*127*128 = 2,064,512 < 2^24 < 2^31` (K5), integer addition is exact and order-independent
here, and the single dequant multiply after the whole K is the reason the order would not matter.
The parent order is preserved anyway, so the argument does not depend on that freedom.

**Conclusion item 3: closed. K32 orthogonality covers all 128 accumulation terms, in the original
order, with the original single dequant and single seed add.**

## 4. What C2 deliberately does *not* do

- does not touch the genuinely cross-subgroup `shK`/`shV` publication or the `barrier()` at the end
  of the body (SPV barrier census: the device-scope `OpControlBarrier` survives; only the
  subgroup-scope E publication pair disappears);
- does not keep 128 hidden channels live: at most the four fragments of the current K32 step exist
  (`e0..e3` scoped to the step block), i.e. 32 hidden features + 16 tokens at a time;
- does not pre-resident any weight: every A block is loaded at its original point, per step;
- does not change bindings, push constants, the debug ABI, or any FP16 attention tail instruction.

## 5. Gap register

`evidence/DESIGN-GAP.json` is empty: every item above closed on CPU. The residual unknowns are
explicitly GPU-side and are listed there as `gpu_only_unknowns` (they are not design gaps):
native register/scratch behaviour under the longer accumulator live range, and the numeric gate
itself. Per §4 of `CONVENTIONS.md`, having no GPU means the numeric gate is **never** reported as
passed.
