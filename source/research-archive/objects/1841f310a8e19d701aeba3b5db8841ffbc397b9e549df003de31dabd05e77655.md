### 528 条 mov 的来源（`zip_blocks.py` 与 `isa_census.py` 的机器输出）

这 528 条不是 A 交接，也不是窄化，而是**一次固定置换**：

```
mov (32|M0) rD.0<2>:uw  rS.0 <32;16,1>:uw
mov (32|M0) rD.1<2>:uw  rS.16<32;16,1>:uw
  =>  dst GRF pair (D, D+1) <- src GRF pair (S, S+1)，字粒度二路交织：
      dst[D].dword[j]   = ( src[S].word[j],   src[S+1].word[j] )   j = 0..7
      dst[D+1].dword[j] = ( src[S].word[8+j], src[S+1].word[8+j] )
  该置换在每对 GRF 上是**对合**（做两次等于没做）。
```

`dst` 基址永远偶数、相邻块基址相差 2，`src` 永远成对 `rS.0 / rS.16`（= `rS`, `rS+1`）：
这就是「把线性行主序矩阵的两个相邻行压进一个 dword」——即 DPAS 操作数（VNNI）布局。

**68 个 zip 块 / 528 条，按进料者分类（机器枚举，见 `zip_blocks.py` 输出）：**

| 进料 | 块数 | mov 数 | 对应源码 |
|---|---:|---:|---|
| `send.ugm … load.ugm.d64x64t`（`wb` 权重块读） | 39 | 312 | **48 个 `coopMatLoad(w,wb,+off,16u,LROW)`**（NRH_B 16×16）：expand 16+16、QKV 12、output 4 |
| `send.slm … load.slm.d64x64t`（`shK`/`shV` SLM 块读） | 17 | 136 | 8 个 `coopMatLoad(b,shK,…)` + 8 个 `coopMatLoad(b,shV,…)` |
| `dpas.8x8` 结果（f32 累加器） | 7 | 56 | `nrh_to_A(nrh_narrow(sc))`：`ea0/ea1`、`ca00..ca11` |
| `mul`（`x*scale` 残差种子） | 4 | 16 | `nrh_to_A(nrh_narrow(nrh_widen_exact(x*scale)))`：`ya00..ya11` |
| 尾块（3+1） | 2 | 8 | shK/shV 尾块 |
| 混装 | 1 | 16 | PV 早期 B |

**1:1 计数交叉验证**（`isa_census.py` 的 send 消息表）：

```
48  load.ugm.d64x64t  rd:8   <->  48 个 wb  NRH_B 站点
16  load.slm.d64x64t  rd:8   <->  16 个 shK/shV NRH_B 站点
 4  load.ugm.d32x64t  rd:4   <->   4 个 imgin NRH_CH 站点（且带 tok_oob 的零填充分支）
64  load.ugm.d32x8t  rd:1   <->   8 个 stride-0 `scale` NRH_CH 站点 × 8 行
64  load.ugm.d32x16t rd:1   <->   8 个 stride-64 `fb` bias NRH_C 站点 × 8 行
```

⇒ **定位结论：528 条 16-lane 交织 mov = `coopMatLoad` 的「线性行主序块读返回 → DPAS
操作数（VNNI）布局」转换，8 条/块读。** 它由**内存布局**驱动（只读模型缓冲 `wb` 的
行主序），不是由 A 交接驱动 —— 与 n01 的读法一致，本卡用枚举把它钉死到 68 个块、
4 类进料，并证明 64 个它认为"已 store-in-layout"的 K/V 交叉 SG 交换**在 load 侧仍然
要付 8 条/次**。

## 1. 本卡改动期望在 ISA 里看到什么

改动：4 个 stride-0 `scale` 片段从"每站点各读一次（共 8 次）"变成"每个片段读一次（共 4 次）"。
SPIR-V 侧实测：`OpCooperativeMatrixLoadKHR 84 → 80`，其余 128 muladd / 60 store 不变。

|---|---:|---:|---|

### 「看不到即 A 类」的阈值（写死）

- **A 类**：`send.ugm` 下降 < 24 条（含 0）。即驱动已经把 8 个 `scale` 站点 CSE 成 4 个；
  本机制在源码层成立但在该身份上不形成处理 ⇒ 记"实现未落地"，**不再换写法重跑**。
- **B 类**：`send.ugm` 下降 ≥ 24，但 `scratch` 从 0 变正，或 `mov` 上升 > 32，或
  `dpas`/`sync.bar`/`math.rsqt` 任何一项变化 ⇒ 按副作用修一版（把 4 个 `scale` 片段
  拆回去一个，只保留最贴近的两个站点）。
- **C 类**：A/B 都不成立（消息确实降了、资源干净）但 ordinary 计时落在噪声里 ⇒ 按形状
  归因，不外推成方向禁令。

## 2. 为什么预测 `mov` 基本不动（并给出可推翻它的观测量）

- 528 条 zip mov 全部来自 `d64x64t` 块读（48 ugm + 16 slm）。本卡**一条都没有删**：
  SPIR-V 里 NRH_B(16×16) 载入 64 → 64 不变（`shape_census` 实测）。所以 528 必须原样。
- 被删的 4 个站点是 `d32x8t`（32 B，一行 GRF）流，8 条消息的返回**直接落在**目标 GRF
  上（父 ISA 里 `mov (W) dst<1> src<1;1,0>` 483 条里含这些搬移）。删站点后这些搬移
  随之消失或被前一个站点覆盖，量级 ≤ 32 条。
- 因此 `mov` 的可观测区间是 **−0 … −32**；若 `mov` 反而上升，说明驱动把 4 个片段的
  活值范围拉长后增加了拷贝 ⇒ B 类。

## 3. 主代理要测什么、怎么归因（第 6 问）

1. **native**（`arms = base, cand`；base = 链头 plan `25cd7faf…`，cand = `715ade76…`）：
   先看 §1 的硬不变量（dpas 128 / sync.bar 1 / math.rsqt 16 / scratch 0 / SLM 8192），
   再看 `send.ugm` 是否进 **[−32,−24]**。不进 ⇒ A，停。
2. **resources**：只确认 scratch 0（这是本卡唯一有真实风险的成本项）。
3. **gate**：`fixed` 与 `fb2` 两套 gold（合同 8.1）必须逐字节 PASS。
   本卡只改"同一片段读几次"，不改任何 FP 表达式，所以 gate 失败即实现错误（E 类）。
4. **ordinary**：`warm1 / reps30 / feedback` 两臂 6 组交替。本卡覆盖 7/232 个派发、
   32/570 条消息（5.6%），单卡期望收益量级 ≈ 0.03–0.10 ms；若 CI 跨 0 按 D 记，
   但**不要把 A 类结果写成"方向无效"**。
