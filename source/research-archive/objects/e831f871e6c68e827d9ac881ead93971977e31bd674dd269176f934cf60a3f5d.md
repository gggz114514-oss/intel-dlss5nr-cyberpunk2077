# F20 score owner：AMD 对照驱动的生产消费改造

主审完成 AMD 工作目录及当前 C32 全族源码对照、映射证明、代码与回读。Luna 只执行指定 GPU 作业。P03 和 peer8 两版候选原文件保留。

## 已解决的代码问题

AMD 的重点是中间结果留在后继消费者的 owner；其字面的 feature×token 方向适用于 AMD C→B 片段映射，而 Intel 当前测得 C→A，保留 token×feature 更直接。F01、七 body、F2 已具备对应的 FFN/attention 直交，不重复改写。对照详见 AMD-LAYOUT-COMPARISON.md，实际工作目录哈希及十个 C32 构建配置详见 AMD-CURRENT-INPUTS.json。

F20 原 score 分割 key，而 den/PV 持有完整 key，产生 P 的 shared 交接。新 candidate.comp 将 score 的 query owner 与 den/PV 一致，Q0/Q1 复用一次加载，P 直接沿 CH→A 分量流动。保持8 SG、原 MMA/half/归约顺序，不新增权重读取。fold/FFN/QKV/norm、PV/output 算术源未改，CONTRACT-CHECK.json 独立确认。

- 独立资源回执的 pipeline38/subgroup32：Scratch Memory Size=0，Workgroup Memory Size=25088B。驱动报告 Instruction Count=4206，与反汇编行数4209属于不同统计口径，分别保留。此单帧仅验资源，不加入性能样本。
- 源级每WG删除P写8KiB+P读8KiB+重复Q读4KiB，共20KiB逻辑SLM访存；共享声明29184→25088B。score片段活值负载小计增加24B/lane，物理GRF峰值未知。

## 仍然存在的边界

这不是全C32瓶颈消失。F20的FFN activation交接、精确norm树、真实跨SG K/V共享仍保留。下一步必须针对这些现存边证明新的工作量/并行度交换，不能再重复当前已删的P交接，也不能把AMD的FP32数学或单wave配置直接移植。
