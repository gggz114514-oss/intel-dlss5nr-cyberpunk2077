## 2. The seed problem, stated exactly

The parent's C operand is not zero:

```
oc0 = nrh_widen_exact(y0 * ars)      // half multiply, exact widen to FP32
oc0 = coopMatMulAdd(w, tb0, oc0)     // + 16 products, FP32 accumulate
oc0 = coopMatMulAdd(w, tb1, oc0)     // + 16 products, FP32 accumulate
o0  = nrh_narrow(oc0)                // ONE narrow, then store
```

An INT32 accumulator **cannot** carry that seed: the seed is FP32 and the accumulator is
integer. Any attempt to move the seed into the accumulator changes the residual value, which
the GUIDE forbids ("不得悄改残差值").

## 3. INT8 EPILOGUE REFERENCE (this is the definition the segment needs)

```
seed[o,t]      = float( H(y_half[o,t] * ars[o]) )        // unchanged: same half multiply, same exact widen
acc[o,t]       = Σ_c qWo[o,c] * qC[c,t]                  // int32, exact, all 32 products
out_half[o,t]  = half( float(acc[o,t]) * (sC * sWo[o]) + seed[o,t] )
```

* one dequant multiply, one FP32 add, **one** narrow — the same shape as the parent's
  contract epilogue `nr_i8_deq_add` (`precise float p = f*fsc[..]; precise float q = p + seed;`
  then one narrow), with the output residual in the seed slot;
* the residual value is **not** rescaled, re-quantised or dropped: it is the same
  `H(Y*ars)` half value the parent uses, widened exactly as before;
* accumulation-order note: the parent adds the seed *first* and then 32 FP32 products; the
  INT8 arm sums the 32 integer products exactly and adds the seed once. The integer sum is
  exact, so the only difference is the INT8 quantization of A and B — no reordering error.

## 5. Named gaps

1. **WO INT8 weight pack**: same offline build as QKV, +4096 B per block in the `w8`
   binding (45056 → 49152 for a block that also does QKV).
2. **Context activation scale**: per tensor needs a capture of the PV output; per token would
   need the cross-lane amax of §PV and is a stage-2 item.
3. **No capture and no gate** for this segment: the epilogue reference above is defined but
   has not been run on real data — unlike QKV, there is no captured context tile in this card.
4. **Store contract**: the output stores (`tok_base + {0,8,256,264}`, stride 16, `tok_oob`
   skip) are part of this segment and must be proven unchanged, since a wrong OOB rule would
   silently drop boundary tokens.
