## 代码中已有的观测点

- 冻结游戏 backend：`@NR_WORKSPACE@/src/project/artifacts/parallel-port-20261013/backend-adapter/game-b3-21-native720-20261014/sources/port_network_bridge_backend.cpp`。`record` 路径包含 history 拷贝、控制更新、gather、按 POLICY 的清零、网络 pass、scatter 及 barrier；网络各 pass 后存在 compute→compute 内存 barrier。这些是待测项目，代码存在并不证明它们构成主瓶颈，也不授予删除同步/生命周期保护的依据。
- 该文件的 staging 上传与逐缓冲 fence 等待位于初始化路径；不能直接算成每帧开销。应把冷启动与稳态分开。
- `@NR_WORKSPACE@/src/project/src/runtime/port_network_model_runner.cpp` 已有 `--per-pass-timing`：相邻 BOTTOM_OF_PIPE 时间戳区间包含 pass 及其 barrier，池化时还可能包括该 pass 前的清零与同步；不是纯 shader 指令时间。整网 GPU 区间含网络/历史操作，上传与最终读回在该计时区间之外。它的 GPU、主机 submit/wait 与游戏帧时不能混称。
- 冻结游戏 backend 文件中未见 query pool/时间戳采集；不能把离线 runner 的开关当成游戏内已有逐 pass 计数器。网页 NR 耗时也应核对实际宏与运行分支后解释。

## 最小采集顺序

1. 协调入口分配独占 GPU 时段后，先确认唯一锁持有协议及 E 盘本地入口；冻结 runtime/构建资料仍含 D 盘绝对路径，当前未完成独立运行适配，不执行旧路径入口。
2. 首先验证 GPA 对一条明确候选的捕获、回放、coopmat 及计数器支持。先取得真实可用字段和原始输出，未通过则记录具体失败，不做一整轮无效采集。若需要独立 GTPin 包或新原生诊断候选，另在本线准备，不修改已封存候选或系统环境。
3. 在同一候选/尺寸/参数下分开保存普通执行与 profiler 执行。先形成整帧 span、网络区间、拷贝/清零/同步和逐 pass 排序；采样插桩时长不当成正常运行成绩。
4. 对实际最重的 SPV 再采可用硬件指标或 GTPin 基本块/指令证据。记录 Active/Stall/Occupancy/Barrier/SBID 等实际存在的字段；不能采的填 unknown，重叠计数不相加。寄存器/spill 不从 SPIR-V 大小或 shared 大小推成事实。
5. 两个候选分别归档，给出证据支持的优化优先级。最终收益仍按协调入口安排的同场景原生 720p 游戏 A/B、现有 NR 通道、画面/运动/历史和稳定性验收；离线诊断只用于归因。
