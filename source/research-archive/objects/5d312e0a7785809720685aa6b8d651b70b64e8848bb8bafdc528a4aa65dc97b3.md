# 工具缺陷登记（影响所有卡的可信度边界）

2026-10-24。本包复用主审计/前序工作的两个 CPU 工具，发现两处缺陷。**它们不改变任何已交付卡的
相对比较结论**（父与候选用同一工具、同一口径），但**改变"0 problems"这句话的绝对含义**。

## D1 `plan_lint.py` 的 BIND 越界检查形同虚设

文件：`work/dsh-int8-same-family-20261023/tools/plan_lint.py`，第 54–65 行。

计划里 BIND 行是 `BIND <binding> <resource> <offset> <bytes>`（5 字段）。工具却写成：

```python
res, off, length = int(w[1]), int(w[2]), int(w[3])
```

即把 **binding 槽当成 resource、把 resource id 当成 offset、把 offset 当成 length**，
并且**完全丢掉了 `bytes`**。后果：

- `res >= nb` 这条检查比的是 binding 槽与 buffer 数量，几乎永远为假；
- `off + length > sz[res]` 比的是 `resource_id + offset` 与某个 buffer 的大小，语义无意义；
- 父计划里那 16 条 `notes`（"BIND ... > declared"）就是这条错位产生的**伪告警**。

**影响**：本包此前所有"`plan_lint` problems 与父完全相同 / 新增 0"的陈述**仍然成立**
（同一工具、同一错位，父与候选可比）；但**不能**据此说"BIND 越界已验证"。
需要 BIND 边界的卡（R08、R13/R14、C2）各自另建 strict 检查（按 5 字段解析、逐条
`offset + bytes <= declared`），结果已写进各卡 `evidence/PLAN-VALIDATION.json` 或等价文件。

## D2 `spv_tools_local.result_id_of` 对协同矩阵扩展 opcode 的表是错的

文件：`build/zcode-fp16-compute-backend-20261021/scripts/spv_tools_local.py` 第 326–337 行。

`RESULT_AT_ZERO_OPS` 把 4456/4457/4458 都当成"结果在 operand 0"，实际（用 40 行探针核过）：

| opcode | 真名 | 结果位置 |
|---|---|---|
| 4456 | `OpTypeCooperativeMatrixKHR` | operand 0（类型） |
| 4457 | `OpCooperativeMatrixLoadKHR` | operand 1 |
| 4458 | `OpCooperativeMatrixStoreKHR` | **无结果** |
| 4459 | `OpCooperativeMatrixMulAddKHR` | operand 1 |

**影响**：任何直接用该表做数据流/计数分析的工具都会把 load/store 认错、把 MulAdd 漏掉。
本包自己的计数工具（`tools/verify_mma_dtype.py` 等价逻辑、各卡的自建解析器）都改用上表，
并用主审计 `FULLNET-RESIDUAL-MMA-SITES.json` 的 word offset / result id **标定过**
（同一位置解出的 result id 与审计一致）。

## 复现口径

- MulAdd 计数与 dtype 判定的权威定义：`4459`，其 operand 0 = 结果类型；结果类型经
  `OpTypeCooperativeMatrixKHR`（4456）→ component type → `OpTypeFloat`/`OpTypeInt` 宽度解析。
  `f32` 累加 = FP16 矩阵乘；`i32` 累加 = INT8 矩阵乘。
- 本包据此独立复算的结论：R08 的 d1/d2 = 6+4 条 i32、**0 条 f32**；其 producer `c128_d4_qx`
  = **2 条 f32**（归 R07）；R13/R14 的 l3/l4 = 各 2 条 i32、父各 2 条 f32。

## D3 计划的 `PASS <n>` 号不唯一

`plan-*.txt` 里 `PASS 129` 出现 5 次、`PASS 137`/`PASS 143` 各 6 次——同一 PASS 号在不同 block 里重复。
唯一键是 **pass 名 + 0 基序号**（或 `plan_order`）。任何按 "PASS n" 定位行的脚本都会拿错行；
本包所有卡都改成按名+序号定位，`collect.py`/`ticket.py` 也只用 0 基序号。

## D4 `PORT_NETWORK_1` 头字段语义

头行是 `PORT_NETWORK_1 <rows> <buffers> <passes> <outputs>`：第 3 字段是 **buffer 计数**、
第 5 字段是 **OUTPUT(dump) 条数**。追加 BUFFER 或 OUTPUT 必须同时改头，否则解析器报
`expected PASS, got BUFFER`。A1/A2/B1/B2/C2/R03/R07/R09/R12/R17/R21 的 plan 都按此规则生成并复核过。
