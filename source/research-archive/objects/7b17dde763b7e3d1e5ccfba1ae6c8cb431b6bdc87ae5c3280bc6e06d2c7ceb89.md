## 1. 这 16 条 `math.inv` 是什么：**同一个运行时除数的倒数，被展开 16 次**

源码里本 PASS 只有**一处**运行时除法（`candidate.comp` 第 61-69 行的 gather 循环）：

```glsl
for (uint e = tid; e < 4096u; e += 256u) {
    const uint s3 = e / pc.p5.x, k3 = e % pc.p5.x;      // ← 唯一除以「非编译期值」的语句
    ... nr3_gbuf[e] = x47[nr3_io_at0(px3, py3, k3, ...)];
}
```

`pc.p5.x` 是 push constant（通道数 256，运行时值）。`e/pc.p5.x` 与 `e%pc.p5.x` 被 IGC 降成
**一条整数除法序列**（商与余数同源），其中第一个算子就是 `math.inv`：

| # | 偏移 | 指令 | 作用 |
|---|---|---|---|
| 34 | `01F0` | `mov r2.8:f ← r2.4:ud` | 除数转 f32（**uniform**，1 lane）|
| 35 | `0200` | `mov r3.1:f ← 0xB4C00000` | 牛顿修正常数 |
| **36** | **`0210`** | **`math.inv (1\|M0) r6.0:f ← r2.8`** | **倒数估计（1 lane）** |
| 37 | `0220` | `mov r4.0<32> ← e` | 被除数广播（独立）|
| 38 | `0230` | `mad r7.0 ← r6.0*r3.1 + r6.0` | **倒数修正**（inv 的首个消费者）|
| 39-40 | `0240`/`0250` | `mov r10.0`, `mul r8.0 ← e * r7.0` | 商估计 |
| 41-47 | `0258`…`02B0` | `mov/mov/add/mov/mov/mov` | 余数修正的准备（e - q̂, d 的副本）|
| 48-51 | `02C0`…`02E8` | `mad/mad/add/mul` | 余数的 Newton 修正 |
| 52 | `02F0` | `xor cr0.0 ^= 0x30` | 谓词翻转（与除零测试配套）|
| 53-58 | `0300`…`0340` | `mov/add/mul/macl/mul/macl` | `q*d` 的 16 位 half 乘法对 |
| 59-61 | `0348`…`0360` | `add/cmp/and` | 余数校正项 |
| 62-63 | `0368`/`0370` | `add3 r92.0`, `add3 r118.0` | **s3 = e/d** 与 **k3 = e%d** 落地 |

**30 条指令**（idx 34–63，`01F0`–`0370`）一个除法站，16 个站 = 16 条 `math.inv`。

**关键事实（本卡最重要的发现之一）**：16 个站的 `math.inv` **目的寄存器全是 `r6.0`、
源操作数全是 `r2.8`、exec mask 全是 `(1|M0)`**，即 16 条**数值完全相同**的 1-lane 倒数
（都在算 `1/pc.p5.x`）。它们不是 16 个不同的除法，而是**同一个倒数被重复算了 16 次**。

### 1.2 L24 定价（不按条数，按操作类）

`ALUWR/PASS = 0.006379 ms`；本 kernel 的 live ALU 当量 `W(ALU) = 1825.4`；16 条 `math.inv`
按 L24 权重 30 = **480 当量 = 26.3%**（下一名 `mul` 298、`macl` 212、`add` 171）。

> **16 条 inv 折算 = 0.006379 × 480 / 1825.4 = 0.001677 ms/PASS**。
> 这就是全 kernel 最大的一类 ALU 当量；重排不改数量，最好情况是把这 0.00168 ms 里的
> **暴露部分**压掉一部分。

## 2. 为什么 100% 暴露：**16 个除法各自独占一个基本块**（结构性的，不是调度器没看见）

每站前面紧邻的 4 条指令（`_audit_a.py` 打印，16 站逐站相同）：

```
[0200] mov r3.1:f  = 0xB4C00000            ← 修正常数（除法站的一部分）
[0210] math.inv r6.0 = 1/r2.8              ← 站本体
        ↑ 前面依次是：
        (W&~f0.0) jmpi L<div>              ← 条件分支：f0.0 = (r2.4 == 0)，即「除数为 0」
        L<else>: mov r92.0 = -1            ← 除数为 0 的兜底：s3 = k3 = 0xFFFFFFFF
                 mov r118.0 = -1
                 (W) jmpi L<join>          ← 跳过整个除法
        L<div>:  xor cr0.0 ^= 0x30         ← 谓词翻转
                 mov r2.8:f = r2.4:ud      ← 除数转 f32
```

ISA 普查（`_audit_a.py` 可直接复算）：

| 模式 | 条数 | 位置 |
|---|---|---|
| `(W&~f0.0) jmpi` | **16** | 每站 1 条，全部是「除数 != 0 才进除法」的除零测试 |
| `(W) jmpi`（跳过除法的 else 出口）| 16（该模式共 19）| 每站 1 条 |
| `mov rN.0 = -1:w`（兜底预置）| **32** | 每站 2 条（s3、k3）|
| `xor cr0.0 ^= 0x30`（谓词翻转）| **32** | 每站 2 条（进入 + 站内）|
| `cmp` | 25 | 其中之一 `[01A0] cmp (eq)f0.0 null r2.4 0:w` = 除零判定，**整 kernel 只算一次** |

⇒ **16 个除法站 = 16 个「只有一条 26 条指令的 then 块」的单入单出 if 区域**。

两个直接后果：

1. **任何按基本块工作的调度器（IGC 的 pre-RA 调度就是）都不可能在两个站之间重叠倒数延迟** ——
   它们在不同的 then 块里，中间隔着 join 块的 ~27 条地址/取数指令。
   所以「16 条全暴露」不是调度器懒惰，而是**代码形状把 16 条最贵的算子钉在了 16 个互不相邻的
   基本块里**。这就是卡面说的「已存在但顺序写错的独立工作」：**除零测试是循环不变量，却被复制了 16 份，
   并且每份都把一条倒数单独关进一个块。**
2. 这 16 份守卫本身是**多余的重复工作**：`pc.p5.x != 0` 在整个 dispatch 里是常量，
   `[01A0]` 已经算过一次。16 个分支 + 32 条 `-1` 预置 + 16 条 `cr0` 翻转 = **80 条指令
   （1375 的 5.8%）**，全部只服务于一条永不执行的路（本 PASS 的 `pc.p5.x` = 通道数 256）。

## 3. 可挪的独立工作清单（逐项判定）

「能不能挪进 inv 与首消费者的 2 条间隙里」——按条数、独立性、代价逐条列：

| # | 已有工作 | 条数 | 与该站倒数独立？ | 可挪？ | 说明 |
|---|---|---|---|---|---|
| 1 | **另外 15 个除法站**（每站 30 条）| 450 | **是**（除数同一个 uniform 值，被除数各不相同；商/余数互不依赖）| **是——唯一有量级的工作** | 只有它能在 12 条延迟量级上填满 16 次；但**必须先把它们放进同一个基本块**（§2）|
| 2 | 被除数广播 `mov r4.0<32> ← e` | 16 | 是 | 是（已用）| IGC 已经把它放在 `inv` 与 `mad` 之间（`[0220]`），正是「延迟槽填 1 条」的证据 |
| 3 | 本站 io_at0 地址数学 | ~20×16 | **否**（依赖本站 s3/k3）| 否 | 只能等本站除法出结果 |
| 4 | `send.ugm load.ugm.d16u32` | 16 | 地址依赖 #3 | 否（本身）| 但**上一站**的 load/store 尾（≈8 条）是独立的 → 见 #6 |
| 5 | `send.slm store.slm.d16u32` | 16 | 同上 | 否 | SLM 写序必须保持 0..15（本卡不动）|
| 6 | 上一站的 load/store 尾 + `r45.x` uniform 常量 | ≈8+2×16 | 是 | 部分可挪 | 属软流水；IGC 已提前发 load（`[04E8]` 发、`[0508]` 用）|
| 7 | barrier 之后的 matmul / blend 两段 | 700+ | 是 | **否** | 跨 `barrier()`，越界即改变 SLM 可见性 |

⇒ **能填 16 次倒数延迟的只有 #1**，而 #1 被 §2 的「一站一块」形状挡住。

**不能走的路线（提前关掉）**：

| 路线 | 为什么不行 |
|---|---|
| 删掉 15 条重复倒数（16→1，CSE）| 源码层无法表达「整数除法共用一个倒数」；这属于**改计数**，违反本卡 native 签名（16 条）与「禁止靠删指令交差」。若 IGC 自己合并，那是**另一个更大的机制**，要单独重判（见 `NATIVE-PREDICTION.md` F2）|
| 把 16 站全塞进一个 `if` | 需要 32 个 dword 同时活着（8 个 s3/k3 对 + 中间值）；gather 段实测峰值 64 dword，kernel 峰值 74 dword ⇒ +30 会顶穿寄存器天花板（L15 的同一堵墙），首个 spill 就破坏 `scratch 0` 不变量 |
| 靠删那 80 条守卫交差 | 守卫是 IGC 对整数除零 UB 的兜底（`s3=k3=-1`），删掉就改了 `pc.p5.x==0` 这条路径的语义；本卡不做，只把守卫**上提合并**（值不变）|

## 4. 三判据：这 16 条到底是"延迟没藏住"还是"同一个倒数算了 16 遍"

主代理 2026-10-28 要求先用 n33 的三条判据（dword 粒度 reaching definition / 站间写 / exec 宽度 / 消费者）
判定真冗余，再决定方向。本卡用 **n33 的原码**（`cards/n33-f02-latency/_c1_redundancy.py`、`_t01_identity.classify+reaching`，
只把 `_isa.CAP/FILES` 指到本 kernel）跑了一遍，产物 `C-REDUNDANCY.json`：

| 判据 | 结果 | 证据 |
|---|---|---|
| ① reaching definition | *指令级* **16 个不同定义**（每站一条 `math.inv`，各读本站自己的 `mov r2.8←r2.4`）；**值根唯一** `distinct_roots = 1` | 每站的源 dword `r2.8` 由本站的拷贝定义；再往回一层，`r2.4` 全核 **0 个写者** |
| ② 站间有没有写源 dword | 源 dword `r2.8`：120/120 对之间有写（都是本站自己的拷贝）；**值根 `r2.4`：120/120 对之间 0 次写，全 kernel 0 次写** | `r2.0–r2.7` 全部零写者 ⇒ push constant 由驱动/硬件预置在 r2，ISA 里没有任何指令能改它 |
| ③ exec 宽度 | 16 站全部 `math.inv (1|M0)`（**1 lane / 32**，master 谓词 `(W)`）| 逐站打印，见 `C-REDUNDANCY.json.sites[].exec_mask` |
| ④ 消费者 | 每站首消费者都是本站的 `mad`（倒数修正），其后 6–8 个读者算**本站的商**（被除数不同）| `C-REDUNDANCY.json.criterion4` |
| ⑤ n33 的叶子签名（最强的一条）| **16 站的 backward slice 长度都是 2，叶子签名都只有 `{(r,2,4)}`，distinct = 1** | `criterion5_leaf_signature.verdict = ALL SITES SLICE DOWN TO THE SAME LEAF` |

⇒ **倒数那 1 条算子是真冗余**（同一函数、同一从未被写的输入、全部 1-lane），
**每站其余 26 条不是**（依赖被除数的商/余数修正）。
这正是主代理给的 F21 形态（"同一 `mov r2.x←r1.0` 重算同一个倒数"）。

> 口径警告：n33 的 `_t02_live.reachable` 在本核上只标 109/1375（它把本核的 `join` 与
> `(W&~f0.0) jmpi` 极性当成跳过岛）。**ord 166 没有 debug 岛**（源码从不读 `pc.p1.w`），
> 所以 live = 全部 1375 条；上面五条判据都不依赖那个掩码。

**为什么 dst 寄存器 `r6.0` 全核有 58 个写者**（16 条 `math.inv` + 42 条 `add/shl/and`）：
倒数结果的生存期只有 2 条指令，同一 scratch 寄存器立刻被地址数学复用 ——
这正是 IGC **每站重新 materialize 一次倒数**的机制解释，也是"值冗余但冗余发生在编译器内部"的证据。

## 4bis. 选中的机制（B 步）

> **把 `pc.p5.x` 的倒数算一次，16 个元素共享它；每站保留只依赖被除数的那部分，并用两步定点修正
> 得到精确商/余数。**

- **不选"重排"**：主代理已用 n32 实测（L26）——纯源码重排改不动 ISA 调度（三组 36 行、距离 2–3 只到 2–6、
  C256 完全没动）。本核 §2 已证明 16 个除法站各自独占基本块，重排连基本块边界都跨不过去。
  本卡早期曾设计"把除零守卫 16 份合并成 4 份让每组 4 条倒数落进同一块"，按 L26 判为低概率，**已弃**。
- **不选"把 16 站塞进一个 if"**：需要 32 个 dword 同时活着（8 个 s3/k3 对）——
  gather 段活值峰值 64 dword、kernel 峰值 74 dword，+30 顶穿寄存器天花板（L15 同一堵墙）。
- **选"共享倒数"**：只删**与被除数无关**的 15 条 `math.inv` + 15 条修正序列 + 64 条除零守卫，
  每站留下 13 条左右的定点修正。精确性由 `_b0_exact.py` 在可达域**穷举**证明
  （`C ∈ [1,4096] × n ∈ [0,4096)` 全 16.7M 对 + 广域 20 万对，全 EXACT；产物 `EXACT-DIVMOD.json`）。
- **顺带消失的重复工作**（入账，不作为交付理由）：15 条除零分支、32 条 `-1` 预置、32 条 `cr0` 翻转、
  每站 4 条 `mul`/`macl` 16-bit 乘加对（共 64）。

结果预期与判据在 `NATIVE-PREDICTION.md`；数值/映射/守卫映射证明在 `PROOF.json`；
账目（删的条数与留下的商修正分开记）在 `COST-LEDGER.json`。

## 6. 天花板：这张卡在帧级读不出来（必须写清楚）

| 量 | 值 | 对比 L13 的 0.03 ms 门 |
|---|---|---|
| 本 PASS gpu | 0.031718 ms（帧 17.498 ms 的 **0.18%**）| — |
| 本 PASS ALUWR | 0.006379 ms | **4.7× 低于门** |
| 16 条 inv 折算的 ALUWR | 0.001677 ms | 18× 低于门 |
| F18 全族 ALUWR（9 PASS）| 0.099791 ms | 成包才有 3.3× 余量 |
