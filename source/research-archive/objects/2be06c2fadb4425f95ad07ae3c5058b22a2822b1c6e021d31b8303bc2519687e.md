## 1. 映射：生产者每个 (lane,component) 代表哪个 (token,channel)，消费者要求什么

### 1.1 三个片段坐标（来自只读头文件 `register_handoff.glsl`，未修改）

头文件把 Intel B580 的实测 lane 图写成闭式函数。设 `l = gl_SubgroupInvocationID`（0..31），`c = component`（0..3 或 0..7）：

```
nrh_coord_A / nrh_coord_CH / nrh_coord_C  (三者函数体逐字相同)
  x = (l<<2)|c ;  z = ((x&3)<<5) ^ ((x&124)>>2) ;  row = z/16, col = z%16
  =>  row = 2c + (l>>4) ,  col = l&15                       … (M-A)
nrh_coord_B
  x = (l<<3)|c ;  z = ((x&7)<<5) ^ ((x&8)<<1) ^ ((x&240)>>4) ;  row = z/16, col = z%16
  =>  row = 2c + (l&1)  ,  col = (l>>1)&15                  … (M-B)
```

可枚举性（覆盖证明的算术部分）：

* (M-A)：`row ∈ {0,2,4,6} ∪ {1,3,5,7} = 0..7`，`col = 0..15`，`32 lanes × 4 comps = 128 = 8×16`，且
  `(l,c) ↦ (2c+(l>>4), l&15)` 的逆为 `l = ((row&1)<<4) | col`、`c = row>>1`，**双射**。
* (M-B)：`row = 2c+(l&1) ∈ 0..15`，`col = 0..15`，`32 × 8 = 256 = 16×16`，逆为 `l = (col<<1)|(row&1)`、`c = row>>1`，**双射**。

### 1.2 语义：片段里的 row 是 token，col 是 channel

C32 head 维 = 32 = 2 × 16，所以 **一个 head 的 32 通道被切成两个 16 通道片段**，一个 SG 的 16 个 token 被切成两个 8 token 片段。四片命名 `X_ij`：`i∈{0,1}` = token 半（tokens 0–7 / 8–15），`j∈{0,1}` = channel 半（ch 0–15 / 16–31）。

证据（来自父源码本身，不靠推测）：

| 证据 | 位置 | 结论 |
|---|---|---|
| `imgin` 每 token 16 half，4 个载入偏移 `+0/+128/+256/+384` halfs | `candidate.comp` L113–L142 | 片段 (0,0)=rows0-7ch0-15, (1,0)=rows8-15, (0,1)=rows16-23, (1,1)=rows24-31 ⇒ 32 行 = 8 token × (2 通道半) × 2 token 半 |
| `ec0 = xa00·w0 + xa01·w1`（两片共用累加器） | L147 / L151 | 同一 token 组、两个 channel 半沿 K 串接 ⇒ `xa0j` 是 j 通道半 |
| `ec1 = xa10·w0 + xa11·w1` | 同上 | ⇒ `xa1j` 是第二个 token 半 |
| `full_norm(q00[c], q01[c], k00[c], k01[c])` 把 j=0 与 j=1 一起平方求和 | L520–L538, L548–L565 | norm 的 K 维 = 整个 32 通道 ⇒ `q00/q01` 是同一 8 token 的两个通道半 |
| 每个 c 调一次 norm，共 4 次 = 8 行（lane<16 的行 2c，lane≥16 的行 2c+1） | 同上 | 一次 full_norm 归一化一整行 32 通道 |

### 1.3 消费者要求什么（本卡改的那一条交接）

消费者是 DPAS 的 **A 操作数**。SPIR-V 里 A 片段（`gl_MatrixUseA` 8×16 half）与 half 累加器片段（`gl_MatrixUseAccumulator` 8×16 half）是不同 coopmat 类型，但**每 lane 的 component↦(row,col) 映射相同**（`nrh_coord_A` 与 `nrh_coord_CH` 逐字相同）。头文件里的 `nrh_to_A(NRH_CH)` 因此是逐 component 恒等拷贝：

```
nrh_to_A(x):  o[0]=unpack(pack(x[0],x[1])).x = x[0]
              o[1]=…y = x[1] ;  o[2]=x[2] ;  o[3]=x[3]        ← 无 shuffle、无 lane 换位
```

**这就是本卡能删的东西的根源**：生产者末次 half 窄化产出的 4 个 half 与消费者 A 的 4 个 half 是同一 (lane,comp)→(row,col)，中间那份 `NRH_CH` 变量只起到"暂存 + 再读一遍"的作用。本卡让它不出现。

### 1.5 已经关掉的交接（因此本轮不改，也不许重跑）

* **K 交叉 SG 交换**：`coopMatStore(k00,shK, sg*256+0, 16, LCOL)` + `k10` 落在 `+8` ⇒ 两个 8×16 列主序写把 16 token × 16 channel 垫成 256 halfs；消费者 `coopMatLoad(b,shK, sg*256, 16, LROW)` 读出的 B 满足 `B[通道][token] = K[token][通道]`（**LCOL 存储本身就是那次转置**）。即"生产者在最后一次 store 直接生成消费者 B 布局"在 K 上**已经成立**。
* **V 交叉 SG 交换**：`coopMatStore(v00,shV, sg*512+0, 16, LROW)`、`v10` 到 `+128`、`v01` 到 `+256`、`v11` 到 `+384` ⇒ 4 SG × 2 通道半 = 8 个 16×16 块，消费者 `shV{0,256,…,1792}` 读取即 B[token][channel]，**无需转置**。
* **P→PV 提前**（父资产 `body-pv-den-overlap`）与 **root-norm 广播**（`root-body`，已测 INDISTINCT）已在父里，本卡不动。
* **scale 片段标量化**（`c32-scale-fragments`，已测 INDISTINCT 且 F2/F20 爆 scratch）**禁止原样重跑**；本卡没有碰任何 `coopMatLoad(scale,…)`。

## 2. 删了什么真实工作

### 2.1 每个站点的源码级正常工作（debug=0 路径）

改前（顺序即源码顺序）：

```
ec   (NRH_C, f32, 8x16)                          ← DPAS 累加器
  narrow:  4× [读 ec[i](f32) → f32→f16 转换 → 写 e[i](half 片段变量)]
  e→A:     4× [读 e[i] → pack2/unpack(纯重解释) → 写 o[i](A 片段变量)]
  act:     4× [读 e[i] → clamp/fma/abs/fma/mul(半精度) → 写回 e[i]]
```

改后：

```
ec   (NRH_C)
  直接:    4× [读 ec[i](f32) → f32→f16 转换 → act（如该站点有激活） → 写 o[i](A 片段变量)]
```

于是**正常路径上消失的是**：

1. `e` 这份 half 累加器片段的**存在**：4 次写 + 4 次读（A 拷贝时再读一遍）。
2. 它在 `if(debug)` 分支上被读，因此改前**跨越整个激活计算保持活跃**（4 个 GRF 的活值），改后该活值只存在于 debug 分支内部。
3. `nrh_narrow()` 与 `nrh_to_A()` 两次函数调用（SPIR-V 层是真实 `OpFunctionCall` + 函数体内的 `OpVariable/AccessChain/Load/Store` 元素访问链）。

不计入节省的：debug 声明本身（`if(debug)` 的 store 仍在，值/偏移/顺序不变）、编译器已消掉的源码。

## 5. 是否真落到 native（预测 + 判据，不声称已实现）

见 `NATIVE-PREDICTION.md`。摘要：

* 父（同一 SPV 的既有捕获，`c32-rest-20261026/body-pv-den-overlap/captures/…/CS_asm7a38a17947f21ae6…asm`）：**4958** 条指令，`mov 2245`，`send.ugm 570`，`send.slm 25`，`dpas.8x8 128`，`sync.bar 1`，`sel 476`，`math.rsqt 16`，scratch 空，SLM 8192。
* 硬判据：`dpas 128 / send.slm 25 / sync.bar 1 / math.rsqt 16 / scratch 0 / SLM 8192` 必须**逐项不变**（任何一项变化 = 实现出错，先查不许计时）。
* 软判据（决定 A 还是 B/C）：`mov` 与总指令数。若总指令数下降 → 落地；若一模一样 → 驱动原本已把逐元素拷贝合掉，本机制在此身份上是 **A 类（IR 已实现、ISA 未形成处理）**，不是方向无效。

### 5.1 实测回读（主代理 GPU 阶段，v1）

| 量 | 父 | v1 | Δ |
|---|---:|---:|---:|
| Instruction Count | 4958 | 5107 | **+149** |
| `mov` | 2245 | 2421 | +176 |
| `hf←f` 窄化 | 432 | 592 | **+160** |
| 16-lane 交织 mov | 528 | 528 | 0 |
| `dpas.8x8`/`send.slm`/`send.ugm`/`sync.bar`/`math.rsqt`/`sel` | 128/25/570/1/16/220 | 同 | **0** |
| scratch / SLM（40 pipeline） | 0 / 8192 | 0 / 8192 | 0 |

⇒ 机制**形成了处理**（不是 A），但方向是**变多**：`+160` 正好等于 20 站点 × 8 条窄化 ⇒ v1 在 20 个 `if(debug)` 块里把 pre-act 窄化重算了一遍。净 `+149` 反推出**被删掉的 20 次恒等 A 拷贝在 ISA 里只值 ≈11 条指令**。**这两个数就是本卡最重要的结论**：`nrh_to_A` 的恒等性使它能被驱动完全合掉，而窄化（每站点 8 条）是数学必需的舍入点，删不掉。v2（一次窄化 + A 片段原地激活 + debug 发布读同一 A 片段）已构建，预测 ≈4947。

## 6. 整体是否更快（★已由主代理 GPU 阶段测完，本卡未运行 GPU）

**结果：INDISTINCT。** `TIMING.json`：两臂 6 组交替、每臂 30 样本（warm1/reps30/feedback、全样本保留、不剔尖峰不补跑），末帧 `2b63d4ba…` = ordinary gold。

| 量 | base | cand(v1) |
|---|---:|---:|
| 组均值（ms） | 19.2042 | 19.1979 |
| base − cand | **+0.003045 ms** | 95% CI **[−0.090099, +0.096189]** |
| 6 组差 | −0.0434 / +0.1803 / −0.0158 / −0.0304 / −0.0110 / −0.0614（4 负 2 正） | |

**归因（只写证据支持的）**：本卡覆盖 7/232 个派发；这 7 个位置上的 40/128 个 DPAS 的 A 供料方式变了，且 IR 少 433 条指令，但 **ISA 反而多 149 条**，于是整体落在噪声里。**不能**把 0.003ms 写成"删逐元素拷贝的收益"（它是 ±0.09ms 区间内的 0）；也**不能**因为它不显著就说方向无效——上限已被两条独立证据夹住：

* 实测：`hf←f` 窄化 +160（= 20×8）全部来自重复计算 ⇒ 去掉重复即回到父值；
* 推断：净 +149 反推被删的 20 次恒等 A 拷贝只值 ≈11 条指令。

⇒ 这条交接的可达上限 ≈ −11 条 / 4958（0.2%），**不可能形成可测净收益**。后续若还要动 F02 body，应转向 `send.ugm 570`、load 侧 528 条 16-lane 交织、`add 690` 地址算术，而不是再重排片段类型。

## 7. 本卡没做什么（下一轮的具体入口）

1. **F01（ord 0）/ F19（ord 226）未动**：不同 shader（`f01-direct-a`、`root-f2`），F19 复现还必须走 `RECIPES.json[7f1ad115…].nc_recipe` 的 `drop_region = full_norm` 分支。按卡要求"入口图像 gather 与 body 连续矩阵不同…不能用 body 通过替代入口"，先让 body 过门。
2. **`qa*` 的同类恒等拷贝（4 处）未并入**：保持本卡只有一条机制。若本卡 native 落地且整体不退化，这是同机制的 4 个免费站点。
3. **重复 scale 读取（4 处）未删**：`scale` 是列常量（`coopMatLoad(scale,wb,base,0u,LROW)` 的 stride=0 ⇒ 值只随 column 变化），`p2.x+8` 被 `xa00`/`xa10` 各读一次、`p2.x+24` 被 `xa01`/`xa11` 各读一次、`p2.y+0`/`+16` 各被 `oc00`/`oc10` 与 `oc01`/`oc11` 读一次 ⇒ 12 次 load 里有 **4 次是同一片段**，可省 4 次 UGM 读。**这不是 `c32-scale-fragments` 的同一身份**（那是"把每次 coopmat 读换成标量读"，本项是"少读 4 次"），但仍须单独开一版并单列成本（`scale` 跨块增活 1 个片段）。
4. **A 片段的 16-lane 交织（ISA 里 528 条 `mov (32|M0) rX.N<2>:uw rY.M<32;16,1>:uw`，占全部指令 10.6%）属于 load 侧（线性内存 → 片段），不是 A 交接**：本卡已用 ISA 证据否掉"把 A 交接当交织来源"的读法，下一轮若要动它必须动内存布局（`imgin`/`wb` 只读，属 N15 窄读/宽读卡）。
