# n06d-f06-c256-atile / ANALYSIS（六问）

卡：F06 C256（15 PASS：38,41,44,47,50,53,56,170,173,176,179,182,185,188,191）
族身份：基线 SPV `881dff8c…a3f0`（源码 `c3efee68…1c16`），父 plan = 当前链头
`accepted/n09c-f09-b-share-20261027/plan.txt`（`25cd7faf…3b61`）。
本卡候选 SPV `ee6cd3a1…f641e`，plan `f76c3f10…ef94`。

机制一句话：**shT 保留**（同一 `half[16384]` = 32 KiB，仍一次 32 KiB 全局读，**不删不分段**），
只把**发布写成消费 tile 序** `shT[(j*16+ki)*128 + dr*16 + dc]`（每个 8×16 A tile = 128 连续 half
= 256 B），于是 A 读的 `coopMatLoad` 从 `(offset=m0*256+k0, stride=256)` 变成
`(offset=((m0/8)*16 + k0/16)*128, stride=16)`。**字节不变，消息数变。**

## 1. 映射：生产者的 (lane, component) 代表哪个 (token, channel/k)，消费者要什么

### 1.1 数据是什么

`shT` 是一个 token 窗口的 **A 操作数**：64 token × 256 channel（K 维），共 16 384 half。
父布局是行主序、行 stride 256：元素 `(m,k)` 在 `shT[m*256 + k]`，即
`gT[w*16384 + m*256 + k]`（`gT` 是只读输入，`w` = 该 workgroup 的窗口号）。

消费者是 8 个 subgroup，每个 SG 用 `MAT_A = coopmat<half, Subgroup, 8, 16, A>`（8×16，LROW）：

| 消费维度 | 取值 | 说明 |
|---|---|---|
| `sg` | 0..7 | 8 个 subgroup；`n0 = (sg%8)*32` 决定它负责的 32 个输出列，但 **A 侧每人都读全表** |
| `j` | 0..7 | `m0 = (sg/8 + j)*8`；subgroup size 32 ⇒ `sg/8 = 0` ⇒ `m0 = 8j` |
| `ki` | 0..15 | `k0 = 16*ki`，K 累加第 ki 步 |
| 矩阵元素 `(i, jc)` | i∈0..7, jc∈0..15 | 对应 A 的 `(m0+i, k0+jc)` = token `8j+i`、channel `16ki+jc` |

所以每个 SG 每 j 读 16 个 8×16 tile（ki=0..15），共 128 tile = 16 384 half = 全表；
8 个 SG 各读一次 ⇒ **每 WG 131 072 次 half 读**，每个元素恰好被 8 个 owner 各读一次。

### 1.2 生产者映射（候选，逐元素可枚举）

发布循环 1 024 个 tile-row；`q = t_local + 256*it`（`t_local`∈0..255，`it`∈0..3，恰好 4 轮，无尾块）：

```
t  = q >> 3          // tile 号 = j*16 + ki   (0..127)
dr = q & 7           // tile 内的行 (0..7)
src = ((t>>4)*8 + dr) << 8 | (t & 15) << 4     // = (8j+dr)*256 + 16*ki   源行首
dst = q << 4                                   // = t*128 + dr*16        目标行首
for dc in 0..15:  shT[dst + dc] = gT[w*16384 + src + dc]
```

关键性质（**这就是"写地址线性"的来源**）：`t*128 + dr*16 == q*16`，因为 `q = t*8+dr`。
所以 1 024 个 tile-row 的目标区间首尾相接，**整片 32 KiB 的目标地址是 `q*16` 线性**；
一个 warp 的 32 个 lane（q 连续）写满连续 1 024 B。

| 生产者 | 写 16 个 half 的源 | 目标 |
|---|---|---|
| thread `t_local`，轮 `it`，q | `gT[w*16384 + (8j+dr)*256 + 16ki + dc]` | `shT[q*16 + dc]` |
| 上式覆盖 | j(8) × ki(16) × dr(8) × dc(16) = 16 384 个 (token,channel) 组合，**一一覆盖** | 16 384 个槽位，**一一覆盖** |

### 1.3 消费者映射（候选）

| 消费者 | 读地址 | 与父的关系 |
|---|---|---|
| SG `sg`, j, ki, 元素 (i,jc) | `shT[((m0>>3)*16 + (k0>>4))*128 + i*16 + jc]` | 槽位 = `perm(父槽位)`；**取到的 half 与父逐字节相同** |

`perm(e)`：`r,c = divmod(e,256)`；`perm = ((r/8)*16 + c/16)*128 + (r%8)*16 + (c%16)`。
`perm` 是 16 384 元素上的双射（PROOF.publish.elementwise.perm_bijective = true）。

### 1.4 必须证明的三件事（PROOF.json 已穷举，全部 0 mismatch）

1. **发布写地址与来源逐元素相同**：16 384 个槽位，每个写一次（`duplicate_writes=0`），
   每个 `gT` 元素被搬一次（`duplicate_sources=0`）；
   对每个父槽位 `e`，候选槽位 `perm(e)` 收到的值恰是父放在 `e` 的值 ⇒
   `value_mismatches=0`、`write_address_mismatches=0`。
2. **读端每 (sg,j,ki,row) 取数位置与父逐字节相同**：131 072 个元组全部检查，
   `value_mismatches=0`；SPIR-V 侧符号化地址链也是可核对的：
   父 `shT[((m0 * 256) + k0)]` stride 256 → 候选 `shT[((((m0 >> 3) * 16) + (k0 >> 4)) << 7)]` stride 16。
3. **无漏读、无重复写、尾块正确**：每个 owner 各读 16 384 个不同槽位
   （`per_owner_distinct_slots` 全 16 384），每槽位恰好被 8 个 owner 读（`slots_read_by_each_owner=[8]`）。
   **没有尾块**：64/8 = 8、256/16 = 16 都是整数，128 个 tile 全是满 tile；
   最大下标 127*128+127 = 16 383 ✓，最大源 63*256+255 = 16 383 ✓。

> lane 级说明：SPIR-V 只规定「矩阵元素 (i,jc) 在哪里」，具体哪个 lane 取哪个元素是
> IGC 的 LROW 展开（自然分配下 lane `l` 取 `i = l>>2`、`jc = (l&3)*4..+3`，4 half = 8 B/lane）。
> 所以本卡把「取数位置相同」证明在**元素**层面（与 lane 分配无关），这也是更强、
> 不依赖编译器实现的表述。

## 2. 删什么真实工作（只算正常执行路径；debug = 0）

| 项 | 父 | 候选 | 差额 | 依据 |
|---|---|---|---|---|
| A 读 SLM 消息/SG | **1 024** 条 32 B | **128（或 256）** 条 256 B（或 128 B） | **−896 … −768** | native 父值 1 024 + 本卡 byte/geometry 计算 |
| A 读的地址形成 | 每 tile 8 条消息 = 8 个地址/增量 | 每 tile 1 条消息 = 1 个地址 | −7/tile，−896/SG（**预期**，IGC 可能已 strength-reduce） | 转置消息是逐行的，行间 512 B |
| A 读**字节** | 32 768 B/SG | 32 768 B/SG | **0** | 128×256 B = 1024×32 B |
| 发布全局读字节 | 32 KiB/WG | 32 KiB/WG | 0 | 仍是一次 32 KiB 读，扇区全用 |
| 发布消息（读+存） | 各 64 条/warp（16 static × 4 轮，64 B/条） | 各 4 条/warp（32 B/lane，1 024 B/条）**或**不变 | −60/warp（最好情况） | 每线程 16 个连续 half 可向量化 |
| workgroup barrier（正常路径） | 1 | 1 | **0** | 本卡不分段、不加屏障 |
| dpas / 权重消息 / seed / 输出 store | 256 / 256 / 128 / 128 | 同 | 0 | 未改 |
| 转换 / shuffle / mov 类 | — | — | 0 | 两侧都没有 shuffle、没有新增类型转换；`pin` 不变 |

**净结论**：本卡删掉的是**消息槽（message issue）**，不是字节、不是屏障、不是转换。
所以它是「降低数据端口压力」的机制，而不是「减少搬运量」的机制——
这也决定了第 6 问的归因方式。

## 3. 重叠：独立工作原来怎么重叠，本卡有没有破坏供料

### 3.1 阶段结构（两侧完全一致）

```
publish(32 KiB, 256 线程)  →  barrier(1)  →  for j in 0..7:
        seed0/seed1 载入(gY, stride 256) + scale 乘  →  for ki in 0..15:
              A 读(shT) ‖ b0/b1 读(pack)  →  2 × dpas  →  (ki 循环结束)  →  2 × store(imgout)
```

本卡**只改「哪个线程写哪个槽」**，不改「何时写/何时读/几道屏障」：
发布仍是一段序言 + 1 道 barrier，消费仍是 8 个 SG 全量读。

### 3.2 生产者 / 最后消费者 / 覆盖者

| 值 | 生产者 | 最后消费者 | 覆盖者 | 边缘类型 |
|---|---|---|---|---|
| `shT[*]`（32 KiB） | 发布段（256 线程各 64 half） | `sg=7, j=7, ki=15, i=7, jc=15` 的 A 读 | 唯一的 workgroup barrier | **RAW ×1**（父同） |
| `pack`（权重/scale） | 宿主（kernel 外） | 各 ki 的 b0/b1 读、j 序言的 scale 读 | 无（只读） | 无 |
| `gY`（seed） | 宿主 | j 序言的 seed 读 | 无（只读） | 无 |
| `gT` | 宿主 | 发布段 | 无（只读） | 无 |
| `imgout` | 各 j 的两条 `coopMatStore` | 宿主 | 无（同 WG 内地址互不相同：`n0` 随 sg 变） | **WAW 无**（每地址写一次） |
| `dbg`（debug ≠ 0） | debug dump | 后续 store | debug 分支自带 barrier（父同） | 仅 debug 路径 |
| `acc0/acc1` | dpas 链 | 本 j 的 store | 私有寄存器 | 无 |

### 3.3 WAW / WAR / RAW 判定（逐项）

| 关系 | 父 | 候选 | 说明 |
|---|---|---|---|
| WAW on `shT` | 0 | **0** | 每槽位只写一次（`duplicate_writes=0`），父同样一次 |
| WAR on `shT` | 0 | **0** | 没有任何阶段在读之后重写 shT（本卡不加分段、不加二次发布） |
| RAW on `shT` | 1（发布→消费，barrier 定序） | **1（同一 barrier、同一方向）** | 变的只是「写者身份」，不是「有无依赖」 |
| 跨 WG | 无 | 无 | `shT` 是 per-WG 数组 |

**判定：不变（既非更强也非更弱）。** 唯一的结构差异是：父是 `shT[e]` 的恒等写，
候选是 `shT[perm(e)]` 的双射写——依赖图上边的**集合**不变（都是「全部写 → 全部读」）。

## 4. 新增成本（全部入账）

| 项 | 计数 | 依据 / 说明 |
|---|---|---|
| 发布地址算术 | 每 tile-row ~8 个整数 op × 4 轮 = ~32 op/线程 | 父是 64 次「下标自增 + 地址加」（每元素 1 个）；净额量级相同 |
| A 读地址算术 | 每 tile 1 个地址（父 8 个） | 符号化链见 PROOF.spirv（父 `m0*256+k0`，候选 `((m0>>3)*16+(k0>>4))<<7`） |
| 循环层数 | 6 → **7**（多一个内层 16 次滚动循环） | `OpLoopMerge` 6→7；**风险项**：若 IGC 不展开，发布端退化（见下） |
| 静态 SPIR-V | 860 → **947** instr（3 466 → 3 811 words，+1 380 B） | 发布体从 1 元素扩到 16 连续 half + 索引算术；debug 分支加逆向映射 |
| 重复权重读 | **0** | 权重代码一字未改（`coopMatLoad(b,pack,…)` 行未进 diff） |
| 重复 A 读 | **0**（字节、次数都未变） | 8 个 owner 仍各读全表一次 |
| shuffle / 复制 / 选择 | **0** | 没有跨 lane 交换，没有临时数组 |
| 同步 | **0**（barrier 数不变） | `OpControlBarrier` 2 = 2（含 debug 分支） |
| 有效 lane | 满（4 轮 × 256 = 1 024 恰好 1 024 tile-row） | 无尾块、无发散，与父的 64 轮同样整齐 |
| WG 数 / 占用 | 不变（grid、binding、push 全不变；`max_r` 期望仍 ≤127） | `--cpu-check` 输出与链头**逐字相同** |
| 活值峰值 | 不变（tile 号是标量；`a`/`b0`/`b1`/`acc0`/`acc1` 寿命未变） | 无新增长寿命对象 |
| 代码体积 | +87 静态指令（ISA 侧预测 7 000–7 300，父 7 087） | 见 NATIVE-PREDICTION P12 |
| **逻辑字节 ≠ DRAM 字节** | 字节两者都不变（gT 32 KiB/WG、SLM 32 KiB/SG） | 本卡不承诺任何 DRAM 收益 |
| **扇区风险（最坏情况）** | 若内层 16 次拷贝**没有**被向量化：每条 2 B/lane 消息触及 32 个不同 32 B 扇区（父是 2 个） | DRAM 仍 32 KiB（16 次复用命中 L1），但扇区请求/message 从 2 升到 32。判据：`store.slm.d16u32` 是否消失（NATIVE-PREDICTION P6） |

## 5. 是否真落到 native（预测 + 判据，不声称已证明）

逐条可观察点与「若看不到就等于未实现」的判据写在 **NATIVE-PREDICTION.md**，核心四条：

| 判据 | 期望 | 反例含义 |
|---|---|---|
| A 读 `load.slm.*` 消息数/SG | **128 – 256**（父 1 024） | 仍 1 024 ⇒ **A 类：布局没被采用**，不是方向无效 |
| `load.slm.d32x8t` | **0**（形态消失） | 仍 1 024 ⇒ 同上 |
| `dpas.8x8` | **256** | ≠256 ⇒ 实现未落地（循环被改动） |
| 权重 `load.ugm.d32x8` | **256** | 变化 ⇒ 越界改了禁区 |

配套：`workgroup memory 32768`、`scratch 0`、`sync.bar` dynamic **1**、
发布 store/load 由 `d16u32`×16 变 4 条/warp 32 B/lane（`d32x8`）。

## 6. 整体是否更快（本卡要测什么、用哪个臂、怎么归因）

- **两臂**：base = 链头 plan `25cd7faf…`；cand = 本卡 `f76c3f10…`（在链头上**只**替换本组 15 个
  PASS，断言 replaced == 15，`--cpu-check` 与链头逐字相同）。
- **门**：fixed（`--pool --warm 0 --reps 1` → `1755e9c2…`）与 fb2（`--pool --warm 0 --reps 2
  --feedback --save-frames` → `9c3e511e…`）；ordinary 末帧 `2b63d4ba…`，三套 gold 不混用。
- **整体量**：ordinary `--pool --warm 1 --reps 30 --feedback`，two-arm-6-alternating，
  逐进程组均值 + 配对组差 + 双侧 t 95%（df = 6−1），不裁剪不重跑。
- **归因量**（比整帧更有分辨力）：
  1. native 两臂 → A 读消息数、`dpas`、权重消息、`sync.bar`、`max_r`、静态指令；
  2. resources 两臂 → 15 个 PASS 的逐 PASS GpuTime（父单样本 30.0–37.0 µs）；
  3. 先看 1（是否形成处理），再看 gates/数值，最后才看时间——**不许用毫秒倒推机制有效**。
- **上限（诚实）**：F06 C256 组实测 484.94 µs = 17 577 µs 帧的 2.76%；
  A 读占该 kernel 数据端口消息约 **60.5%**，但只占字节 **18.5%**，而本卡**只降消息不降字节**。
  所以整帧上界 ≈ 0 到 0.2 ms（≤1.4% 帧时）；若该 kernel 是字节受限，整帧会是 D；
  若它是消息槽受限，逐 PASS 应出现同向变快。**这个上界高于 ordinary 的 CI 分辨率（≈0.03 ms），
  与 n06c（上界 < 分辨率）不同，值得花一个 GPU 时段。**
- **单链归因只写证据支持的部分**：本卡不改 F06 C256 的数学，所以任何 gates 差异都是实现错误
  （E 类），不能归因成「布局错」。
