# n23-f05-shape / SHAPE-PROBE (step A)

Question the card asks: **does `coopmat<float16_t, Subgroup, 8, 32, Accumulator>` (or an
equivalent 16x32 form) compile under this repository's glslang 16.5.0 and pass the CPU
SPIR-V validator?** Answer: **yes, all of them.** The shape is *not* the obstacle.

Toolchain (fixed by COMMON.py): `glslang.exe -V --target-env vulkan1.3`, glslang 16.5.0;
validator `spv_validate_cpu.exe` (SPIRV-Tools v2026.3, `SPIRV_TOOLS_CPU_VULKAN13_VALIDATION`).

## A.2 what A does *not* settle (and why that is the real gate)

Compiling and validating say nothing about (i) how the merged accumulator is distributed over
lanes/components, nor (ii) how a 32-column B fragment maps onto the weight pack. Both are decided
by the driver/IGC and both are load-bearing for this card. Two lemmas, both settled here without
a GPU:

### Lemma 1 (pack width): the published weight layout only supports 16-wide B tiles

The parent reads the QKV projection weights as

```
coopMatLoad(b0, pack, wq + (((96u*h + c)/16u)*8u + ki)*256u, 16u, LCOL)
```

(`family/c128/candidate.comp`, 6 sites). With `LCOL` and stride 16 halves, one 16x16 tile is
512 B of contiguous memory: column (output channel) `n` at `+32 B`, key `k` inside the column.
A 16-channel block therefore spans `8 ki * 512 B = 4 KB`, and consecutive 16-channel blocks are
4 KB apart (`wq + j*4096 B`).

A single `B 16x32` load requires channels `n = 0..31` at a **uniform** stride
`base + n*stride + k`. Channels 0..15 sit at `32 B` steps; channels 16..31 sit `4096 B` further
on. No single `(base, stride)` satisfies both, so the merged 32-channel fragment **cannot** be
read from the current pack — the 96 output-channel blocks have to be re-blocked from
"16 channels x 8 k-tiles" to "32 channels x 8 k-tiles" (a pure permutation, byte-for-byte: tile
`(pair p, ki, half h)` moves from `(2p+h)*4096 + ki*512` to `p*8192 + ki*1024 + h*512`).

**Applied** (main-agent ruling 2026-10-28): the twelve permuted packs are built in
`packed/*.reblocked.fp16.bin` (sealed assets untouched, read only), the BUFFER rows are delivered
machine-readable in `BUFFER-EDITS.json` (12 entries: resource index, original line, new line, new
sha256/bytes, source sha256, permutation id + both address laws), and the reorder is proved
exhaustively in `build/PERMUTATION-PROOF.json`: **589824 of 589824** `(w, c, k)` coordinates equal
across the 12 files, bytes outside the QKV interval bit-identical, whole-file half multiset
unchanged, file sizes unchanged. The QKV interval is *disjoint* from everything else in each file
and is read **only** by this pass: no other pass source references `pc.p3.w` (the slot that carries
`wq`), and the neighbour intervals `wo/wc/we/wm/rs` tile the file around it.

| pass | weights file | `wq` (halves) | QKV region (halves) | file (halves) | other passes on the file using `wq` |
|---|---|---|---|---|---|
| 19 block9_swin_body_3 | swin_9_weights | 131328 | 131328..180480 | 180744 | none (F04 uses `we/wm/wc`, F06 uses `wo`) |
| 22..31 (blocks 10-13) | swin_10..13 | 131328 | 131328..180480 | 180744 | none |
| 34 block14 | swin_14_weights | 131200 | 131200..180352 | 180616 | none |
| 195..210 (blocks 56-61) | swin_56..61 | 131328 | 131328..180480 | 180744 | none |

(`we=49408, wc=33024, wm=114944, rs≈180488, wo=0` tile the same file without touching the QKV
interval; see `build/overlap.json`.)

### Lemma 2 (shape map): no 8x32 accumulator lane map exists in this workspace

`register_handoff.glsl` (the file that carries the *measured* B580 map, bound "to accompanying
compiler/driver/SPV identity") documents only the 8x16 accumulator:

```
row = 2*component + (lane>>4),  col = lane & 15            (nrh_coord_CH / nrh_coord_C)
```

A scan of every `coopmat<...,8,32,...>` declaration under `@NR_WORKSPACE@`
finds 60+ hits and **all of them are `gl_MatrixUseA` int8 fragments**; the tree even says so
explicitly:

```
vit_nb04_mpair.glsl: "requires the measured B580 lane map for a coopmat<int8,8,32,A>.
                      This workspace has no s[uch map]"
```

That matters because the parent's Q/K normalisation is **componentwise**:

```
nr_norm_component(f16vec2(q0[i],k0[i]), f16vec2(q1[i],k1[i]), lane)   // i = 0..3
  v = q0[i]^2 + q1[i]^2      -> the sealed tree's (sq[c] + sq[c+16]) term
  then xor8, xor4, xor2, xor1 over (lane&15), broadcast from lane (lane&16)
```

Merging `Q0+Q1` into one 8x32 accumulator changes that pairing from "component `i` of two
matrices" to "components `i` and `i+4` of one matrix" **if and only if** the merged shape nests
the two 16-column halves inside one lane. Under the other plausible lowering (32 lanes = 32
columns, 8 components = 8 rows) the pairing becomes a lane `xor16`, a different expression with
the same 32 terms. The two produce *different f16 rounding sequences* if chosen wrongly, and the
acc GRF budget also differs by a factor of two (16 GRF vs 8 GRF per merged accumulator). Neither
can be derived offline.

## A.3 the probe that settles Lemma 2 (this card's candidate arm)

`candidate.comp` (one dispatch, no barrier, no writes outside the `dbg` debug buffer) dumps, per
`(lane, component)`, the value held by

* `H16` / `C16`  - the documented 8x16 half and fp32 accumulators (**control**: must reproduce
  `nrh_coord_CH` exactly, otherwise nothing else is trusted),
* `H32` / `C32`  - the 8x32 half and fp32 accumulators, loaded from a fixed window of the weights
  pack whose bytes are known offline (half offset 28624: **237 of 256 distinct fp16 values**, so
  a wrong hypothesis cannot match all lanes),
* `MMA32` / `MMA16` - the 8x32 and 8x16 MMAs (so the native capture shows the `dpas` shape and the
  accumulator register footprint for both).

`probe_read.py` scores four candidate laws by exact fp16 equality and prints the table for
anything else. It is unit-tested without a GPU (`--synthetic NESTED|LANE-COL`):

| synthetic truth | NESTED | LANE_COL | SWAP_HALVES | EXOTIC | verdict |
|---|---|---|---|---|---|
| NESTED | **256/256** | 32/256 | 0/256 | 4/256 | `NESTED` |
| LANE-COL | 32/256 | **256/256** | 0/256 | 3/256 | `LANE-COL` |

with the 8x16 controls at 128/128 in both runs.

## A.4 consequence for the card

* A passed: the shape is available; `coopmat<f16,Subgroup,8,32,Acc>` and 16x32 both compile and
  validate, so the card does not fall back to B2.
* B1 is nevertheless **stopped at proof 2** (K order / half rounding points) and at proof 3
  (live-value peak) because Lemma 2 leaves the merged accumulator's component semantics
  undetermined, and at the delivery level because Lemma 1 shows the merged B tile needs the
  weight pack re-blocked (12 files, 12 `BUFFER` rows — an asset change, not a shader delta).
* The one-dispatch probe above removes both unknowns' *first* half (the map) at negligible cost;
  after it, B1 is a mechanical rewrite. See `RESUME.txt` for the exact order of operations.

## A.5 rev 3 additions (measured after the first probe attempt)

### A.5.1 the element-access premise is false in this toolchain

The "write the normalisation with `m[i][j]` element access so the lane map does not matter" route
was tested directly:

| probe | construct | glslang 16.5.0 | spv_validate |
|---|---|---|---|
| `probe/p5_2d_element.comp` | `float x = c[3][5];` on an 8x32 fp32 accumulator | **rc 2**: `left of '[' is not of type array, matrix, or vector` | n/a |
| `probe/p6_component.comp` | `float x = c[7];` | rc 0 | `result=0` |
| `probe/p7_len16.comp` | `for (i < c.length()) s += c[i];` | rc 0 | `result=0` |

Cooperative matrices expose only the *component* subscript (uniform over the invocation), never a
(row, col) pair. A componentwise re-expression of the sealed denominator tree therefore still needs
to know which (row, col) each component holds. Consequence: the Q/K merge is blocked on the lane
map, not on coding effort (PROOF.json `proof2.blocked_for_Q_and_K`).

### A.5.2 the debug buffer *is* dumpable - one POLICY token, no runner change

`clock_runner.cpp`:

```
if (dump) {
  for (size_t i = 0; i < plan.buffers.size(); ++i)
    if (!plan.buffers[i].resident) {
      plan.outputs.push_back({i, "raw", "dump_" + plan.buffers[i].name + ".bin"});
      plan.buffers[i].resident = true;      // the end-of-network readback is a real last consumer
    }
}
```

and `resident` comes from the plan row `POLICY <resource> <resident> <firstPass> <lastPass>
<clear>`. `swin_9_debug` is resource 50 with `POLICY 50 1 0 233 0`, i.e. resident, which is the
single reason it never showed up in `--dump-intermediates` (and why n02d hit the same wall).
`probe/lanemap-probe.plan.txt` sets that field to 0 and leaves everything else alone, so the probe
dumps without any tooling change.
